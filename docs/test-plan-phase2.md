## 1. 测试概述

### 1.1 测试目标

验证 Phase 2 新增业务模块的功能正确性、数据一致性和金额精度，确保：
- 供应商管理 CRUD 及联系人功能正常
- 采购全流程（订单→入库→退货→付款）状态流转正确
- 销售退货流程（创建→审核→退款）库存回滚正确
- 客户对账/收款金额计算准确
- 库存预警阈值触发正确
- **所有金额计算精确到分，无浮点误差**
- **所有单据状态流转符合业务规则，非法跳转被拦截**

### 1.2 测试范围

| 模块 | 接口数 | 优先级 | 测试重点 |

| 采购订单 | 7 | P0 | 金额计算、状态流转、税额计算 |
| 采购入库 | 5 | P0 | 库存增加、状态流转、关联订单 |

| 采购付款 | 3 | P1 | 金额核销、状态流转 |
| 销售退货 | 5 | P0 | 库存回滚、退款处理、金额计算 |
| 客户对账单 | 4 | P1 | 金额汇总、期初/期末余额计算 |
| 客户收款 | 3 | P1 | 金额核销、对账关联 |
| 库存预警 | 3 | P1 | 阈值触发、预警级别 |

**合计：9 个模块，42 个接口，其中 P0 模块 5 个，P1 模块 4 个**

## 3. 专项测试策略

### 3.1 金额精度测试（重点）

#### 3.1.1 测试原则

- 所有金额单位为**元**，精确到**分**（2 位小数）
- 数据库使用 `DECIMAL(12,2)` 存储
- 计算过程保留 2 位小数，四舍五入
- 断言使用 `Math.abs(actual - expected) < 0.001`

#### 3.1.2 边界值矩阵

| 边界类型 | 测试值 | 验证点 |
|---------|--------|--------|
| 最小金额 | 0.01 元 | 能正常创建、计算正确 |
| 零金额 | 0.00 元 | 允许创建、合计正确 |
| 大额金额 | 9999999.99 元 | 不溢出、计算正确 |
| 负数金额 | -10.00 元 | 被拒绝、返回 400 |
| 三位小数 | 9.995 元 | 四舍五入到 2 位 |
| 浮点经典 | 0.1 + 0.2 | 结果 = 0.30，非 0.30000000000000004 |

#### 3.1.3 金额计算场景

| 场景 | 涉及模块 | 计算公式 |
|------|---------|---------|
| 商品金额 | 采购/销售 | sum(qty * unitPrice) |
| 税额计算 | 采购订单 | goodsAmount * taxRate |
| 优惠扣减 | 采购/销售 | goodsAmount - discountAmount |
| 应付金额 | 采购/销售 | goodsAmount + taxAmount - discountAmount |
| 已付/未付 | 采购付款 | payableAmount - paidAmount = unpaidAmount |
| 期初余额 | 客户对账 | 上期期末余额 |
| 期末余额 | 客户对账 | opening + sales - returns - payments |
| 退货金额 | 销售退货 | sum(qty * unitPrice) - discount |
| 退款金额 | 销售退货 | returnAmount - refundedAmount |

#### 3.1.4 测试方法

```
1. 单条明细：qty=1, unitPrice=9.99 → subtotal=9.99
2. 多条明细累加：验证合计是否正确
3. 含税额计算：goodsAmount=100, taxRate=0.13 → taxAmount=13.00
4. 含折扣：goodsAmount=1000, discount=100.50 → payable=899.50
5. 部分付款：payable=1000, paid=300 → unpaid=700
6. 四舍五入验证：qty=2, unitPrice=9.995 → subtotal=19.99
7. 0.1+0.2 浮点误差验证
```

### 3.2 状态流转测试（重点）

#### 3.2.1 状态流转图

```
采购订单：
  DRAFT → SUBMITTED → APPROVED → PARTIAL → COMPLETED
    ↓         ↓          ↓
  CANCELLED CANCELLED  CANCELLED（仅限未入库）

采购入库：
  PENDING → COMPLETED
     ↓
   VOIDED（审核前可作废）

采购退货：
  PENDING → COMPLETED
     ↓
   VOIDED（审核前可作废）

销售退货：
  PENDING → COMPLETED → REFUNDED
     ↓
   VOIDED

客户对账单：
  DRAFT → CONFIRMED → PAID
```

#### 3.2.2 状态流转矩阵

| 单据 | 当前状态 | 允许操作 | 目标状态 | 禁止操作 |
|------|---------|---------|---------|---------|
| 采购订单 | DRAFT | 提交、取消 | SUBMITTED / CANCELLED | 审核、入库 |
| | SUBMITTED | 审核、取消 | APPROVED / CANCELLED | 直接入库 |
| | APPROVED | 入库、取消 | PARTIAL / COMPLETED | 编辑 |
| | CANCELLED | 无 | - | 所有操作 |
| 采购入库 | PENDING | 审核、作废 | COMPLETED / VOIDED | - |
| | COMPLETED | 无 | - | 作废 |
| 销售退货 | PENDING | 审核、作废 | COMPLETED / VOIDED | 退款 |
| | COMPLETED | 退款 | REFUNDED | 再审核 |
| 客户对账 | DRAFT | 确认 | CONFIRMED | 收款 |
| | CONFIRMED | 收款 | PAID / PARTIAL | 编辑 |

#### 3.2.3 测试方法

```
1. 正常流转：每个单据测试完整的正向流程
2. 非法跳转：测试每个状态下的禁止操作，验证返回 400
3. 部分流转：部分入库、部分收款等中间状态
4. 回退验证：作废/取消后状态正确回退
5. 幂等性：重复审核、重复取消应拒绝
```

### 3.3 并发测试

| 场景 | 测试方法 | 预期结果 |
|------|---------|---------|
| 同时审核订单 | 2 个请求同时审核同一订单 | 1 个成功，1 个失败 |

## 6. 测试规范

### 6.1 接口测试规范

- 每个测试文件独立，使用 `resetMockDb()` 隔离数据
- 测试命名：`模块 - 场景 - 预期结果`
- 每个接口至少覆盖：正常、异常、边界值 3 种场景
- 金额断言使用 `toBeCloseTo(2)` 避免浮点误差
- 状态断言使用精确匹配

### 6.2 金额精度规范

- 所有金额单位为元，精确到分（2 位小数）
- 比较时使用 `Math.abs(actual - expected) < 0.001`
- 必须覆盖的边界值：0.01 元、0 元、9999999.99 元、负数
- 必须覆盖的计算场景：加法、减法、乘法、四舍五入
- 必须验证的模块：采购订单、采购入库、销售退货、客户对账

### 6.3 状态流转规范

- 每个单据必须覆盖完整正向流程
- 每个状态必须验证允许的操作和禁止的操作
- 非法操作必须返回 400 状态码和明确错误信息
- 状态变更必须幂等，重复操作不产生副作用
- 状态变更必须有操作人记录和时间戳

### 6.4 测试数据规范

- 测试数据使用有意义的命名，如 `测试供应商A`、`测试白酒A`
- 金额测试使用易计算的数字，如 10.00、50.50、99.99
- 边界值测试使用特定数字，如 0.01、0、-1、9999999.99
- 每条测试用例只验证一个核心点，避免多重断言混淆

## 7. 风险与应对

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|---------|
| 接口变更频繁 | 测试用例需同步修改 | 高 | 与阿坚保持每日沟通，接口变更即时通知 |
| mock-db 与真实 DB 差异 | 测试通过但生产报错 | 中 | S104 增加集成环境验证，关键路径上生产前手测 |
| 金额浮点精度 | 对账不平、财务纠纷 | 高 | 统一使用 DECIMAL(12,2)，增加专项金额精度测试 |
| 并发操作 | 超卖、重复审核、重复收款 | 中 | 增加并发测试用例，关键操作加锁 |
| 开发进度延期 | 测试时间被压缩 | 中 | 优先测 P0 模块，P1 模块可延后 |
| 需求变更 | 测试用例重做 | 中 | 测试计划预留 20% 缓冲时间 |
