## 一、可以直接照抄修（1 处，改动局部、租户来源明确）——**已按 R3 完成**

### 1–4. `t_miniapp_order` / `t_miniapp_order_item`（即时零售 webhook）—— **不是"补个参数"那么简单，见第二节**

**已有正确写法可对照**（同表同族）：`backend/src/services/miniapp/checkout.service.ts:283-286` 的
`INSERT INTO t_miniapp_order (… , tenant_id)`（带租户，来自下单请求的登录态）；本 webhook 路径**没有登录态**，故无同源取值。
另注：`t_platform_config` 表**有** `tenant_id` 列（`074_即时零售表.sql:8-24`，`UNIQUE(platform,store_id,tenant_id)`），
但 `common.service.ts:33-63 getPlatformConfig()` 的返回体 `PlatformCredentials`（`instant-retail/types.ts:19-30`）**没有暴露它**，
且该函数在不传 `storeId/tenantId` 时是 `LIMIT 1` 取任意一行 ⇒ 拿它当租户来源**不保证是该门店/该租户**（需一并按 `storeId` 收敛）。
若要按"门店 → 租户"取值，仓库内**没有** `webhook → 租户` 的既有先例（`rg 'FROM t_store WHERE id'` 命中的都是带登录态的租户内校验）。

（这 4 处列在本节只为编号连续，实际处理方案见 §二。）

### 5. `t_sys_user_role`（种子数据）

- 位置：`backend/src/shared/seed-data.ts:107`
- 现状：
  ```
  INSERT INTO t_sys_user_role (user_id, role_id)
  SELECT ?, id FROM t_sys_role WHERE role_code = ?
  ON DUPLICATE KEY UPDATE user_id = VALUES(user_id)
  ```
- 问题：`INSERT … SELECT` 无 `tenant_id`，落列默认值 `'default'`（`migration.ts:192` / `init_database.sql:311` 均为 `NOT NULL DEFAULT 'default'`）。
  该文件上方第 85–90 行插入 `t_sys_user` 时**已显式写了 `tenant_id`**（`TENANT_ID` 常量）——同一函数内两种写法不一致。
- 建议改法（2 行）：
  ```diff
  -                `INSERT INTO t_sys_user_role (user_id, role_id)
  -                 SELECT ?, id FROM t_sys_role WHERE role_code = ?
  +                `INSERT INTO t_sys_user_role (user_id, role_id, tenant_id)
  +                 SELECT ?, id, ? FROM t_sys_role WHERE role_code = ?
                   ON DUPLICATE KEY UPDATE user_id = VALUES(user_id)`,
  -                [userId, demoRoleCodes[acc.username]]
  +                [userId, TENANT_ID, demoRoleCodes[acc.username]]
  ```
  ⚠️ 注意参数顺序：`SELECT ?, id, ?` 里第二个 `?` 在 SQL 文本中位于 `WHERE role_code = ?` **之前**，因此参数数组必须是
  `[userId, TENANT_ID, roleCode]`（MySQL 按文本顺序取值）。

## 二、必须先裁定的 5 处（改法取决于产品口径，擅自补参数会写错租户）

### 2.1 `t_miniapp_order` / `t_miniapp_order_item`（4 处，同一批代码的两个副本）

| 位置 | 函数 | 关键事实 |
|---|---|---|
| `backend/src/services/admin/instant-retail.service.ts:307 / :324` | `handleWebhook(platform, rawBody, signature, timestamp)` | **函数没有 tenantId 形参** |
| `backend/src/services/instant-retail/platform-integration.service.ts:102 / :119` | 同名 `handleWebhook(...)` | 同上（两份实现互为副本） |

事实链（可复跑核对）：

1. `handleWebhook` 内解析租户配置用的是 `getPlatformConfig(platform)` —— **不带租户**；
2. 事务里同时写 `t_platform_order`（该表**没有** `tenant_id` 列，属平台级表）与 `t_miniapp_order` / `t_miniapp_order_item`；
3. 因此这两条 INSERT 的 `tenant_id` **在当前代码里没有可用的取值来源** —— 现有行为是静默落 `'default'`。

⇒ 两种口径，需凌舟指定其一：

| 方案 | 内容 | 代价 / 风险 |
|---|---|---|
| **A（推荐）显式声明平台级** | 明写 `tenant_id` 并取值 `'default'`（=平台租户），同时补注释说明"外部平台 webhook 无租户上下文，统一落平台租户" | 改动仅 2 文件 4 处、零 DDL；**不改行为**，只把隐式变显式，消除"将来有人加了 tenant 上下文反而写错"的隐患 |
| **B 做真租户归属** | `getPlatformConfig` 与 webhook 全链路加租户维度（配置表按租户查、订单落实际租户） | 涉及配置解析、适配器、路由（webhook 入口无登录态，租户从哪里来需产品定义：平台配置里存租户？店铺→租户映射？）；**属功能变更**，须另立卡，不在 B-2b 范围 |

### 2.2 `t_report_permission_matrix`

- 位置：`backend/src/services/admin/report-permission.service.ts:27`（`saveMatrix`）
- **本表的问题比"漏一列"大**：同一文件 `getMatrix()`（第 11–16 行）用普通 `query()` 无任何租户条件；
  `saveMatrix` 先 `DELETE FROM t_report_permission_matrix WHERE 1=1`（**清全表、跨租户**）再重插。
  ⇒ 现状是"**全局唯一一份**报表权限矩阵"，`tenant_id` 只是建表时顺手加的默认列。
- ⇒ 单点补 `tenant_id` 会造成**自相矛盾**（写的时候带租户、读/删的时候不带），必须整体裁定：
  ① 矩阵是平台全局（则 `getMatrix/saveMatrix` 保持全局，把 `tenant_id` 当无效列，登记 S3 类治理项）；
  ② 矩阵按租户（则读/写/删三处一起改：`getMatrix(tenantId)` 带 `tenant_id = ?`、`DELETE ... WHERE tenant_id = ?`、
     INSERT 补 `tenant_id`），并同步改控制器 `report-permission.controller.ts` 传参。
- **建议**：按 ② 修，但这属"租户隔离缺口"（比 B-2b 的"漏列"更重），建议单独立卡并纳入安全类验收。

### 2.3 `t_platform_subscription_apply`

- 位置：`backend/src/services/platform-miniapp.service.ts:172`（普通 `query()`，无自动注入）
- 表语义：小程序端提交的**平台订阅申请**（字段：openid/plan_id/company/contact/mobile/remark/status），
  `131_platform_subscription_apply.sql:14` 的 `tenant_id VARCHAR(36) NOT NULL DEFAULT 'default'` 更像"建表模板顺带"。
- ⇒ 与 §2.1 同型：先定"这是平台级申请（落 `'default'`/`'platform'`）还是租户级申请（需从 openid→租户映射）"，
  再决定改法。**建议**：明写 `tenant_id` 并取平台租户值 + 注释（方案 A 同型）。

## 三、给出"现状即错误"的证据边界

1. 上述 5 处均**未做运行时复现**（沙箱无 MySQL、无外部平台报文），判定依据是**代码事实**：函数无租户形参、
   配置解析不带租户、同事务内主表无 `tenant_id` 列 ⇒ 租户取值来源不存在。
2. 上述 6 处（webhook 4 + 报表权限矩阵 1 + 订阅申请 1）均未做运行时复现；若凌舟判定"平台级"成立，则这 6 处**不是数据错误**，
   而是"隐式依赖列默认值"的**可维护性缺陷**（与 S3-85 同族）；若判定"应归属租户"，则这 6 处是**与红点①同级**的租户隔离缺陷
   （生产一旦有该入口的真实流量即产生脏数据）。
