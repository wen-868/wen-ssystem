| 位置 | 原文 | 实际实现 |

| `app-mobile/src/api/sync.ts:208` | `使用服务端 makeBizNo("XS") 生成 billNo，不依赖客户端时间` | 服务端把 `draftNo` 直接当 `billNo` 落库 |

## 二、为什么"现在就改成 makeBizNo"不是改一行（关键影响面）

幂等链路的**唯一锚点就是"`bill_no == draftNo`"**：

```
delta-sync.service.ts:681  SELECT bill_no AS billNo FROM t_sale_bill WHERE bill_no = ? AND tenant_id = ?   -- 参数 = order.draftNo
delta-sync.service.ts:727  INSERT INTO t_sale_bill (bill_no, …) VALUES (order.draftNo, …)
```

若把实现改为 `makeBizNo("XS")`（服务端另行生成单号）：

1. 上面的查重 SQL 用 `draftNo` 永远查不到已落库的单（库里存的是 `XS…`）⇒ **幂等立即失效**：
   "已写库但响应丢失"后的重试会**再落一单**（当前 B-2 已核验的"同键只落一单"结论被推翻）。
2. 要重新拿到幂等，必须**新增一列**（如 `t_sale_bill.draft_no`）**并加唯一键**（`UNIQUE(tenant_id, draft_no)`）——
   这与本卡 **"零 ALTER"** 直接冲突，也踩红线 2（不动 `uk_sale_bill_no`），且需要回填历史行的 `draft_no`（无数据源 ⇒ 不可能）。
3. 即便退一步"靠 `uk_sale_bill_no` 兜底"，它挡的是**全局同名**而不是"同一 App 草稿"⇒ 只能阻止重复写，不能返回"同一张单"，
   语义与客户端期望（幂等成功）不一致。
4. 客户端侧还有配套影响：`app-mobile/src/utils/sync-manager.ts:442-444` 用返回的 `draftNo` 匹配本地草稿、
   `local-db.ts` 用 `draftNo` 做本地主键与删除条件 ⇒ 服务端返回的 `billNo ≠ draftNo` 时，客户端必须把服务端单号**另存**，
   否则"已同步"的本地草稿与库里单号对不上（排障/对账断链）。这些都在 `app-mobile/**`（本卡红线禁改）。

## 三、两个方案

### 方案 A：**改注释对齐实现**（保留 `billNo = draftNo`）

- 动作：把 `app-mobile/src/api/sync.ts:208` 与 `delta-sync.service.ts:654` 的 "使用服务端 `makeBizNo("XS")` 生成 `billNo`，不依赖客户端时间"
  改为如实描述："服务端把 App 端 `draftNo` 作为 `billNo` 落库（幂等键实现方式）；重复提交返回既有 `billNo` 且 `success=true`"。
- 影响面：**零代码、零 DDL、零契约变更**；只改 2 处注释（客户端 1 处 + 后端 1 处）。
- 遗留：① 单号规则与其它单据（`makeBizNo("XS…")`）不一致，单号由客户端时间/规则决定（服务端不再"不依赖客户端时间"）；
  ② 跨租户同名单号互相顶掉的风险仍在（`uk_sale_bill_no` 全局唯一）→ 由 **S3-84** 一并处置；
  ③ 客户端本地草稿号直接成为对账单号，若客户端规则未来变化，历史可读性受影响。

### 方案 B：**改实现对齐注释**（服务端生成 `makeBizNo("XS")`）

- 动作：① `delta-sync` 改为服务端生成 `bill_no`；② **新增** `t_sale_bill.draft_no` 列 + `UNIQUE(tenant_id, draft_no)`；
  ③ 查重 SQL 改为按 `draft_no` 查；④ 客户端改存服务端单号；⑤ 契约文档同步。
- 影响面：**DDL（新增列 + 唯一键）× 幂等逻辑 × 客户端 × 对账口径**，且历史数据无 `draft_no` 无法回填。
- 与既有裁定的冲突：本卡"零 ALTER"、红线 2"不动 `uk_sale_bill_no`"；且属 S3-84（唯一键与单号口径）范围。

## 四、推荐意见

**短期取方案 A（改注释对齐实现），不要在本轮动实现。** 理由：

1. 幂等键的真实语义是"App 端草稿单号"，这是**产品需要**（离线可重复提交），不是实现偷懒；
2. 方案 B 必须加列 + 改唯一键 + 回填（无数据源）⇒ 不可逆、范围远超本卡，必须与 S3-84（`uk_sale_bill_no` 租户化）**合并设计**，
   由凌舟在阶段三"多租户开放前"统一决策；
3. 方案 A 的成本是"文档与实现不一致"这一项，本轮即可清零——**改注释属于文档一致性，不是功能变更**。
