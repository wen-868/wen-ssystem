## 1. 什么是"常驻红"（本清单口径，先钉死）

**常驻红** ＝ 在 **`main` 上连续 ≥5 次 run** 里，**同一个 job（或同一具体步骤）恒为 `failure`**，且该 job **不是 required**。

三条附加口径：

1. **看 job 级，不看 workflow 级**：本仓 `ci.yml` 一个文件里既有 `build-and-test`（绿）又有 `migration-check`（红）⇒ workflow 整体显示红**不代表代码坏了**。判常驻红必须落到 job/步骤。
2. **"红得有原因" ≠ "有分辨力"**：常驻红哪怕每次红都由真实缺陷引起，它的**红/绿与提交好坏无关** ⇒ 作为门禁**无分辨力**，不得据此拦合并，也**不得因此进 required**。
3. **观测字段（每次刷新必须记全）**：`观测日` / `数据来源（run id 列表）` / `该 job 最近 N 次结论` / `最近一次"实质推进"日` / `归属卡` / `谁在等它`。

**"实质推进"判定**（决定 30 天时钟是否重置）：归属卡上出现**根因定位 + 修复/演练方案 + 验证计划**，并且**至少一步已落地**（提交哈希 / run id / 演练记录可查）。
❌ **不算推进**：再次体检、再次登记、把结论换个说法重发、只更新看板状态。

## 3. "30 天无推进即升级 P0"的判定口径

| 项 | 规则 |
|---|---|
| 计时起点 | 该常驻红**首次被确认为常驻**的日期（上表"起算日"）；本次 `migration-check` = **2026-09-17** |
| 重置条件 | 出现**实质推进**（§1 定义）：归属卡上根因定位 + 方案 + 验证计划，且至少一步落地（提交哈希 / run id / 演练记录）⇒ 计时**重置为推进日** |
| 升级条件 | 距最近一次实质推进 **≥30 天**（含首末日）仍无推进 ⇒ **升级 P0**，并在 `docs/tasks/R101-总进度与推进计划.md` 的该行置 P0 标记 |
| 升级后的动作 | ① 冻结与该常驻红**同一文件域**的新派单（避免继续往上压）；② 由凌舟指定唯一责任人 + 时间盒（≤2 个工作日）出根因结论；③ 结论必须选 A/B/C 之一并落卡（不得再次"维持现状而不标注"） |
| 判据留痕 | 每次刷新必须在 §2 表里追加一行"观测日 + run id 列表 + 结论"，**不得覆盖**历史行（防"进度源过期"） |
| 反例（明确不算） | "再看一次仍红"、"换个人再体检一次"、"更新看板状态"——这些都不重置计时 |

**当前计时（2026-09-25）**：`migration-check` 常驻 **8 天**（09-17 → 09-25），距 30 天到期还有 **22 天**（到期日 **2026-10-17**）。
