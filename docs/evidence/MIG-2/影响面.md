**为什么"旧结果表名"全是 `t_IF`**：`` CREATE TABLE IF NOT EXISTS `x` `` 里，可选组 `(?:IF\s+NOT\s+EXISTS\s+)?` 贪婪匹配成功后，名字组 `[a-z_][a-z0-9_]*` 撞上反引号失配 → 正则回溯让可选组退化为空 → 名字组抓到关键字 `IF` → 被补成 `t_IF`。修复后名字组同时接受 `` `x` `` 与 `x` 两种形态，保留反引号（`` `t_x` ``），不再回退到关键字。

## 七、影响面的边界与遗留（如实标注）

1. 本影响面是**静态**结论：只复演 runner 的切分与 `addTablePrefix` 的改写，**未连库、未执行任何 SQL**（E8：无 MySQL 监听 / 无 docker）。"5 条语句恢复可执行"是**改写层面**的必然结论；**执行层面**是否真的建成表，需部署后由凌舟在服务器侧用表数/表名核对（本单不碰生产）。
2. 差异成因 B 类（旧"漏改反引号表名"、新"补上前缀"）在本仓库为 **0 条**；即当前迁移集里反引号表名一律已是 `t_` 前缀或系统库，新模式不会对它们追加前缀。
3. 已知存量行为（**未在本单修改，属红线范围外**）：`FROM`/`JOIN` 等模式会改写字面量里的同名文本（如 `VALUES ('FROM y')` → `('FROM t_y')`），修复前后逐字节一致（见 `02-verify.txt` 用例 H19 冻结位）；`RENAME TABLE x TO y` 的 `TO` 目标名不参与加前缀（修复前后一致）。两者都是"存量"，本单不扩大也不顺手修，登记在回传卡的「风险与自我报备」。
4. `DROP TABLE` 模式虽已支持反引号（用例 H12），但 runner 有"跳过 DROP TABLE 保护生产数据"的既有拦截（本次统计 37 条被跳过），因此该分支对生产**不生效**，改动只为模式族一致性，不产生实际影响面。
