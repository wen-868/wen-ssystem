## 二、功能对照结果

### 2.1 能力说明书 25 项被动能力 → **23 项已实现，2 项真缺**

| 缺口 | 详情 | 判定 |
|---|---|---|
| **P04 取消销售单** | 文档承诺工具 `cancelSalesOrder`；实际 `cancel-order.tool.ts` 只支持 `ORD` 前缀（即时零售订单），**不支持 SO/SB 销售单**（`/api/store/sale-bills` 无取消工具） | **真缺口**（写能力）|
| **P25 系统状态** | 文档承诺 `getSystemStatus` 工具；实际只有 `admin/health`、`/health/ready` HTTP 端点，**没有对话可用的系统状态工具** | **真缺口**（对话内不可查）|

其余 23 项全部落地（部分为**改名**：`querySalesOrders`→`query-sale-bills`、`queryCustomer`→`search-customer`、`inventoryCheck`→`stock-check` 等 —— **文档用的是旧名**）。

### 2.2 主动能力 9 项 → **12 项实现，超额** ✅

文档承诺的 9 项（库存预警/订单异常/应收催收/经营异常/每日简报/补货建议/配送异常/客户流失/毛利异常）**全部有实现**，另多出 3 个（weekly-plan、proactive-push、proactive 本体）。**无缺口**。

营销活动全家桶（秒杀/拼团/满减/赠品/优惠券/客户分群）、费用报销、采购合同/付款/计划/转换、佣金计算、客户拜访、关怀规则、数字员工派发、平台公告、审批处理、订阅申请 —— **能力说明书 v1 完全没覆盖**（它是按"9 大业务域"写的，营销/费用/合同/数字员工是后加的）。

## 三、两个系统对接与权限分域

### 3.1 架构已有基础（文档层面）
- **§3.3 独立部署形态**：明确「AI 底座可独立部署、**可服务多个业务系统**，复用同一套大脑+工具适配层」—— **你的"对接两个系统"愿景在架构文档里有据**，但**只有一句愿景，无落地设计**（第二个系统如何注册？工具如何分域？权限如何隔离？）

### 3.2 实现层面（代码现状）
- **管理系统的对接已完备**：53 个内置工具 + 43 个 API 目录动态工具，全部经 ServiceClient + 治理链（写全审核/租户隔离/幂等/熔断/审计）
- **第二个系统的对接能力**：❌ **不存在** —— 无"外部系统注册/工具分域/按系统路由"的任何机制
- **权限分域现状**：只有 `scope: mgmt/platform` 两域（租户 vs 总台）—— **没有"按业务系统分域"**（如"这套工具属于管理系统、那套属于 OA"）

## 四、办公需求 —— **设计文档零覆盖**

## 六、结论与建议

### 结论
- **AI 底座"已实现"的能力面扎实**（主动能力超额、内置工具 + 动态技能共 96 个、治理链完整）
- **但有 2 个文档承诺的能力未实现**（取消销售单、系统状态工具）
- **文档体系落后于实现约一个版本**（能力说明书/API 契约/开发文档都滞后）
- **业主三个关切中，"两系统对接"只有架构愿景、"办公需求"完全空白**

### 建议的行动排序
1. **先补 2 个真缺能力**（P04 取消销售单工具、P25 系统状态工具）—— 半天量，能力说明书即可"承诺=实现"
2. **文档治理一单**：能力说明书收录 32 个新工具 + 改名对齐 + API 契约迁移（127 端点分批）+ v2.0 开发文档升 v3.0
3. **办公需求澄清会**（需要业主输入）：AI 底座的办公能力边界（OA 审批/待办/日程/通知哪些要做？）
4. **两系统对接方案**（需要业主输入）：第二个系统是什么？其工具如何注册进 ToolRegistry？权限如何按系统分域？（我建议的 MCP Client 路径可复用，但需先定第二个系统形态）
