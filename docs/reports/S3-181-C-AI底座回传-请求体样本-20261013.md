## 〇、先回应一处事实偏差（重要，涉及第 1 项怎么改）

贵方第 1 项描述为「`createCustomer` 对后端的入参由 `phone` 改为 `mobile`」，并称「契约要求 mobile，你们发的是 phone」。

**我方核实结论：我们发给后端的已经是 `mobile`，不是 `phone`。**

证据 `src/tools/definitions/create-customer.tool.ts`：
```ts
// :247-254 —— 校验并转换
if (!customerArgs.phone || !customerArgs.phone.trim()) { … }
const mobile = customerArgs.phone.trim();

// :257-264 —— 发给后端的 body
const requestBody = {
  name: customerArgs.name,
  mobile,                    // ← :259 字段名就是 mobile
  customerType: customerArgs.customerType,
  address: customerArgs.address ?? undefined,
  settlementType: customerArgs.settlementType,
  remark: customerArgs.remark ?? undefined,
};
```
贵方栈也印证这一点：报错是 `Duplicate entry '13900000001' for key 't_member.uk_member_mobile'` 与 `Column 'mobile' cannot be null` —— **若发的是 `phone`，后端不会在 `mobile` 列上触发唯一键冲突/NOT NULL**。

**但我方认同第 1 项仍应做**，理由不同：工具的**对外（LLM 可见）参数名**叫 `phone`，与后端权威契约（`docs/API接口文档.md:417-430`，`name` + `mobile` 必填）不一致 —— 这是长期隐患。
⇒ **我方改法**：把工具对外参数名统一为 `mobile`（`parameters`/`description`/解析/幂等字段/预览展示），内部 `phone→mobile` 转换随之消失。已派发施工，**不改后端契约字段名**（`mobile` 为权威口径）。

## 二、请求头清单（`service-client.ts:360-395` 构造）

除 `Authorization` / `x-csrf-token` / `X-Tenant-Id` 之外**只多一个**：

| 头 | 是否必带 | 来源 |
|---|---|---|
| `Content-Type: application/json` | 是（axios 实例默认，:178-181） | 实例级默认头 |
| `Accept: application/json` | 是（同上） | 实例级默认头 |
| `X-Tenant-Id` | 是 | `context.tenantId`（:365） |
| `x-csrf-token` | 写操作必带 | `HMAC-SHA256(csrfSecret, userId)`（:370-374）；`csrfSecret = CSRF_SECRET ?? JWT_SECRET`（:160-163），缺失时不注入并启动告警 |
| `Authorization: Bearer <JWT>` | 是（若 `context.authToken` 存在） | `context.authToken`（:377-379） |
| **`X-Request-Id`** | **条件带** | 仅当 `context.requestId` 存在时透传（:382-384） |

⇒ **除贵方点名的三个之外，只额外带 `X-Request-Id`（且仅在上下文有 requestId 时）**，其余为 axios 默认头。
`buildRequestConfig` 有防覆盖加固（:386-394：headers 强制合并，调用方 config 无法覆盖身份头）。
