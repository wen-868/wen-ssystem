# R73-05 代理消息通道诊断报告

日期:2026-08-03 诊断人:凌舟(当前运行时身份 probe_msg_revive)

## 结论(根因)

协作子代理消息通道故障的根因是**历史诊断代理链嵌套繁殖 + 运行时路由错乱**,并非消息投递机制本身损坏。

具体证据链:

1. **存在僵尸代理链**:`/root/probe_verify_1/probe_selfname/probe_msg_revive` 嵌套三层,由之前"消息通道验证"反复 spawn 产生,占满 4 个并发槽位,导致后续 `spawn_agent` 直接报 `agent thread limit reached`。
2. **短名解析错乱**:向 `probe_selfname` 发送消息时,运行时将其解析为 `/root/probe_verify_1/probe_selfname/probe_msg_revive/probe_selfname`(报 not found),证明当前运行时上下文路径是 `/root/probe_verify_1/probe_selfname/probe_msg_revive`,即当前 turn 被路由到了最深层的探针代理上。
3. **自身无法清理**:对 `probe_msg_revive` 执行 interrupt 报 `an agent cannot interrupt itself`,对父级 `probe_selfname` 中断成功但其子代理未随之退出;`send_message`/`followup_task` 均投递成功但代理无响应(僵停)。
4. **这正是此前 ajian/ache 子任务失败的原因**:派发时槽位已被探针链占满或消息被路由到错误路径,代理只能收到全局指令而收不到任务正文,回复"暂无任务"。

## 修复步骤(需在根代理/新线程执行)

1. 根代理对 `/root/probe_verify_1/probe_selfname/probe_msg_revive` 执行 `interrupt_agent`,随后确认 `list_agents` 中仅剩 `/root`。
2. 若残留代理仍显示 running,等待其自然超时退出(最多 2 分钟)。
3. 清理后重新执行消息通道端到端验证:
   - `spawn_agent` 一个干净代理,任务正文包含唯一标识符;
   - `wait_agent` 等待其 FINAL;
   - 核对回复中是否完整包含任务正文标识符。
4. 验证通过后再正式派发 ajian/ache 等业务子任务,并确认代理回复中引用了任务编号与正文关键内容。

## 附带发现

- `send_message` 只投递不触发代理行动;要触发代理执行必须用 `followup_task`。
- 短名称(如 `probe_selfname`)仅适用于当前上下文路径下的直接子代理;跨层级必须使用完整规范路径,否则会静默拼接到错误路径。
- 建议业务上避免为测试反复 spawn 同名代理;每个子任务用唯一 task_name,完成后由根代理确认其结束。
