> 提出：凌舟（MS 线 / 总负责人）｜针对：AI 底座线 2026-10-17 01:26 的"生产部署实测矛盾"报告

## 二、真正根因：**新工具没进"执行器注册表"**

生产同一进程内的两条日志自相矛盾，正好把问题夹出来：

```
[AdminController] 收到 tools 请求，返回 96 个工具          ← 列表端点
[ToolExecutor] 工具 "getSystemStatus" 未注册（已注册工具：107 个）  ← 执行器注册表
```

代码侧证据（`/opt/zhixiang/ai-base`）：

| 检查 | 读数 |
|:--|:--|
| `src/tools/tool-bootstrap.ts` 里 `import ... from "./definitions/ai-*"` | **0 处** |
| 该文件的 `registry.registerAll([ ... ])`（第 161 行起，**手工维护的实例数组**） | 其中 `GetSystemStatusTool` / `AiNoticeListTool` / `AiTodoListTool` / `AiScheduleListTool` / `ForecastSalesTool` 命中数 **各 0** |
| `GetSystemStatusTool` 的**另一处**声明 | 只在 `src/tools/tools.module.ts`（Nest providers）里 —— 那是 DI 容器，**不是执行器注册表** |

而 `tool-bootstrap.ts` 自己的注释写着：
> "ToolBootstrap 集中管理工具注册，**后续新增工具只需在此处注入并 registerAll**"

⇒ 结论：**27 个办公工具与 `getSystemStatus` 从未被登记进执行器注册表**，因此生产执行必然报"未注册"。
这与部署无关、与环境依赖（better-sqlite3 等）无关，是**代码侧接线缺失**。

## 三、附带发现（同样要收敛，别再拿它当上线判据）

**列表端点（96）≠ 执行器注册表（107）**，两个数打的是两套账 ⇒
"`GET /api/admin/tools` 还是 96 ⇒ 没上线"这条判据**本身不可靠**（它连执行器里已有的 107 个都没报全）。
建议：列表端点直接读执行器注册表（`ToolRegistry.list()`），并把该数作为**唯一工具数口径**。

## 四、我方建议的修复 + 防复发门禁（属 AI 仓，我方不代改）

1. **修复**：在 `tool-bootstrap.ts` 注入并 `registerAll` 这 27 个办公工具 + `GetSystemStatusTool`（并确认 `tools.module.ts` providers 与此同步）；
2. **门禁（缺的就是它）**：加一条机械判据 —— **`src/tools/definitions/*.tool.ts` 的文件数 == 注册表条目数 + 具名豁免清单**（含理由）。
   本单之所以 182 套件/1898 用例全绿却漏掉整族工具，就是因为没有任何断言把"定义文件"与"注册数组"绑在一起；
   这与 MS 侧 `guard-rbac-wiring`（端点 ↔ 台账）同型，属可复用的成熟形态。
3. 复验口径建议：**以执行器为准** —— `POST /api/admin/tools/execute {"name":"getSystemStatus"}` 必须返回业务结果（不是"未注册"），
   而不是看列表端点的 total。
