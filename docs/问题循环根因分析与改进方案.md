# 问题循环根因分析与改进方案

> **日期**：2026-07-29
> **制定人**：凌舟
> **背景**：R42至R66共25轮任务，问题反复出现、前面修后面又坏。用户提出严肃质疑："是不是同事没有按统一标准执行？还是统一标准出了问题？"
> **结论**：不是同事不努力，是项目管理体系存在5个结构性缺陷，导致修复无法落地、验证无法闭环、协作无法对齐。

---

## 一、五大根因分析

### 根因1：验证机制完全缺失（最严重）

**现象**：
- 踩坑日志[11]：阿坚R58-01报告"已清理3个文件12处any，commit 4cb3bd1"，经核查commit不存在、文件未修改、grep验证仍是原状
- 踩坑日志[12]：阿坚R56-04报告"已清理14个路由文件重复中间件"，阿澈后来grep发现14个文件一个都没改
- R66测试发现：多轮"已完成"的修复在实际体验时仍然报错

**根因**：
任务标记"已完成"后，没有任何人用 `git log` + `grep` 双重验证就直接通过。文本报告不等于代码已修改。

**影响**：
问题被标记为"已解决"，但实际从未修复。下一轮测试时问题原封不动地再次出现，形成无限循环。

---

### 根因2：前后端协作断裂

**现象**：
| 问题 | 前端 | 后端 | 结果 |
|------|------|------|------|
| R66-05 | 移动端调用 `/admin/dashboard` | 后端只有 `/store/dashboard` | 401错误 |
| R66-02 | 代码用 `order_no` 字段 | 数据库字段是 `bill_no` | 500错误 |
| R66-06 | 登录页"智享全链管理系统" | 侧边栏"智享酒仓" | 品牌不一致 |
| R66-15 | 官网链接 `store.onepan.cn` | 域名已删除 | 死链 |

**根因**：
前后端各自独立开发，没有API契约文档约束。前端按自己的理解调API，后端按自己的理解写字段，合并到一起就是错。

**影响**：
单端测试通过 ≠ 系统正常。只有两端联调时才暴露问题，但项目流程中从未有联调环节。

---

### 根因3：数据库管理混乱

**现象**：
- `t_stock_warning` 表全项目无建表语句，从未创建
- `t_alert_record` 表的092迁移脚本用了不带t_前缀的错误表名，ALTER TABLE静默失败
- 代码审计确认SQL字段全部正确，但12个API仍返回500，因为数据库表根本不存在
- 迁移脚本执行情况无人跟踪、无人验证

**根因**：
- 没有"数据库变更清单"，迁移脚本散落在docs/migrations/目录，无人确认哪些已执行、哪些未执行
- 迁移脚本编写后不测试（表名写错都不自知）
- 没有统一的数据库初始化验证流程

**影响**：
后端代码看起来正确，但运行时因数据库表/字段缺失而500。代码审计无法发现这类问题。

---

### 根因4：派单基于过时信息

**现象**：
- 踩坑日志[13]：R63-07/08派单称8个路由文件"缺少routeConfig导出"，实际全部已导出`routeConfigs`（复数形式，完全合法）
- 派单称`sync.routes.ts`是"空Router需删除"，实际有9个端点+36个测试用例
- 派单前没有grep核实当前代码状态

**根因**：
凌舟在派单时基于记忆或过时的代码分析结果，没有在派单前执行grep/read核实当前代码实际状态。

**影响**：
团队成员收到错误的任务描述，要么执行了不必要的修改（浪费工时），要么差点执行破坏性删除（险些删除有9个端点的路由文件）。

---

### 根因5：没有端到端集成测试

**现象**：
- R42到R66，25轮任务中20+轮是"修复后发现新问题"的循环
- 各端独立开发、独立测试（甚至不测试）
- 代码审计只看代码不看数据库
- 从未在真实部署环境做过端到端验收
- 只有到用户实际体验时才发现"API返回500"、"页面空白"、"登录不跳转"

**根因**：
项目流程中缺少"集成验收"环节。每个成员只对自己的代码负责，没有人对"系统整体可用性"负责。

**影响**：
问题积累到部署后才集中爆发，每轮验收都发现一批新问题，修了又引出新问题，形成恶性循环。

## 二、五道防线改进方案

### 防线1：任务完成验证标准（解决根因1）

**规则**：任何任务标记"已完成"前，必须满足以下全部条件：

1. **git验证**：`git log --oneline -1` 确认有对应commit
2. **代码验证**：`grep` 确认目标代码已修改（具体grep命令写入任务验收标准）
3. **构建验证**：`npm run build` 或 `npx tsc --noEmit` 0错误
4. **测试验证**：`npx vitest run` 全部通过（后端）/ 前端构建成功
5. **凌舟复核**：凌舟亲自执行上述1-4步，确认全部通过后才标记"已完成"

**执行方式**：
- 任务文件中每个任务的"验收标准"必须包含具体的grep命令和预期输出
- 凌舟在标记"已完成"前，必须执行验收命令并记录输出
- 任何一项不通过，任务状态保持"进行中"

---

### 防线2：API契约文档（解决根因2）

**规则**：所有前后端交互的API必须先写契约文档，再开发。

**文档位置**：`docs/API.md`（已有，需补全）

**契约格式**：
```
### POST /api/store/auth/login
- 端类型：移动端
- 请求体：{ username: string, password: string }
- 响应：{ code: 0, data: { token: string, user: {...} } }
- 后端文件：backend/src/routes/store-auth.routes.ts
- 前端文件：app-mobile/src/api/modules/auth.ts
```

**开发流程**：
1. 阿坚先在API.md中定义接口（路径、请求体、响应体）
2. 前端（墨/阿澈）根据API.md开发，不得自行编造路径
3. 后端阿坚按API.md实现，不得自行改字段名
4. 任何API变更必须先改API.md，再改代码

**重点检查**：
- 移动端只能调用 `/api/store/*` 端点，不能调用 `/api/admin/*`
- 管理后台只能调用 `/api/admin/*` 端点
- 超级后台只能调用 `/api/platform/*` 端点

---

### 防线3：数据库变更管理（解决根因3）

**规则**：所有数据库变更必须统一管理、统一执行、统一验证。

**数据库变更清单**：
- 文件位置：`docs/database-changelog.md`
- 记录每个迁移脚本的：文件名、执行状态、执行日期、验证结果
- 凌舟维护此文件，每次执行迁移后更新

**迁移脚本规范**：
1. 文件名格式：`NNN_简短描述.sql`（NNN为三位数字序号）
2. 每个脚本必须包含 `IF NOT EXISTS` / `IF EXISTS` 保护，确保可重复执行
3. 脚本末尾必须包含验证SQL（如 `SELECT COUNT(*) FROM information_schema.tables WHERE table_name = 't_xxx'`）
4. 表名必须带 `t_` 前缀
5. 字段必须有中文COMMENT

**服务器执行流程**：
1. 阿坚在本地编写并测试迁移脚本
2. 凌舟将命令发给用户在服务器执行
3. 用户执行后，凌舟通过API或命令验证表/字段是否创建成功
4. 更新 `docs/database-changelog.md`

---

### 防线4：派单前核实制度（解决根因4）

**规则**：凌舟在派发任何任务前，必须先核实当前代码状态。

**核实清单**：
1. `grep` 确认问题代码确实存在（而不是已修复）
2. `git log --oneline -5` 查看最近提交，确认没有其他人已修复
3. 如果任务涉及删除文件，必须先 `Read` 文件确认内容
4. 任务描述中的"问题"和"修复方向"必须基于实际代码，不能基于记忆

**执行方式**：
- 派单前在任务文件中记录核实命令的输出结果
- 例如：`核实：grep -c "order_no" dashboard.service.ts → 3（确认问题存在）`

---

### 防线5：端到端集成验收（解决根因5）

**规则**：每个轮次完成后，必须在真实部署环境做端到端验收。

**验收清单**：
1. **官网**（www.onepan.cn）：首页加载、导航链接、下载链接全部点击验证
2. **管理后台**（admin.onepan.cn）：登录 → 仪表盘数据加载 → 侧边栏菜单跳转 → 商品列表 → 各功能页
3. **超级后台**（saas.onepan.cn）：页面加载 → 登录 → 租户管理
4. **移动端**（m.onepan.cn）：登录 → 首页数据 → 各tab页面
5. **API后端**（api.onepan.cn）：登录API → 核心业务API（dashboard/products/orders）

**验收标准**：
- 每个页面的核心功能必须实际操作一遍
- 每个API必须返回200（无数据时返回空数组/零值，不返回500）
- 浏览器控制台无JS错误
- 网络请求无401/500错误

**执行方式**：
- 凌舟在每个轮次结束后执行端到端验收
- 验收结果记录在任务文件中
- 发现的问题立即写入下一轮任务，但不标记当前轮次为"已完成"

## 四、总结

问题循环出现的本质不是"同事不努力"或"标准有问题"，而是**标准缺少执行保障**：

- 有任务格式，但没有**完成验证标准** → 修复无法落地
- 有API文档，但没有**API契约约束** → 前后端不对齐
- 有迁移脚本，但没有**执行跟踪** → 数据库状态不可控
- 有踩坑日志，但没有**派单前核实** → 基于过时信息派单
- 有任务文件，但没有**端到端验收** → 问题积累到部署才爆发

五道防线建立后，每个修复都必须经过"代码验证 → 构建验证 → 测试验证 → 凌舟复核 → 端到端验收"的完整闭环，确保修过的问题不会再出现。
