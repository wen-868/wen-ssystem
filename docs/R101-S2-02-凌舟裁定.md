## 一、口径裁定：**取 X（认可 JSON 包 + 通用端点 + 受限迁移）**

**红线原意**是禁止"先建表再说"、禁止 schema 失控蔓延与跨服务擅自建模；**"配置项以 JSON 包写入既有配置 KV 表"是配置存储模式，不是新业务数据模型**，且有现网先例（`platform-sys-config.service.ts` 的 `saas_settings` 整包 JSON + GET 补 DEFAULTS / PUT 整包 upsert，08 系统配置页正在跑）。据此：

**允许**：
1. 复用现有配置表（`t_platform_config` / `t_sys_config`）以 JSON 包承载 B 类配置；
2. 新增**通用配置端点**（建议 `GET/PUT /api/platform/config/kv/:key`，沿用 `saas_settings` 模式）；
3. **受限 DDL**：幂等迁移补唯一索引 / 补种子 / **给现有表 ALTER 加列**（不含新表）。

**不允许**：
4. 新建**业务表**；
5. 跨服务建表（ai-base 侧价格/计费模型 → 走协同，见第三节）；
6. "先建表再说"——任何 DDL 必须先登记 `docs/数据库变更清单.md` 再执行。

## 二、JSON 包落地的六条护栏（缺一即退回）

1. **优先不改索引**：平台级配置优先沿用"**整包 JSON 一行**"（现网 `saas_settings` 模式，`t_platform_config` 唯一键 `(platform, store_id, tenant_id)` 不含 `config_key`，天然一租户/门店一行）；**只有当确需"同一 (platform,store,tenant) 下多键并存"时**才动唯一键，且迁移必须：先查重复 → 给存量行补 `config_key` 默认值 → 幂等加索引。
2. **租户级优先用 `t_sys_config`**（其唯一键含 `config_key`，天然多键）。
3. **契约先行**：每个配置键在 `docs/API接口文档.md` 登记 **key / 值结构 / 默认值语义 / 是否必填 / 未配置时的界面行为**。
4. **包内必须有 schema 与版本**：zod 校验 + `version` 字段（便于后续演进）；`updated_by` / `updated_at` 留痕（表内已有）。
5. **默认值红线（重要）**：`GET` 补 DEFAULTS **只允许**用作"表单初值 / 空态展示"，**不得让"未配置"与"已配置为默认值"不可区分**——前端必须能呈现"**未配置（置灰阻断）+ 原因**"状态；DEFAULTS **不得被当作已生效配置写回**。
6. **分批**：每批 ≤ 3 组，独立提交、独立证据（沿用 S2-01 节奏）。
