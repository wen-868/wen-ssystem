## 零、核心原则

**以下三条原则高于一切具体规则：**

1. **一个标准，一个项目。** 所有人读同一份标准，所有代码按同一份标准写。不存在"后端标准"和"前端标准"两份东西。

2. **先达标，再提交。** TS 报错不过不提交，构建失败不提交，与标准不符不提交。这是铁律，没有例外。

3. **公共逻辑只写一次。** 编号生成、价格判断、权限校验、追溯码解析、错误处理——这些只能存在于一个地方。任何地方出现第二份实现，就是 Bug。

4. **错误面前没有"不是我引入的"。** 遇到 TS 报错、构建失败、测试不过，不允许以"这是预存的""这是第三方库的问题""这不是我改的"为由推卸。每条错误只有三种归宿：修复、记录到踩坑日志并标注原因、报告凌舟决策。任务执行人对自己触及的全部代码质量负责。

## 第一章：后端架构分层

### 1.1 固定目录结构

```

├── config/                    ← 全局配置（集中管理）
│   ├── env.ts                 ← 环境变量
│   ├── database.ts            ← 数据库连接池
│   ├── redis.ts               ← Redis 连接
│   ├── wechat-pay.ts          ← 微信支付配置
│   ├── tenant.ts              ← 租户配额（10G 等）
│   ├── api-billing.ts         ← API 计费配置
│   ├── permission.ts          ← 权限开关
│   └── constants.ts           ← 业务常量（箱规、导出上限、告警阈值等）
├── middleware/                 ← 全局中间件
│   ├── auth.ts                ← Token 鉴权（requireAuth/requirePlatformAuth/requireRoles）
│   ├── tenant.ts              ← 租户隔离校验
│   ├── price-guard.ts         ← 价格权限拦截

│   └── response-tracker.ts    ← API 响应时间追踪
├── controller/                ← 接口层（只做参数接收和返回）
│   ├── admin/                 ← 管理后台
│   ├── store/                 ← 门店端
│   ├── miniapp/               ← 小程序端
│   ├── platform/              ← 平台端
│   └── instant-retail/        ← 即时零售
├── service/                   ← 业务逻辑层（所有数据库操作在此）
│   ├── admin/                 ← 同 controller 分端
│   ├── store/
│   ├── miniapp/
│   ├── platform/
│   └── instant-retail/
├── route/                     ← 路由定义（只做路由注册，不写业务逻辑）
│   └── *.route.ts             ← 每个模块一个路由文件
├── shared/                    ← 公共工具（纯函数，无框架依赖）
│   ├── response.ts            ← 统一返回格式（ok/fail）
│   ├── biz-no.ts              ← 单据编号生成（唯一实现）
│   ├── password.ts            ← 密码哈希
│   ├── date-utils.ts          ← 日期工具
│   ├── field-sync.ts          ← 字段同步

│   ├── price-filter.ts        ← 价格权限过滤（纯函数，非中间件）
│   ├── trace-code.ts          ← 追溯码生成/解析（唯一实现）
│   └── logger.ts              ← 日志
├── types/                     ← 类型定义
├── jobs/                      ← 定时任务
└── server.ts                  ← 入口文件
```

### 1.2 分层规则（不可违反）

| 层 | 允许做什么 | 禁止做什么 |
|:---|------|------|
| **controller** | 接收参数 → 调用 service → 返回结果 | 直接操作数据库（import db/query/pool） |
| **service** | 业务逻辑、数据库操作、调用外部 API | 直接操作 req/res 对象 |
| **route** | 注册路由、挂载中间件 | 写业务逻辑、直接操作数据库 |
| **shared** | 纯工具函数、不依赖 Express | 依赖 req/res、使用 Express 类型 |
| **middleware** | 请求拦截、鉴权、校验 | 写业务逻辑 |
| **config** | 导出配置常量 | 写业务逻辑、依赖 runtime 状态 |

### 1.3 当前差距（对照整改清单）

| 标准要求 | 当前状态 | 整改方向 |
|------|------|------|
| 有 `config/` 目录 | 无，配置散落在 `shared/` 中（db.ts、env.ts、wechat-pay.ts、redis-cache.ts） | 迁移到 `config/`，在 shared/ 中留 re-export 兼容 |
| 有 `middleware/` 目录 | 无，中间件混在 `shared/` 中（auth.ts、tenant.ts、price-guard-middleware.ts、error-handler.ts、async-handler.ts） | 迁移到 `middleware/` |
| controller 不操作数据库 | 2 个违规（wechat.controller.ts 直接 SQL、notification.controller.ts 传递 pool） | 下沉到 service |
| 返回体使用 `msg` | 当前使用 `message` | 改为 `msg`，补充 traceId/apiCost |

## 第三章：全局返回体统一标准

### 3.1 强制格式

所有 API 接口**必须**使用以下格式返回，不允许任何特例：

```typescript
{
  code: string;    // "0"=成功，非 0=错误
  msg: string;     // 提示文字
  data?: T;        // 业务数据
  traceId: string; // 全局追踪 ID（UUID）
  apiCost: number; // 本次调用消耗计量数
}
```

### 3.2 统一返回函数（唯一出口）

**文件：** `backend/src/shared/response.ts`

```typescript
// 成功
export function ok<T>(data?: T) {
  return { code: "0", msg: "成功", data, traceId: uuid(), apiCost: 1 };
}

// 失败
export function fail(msg: string, code = "400") {
  return { code, msg, traceId: uuid(), apiCost: 1 };
}
```

**所有 controller 必须使用 `ok()` 和 `fail()` 返回，禁止直接 `res.json({...})`。**

### 3.3 错误码规范

| code | 含义 |
|------|------|
| "0" | 成功 |
| "400" | 参数错误 |
| "401" | 未认证 |
| "403" | 权限不足 |
| "404" | 资源不存在 |
| "500" | 服务器内部错误 |
| "1001" | 租户配额超限 |
| "1002" | 存储容量超限 |
| "1003" | 价格权限不足 |

## 第四章：公共工具层标准（shared/）

### 4.1 必须存在的公共工具

| 工具 | 文件 | 说明 |
|------|------|------|
| 编号生成器 | `shared/biz-no.ts` | **唯一实现**。所有单据编号必须调用此函数 |
| 追溯码生成/解析 | `shared/trace-code.ts` | **唯一实现**。生成箱码/瓶码，扫码解析 |
| 价格过滤 | `shared/price-filter.ts` | 纯函数。根据角色过滤价格字段 |
| 密码哈希 | `shared/password.ts` | bcrypt 封装 |
| 日期工具 | `shared/date-utils.ts` | 日期格式化、范围计算 |
| 订单履约分流 | `shared/fulfillment.ts` | WHOLESALE/RETAIL 状态机分流 |
| 返回格式 | `shared/response.ts` | ok/fail 统一返回 |
| 日志 | `shared/logger.ts` | pino 日志 |

### 4.2 公共工具规则（不可违反）

1. **禁止重复实现。** 同一个功能在 shared/ 中只能有一份代码。发现第二份，立即删除并统一。
2. **禁止在业务代码中内联公共逻辑。** 价格判断、编号生成、追溯码解析——业务代码中直接调用 shared/ 函数，不得手写内联逻辑。
3. **shared/ 不依赖 Express。** 公共工具是纯函数，不依赖 req/res/next。

### 4.3 当前差距

| 问题 | 当前状态 | 整改 |
|------|------|------|
| 两套编号生成 | `biz-no.ts`（Math.random）+ `id.ts`（crypto） | 统一为一个 |
| 价格判断重复 | 3 处手写 `customerType === "WHOLESALE"` | 统一调用 price-filter.ts |
| 追溯码未抽取 | 逻辑内联在 trace-records.service.ts | 抽取到 shared/trace-code.ts |
| 订单流程重复 | 3 处独立实现下单流程 | 统一到 fulfillment.ts |

## 第五章：业务硬性约束

### 5.1 价格隔离（不可违反）

| 角色 | 可见价格 | 规则 |
|------|------|------|
| 零售商 | 零售价 | 不可见批发价、成本价 |
| 批发商 | 批发价 | 不可见上游底价/成本价 |
| 供应商 | 供货价 | 不可见下游成交零售价 |
| 管理员 | 全部价格 | 审计日志记录每次查询 |

**中间件：** `price-guard.ts` 必须应用到**所有价格敏感路由**，包括：
- `product.route.ts` — 商品列表/详情
- `admin-order.route.ts` — 订单管理
- `store.route.ts` — 门店销售
- `miniapp.route.ts` — 小程序
- `export.route.ts` — 导出

**禁止**在服务层手写 `customerType === "WHOLESALE"` 判断价格可见性，必须调用 price-guard。

### 5.2 追溯码（不可违反）

1. 出入库**必须**自动绑定追溯码，写入 `trace_event_log`
2. 追溯码生成/解析**必须**调用 `shared/trace-code.ts`
3. 追溯码支持按商品/分类启停（总开关在 `config/permission.ts`）

### 5.3 销售中心

1. 批发和零售共用同一套单据体系（`sale_bill` 表），通过 `customer_type` 字段区分
2. 批发订单：跳过支付、ACCOUNT 结算、不锁定库存
3. 零售订单：正常支付流程、CASH/CREDIT 结算

### 5.4 数据存储

1. 每个租户配额固定 10G，超容量弹窗提醒，**禁止自动删除历史单据**
2. 结构化数据全部存入 MySQL
3. 图片/附件本地归档，不上云

### 5.5 历史单据

1. 支持归档标记（`archived` 状态），归档后不可编辑
2. 支持 CSV 导出
3. 禁止物理删除已完成单据
4. 归档逻辑统一在 `service/admin/archive.service.ts` 中

## 第七章：代码提交标准

### 7.1 提交前检查（铁律）

**以下 3 步必须全部通过才能提交，不允许跳过：**

```
# 后端
cd backend
npm run typecheck    # tsc --noEmit → 0 错误
npm run build        # 构建成功

# 前端（改哪个项目跑哪个）
cd admin-web && npm run build
cd saas-admin && npm run build
cd merchant-mobile && npm run build
```

### 7.1.1 错误责任制（铁律）

**提交前检查时遇到的任何 TS 错误、构建错误、测试失败，无论是否由本次修改引入，执行人必须处理。**

处理方式只有三种，不允许第四种：

| 方式 | 说明 | 示例 |
|------|------|------|
| **修复** | 直接修掉 | 缺类型声明 → 补 `@types/xxx`；拼写错误 → 改正 |
| **记录** | 修不掉但已知原因，写入踩坑日志 | uni-app 预编译指令 TS 报错 → 记录到踩坑日志，标注"非运行时错误，uni-app 编译期处理" |
| **报告** | 不确定如何处理的，报告凌舟决策 | 第三方库类型冲突 → 附错误截图和上下文，等凌舟决策 |

**禁止行为：**
- "这不是我引入的，我不处理" → 红线第 11 条
- "这是预存的，跟我没关系" → 红线第 11 条
- "这是第三方库的问题，没办法" → 红线第 11 条
- 不记录、不报告、不修复，直接提交 → 红线第 11 条

**R8-6 任务特别说明：** 247 个 TS 错误中，如遇到 uni-app 预编译指令（如 `#ifdef`、`#ifndef`）或 `@dcloudio` 类型定义导致的 TS 报错，且确认不影响运行时，**必须记录到踩坑日志**并标注原因，**不得跳过不处理**。阿坚修复 R8-6 时，每条错误必须有归宿——修复或记录，不允许遗漏。

### 7.2 提交信息格式

```
type: 中文描述

可用的 type：
  feat:  新功能
  fix:   修复
  docs:  文档
  chore: 维护/清理
  refactor: 重构（不改变功能）
```

示例：
```
fix: 修复商品创建时品牌字段未发送
refactor: 统一编号生成器，删除 biz-no.ts 旧实现
docs: 更新项目统一标准 v1.0
```

### 7.3 提交粒度

1. 一次提交只做一件事
2. 不要一次提交 96 个文件
3. 功能修改和代码清理分开提交

## 第九章：禁止事项（红线）

**以下行为一旦发现，立即回退：**

1. TS 错误不为 0 就提交代码
2. 构建失败就提交代码
3. 直接 `res.json({...})` 绕过 `ok()`/`fail()` 统一返回
4. Controller 直接操作数据库（import db/query/pool）
5. 手写价格判断逻辑（`customerType === "WHOLESALE"`）绕过 price-guard
6. 手写编号生成逻辑绕过 `shared/biz-no.ts`
7. 创建多个分支（只保留 main）
8. 创建多个任务文件（只有 `docs/tasks/current-tasks.md`）
9. 在代码中硬编码敏感信息（密码、密钥、Token）
10. 使用英文写文档内容

## 第十三章：错误处理规范

### 13.1 错误分类

| 分类 | 错误码范围 | 说明 | 示例 |
|------|:---:|------|------|
| 成功 | 0 | 操作成功 | — |
| 参数错误 | 400 | 请求参数不合法 | 必填字段为空、格式不正确 |
| 认证错误 | 401 | 未登录或 token 失效 | token 过期、未携带 token |
| 权限错误 | 403 | 无权限访问 | 角色权限不足、价格权限不足 |
| 资源不存在 | 404 | 请求的资源不存在 | 商品不存在、订单不存在 |
| 业务错误 | 1000-1999 | 业务逻辑错误 | 库存不足(1001)、配额超限(1002)、状态不允许(1003) |
| 系统错误 | 2000-2999 | 系统级错误 | 数据库错误(2001)、外部服务错误(2002) |
| 服务器错误 | 500 | 未预期的内部错误 | 代码异常 |

### 13.2 错误处理流程

```
controller 调用 service
    ↓
service 抛出业务异常
    ↓
async-handler 捕获异常
    ↓
error-handler 统一处理
    ↓
返回统一格式 { code, msg, traceId, apiCost }
    ↓
飞书告警（P0 错误）
    ↓
错误日志持久化
```

### 13.3 错误处理规则

1. **controller 层禁止 try-catch。** 所有错误由 async-handler 自动传递到 error-handler，不要在 controller 中手动捕获。
2. **service 层抛出业务异常。** 使用 `throw new AppError(code, message)` 抛出可识别的业务错误。
3. **禁止直接 `res.status().json()`。** 错误响应统一走 `ok()`/`fail()` 或 error-handler。
4. **P0 错误必须飞书告警。** 错误码 500 和 2000-2999 范围的错误，必须触发飞书通知。

### 13.4 当前问题

当前 47 个 controller 中有 168 个 try-catch 直接 `res.status().json()` 返回错误，导致全局 errorHandler、飞书告警、错误日志持久化全部失效。需按标准整改。

### 14.1 日志级别

| 级别 | 用途 | 生产环境 |
|------|------|:---:|
| DEBUG | 开发调试信息 | 关闭 |
| INFO | 业务流程记录 | 开启 |
| WARN | 可恢复的异常 | 开启 |

## 第十七章：前端状态管理规范

### 17.1 状态管理库

- **统一使用 Pinia。** 禁止使用 Vuex（已过时）。
- Store 文件命名：`stores/模块名.ts`（如 `stores/user.ts`、`stores/cart.ts`）

### 17.2 Store 命名约定

```typescript
// stores/user.ts
export const useUserStore = defineStore('user', () => {
  // state
  const userInfo = ref<UserInfo | null>(null);
  const token = ref('');

  // getters
  const isLoggedIn = computed(() => !!token.value);

  // actions
  async function login(username: string, password: string) { ... }
  function logout() { ... }

  return { userInfo, token, isLoggedIn, login, logout };
});
```

**规则：**
- Store ID 和文件名一致（`stores/user.ts` → `defineStore('user', ...)`）
- 使用 Composition API 风格（`setup store`），不使用 Options API 风格
- 函数命名：`useXxxStore`

### 17.3 持久化策略

- 用户 token 和基本信息：持久化到 localStorage，使用 `pinia-plugin-persistedstate`
- 购物车数据：后端存储，前端只做缓存
- 临时筛选条件：不持久化，页面切换后重置

### 17.4 跨组件通信

| 场景 | 方案 |
|------|------|
| 父子组件 | props + emits |
| 跨层级组件 | Pinia store |
| 全局状态 | Pinia store |
| 事件总线 | 禁止使用（Vue3 已废弃 EventBus） |

### 17.5 禁止事项

1. 禁止在组件中直接操作 localStorage/sessionStorage
2. 禁止使用 Vuex
3. 禁止使用 EventBus（`mitt` 等）
4. 禁止在 store 中直接操作 DOM
