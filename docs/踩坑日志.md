### [1] PowerShell正则lookahead写错导致路径过度替换

- 日期：2026-07-22
- 踩坑人：墨
- 关键词：正则替换, 相对路径, 目录迁移, lookahead
- 现象：views目录重组时，用正则 `(['\"])\.\./(?!/)` 批量替换 `../` 为 `../../`，结果7个已经正确的文件（已是`../../`）被错误替换成 `../../../`，导致vue-tsc报 Cannot find module 错误
- 原因：负向先行断言 `(?!/)` 只检查 `../` 后面是否是 `/`，但对于 `../../api`，匹配到第一个 `../` 后，下一个字符是 `.`（不是 `/`），断言通过，导致 `../../` 被替换成 `../../../`
- 解决：正确断言应为 `(?!\.\./)`（检查后面不是又一个 `../`）。但更安全的方法是直接用字符串替换：`$c.Replace("../../../", "../../")`，避免正则引号转义问题
- 教训：批量正则替换路径时，必须用测试用例验证 lookahead 逻辑；对于已知模式的替换，优先用字符串Replace而非正则

### [2] git mv批量迁移时遗漏重复文件清理

- 日期：2026-07-22
- 踩坑人：墨
- 关键词：git mv, 目录迁移, 重复文件
- 现象：R53-06前期迁移用"复制"方式（cp到子目录）而非"移动"（git mv），导致根目录和子目录存在同名文件，git双重跟踪。后续迁移时根目录旧文件干扰判断
- 原因：前期迁移commit只把文件复制到子目录并修复路径，没有删除根目录原文件。git status显示clean（因为两个版本都被跟踪），但根目录旧文件的 `../` 路径已失效
- 解决：对已存在于子目录的根目录文件，用 `git rm -f` 删除根目录副本；对需要迁移的文件用 `git mv` 移动
- 教训：目录迁移必须用 `git mv`（移动+保留历史），不要用 cp 复制；迁移后立即检查根目录是否有遗漏的旧文件

### [3] ./components/ 相对导入在目录迁移后失效

- 日期：2026-07-22
- 踩坑人：墨
- 关键词：相对导入, components, 目录迁移
- 现象：两个文件（InstantRetailPlatform.vue / ProductReviewTasks.vue）在根目录时用 `./components/XXX.vue` 导入（指向 views/components/），迁移到子目录后 `./components/` 指向 views/子目录/components/（不存在），vue-tsc报错

### [4] 同一文件多处修改时并行 Edit 导致部分修改被覆盖丢失

- 日期：2026-07-24
- 踩坑人：墨
- 关键词：并行编辑, Edit 工具, 同文件多处修改, 批量弹窗宽度统一
- 现象：R53-18第三轮修复 48 处不规范弹窗宽度时，对同一文件（如 StoreValueCards.vue 有 5 处弹窗）在同一批次中发起多个 Edit 调用，结果部分修改被覆盖丢失。首次提交（6beedf46）的统计显示 StoreValueCards.vue 仅 `2 ++ 2 --`（1 处），但实际应修改 5 处。grep 复查发现仍有 500px、650px、700px、800px 等非标准宽度残留
- 原因：同一文件的多个 Edit 调用如果在同一响应中并行发出，工具会基于同一原始内容做替换，后执行的 Edit 可能覆盖前一次 Edit 的修改结果（基于旧的 file content 快照），导致部分修改丢失
- 解决：分两步处理：①首次提交用并行 Edit 处理多个文件（每文件 1 处）；②对有 2 处以上修改的文件（如 StoreValueCards.vue 5 处、PurchasePlans.vue 3 处、ProductCombo.vue 2 处等），单独串行 Edit 处理；③提交后立即用 `grep \"width=\\\"(500|550|600|650|700|750|800|850)px\\\""` 复查，发现残留后单独补充修复并提交（b2c5d5bf）
- 教训：对同一文件多处修改时严禁并行 Edit，必须串行处理（一个 Edit 完成后再发下一个）；批量任务完成后必须用 grep 复查实际修改结果是否与预期一致，不能只看 Edit 工具的返回 success

### [5] 替换 queryOneWithTenant<any> 时误加 null 检查破坏原始返回语义

- 日期：2026-07-24
- 踩坑人：阿坚
- 关键词：类型安全改造, any 替换, null 检查, 返回类型, 测试失败
- 现象：R55-04 第五批清理 admin service 目录 any 时，把 `credit-adjust.service.ts` 的 `adjustLimit`/`adjustTerm` 末尾 `const record = await queryOneWithTenant<any>(...)` 替换为明确接口 `CreditRecordRow` 后，顺手添加了 `if (!record) throw Object.assign(new Error("授信记录不存在"), { statusCode: 404 })`。vitest 报 1 个失败：用例 "成功调整 + credit 为 null（?? 右分支）" mock `queryOneWithTenant` 第二次返回 null，期望 `adjustLimit` 返回 null，实际却抛 404
- 原因：原始代码末尾是 `return record;`（直接返回，允许 null），返回类型 `Promise<any>` 隐式允许 null。替换 `<any>` 为 `<CreditRecordRow>` 后，为消除 `record` 的 null 风险"自作主张"加了抛错检查，改变了原始业务语义——原始逻辑在记录不存在时返回 null 由调用方处理，而非抛 404
- 解决：移除自己添加的 `if (!record) throw ...` 检查，恢复 `return record;` 原始行为；将返回类型从 `Promise<CreditRecordRow>` 改为 `Promise<CreditRecordRow | null>` 以兼容 null 返回。同步排查 `credit-collection.service.ts` 的 `createCollection`/`updateCollection`，发现也误加了同样模式的 null 检查，一并移除并改返回类型为 `Promise<... | null>`。修复后 vitest 416 文件 4857 用例全部通过
- 教训：替换 `<any>` 泛型时只做"类型标注"这一件事，严禁顺手添加原始代码没有的 null 检查/分支/业务逻辑；若类型系统报 `record` 可能为 null，正确做法是把返回类型标注为 `Promise<接口 | null>`（匹配原始 return 语义），而不是加抛错改变行为；改完后必须跑 vitest 验证 mock 返回 null 的用例仍能通过

### [6] auto-routes 与路由文件内部重复注册 requireAuthWithTenant

- 日期：2026-07-28
- 踩坑人：阿澈
- 关键词：路由注册, 认证中间件, Express, auto-routes, 重复注册
- 现象：R56-04 清理路由重复注册时发现，14 个路由文件内部使用 `router.use(requireAuthWithTenant)`，同时 `auto-routes.ts` 根据 `routeConfig.auth` 配置在外层统一添加认证中间件。导致每个请求经过两层 `requireAuthWithTenant`，认证逻辑被执行两次
- 原因：路由文件在开发时未意识到 auto-routes 已统一处理认证，习惯性地在 router 内部又加了一层 `requireAuthWithTenant`。对于有 `priceResponseFilter()` 等业务中间件的路由文件，开发者将认证中间件与业务中间件并列添加，未区分两者职责
- 解决：14 个路由文件中移除 `router.use(requireAuthWithTenant)`，保留 `priceResponseFilter()` 等业务中间件（这些是路由自身逻辑，非 auto-routes 职责）；auto-routes.ts 新增重复前缀检测，发现多个路由注册同一前缀时输出警告日志
- 教训：使用 auto-routes 统一注册后，路由文件内部不应再添加 auto-routes 已处理的中间件（认证、租户校验）；路由文件只负责业务中间件和具体路由定义；新增路由文件时必须确认 auto-routes 的注册规则，避免重复添加

### [7] 替换 connExecute 后遗漏 vi.doMock 动态 mock 文件导致测试失败

- 日期：2026-07-28
- 踩坑人：阿坚
- 关键词：connExecute, vi.mock, vi.doMock, 测试 mock 遗漏, tenant-isolation
- 现象：R58-01 将 `(conn as any).execute` 替换为 `connExecute` 工具函数后，同步更新了 6 个测试文件的 `vi.mock("../../../shared/db")` 补充 `connExecute` 导出，但遗漏了 `tenant-isolation.test.ts`。该文件同时使用了 `vi.mock`（静态）和 `vi.doMock`（动态）两种 mock 方式，导致 vitest 报错 `[vitest] No "connExecute" export is defined on the "../shared/db" mock`，1 个用例失败
- 原因：`tenant-isolation.test.ts` 的 seckill 租户隔离用例使用 `vi.doMock` 动态替换 `../shared/db` 模块（仅包含 `transaction/query/queryOne`），未包含 `connExecute`；而 `buySeckill` 内部调用 `connExecute` 时找不到导出。排查时只关注了 `vi.mock` 静态 mock 的文件，漏扫了 `vi.doMock` 动态 mock 的文件
- 解决：在 `tenant-isolation.test.ts` 的 `vi.hoisted`/`vi.mock` 中补充 `connExecute` 导出，`beforeEach` 中实现 `mocks.connExecute.mockImplementation(async (conn, sql, params) => conn.execute(sql, params))`；同时在 `vi.doMock` 中补充 `connExecute: async (conn, sql, params) => conn.execute(sql, params)`。修复后 vitest 416 文件 4857 用例全部通过
- 教训：替换共享模块（如 db 工具函数）的导出后，必须全量扫描 `vi.mock` 和 `vi.doMock` 两种 mock 方式的所有测试文件，不能只搜 `vi.mock`；`grep -rn 'doMock.*shared/db'` 应与 `grep -rn 'mock.*shared/db'` 同步检查；动态 `vi.doMock` 的模块对象也必须包含新增的导出函数
