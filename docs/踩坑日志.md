## 坑列表

### [1] vitest ESM 下 isRouter() 对 Express Router 返回 false
- 日期：2026-07-05
- 踩坑人：凌舟
- 关键词：vitest, ESM, Express Router, auto-routes
- 现象：`npx vitest run` 下 125 个测试全部 404，因为 0 条路由注册成功
- 原因：`isRouter()` 中 `typeof v.use === "function"` 在 vitest ESM 转换后失效，对 Express Router 实例返回 false。`auto-routes.ts` 的 `.routes.ts` 过滤器在 dist 目录只能匹配 `.routes.js`
- 解决：消除 `isRouter()` 调用，直接信任 `routeConfig.router` 导出；过滤器兼容 `.routes.ts` 和 `.routes.js` 两种扩展名
- 教训：vitest 的模块转换会影响运行时的 `typeof` 判断。路由注册逻辑中不要依赖 `typeof` 检测第三方库实例

### [2] 自动路由注册与手动路由注册冲突
- 日期：2026-07-05
- 踩坑人：凌舟
- 关键词：auto-routes, server.ts, 路由注册, 合并冲突
- 现象：阿坚提交了删除 auto-routes.ts 改手动注册的方案，但与我们拆分后的子路由文件结构不兼容，合并后大量 TypeScript 错误
- 原因：阿坚基于旧版单一 `routes/*.routes.ts` 文件结构（admin.routes.ts、store.routes.ts 等），而当前代码已拆分为子目录的模块化路由文件
- 解决：保留 auto-routes.ts 自动注册方案，修复 isRouter 问题，而非删除它
- 教训：两人的方案方向不同时，要对比代码结构差异，选兼容性更好的方案

### [3] 三方合并时 package-lock.json 冲突处理
- 日期：2026-07-05
- 踩坑人：凌舟
- 关键词：合并, package-lock.json, npm, 冲突
- 现象：合并三个分支时，package-lock.json 和 package.json 每次都冲突
- 原因：合并前 package.json 有新增依赖（如 pino），而各分支基于旧版 package.json 开发
- 解决：`git checkout --ours` 保留 main 的 package.json 和 package-lock.json
- 教训：合并前先检查 package.json 差异，提前决定用哪个版本

### [4] 路由注册 order 导致认证中间件失效
- 日期：2026-07-05
- 踩坑人：阿坚
- 关键词：Express, 中间件, 路由顺序, 认证
- 现象：Store `/me` 端点未认证用户访问时崩溃，`req.user!` 非空断言导致 NPE
- 原因：`/me` 路由在 `requireAuthWithTenant` 中间件之前注册
- 解决：将 `/me` 路由移到 `requireAuthWithTenant` 之后
- 教训：Express 路由注册顺序就是中间件执行顺序，`app.use(auth)` 之前的所有路由都不受保护

### [5] vitest 与 jest 不兼容 — jest.fn() vs vi.fn()
- 日期：2026-07-05
- 踩坑人：凌舟
- 关键词：vitest, jest, mock, 测试
- 现象：`tests/auth.test.ts` 中 4 个测试失败，报 `jest is not defined`
- 原因：项目使用 vitest 但测试文件引用了 jest 的 API（jest.fn()）
- 解决：将 `jest.fn()` 替换为 `vi.fn()`
- 教训：迁移到 vitest 后，全局搜索 `jest.` 替换为 `vi.`

### [6] 品牌字段存储类型不一致 — VARCHAR vs 外键
- 日期：2026-07-05
- 踩坑人：凌舟
- 关键词：品牌, brand, 外键, DDL, 数据一致性
- 现象：product_spu.brand 是 VARCHAR(128) 存品牌名，但存在独立的 brand 表（id/name/logo）。前端传 brandId 数字 ID，后端当字符串存储
- 原因：初期设计时 brand 是自由文本字段，后来增加了 brand 独立表，但未同步修改 product_spu
- 解决：添加 brand_id 外键字段，迁移现有数据，后端改为接受 brandId
- 教训：增加独立实体表后，必须同步修改所有引用该实体的表，统一使用外键关联

### [7] 成本价被硬编码为 0
- 日期：2026-07-05
- 踩坑人：凌舟
- 关键词：成本价, 硬编码, 价格, 前端表单
- 现象：所有商品创建时 costPrice 固定为 0，前端表单无成本价输入框
- 原因：Products.vue 第 555 行 `costPrice: 0` 硬编码，后端 createProduct 也未处理 costPrice
- 解决：前端补 costPrice 输入框，后端 createProduct 接受 costPrice 参数
- 教训：创建商品时必须同时录入价格，不能给默认值。涉及金额的字段绝不能用硬编码 0

### [8] 前后端 API 路径不匹配 — 多了 /finance/ 和 /system/ 段
- 日期：2026-07-05
- 踩坑人：凌舟
- 关键词：API 路径, 路由, 前后端不匹配
- 现象：费用管理前端调 `/api/admin/finance/expenses`，后端注册 `/api/admin/expenses`；审批前端调 `/api/admin/system/approval/...`，后端注册 `/api/admin/approval/...`
- 原因：前端 api.ts 在路径中额外加了 `/finance/` 和 `/system/` 段，与后端注册路径不一致
- 解决：以后端路径为准，前端去掉多余路径段
- 教训：前后端 API 路径必须严格一致，开发时以路由注册代码为准，不要在 api.ts 中自行添加路径段

### [9] 错误处理不统一 — controller 层 try-catch 绕过全局 errorHandler
- 日期：2026-07-05
- 踩坑人：阿坚
- 关键词：错误处理, try-catch, errorHandler, 飞书告警
- 现象：47 个 controller 的 168 个 try-catch 直接 `res.status().json()` 返回错误，导致全局 errorHandler、飞书告警、错误日志持久化全部失效
- 原因：开发初期没有统一的错误处理中间件，各 controller 自行处理错误。后来加了 errorHandler 但未同步清理 controller 中的 try-catch
- 解决：移除 controller 中的 try-catch，让 asyncHandler 自动传递错误到 errorHandler
- 教训：先建立全局错误处理机制，再写业务代码。不要在 controller 中直接 res.json 错误

### [10] 多个任务文件导致成员读错文件
- 日期：2026-07-05
- 踩坑人：凌舟
- 关键词：任务文件, 混乱, 文件管理
- 现象：三人各有一个任务文件（ajian-tasks-v7.md、mo-tasks-v7.md、ache-tasks-v7.md），加上 task-plan-v7.md、task-breakdown-v7.md，成员经常读错文件或漏掉更新
- 原因：多人多文件模式下，任务状态分散在多个文件中，更新不及时
- 解决：合并为单一文件 `docs/tasks/current-tasks.md`，按轮次（R1/R2/R3）编号，所有人读同一个文件
- 教训：任务管理必须集中化，一个文件、一个位置、一个格式
