### [1] vitest ESM 下 isRouter() 对 Express Router 返回 false
- 日期：2026-07-05
- 踩坑人：凌舟
- 关键词：vitest, ESM, Express Router, auto-routes
- 现象：`npx vitest run` 下 125 个测试全部 404，因为 0 条路由注册成功
- 原因：`isRouter()` 中 `typeof v.use === "function"` 在 vitest ESM 转换后失效，对 Express Router 实例返回 false。`auto-routes.ts` 的 `.routes.ts` 过滤器在 dist 目录只能匹配 `.routes.js`
- 解决：消除 `isRouter()` 调用，直接信任 `routeConfig.router` 导出；过滤器兼容 `.routes.ts` 和 `.routes.js` 两种扩展名
- 教训：vitest 的模块转换会影响运行时的 `typeof` 判断。路由注册逻辑中不要依赖 `typeof` 检测第三方库实例

### [15] uni-app 条件编译导致 vue-tsc 误报重复声明
- 日期：2026-07-05
- 踩坑人：阿澈
- 关键词：uni-app, 条件编译, vue-tsc, #ifdef, BASE_URL, TS2451
- 现象：`app-mobile/src/api/request.ts` 中使用 `#ifdef H5` / `#ifndef H5` 为不同平台定义不同的 `const BASE_URL`，vue-tsc 无法识别 uni-app 条件编译指令，将两个 `const BASE_URL` 视为重复声明，报 TS2451

- 教训：uni-app 项目中涉及条件编译的 `const` 声明要避免 vue-tsc 看到重复声明，统一用 IIFE 或函数包裹多分支

### [18] re-export 文件用 `export { x } from` 在 v8 覆盖率中显示 0%
- 日期：2026-07-07
- 踩坑人：阿坚
- 关键词：vitest, coverage, v8, re-export, export *, shared/, 兼容层
- 现象：shared/ 下 db.ts、env.ts、redis-cache.ts、wechat-pay.ts、auth.ts 这 5 个纯 re-export 兼容文件，v8 覆盖率恒为 0%（lines/branches/functions/statements 全 0），导致整体 shared/ 覆盖率卡在 97% 上不去
- 原因：`export { queryWithTenant, queryOneWithTenant } from "../config/database.js"` 这种**命名导出 re-export**语法，v8 coverage 引擎视为不可达代码，无论被多少测试导入都计 0%。而 `export * from "..."`（namespace re-export）能被正确统计
- 解决：将 5 个 re-export 兼容文件全部从 `export { x, y } from` 改为 `export * from`，并在 `__tests__/shared/re-exports.test.ts` 中显式 import 触发统计。覆盖率立即从 97.29% 跃升至 100%
- 教训：**v8 coverage 对 re-export 语法的处理是不对称的**——`export *` 统计正确，`export { x } from` 统计为 0%。当 re-export 文件覆盖率恒为 0% 时，不要继续加测试，先改语法。这条规则对纯兼容层文件尤其重要

### [19] `Number(undefined) ?? 0` 返回 NaN（不是 0）
- 日期：2026-07-07
- 踩坑人：阿坚
- 关键词：JavaScript, NaN, nullish coalescing, ??, ||, Number, product-sync, 隐式类型转换
- 现象：product-sync.ts 中 `Number(result?.affectedRows) ?? 0` 在 result 为 null/undefined 时，affectedRows 最终变成 NaN 透传到下游，导致同步统计失真
- 原因：`Number(undefined)` 返回 `NaN`（不是 `null` 也不是 `undefined`）。而 `??`（nullish coalescing）**只在左侧为 null/undefined 时才取右侧**，NaN 既不是 null 也不是 undefined，所以 `NaN ?? 0` 仍然返回 NaN。这是 JS 隐式类型转换 + 空值合并运算符语义的交叉陷阱
- 解决：改用 `|| 0`（logical OR，左侧 falsy 即取右侧，NaN 是 falsy 所以正确兜底为 0）。共修复 14 处
- 教训：**`?? 0` 只能兜底 null/undefined，不能兜底 NaN/0/""**。当左侧是 `Number(x)` / `parseInt(x)` / `parseFloat(x)` 这类可能返回 NaN 的转换时，必须用 `|| 0` 而非 `?? 0`。或者更稳妥：先用 `Number.isFinite()` 判断

### [20] migration.ts safeExec 长 `||` 链导致分支爆炸，覆盖率无法 100%
- 日期：2026-07-07
- 踩坑人：阿坚
- 关键词：vitest, coverage, branches, || 短路, migration, safeExec, 重构
- 现象：migration.ts safeExec 中 `if (msg.includes("duplicate") || msg.includes("already exists") || ... 10个 ||)` 共 10+ 个 `||` 短路分支，每个分支都需单独测才能 100% branches 覆盖率，测试用例数量爆炸
- 原因：v8 把每个 `||` 视为独立分支，N 个 `||` 就是 N 个分支需 N 个测试。同时还存在 `(msg.includes("table") && msg.includes("already exists"))` 这种已被前面 `||` 链覆盖的死代码分支
- 解决：将 13 个错误消息模式提取到 `SKIP_PATTERNS` 数组常量，用 `.some((p) => msg.includes(p))` 遍历替代 `||` 链，分支数从 13 降到 1。同时删除已被覆盖的死代码条件。覆盖率轻松 100%
- 教训：**测试覆盖率 100% 不是靠堆测试用例，而是靠重构代码减少分支。** `||` 链超过 5 个就该考虑改成数组 + `.some()`/`.includes()`。覆盖率卡在 99% 时先看是不是有死代码分支或 `||` 短路链
