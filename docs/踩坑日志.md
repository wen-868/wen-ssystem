### [1] PowerShell正则lookahead写错导致路径过度替换

- 日期：2026-07-22
- 踩坑人：墨
- 关键词：正则替换, 相对路径, 目录迁移, lookahead
- 现象：views目录重组时，用正则 `(['\"])\.\./(?!/)` 批量替换 `../` 为 `../../`，结果7个已经正确的文件（已是`../../`）被错误替换成 `../../../`，导致vue-tsc报 Cannot find module 错误
- 原因：负向先行断言 `(?!/)` 只检查 `../` 后面是否是 `/`，但对于 `../../api`，匹配到第一个 `../` 后，下一个字符是 `.`（不是 `/`），断言通过，导致 `../../` 被替换成 `../../../`
- 解决：正确断言应为 `(?!\.\./)`（检查后面不是又一个 `../`）。但更安全的方法是直接用字符串替换：`$c.Replace("../../../", "../../")`，避免正则引号转义问题
- 教训：批量正则替换路径时，必须用测试用例验证 lookahead 逻辑；对于已知模式的替换，优先用字符串Replace而非正则

### [4] 同一文件多处修改时并行 Edit 导致部分修改被覆盖丢失

- 日期：2026-07-24
- 踩坑人：墨
- 关键词：并行编辑, Edit 工具, 同文件多处修改, 批量弹窗宽度统一
- 现象：R53-18第三轮修复 48 处不规范弹窗宽度时，对同一文件（如 StoreValueCards.vue 有 5 处弹窗）在同一批次中发起多个 Edit 调用，结果部分修改被覆盖丢失。首次提交（6beedf46）的统计显示 StoreValueCards.vue 仅 `2 ++ 2 --`（1 处），但实际应修改 5 处。grep 复查发现仍有 500px、650px、700px、800px 等非标准宽度残留
- 原因：同一文件的多个 Edit 调用如果在同一响应中并行发出，工具会基于同一原始内容做替换，后执行的 Edit 可能覆盖前一次 Edit 的修改结果（基于旧的 file content 快照），导致部分修改丢失
- 解决：分两步处理：①首次提交用并行 Edit 处理多个文件（每文件 1 处）；②对有 2 处以上修改的文件（如 StoreValueCards.vue 5 处、PurchasePlans.vue 3 处、ProductCombo.vue 2 处等），单独串行 Edit 处理；③提交后立即用 `grep \"width=\\\"(500|550|600|650|700|750|800|850)px\\\""` 复查，发现残留后单独补充修复并提交（b2c5d5bf）
- 教训：对同一文件多处修改时严禁并行 Edit，必须串行处理（一个 Edit 完成后再发下一个）；批量任务完成后必须用 grep 复查实际修改结果是否与预期一致，不能只看 Edit 工具的返回 success

### [5] 替换 queryOneWithTenant<any> 时误加 null 检查破坏原始返回语义

- 日期：2026-07-24
- 踩坑人：阿坚
- 关键词：类型安全改造, any 替换, null 检查, 返回类型, 测试失败
- 现象：R55-04 第五批清理 admin service 目录 any 时，把 `credit-adjust.service.ts` 的 `adjustLimit`/`adjustTerm` 末尾 `const record = await queryOneWithTenant<any>(...)` 替换为明确接口 `CreditRecordRow` 后，顺手添加了 `if (!record) throw Object.assign(new Error("授信记录不存在"), { statusCode: 404 })`。vitest 报 1 个失败：用例 "成功调整 + credit 为 null（?? 右分支）" mock `queryOneWithTenant` 第二次返回 null，期望 `adjustLimit` 返回 null，实际却抛 404
- 原因：原始代码末尾是 `return record;`（直接返回，允许 null），返回类型 `Promise<any>` 隐式允许 null。替换 `<any>` 为 `<CreditRecordRow>` 后，为消除 `record` 的 null 风险"自作主张"加了抛错检查，改变了原始业务语义——原始逻辑在记录不存在时返回 null 由调用方处理，而非抛 404
- 解决：移除自己添加的 `if (!record) throw ...` 检查，恢复 `return record;` 原始行为；将返回类型从 `Promise<CreditRecordRow>` 改为 `Promise<CreditRecordRow | null>` 以兼容 null 返回。同步排查 `credit-collection.service.ts` 的 `createCollection`/`updateCollection`，发现也误加了同样模式的 null 检查，一并移除并改返回类型为 `Promise<... | null>`。修复后 vitest 416 文件 4857 用例全部通过
- 教训：替换 `<any>` 泛型时只做"类型标注"这一件事，严禁顺手添加原始代码没有的 null 检查/分支/业务逻辑；若类型系统报 `record` 可能为 null，正确做法是把返回类型标注为 `Promise<接口 | null>`（匹配原始 return 语义），而不是加抛错改变行为；改完后必须跑 vitest 验证 mock 返回 null 的用例仍能通过

### [8] maskConfig 替换 any 时若用窄接口会导致 `...config` 丢失字段

- 日期：2026-07-28
- 踩坑人：阿坚
- 关键词：any 替换, 泛型, 展开运算符, 字段丢失, maskConfig, MaskConfigInput
- 现象：R58-02 把 `common.service.ts` 的 `maskConfig(config: any)` 替换为明确接口时，初版定义 `MaskConfigInput` 仅包含 `appSecret?/accessToken?/refreshToken?` 三个字段，入参类型改为 `MaskConfigInput | null | undefined`。tsc 通过，但 `maskConfig` 内部 `return { ...config, appSecret: ..., ... }` 中 `...config` 只展开 3 个字段，原对象的其他字段（id/platform/storeId/appKey/merchantId/enabled/configJson/createdAt/updatedAt）全部丢失，调用方拿到的脱敏对象只剩 3 个字段，是严重 BUG
- 原因：TypeScript 的展开运算符 `...config` 按 config 的声明类型展开，而非实际运行时类型。当 config 声明为窄接口 `MaskConfigInput`（只有 3 个字段）时，TypeScript 认为 config 只有这 3 个字段，`...config` 只展开这 3 个字段；调用方传入的 `PlatformConfigRow`（10+ 字段）虽运行时有所有字段，但类型上被窄化为 3 个字段
- 解决：`maskConfig` 改用泛型 `<T extends MaskConfigInput>(config: T | null | undefined)`，约束 T 必须满足 MaskConfigInput（有 appSecret/accessToken/refreshToken 可选字段），但保留 T 的所有字段。这样 `...config` 按 T 展开，保留所有字段；同时 `config.appSecret` 等访问仍受 MaskConfigInput 约束。调用方 `maskConfig(row)` 中 row 是 PlatformConfigRow，T 推断为 PlatformConfigRow，返回类型保留所有字段
- 教训：替换接收"任意对象 + 访问少数字段"的 `any` 入参时，不能用窄接口（会丢失 `...展开` 的其他字段）；正确做法是用泛型 `<T extends 窄接口>` 约束 T 满足少数字段访问，同时保留 T 的所有字段；同理适用于 `_.pick(obj, keys)` / `Object.assign({}, obj, ...)` / `{...obj, ...}` 等展开场景

### [9] mockFallback 的 `as any` 是 mock 返回值与泛型 T 不一致的设计 hack

- 日期：2026-07-28
- 踩坑人：阿坚
- 关键词：any 替换, mockFallback, platformCall, as unknown as, 设计 hack, 泛型不匹配
- 现象：R58-02 清零 3 个 adapter 的 `}) as any` 时，发现这些 `as any` 是加在 `platformCall<T>(..., mockFallback: () => Promise<T>)` 的 mockFallback IIFE 后面。mockFallback 实际返回的是业务结果（如 `SyncOrdersResult` / `PlatformCredentials`），而 T 是 API 响应包装结构（如 `{ data: { order_list: ... } }`），两者类型不匹配。这是代码设计 hack：useMock() 为 true 时直接返回 mockFallback()，外部用 `as unknown as SyncOrdersResult` 转回业务类型
- 原因：mock 路径与真实路径返回结构不一致——mock 直接返回业务结果（跳过解包），真实返回 API 包装结构（外部解包）。这种设计让 mockFallback 的返回类型与 T 不匹配，必须用 `as any` 绕过类型检查
- 解决：用 `as unknown as () => Promise<XxxResponse>` 代替 `as any`，明确转换目标类型（如 `() => Promise<MeituanResponse<{ access_token: ... }>>`）。同时在 mockFallback IIFE 内部用 `return creds as unknown as XxxResponse` 把业务对象强转为 API 响应类型。这样既消除了 `as any`，又保留了原有 mock 行为（useMock 时外部仍用 `as unknown as SyncOrdersResult` 转回）
- 教训：遇到 `mockFallback as any` / `callback as any` 这类函数类型转换的 `as any`，要先看清楚是"函数返回类型与泛型 T 不匹配"还是"HTTP 响应强转"；前者用 `as unknown as () => Promise<T>` 中转，保留设计 hack；后者用 `as XxxResponse<...>` 明确响应类型。不要试图重构 mock 逻辑让返回类型一致（会改业务行为，违反"只做类型标注"原则）

### [10] 替换 row: any 后引出的连锁类型问题（VO 放宽 / Map.get undefined / 算术运算）

- 日期：2026-07-28
- 踩坑人：阿坚
- 关键词：any 替换, VO 类型放宽, Map.get undefined, 非空断言, 算术运算, mysql2, 隐蔽 any
- 现象：R58-03 把 `mapXxxRow(row: any)` 替换为 `mapXxxRow(row: SupplierRow)` 后，tsc 报 11 个错误：① `row.created_at`（`string | Date`）不能赋值给 VO 的 `createdAt: string`；② `row.tax_rate`（`number | string`）不能赋值给 VO 的 `taxRate: number`；③ `AuthUser.storeId`（`number | null | undefined`）不能赋值给 `StoreAuthUserInput.storeId`（`number | undefined`）；④ `spuMap.get()` 返回 `T | undefined`，后续 `.skus.push` 报 Object possibly undefined；⑤ `row.wholesalePrice * row.quantity` 报算术运算类型错误（`number | string` 不能参与 `*`）。另外发现 `Map<number, any>()` 中的 `any` 不被验收 grep pattern `: any|as any|<any>` 匹配（因为是 `, any`），需用 `\bany\b` 宽泛 pattern 才能发现
- 原因：`row: any` 时所有字段访问和运算都是 any，绕过了 strictNullChecks 和类型兼容检查。替换为明确 Row 接口后，mysql2 返回的 `string | Date` / `number | string` 联合类型与 VO 的窄类型不匹配；`Map.get()` 的返回类型从 any 变为 `T | undefined`；`number | string` 参与 `*` 运算不再被 any 掩盖
- 解决：三方向修复，均不改变业务逻辑：① 放宽 VO 字段类型：`createdAt: string` → `string | Date`、`taxRate: number` → `number | string`、`storeId?: number` → `number | null`（mysql2 日期/数值字段的联合类型是运行时真实情况，VO 应兼容）；② 非空断言：`spuMap.get(id)!`（前面 `if (!spuMap.has(id)) { spuMap.set(id, ...) }` 保证了存在，非空断言只是告知 TS 这一业务逻辑保证）；③ `Number()` 转换：`Number(row.wholesalePrice) * row.quantity`（原来 `any * number` 隐式转 number，现在显式转）。另外验收时除 `: any|as any|<any>` 外，必须加跑 `grep '\bany\b'` 发现 `Map<..., any>` 等隐蔽 any
- 教训：替换 `row: any` / `param: any` 后会引出三类连锁类型问题——VO 字段类型过窄（用 `string | Date` / `number | string` 放宽）、`Map.get()` 返回 undefined（用 `!` 非空断言，前提是前面有 has 检查）、联合类型参与运算（用 `Number()` 显式转换）；验收 grep 必须同时跑 `: any|as any|<any>` 和 `\bany\b` 两种 pattern，前者匹配常见形式，后者发现 `Map<..., any>` / `Array<any>` 等隐蔽形式
