# R101-S2-02 配置项契约登记表

> **依据**：凌舟裁定 R101-S2-02 护栏②（契约先行）—— 每项配置须登记 **key / 值结构 / 默认值语义 / 未配置时的界面行为**。
> **存储口径（口径 X）**：配置以 JSON 包写入**既有**存储（平台级 `t_platform_config` 整包一行；租户级 `t_sys_config` 唯一键 `(config_key, tenant_id)`），**零新建业务表**。
> **权威实现**：
> - 组1 套餐类 → `backend/src/schemas/plan.schema.ts` + `backend/src/controllers/admin/subscription-plan.controller.ts`；前端唯一事实源 `saas-admin/src/constants/plan-features.ts`
> - 组4① 全局功能开关 → `backend/src/services/platform/platform-sys-config.service.ts`；前端 `saas-admin/src/views/Settings.vue`
> **变更记录**：新增条目须同步本节与《数据库变更清单》；DDL 一律先登记后执行。

## 一、通用语义（适用于本表全部条目）

| 语义 | 约定 |
|---|---|
| **已配置** | 该键在库中存在（JSON 包内 `hasOwnProperty` 为真） |
| **未配置** | 键不存在。后端以 `null` 或省略表示；`GET` 响应以 `_unconfigured: string[]` 明确列出「未落库的顶层键」 |
| **DEFAULTS** | 仅作**表单初值 / 空态展示**，**禁止回写**（`PUT` 过滤 `null` 值与 `_` 前缀元字段） |
| **前端义务** | 未配置项一律**置灰阻断 + 提示原因**，不得以任何默认值冒充「已生效配置」 |
| **version** | 每个 JSON 包携带 `version`（组1 策略包 / 组4① 设置包当前均 = `1`），结构变更时递增 |
| **留痕** | `updated_by` / `updated_at` 由存储表列承担（`t_platform_config` 152 迁移已加 `updated_by`） |

### 2.5 策略包（`plan_policy:<planId>`）存储契约

**实现**：`backend/src/services/platform/plan-policy.service.ts`（zod：`backend/src/schemas/plan.schema.ts` 的 `planPolicySchema`）

```
{
  version: 1,                                   // 护栏③：恒带版本号
  quota?:     { apiDaily?: number, aiMonthly?: number },
  upgrade?:   { mode: 'IMMEDIATE' | 'NEXT_CYCLE' },
  downgrade?: { mode: 'NEXT_CYCLE' | 'IMMEDIATE_NEXT_PRICE' },
  renew?:     { policy: 'FORBID_GUIDE_UPGRADE' | 'ALLOW_LAST_YEAR' | 'AUTO_RECOMMEND_PLAN' },
  promo?:     { price?: number, start?: string, end?: string }
}
```

| 项 | 约定 |
|---|---|
| **键隔离** | 每个套餐一行，`config_key = 'plan_policy:<planId>'`，互不覆盖 |
| **DDL** | **零新增**：复用 `t_platform_config` 既有列（`config_key` / `config_value` / `category` / `updated_by` 由 `152_business_columns_fill.sql` 补齐） |
| **校验** | `PUT` 前经 `planPolicySchema.parse()`；越界枚举 / 负数额度直接 400，不落脏配置 |
| **未配置** | 库中无该行 → `GET` 返回 `{ version:1, _unconfigured:['quota','upgrade','downgrade','renew','promo'], _configured:false }` |
| **清空** | 全部策略项为空时写入 `{version:1}`（null 与 `_` 前缀元字段不落库）→ 等价于「未配置」，不会固化占位值 |
| **留痕** | `updated_by` = 操作人 `req.user?.username ?? 'system'`；`updated_at` 由 SQL `NOW()` 写入 |
| **前端** | `PackageForm.vue` 保存主记录后单独 `PUT` 策略包；失败时**不跳转**，在内容区显示错误态（不重复弹 toast） |

> `POST /plans` 现返回 `{ plan_code, id }`（新增 `id`，向后兼容），否则新建后拿不到主键无法保存策略包。

### 6.1 欠费处理策略（`billing:arrears_policy`）

| key | 值结构 | 默认值语义 | 未配置时界面行为 |
|---|---|---|---|
| `graceDays` | 整数 ≥0（天） | **无** | 显示「未配置」并置灰；「宽限期结束自动降级」说明改为「需先配置宽限期天数」 |
| `freezeAfterDays` | 整数 ≥0（天） | **无** | 同上；「降级后自动冻结」说明改为「需先配置宽限期与冻结间隔」 |
| `retainDays` | 整数 ≥0（天） | **无** | 同上；「保留期结束自动注销」说明改为「需先配置保留期天数」 |
| `remindNodes` | 整数数组（天），如 `[7,3,1]` | **无** | 界面用「7 / 3 / 1」输入，解析为数字数组；未配置时提醒说明提示先配置 |
| `channels` | 枚举数组 `IN_APP|SMS|EMAIL|WECHAT`（白名单，防脏值） | **无** | 通道以按钮组呈现，未选即未配置，不上送 |
| `autoDowngrade` / `autoFreeze` / `autoRemind` / `autoCancel` | boolean | **无**；`undefined`＝未配置 ≠ `false`＝已配置为关闭 | 标签显示「未配置」；点击开关即视为配置意图，方可上送 |

**派生文案一律由配置值推导，禁止写死**：原「D+16」「降级 30 天后（D+31）」「D+90」分别改为 `D+(graceDays+1)`、`D+(graceDays+freezeAfterDays+1)`、`D+retainDays`。

**页顶「欠费处理时间线」同属硬编码，一并改为派生**（原 `宽限期 15 天 → D+16~30 → D+31~60 → D+61~90`，其中 15 / 30 / 60 / 90 均为写死业务值）：

| 状态 | 文案 |
|---|---|
| 三要素（`graceDays` / `freezeAfterDays` / `retainDays`）任一未配置 | `欠费处理时间线待配置：请先在「欠费处理策略」中配置宽限期天数、降级后冻结间隔与冻结后保留期天数，配置后此处按配置值生成。` |
| 已配置 | 由值拼接：`宽限期 N 天（全功能）→ 功能降级·只读（D+g+1~g+f）→ 冻结·仅可导出（D+g+f+1 起）→ 保留期至 D+r → 注销清除（D+r 后转人工确认）`；`freezeAfterDays=0` 时省略降级段，`retainDays <= 冻结日` 时省略保留期段 |

> 注：原写死文案内含 `D+31~60 / D+61~90` 两段区间，需要「冻结持续天数」这一**契约中不存在的字段**才能推导，属原稿自身矛盾。本轮不新增字段（零 DDL 口径），按现有三要素推导，**不臆造第四个维度**。

### 6.4 裁定①修订：欠费处理时间线补足 **4 段边界字段**（2026-09-15 凌舟裁定）

**依据**：设计稿 v1.6 **第 809 行**原文 ——

> 欠费处理时间线：**宽限期 15 天（全功能）→ 功能降级·只读（D+16~30）→ 冻结·仅可导出（D+31~60）→ 保留期（D+61~90）→ 注销清除**。降级采用整体只读模式，由配额引擎自动执行。

设计稿是 **4 段边界**（15 / 30 / 60 / 90，自欠费起始日 `D+0` 起算的**绝对截止天数**）；原 §6.1 的 `freezeAfterDays` 是「间隔」语义，推不出设计稿的 `D+31` / `D+61`。故补足 4 个边界值 —— **不是臆造第四维，而是把设计稿已有的 4 段做成可配置**。**零 DDL**（仍走同一个 JSON 包）。

#### 6.4.1 字段表（取代 §6.1 的三个天数字段）

| 字段 | 含义 | 单位 / 取值范围 | 设计稿对应 | 未配置时界面行为 |
|---|---|---|---|---|
| `graceEndDays` | 宽限截止：`D+1` ~ `D+graceEndDays` 全功能可用 | 整数天 ≥0 | 15 | 显示「未配置」并置灰 |
| `degradeEndDays` | 降级截止：`D+(graceEndDays+1)` ~ `D+degradeEndDays` 功能降级·只读 | 整数天 ≥0 | 30 | 同上 |
| `freezeEndDays` | 冻结截止：`D+(degradeEndDays+1)` ~ `D+freezeEndDays` 冻结·仅可导出 | 整数天 ≥0 | 60 | 同上 |
| `retainEndDays` | 保留截止：`D+(freezeEndDays+1)` ~ `D+retainEndDays` 保留期；`D+retainEndDays` 后转人工注销 | 整数天 ≥0 | 90 | 同上 |

> `remindNodes` / `channels` / `autoDowngrade` / `autoFreeze` / `autoRemind` / `autoCancel` 六个键**不变**，语义同 §6.1。

#### 6.4.2 严格递增校验（裁定要求②）

- 规则：**宽限截止 < 降级截止 < 冻结截止 < 保留截止**；
- 实现：`arrearsPolicySchema` 用 `.superRefine()` 对相邻三对逐一校验，**仅当两个值都已配置时才校验**（部分配置不误伤）；
- 违反时由 zod 拒绝（HTTP 400），**中文提示**须指出冲突对象与具体值，例如：`时间线截止天数必须严格递增：宽限截止 30 必须小于 降级截止 20`；
- 全不配（仅 `version`）→ 通过；只配前两项且递增 → 通过。

#### 6.4.3 未配置与展示（裁定要求③④）

| 项 | 约定 |
|---|---|
| 未配置 | 4 个边界任一为 `null` → 页顶时间线与对应开关说明均显示「待配置」提示，**不回落任何默认天数** |
| 页顶文案 | 完全由 4 个边界推导：`宽限期 N 天（全功能）→ 功能降级·只读（D+a+1~b）→ 冻结·仅可导出（D+b+1~c）→ 保留期（D+c+1~d）→ 注销清除`，**不得写死任何天数** |
| 开关说明 | `autoDowngrade`→`D+(graceEndDays+1)`；`autoFreeze`→`D+(degradeEndDays+1)`；`autoCancel`→`D+retainEndDays` |

#### 6.4.4 废弃字段与迁移

| 废弃字段 | 原因 | 处置 |
|---|---|---|
| `graceDays` | 与 `graceEndDays` 同义，统一到「截止日」坐标系 | 删除 |
| `freezeAfterDays` | 间隔语义，无法表达设计稿 4 段边界 | 删除 |
| `retainDays` | 与 `retainEndDays` 同义 | 删除 |

> **存量影响**：S2-02 目前处于「待取证」状态，**真库尚未落库该配置包，无存量数据**，故重命名零迁移成本。若日后在真库发现含旧字段的存量包：读取时**忽略**旧字段，**不自动推算、不回落任何默认天数**（按未配置处理，由管理员重新配置）。
