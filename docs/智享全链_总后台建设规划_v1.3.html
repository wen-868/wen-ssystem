2.2 总后台的"三不"边界

"三不"边界不是宣传口号，而是要落成权限配置 + 代码拦截 + 流程规则三道硬约束。

边界原则含义与落地方式例外通道（唯一合法路径）
一不：不改业务数据总后台不直接对租户的采购单、销售单、库存、会员等业务表做任何增删改。接口层不做业务表写通道，权限系统不提供业务写权限项。无例外。唯一可写的租户侧字段是元数据：租户状态、配额、套餐开关。
二不：不看业务明细不逐笔查看某租户的销售单、客户名单、成本毛利。平台大盘只展示聚合统计（总量/总额/趋势），不提供下钻到单条业务记录的入口。仅两条：① 租户在商家后台主动授权（如提交问题单据协查，授权范围+时限）；② 平台代登录（申请→审批→限时→留痕→可回放，见 4.1 与 6.1）。
三不：不干预商户内部权限租户内部员工账号、角色、审批流由商户自行管理。总后台不提供"替商户改员工权限"的功能。仅租户级整体管控：禁用/冻结/注销作用于整个租户空间（登录阻断），而非篡改其内部角色配置。
边界与单据规则的衔接租户单据遵循"待审核/已审核可作废删除；已作废仅可删"的既定规则，该状态机完全由商家后台实现与维护。总后台在代登录、数据协查、数据重置等场景中，同样必须以该状态机为前提：不得通过平台侧通道变更单据审核状态，数据重置仅按"作废→删除"的合法链路批量执行并留痕。

2.3 数据隔离原则（五条铁律）

  1. 存储隔离：全部租户业务数据行级携带 tenant_id；总控库（租户元数据/账单/日志/配置）与租户业务数据物理或逻辑分离。
  2. 访问隔离：租户业务接口强制携带租户上下文（ORM 层自动注入 tenant_id 过滤）；总后台管理员账号不在任何业务接口的白名单内。
  3. 展示隔离：总后台页面只呈现租户概况的聚合数值（商品数、订单量、活跃度分级），数据结构上杜绝"按租户查业务明细"的查询能力。
  4. 导出隔离：涉及租户业务数据的导出，必须经"租户授权（或工单依据）+ 平台双人审批 + 水印加密"三重控制，全程审计。
  5. 删除隔离：租户注销走"申请→7 天冷静期→备份→清除"流程；总控元数据仅归档不物理删除，满足对账与争议追溯。

3.4 多租户技术架构：数据隔离方案对比与推荐

三种主流隔离方案对比（评估基准：中小批零商户、预期 3 年内千级租户、平台需做跨租户聚合统计）：

方案说明成本隔离强度跨租户聚合统计单租户备份/恢复运维复杂度
独立库
每租户一个数据库		租户数据物理完全隔离，最彻底；连接数与实例数随租户线性增长高★★★★★难，需跨库汇聚天然支持高
共享库 + Schema
每租户一个 Schema		逻辑隔离较强；Schema 数量受限（通常数千级），DDL 变更需批量执行中★★★★较难，跨 Schema 汇聚可按 Schema 导出中高
共享库 + tenant_id
行级隔离		所有租户同表共存，行级携带租户标识，依赖 ORM 拦截器强制过滤低★★★（依赖代码纪律）容易，天然支持需按租户条件导出低
推荐结论：主方案 = 共享库 + 租户 ID 字段 + 行级隔离
理由：① 智享全链目标客群为中小批零商户，数量多、单体数据量小，行级隔离的边际成本最低，与免费版"零成本承载海量小租户"的商业漏斗最匹配；② 平台大盘、套餐分布、AI 消耗等统计天然需要跨租户汇聚，同表结构使聚合查询与 ETL 大幅简化；③ 通过"ORM 层全局租户拦截器 + 新增接口强制检查清单 + 自动化隔离测试用例 + 季度渗透抽测"四道防线弥补隔离强度短板。
升级保留：对有合规/定制需求的旗舰大客户，提供"独立逻辑库"增值方案（按租户独立建库，收费另议），并预留数据迁移工具。建议触发条件：单租户月单据量 > 10 万笔，或客户明确提出数据物理隔离合规诉求。

行级隔离的四道落地防线

  1. ORM 全局拦截器：所有业务表 Model 强制继承租户基类，查询/写入自动注入 tenant_id；禁用裸 SQL 直查业务表，纳入代码评审门禁。
  2. 上下文强制校验：网关层校验 Token 租户身份，管理端 Token 与租户端 Token 完全隔离，杜绝越权字段注入。
  3. 自动化隔离测试：CI 中内置"跨租户越权"用例集（A 租户 Token 访问 B 租户数据必须 403/空集），每次发版必跑。
  4. 季度渗透抽测：对代登录、数据导出、AI 网关、Webhook 回调四个高危面定期做渗透测试与整改。

4.12 大模型计费体系 v1.1 新增

模块目标

4.11 解决"额度给多少、用了多少"；本节在其上深化"钱怎么算"：以 Token 为计量原子，平台网关统一代理采集，形成"成本单价 → 加成定价 → 三种租户计费模式 → 账单对账"的完整大模型计费体系。三个验收口径：成本算得清（逐 Token 可追溯到单次调用）、价格定得准（成本加成、按套餐差异倍率、旗舰最优）、模式选得活（预付 / 后付 / 订阅含量按套餐组合启用）。

4.13 积分抵扣 Token 机制 v1.1 新增

模块目标

把 4.9 运营营销发放的积分（老带新奖励）与 4.12 大模型计费打通，为积分提供一条高频、刚需、自闭环的消耗出口：商户用 AI 的意愿越强，积分消化越快，老带新激励的边际成本越低。

机制口径（必须准确）：抵扣，而非兑换积分抵扣 Token，不是积分兑换 Token。Token 始终按实际用量计量（4.12 计量流水），扣减时积分按管理员配置的汇率冲抵当次应计用量——积分是支付抵扣手段，不发生"积分资产 → Token 资产"的转换：没有固定兑换池、不产生新资产科目、不存在"先换后用"。例如客户有 10 万积分，按当前配置汇率可冲抵对应的 Token 用量；调用发生才扣，不调用不扣，扣多少记多少。

4.13.1 核心映射：积分 → 可抵扣 Token（汇率为手动配置项）

  • 汇率手动配置：映射比例按"1 积分 = X Token"定义，X 为平台管理员手动配置项，系统不内置固定汇率；首次启用积分抵扣前必须先完成汇率配置，未配置时抵扣功能整体置灰不可用（平台侧启用开关与商户端入口同步禁用）。
  • 示例值声明：下文与示例表中的 X = 50（即 1 积分 = 50 Token、10 万积分 ≈ 500 万 Token 抵扣力）仅为文档示意，实际以管理员配置为准。
  • 金额等值展示：金额等值 = 可抵扣 Token ÷ 1000 ×（模型成本单价 × 加成倍率），随倍率与模型结构动态计算，仅作展示参考，实际以逐笔计量为准。
  • 管理位置：汇率与加成倍率同在「AI 计费管理」模块维护（见 4.13.4 汇率治理、4.13.8 界面落点）。

4.13.4 汇率治理（手动配置 + 变更留痕）

  • 配置方式：汇率由平台管理员在「AI 计费管理 · 积分抵扣」页签手动录入（1 积分 = X Token），系统不预置固定值；启用积分抵扣的前提是汇率已配置且开关打开。
  • 消耗时锁定汇率：每笔抵扣流水记录调用时点汇率快照；汇率调整不追溯历史用量，仅对新调用生效；已出账单不变。
  • 变更留痕与复核：汇率每次修改记录修改人 / 修改时间 / 修改前后值，生成版本流水可回查；建议双人复核后生效（是否强制双人复核，并入决策点 D10 一并拍板）。
  • 统一管理位：汇率与 4.12.3 的加成倍率同在 AI 计费模块维护，变更均需留痕（联动 6.1 审计）；汇率变更后，商户端"可抵扣 Token"展示同步刷新。

4.14 代理商体系（配置 + 分润） v1.2 新增

模块目标

面向同行批零商家的 B 端分销伙伴：让"卖软件的人"从平台直销延伸到渠道合伙。代理商体系与商户侧老带新（C 端裂变积分奖励，见 4.9 / 5.6）构成双轨渠道体系——B 端代理商走"现金分润"的重激励，C 端老带新走"积分奖励"的轻激励。本节回答四件事：代理商怎么进（档案与状态机）、业绩算谁的（归因规则）、佣金怎么分（分润引擎）、钱怎么结（结算与冲回）。三个验收口径：层级配得活（支持自定义命名与扩展）、比例定得清（矩阵手动配置、不内置定死）、佣金算得准（基数口径唯一、冲回有账可对）。

双轨渠道体系口径（B 端 × C 端）B 端代理商：同行批零商家 / SaaS 渠道从业者，签约审核后以专属推广码获客，报酬为现金分润；C 端老带新：已付费商户自发推荐，报酬为积分奖励（实付 × 20%、年度上限 60k，见 4.9 / 5.6）。两轨服务不同增长对象、互不替代，可并存但归因唯一：同一商户全生命周期只归属一个渠道主体，代理商邀请与老带新邀请同时出现时代理商优先（见 4.14.3）。

4.14.1 代理商定义与层级模型

  • 代理商定义：与平台签约的 B 端分销伙伴（主体为同行批零商家或 SaaS 渠道商），独立签约、独立结算、独立提现；区别于 4.9 的"市场渠道推广码"——渠道码仅做归因统计、不结算，代理商是结算主体。
  • 与直销的关系：代理商是渠道增量而非替代——无码注册仍归平台直销；代理商覆盖的是平台销售触达不到的"同行圈层"（同行更懂同行）。
  • 层级模型：一级代理 / 二级代理（出厂预置，支持后期自定义层级命名与扩展，见决策点 D11）；各层级权益由"可售套餐范围 × 拿货折扣区间 × 是否允许发展下级"三个维度定义，见下表。

4.15.1 定位与边界（先讲边界，再讲功能）

边界铁律：平台管"公共主数据"，不碰"租户私有明细"商品库全部能力围绕平台公共商品主数据展开；总后台不提供查看、检索、导出任何租户私有商品档案（进价、销量、供应商、毛利）的入口——2.2"三不"边界与 3.4 数据隔离原则在商品域同样成立。调取的本质是租户主动发起的单向数据复制（公共主数据 → 租户私有档案），落库即隔离。
  • 与商家后台商品中心的衔接：租户调取后按现有系统商品中心结构生成租户侧档案——SPU / SKU / 品类树 / 品牌（对应商家后台既有接口体系：/api/v1/spu、/api/v1/sku、/api/v1/categories/tree、/api/v1/brands），字段结构一一映射，避免商户重复录入；调取落库后即可在商家后台正常编辑、上下架、配置价格。
  • 类目与品牌映射：平台公共类目树 / 品牌库与租户侧品类树 / 品牌管理结构对齐；调取时租户侧已有同名类目 / 品牌则自动关联映射，无同名则按公共数据自动创建，映射关系留痕可查。
  • 定位澄清：公共主数据是"半成品原料"（标准描述 + 参考价），不是"成品货架"——平台不向 C 端提供任何商品展示与交易能力，商品库只服务于总后台与商家后台之间。

4.15.4 租户调取机制（复制式调取，单向复制）

  • 平台更新不强制覆盖：公共主数据后续更新（版本 +1）时不自动改动租户已调取档案；租户侧展示"有新版本可同步"提示，点开可预览字段级差异，由租户自行决定同步或忽略。
  • 调取计入商品配额：每次调取生成一条租户私有商品，计入套餐商品上限，由配额计量引擎硬拦截（见 3.4 / 5.1）；配额不足时阻断调取并提示升级，分档策略见 4.15.6（决策点 D12）。
  • 批量调取：支持勾选批量调取与按类目整包调取；批量执行前预检商品配额余量，不足部分跳过并汇总提示。

5.3 免费版的商业逻辑：获客漏斗的第一格

定位：免费版不是公益，是漏斗免费版承担"让商户低成本把店搬进来"的获客任务，其配额经过刻意收紧：1 个账号 / 100 个商品 / 1 个仓库 / 500 张月单据。这组数字的用意是覆盖"夫妻小店真实起步形态"，同时保证商户一旦生意起量（雇第 2 个人、上第 2 个仓、商品破百）必然触顶。
  • 触顶即引导：配额达 80% 时商家后台出现温和提醒；达 100% 硬拦截（无法新建商品/账号），拦截弹窗直接给出"升级基础版"入口与价签——升级动机由商户自己的业务增长产生，而非销售话术。
  • 数据无缝升级：免费版升付费版数据完全保留、即时生效；付费降免费则功能关闭但数据保留 90 天（超过进入 5.6 欠费流程）。
  • 免费版反滥用：同手机号/同主体仅可开 1 个免费租户；30 天零登录的免费租户进入"沉睡名单"做召回触达，不占用客服资源。
  • 转化观测：运营大盘的转化漏斗（4.5）重点监控"免费触顶率→升级率"，作为定价校准依据。
  • 免费版 AI 使用口径 v1.1：免费客户不支持自定义模型（设计稿规则，仅付费用户支持）；免费租户的 AI 用量 = 每月赠送的小额 Token 额度（仅平台公共模型，见 4.12）+ 积分抵扣（仅公共模型，见 4.13）——免费租户"尝到甜头"的每一分 AI 用量都发生在平台公共模型上，为升级付费（解锁自定义模型 + 更大内含额度）留出清晰梯度。
