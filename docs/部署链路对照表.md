## 服务器工作区维护规范（2026-09-16 凌舟）

### 一、铁律：服务器（生产检出）工作区必须保持干净

服务器是**生产部署目录**，脏工作区会带来两类真实风险：① `git pull` 被本地改动阻塞/冲突（本次 `package-lock.json` 就是），② 未跟踪文件被误当成"临时垃圾"清掉（可能是唯一的取证产物）。

**清理三原则**：
1. **先备份再删**：不确定的文件一律先 `cp` 到 `/root/server-artifacts/<YYYYMMDD>/` 再删（本次 `NUL` 即如此）；
2. **取证产物先回填仓库再清**：服务器上产生的报告（如 `docs/reports/*`）**先把文件取回仓库并提交**，服务器再删——回填后 `git pull` 会把它作为 **tracked** 文件带回，工作区自然干净（本次 4 份 ai-base e2e / load-test 报告即按此处理）；
3. **本地产物不提交**：`npm install` 造成的 `package-lock.json` 漂移一律 `git checkout --` 还原，不要提交（否则污染依赖锁）。

### 二、`NUL` 文件的来源与判据

`NUL`（72 字节）来自 Windows 风格重定向在 Linux 上的误用（`command 2>NUL`）。**判据**：仓库内出现名为 `NUL` 的小文件 = 有人在 Linux 上照抄了 Windows 命令 → 直接删，同时把那条命令改成 `2>/dev/null`。

### 五、为什么服务器工作区会反复变脏（2026-09-16 凌舟定位）

**现象**：`git checkout -- package-lock.json` 还原后，跑一次部署又变脏（250 增 / 85 删）。

**根因（已取证）**：
1. 服务器 npm registry = `https://mirrors.tencentyun.com/npm`（`~/.npmrc`）；仓库里**没有** `.npmrc`，committed `package-lock.json` 的 `resolved` 字段记的是**另一个源**；
2. 部署脚本用的是 **`npm install`**（`deploy/auto-deploy.sh:14`、`deploy/03-deploy.sh:40`、`deploy/07-local-archive-deploy.sh:27`、`deploy/rollback.sh:36`、`deploy/deploy-production.sh:91`）——**`npm install` 会按当前 registry 重写 lockfile 的 `resolved` 字段**（本次差异里新增的就是 `admin-web/node_modules/*` 指向 `mirrors.tencentyun.com` 的条目）；
3. 于是**每次部署都会把生产检出改脏**，与是否有人手滑无关。**`NUL` 那种是垃圾，这个不是——它是部署流程的副作用。**

**修复方向（登记 S3-39）**：
1. 部署脚本里**非全局**的 `npm install` 一律改 **`npm ci`**（严格按 lockfile 安装、**不重写 lockfile**）；需要走镜像时用 `npm ci --registry="$npm_config_registry"`；
2. **全局安装保留**（`npm install -g pm2` / `-g pnpm@9` 不影响 lockfile）；
3. ai-base 的 `pnpm install --no-frozen-lockfile`（`deploy/ai-base-deploy.sh:146`）同理改 `--frozen-lockfile`（在 ZXQL-AI 仓库侧处理）；
4. **每个部署脚本末尾加工作区自检**：`if [ -n "$(git status --porcelain)" ]; then echo "[!] 部署后工作区变脏："; git status --short; fi` —— 让"部署引入脏改动"当场暴露，而不是等下一次 pull 冲突；
5. **验收**：跑一次完整部署后 `git status --short` 必须为空（这正是 S3-38 部署后变脏的直接回归测试）。

**判据（写给后续所有人）**：生产检出出现**大范围 `resolved` 字段差异**的 lockfile 改动 = 部署脚本的 registry 副作用，**不要提交、也不要只 revert 了事**——改脚本才是根治。
