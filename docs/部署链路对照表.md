## 服务器工作区维护规范（2026-09-16 凌舟）

### 一、铁律：服务器（生产检出）工作区必须保持干净

服务器是**生产部署目录**，脏工作区会带来两类真实风险：① `git pull` 被本地改动阻塞/冲突（本次 `package-lock.json` 就是），② 未跟踪文件被误当成"临时垃圾"清掉（可能是唯一的取证产物）。

**清理三原则**：
1. **先备份再删**：不确定的文件一律先 `cp` 到 `/root/server-artifacts/<YYYYMMDD>/` 再删（本次 `NUL` 即如此）；
2. **取证产物先回填仓库再清**：服务器上产生的报告（如 `docs/reports/*`）**先把文件取回仓库并提交**，服务器再删——回填后 `git pull` 会把它作为 **tracked** 文件带回，工作区自然干净（本次 4 份 ai-base e2e / load-test 报告即按此处理）；
3. **本地产物不提交**：`npm install` 造成的 `package-lock.json` 漂移一律 `git checkout --` 还原，不要提交（否则污染依赖锁）。

### 二、`NUL` 文件的来源与判据

`NUL`（72 字节）来自 Windows 风格重定向在 Linux 上的误用（`command 2>NUL`）。**判据**：仓库内出现名为 `NUL` 的小文件 = 有人在 Linux 上照抄了 Windows 命令 → 直接删，同时把那条命令改成 `2>/dev/null`。

### 三、操作归属与验证分工（2026-09-16 用户明确）

- **林夕可直接操作服务器**（其 WorkBuddy 与服务器同属腾讯生态，无需人工介入转发）；
- **但林夕侧环境 `curl` 被 MCP 策略拦截**（一律 `AccessDeny`），`ls/grep/git log` 可用 → **HTTP 层验证固定由凌舟执行**：

### 五、为什么服务器工作区会反复变脏（2026-09-16 凌舟定位）

**现象**：`git checkout -- package-lock.json` 还原后，跑一次部署又变脏（250 增 / 85 删）。

**根因（已取证）**：
1. 服务器 npm registry = `https://mirrors.tencentyun.com/npm`（`~/.npmrc`）；仓库里**没有** `.npmrc`，committed `package-lock.json` 的 `resolved` 字段记的是**另一个源**；
2. 部署脚本用的是 **`npm install`**（`deploy/auto-deploy.sh:14`、`deploy/03-deploy.sh:40`、`deploy/07-local-archive-deploy.sh:27`、`deploy/rollback.sh:36`、`deploy/deploy-production.sh:91`）——**`npm install` 会按当前 registry 重写 lockfile 的 `resolved` 字段**（本次差异里新增的就是 `admin-web/node_modules/*` 指向 `mirrors.tencentyun.com` 的条目）；
3. 于是**每次部署都会把生产检出改脏**，与是否有人手滑无关。**`NUL` 那种是垃圾，这个不是——它是部署流程的副作用。**

**修复方向（登记 S3-39）**：
1. 部署脚本里**非全局**的 `npm install` 一律改 **`npm ci`**（严格按 lockfile 安装、**不重写 lockfile**）；需要走镜像时用 `npm ci --registry="$npm_config_registry"`；
2. **全局安装保留**（`npm install -g pm2` / `-g pnpm@9` 不影响 lockfile）；
3. ai-base 的 `pnpm install --no-frozen-lockfile`（`deploy/ai-base-deploy.sh:146`）同理改 `--frozen-lockfile`——**flag 在 wen-ssystem 的部署脚本里，它冻结的是 ZXQL-AI 检出的 `pnpm-lock.yaml`**（本机已核 ZXQL-AI 仓内无第二处 `frozen-lockfile` 引用，故只此一处）；
4. **每个部署脚本末尾加工作区自检**：`if [ -n "$(git status --porcelain)" ]; then echo "[!] 部署后工作区变脏："; git status --short; fi` —— 让"部署引入脏改动"当场暴露，而不是等下一次 pull 冲突；
5. **验收**：跑一次完整部署后 `git status --short` 必须为空（这正是 S3-38 部署后变脏的直接回归测试）。

**判据（写给后续所有人）**：生产检出出现**大范围 `resolved` 字段差异**的 lockfile 改动 = 部署脚本的 registry 副作用，**不要提交、也不要只 revert 了事**——改脚本才是根治。

### 六、失败信号约定（S3-40，2026-09-16 凌舟裁定）

**背景**：`deploy/ai-base-deploy.sh` 原有 **5 处失败路径一律 `exit 0`**（源码不可用 / pnpm 安装失败 /
pnpm install 失败 / 构建失败 / pm2 启动失败），`auto-deploy.sh` 又用 `|| echo "跳过"` 吞掉 →
AI 底座没部署成功时，整条流水线仍报"部署完成"。
**"容错不阻断"是对的，"静默返回成功"是错的**——与"假 CI 门禁"同类：**绿灯 ≠ 真的部署了**。

**约定（新写部署脚本必须遵守）**：

1. **统一失败标记**：`❌ [<组件>] 部署失败：<原因>`（当前组件名 = `AI底座`），打印到 **stderr**；
2. **不阻断**：仍 `exit 0`（容错设计，不能让次要组件失败拖垮主后端发布）；
3. **汇总**：调用方（`auto-deploy.sh`）捕获输出，用 **`grep -F`（固定字符串，避免 `[ ]` 被当字符类）**
   收集标记行，末尾**汇总列出失败项**；
4. **退出码**：汇总非空 **且**（`DEPLOY_STRICT=1` **或** 非交互 stdin `[ ! -t 0 ]`）→ **`exit 1`**，
   供上游流水线判定；
5. **只有全程无失败**才输出"部署完成"；出现软失败（如健康检查未通过）在收尾处统一出标记。

**判据**：凡"捕获异常后继续"的分支，都必须留下**机器可判定的失败痕迹**（标记 / 汇总 / 退出码）。
"不阻断"与"不撒谎"是两件事，必须同时满足。

### 七、文件级铁律：提交前必看 `git diff --stat`

- **判据**：行数远超实际改动 = **换行符 / 编码漂移**，不是"改动多"。
- **原因**：本仓 `core.autocrlf=true`，多数文件是 LF，但**个别文件是 CRLF**
  （如 `docs/tasks/current-tasks.md`：3376 CRLF + 203 LF 混合）→ 编辑工具写回 LF 会让 1 行改动变成整文件重写。
- **处置**：`git checkout HEAD~1 -- <file>` 还原 → 用**保留原换行符**的脚本重做改动 →
  `git -c core.autocrlf=false add/commit --amend`。
- **复发史**：踩坑 **[62]**（首次）→ **[66]**（混合换行插入）→ **[73]**（第 3 次）。
  已升级为铁律，不再当个案处理。

## 八、生产部署并发保护：哪些 workflow 可并入 `production-deploy`

> 建立：2026-09-21 · 来源 **S3-62（C-2）** / 派单 **D-1 + E-2** · 取证卡 `docs/tasks/cards/R101-D1-林夕回传.md`

### 8.1 为什么需要本条

`concurrency` **只对同一个 workflow 生效**。S3-62 已给 `deploy.yml` 加了 `concurrency: {group: production-deploy, cancel-in-progress: false}`，但**其他 workflow 不在同一互斥组内**——它们若也改变生产运行态，仍会与部署并发。

派单 D-1 的全仓扫描（2026-09-21）结论是「当前只有 `deploy.yml` 一条部署路径」，但**空集不会自我维持**：任何未来新增的 workflow（或给现有 workflow 加一个 ssh / pm2 步骤）都会**静默**落在保护范围外，且不会有人主动发现。故把判定规则成文。

### 8.2 判定规则（唯一判据）

> **只有「会改变生产运行态」的 workflow 才可并入 `production-deploy`。**
>
> 「改变生产运行态」＝ 远程执行（ssh / scp / rsync）／ 进程与服务管理（pm2 / systemctl / nginx reload / restart）／ 生产库写入或迁移 ／ 容器发布到生产。

不满足该判据的 workflow **一律不并入**（并入只会造成误排队，见 8.5）。**禁止凭文件名推断**——判定必须给「步骤名 + 行号」证据。

### 8.3 全仓现状（2026-09-21 扫描，5 个文件 / 564 行）

### 8.4 `ci.yml` 明确不并入 —— 两条理由（缺一不可）

1. **无收益**：它**不含任何改变生产运行态的动作**。其 `deploy` 命中来自 `bash -n` 语法检查（L32 / L44 / L47）——那是**静态解析**，既不执行部署脚本，也不触碰服务器。并入后它不会与部署争抢任何资源。
2. **有明确副作用**：`ci.yml` **同时由 `pull_request` 触发**。若并入 `production-deploy`，则**每个 PR 的 CI 都会与生产部署互相排队**——PR 密集时段，一次热修部署会被若干 PR 的 CI 反复推迟；反之 CI 也会被部署阻塞、拖慢 PR 反馈。这是拿「看起来更安全」换「实际更慢且更堵」。

> 同理，`build-exe.yml` 属**制品发布**（GitHub Release），与生产部署无资源竞争，也不并入。

### 8.5 误排队的代价（为什么反对「全都塞进同组」）

把不相关 workflow 硬塞进同一组会造成**双向拖延**：一次静态扫描排在生产部署之后执行；一个 8 分钟的 e2e 会把紧急部署堵住。**「全绿」的观感换不来安全，只会换来更长的恢复时间。**

### 8.6 未来新增部署类 workflow 的强制要求

1. **必须并入**：在该 workflow 顶层加

   ```yaml
   concurrency:
     group: production-deploy
     cancel-in-progress: false
   ```

2. **必须配反测**：故意让该 workflow 与 `deploy.yml` 并发触发，**证明当前会排队**（未反测＝未验收）。
3. **不得改动** `group` 名（改名＝另起一组，保护立即失效）与 `cancel-in-progress`（必须 `false`；`true` 会在中途取消、留下「拉了一半」的半状态，比串行更糟）。
4. **不得删除** `workflow_dispatch` 手动入口（`paths-ignore` 会堵死「只想把已推的提交再部署一次」这条路径）。
