## 二、测试流程（必须遵守）

### 2.1 验收三步法

每次验证必须执行以下三步，缺一不可：
1. **读代码** — 打开文件，看实际内容
2. **跑命令** — `tsc --noEmit`、`npm run build`、`grep`、`vitest run --coverage`
3. **看结果** — 每条结论附代码证据或命令输出

### 2.3 环境准备

```bash
# 根目录（workspaces）
```

## 五、踩坑记录（苏然相关）

### 坑 [17] 未安装依赖就跑测试

- 现象：877 个模块未找到误报
- 原因：未 npm install
- 教训：**执行任何需要解析 node_modules 的命令前，必须先 npm install**

### 坑 [11] subagent 漏项

- 现象：批量任务遗漏字段和校验
- 教训：subagent 输出必须逐项核对，不能直接信任

### 坑 [5] vitest 与 jest 不兼容

- 现象：jest.fn() 报 jest is not defined
- 解决：替换为 vi.fn()（R18 最终修复）

### 坑 [25] 同名 service 文件测错版本（R16 发现）

- 现象：order.test.ts 导入路径写成了 store/order.service.js，导致 admin/order.service.ts 覆盖率 0%
- 教训：遇到同名文件（store/xxx vs admin/xxx）必须逐项核对导入路径

### 坑 [37] istanbul 对 Express Router 分支覆盖率统计失效（R23 发现）

- 现象：routes 分支覆盖率仅 9.6%，controllers 分支覆盖率 61.02%
- 原因：istanbul 对 Express Router 的 router.get/post 调用视为函数分支，但无法追踪回调执行
- 教训：不能仅依赖覆盖率数字判断测试质量，需结合实际测试用例数量综合评估

### 坑 [40] 业务错误使用普通 Error 导致 HTTP 500（R23 发现）

- 现象：测试期望返回 400 状态码，但实际返回 500
- 原因：service 层抛出普通 new Error()，全局错误处理器视为服务器错误返回 500
- 解决：使用 Object.assign(new Error("消息"), { statusCode: 400 })

### 坑 [45] mock-db INSERT 参数索引错误（R23 发现）

- 现象：测试创建采购订单后无法查询到数据，返回 404
- 原因：SQL 中 paid_amount 硬编码为 0，mock handler 仍按原参数索引读取
- 教训：编写 mock handler 时，必须仔细对照实际 SQL 语句的参数位置

### 坑 [46] mock-db UPDATE 使用 id 查找但实际使用 return_no（R23 发现）

- 现象：采购退货审核后状态未更新
- 原因：mock handler 使用 id 查找记录，但实际 SQL 使用 return_no 和 tenant_id 条件
- 教训：编写 UPDATE mock handler 时，必须使用实际 SQL 中的 WHERE 条件字段
