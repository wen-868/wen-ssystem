### 2.2 分层规则（不可违反）

| 层 | 允许做什么 | 禁止做什么 |
|:---|------|------|
| **controller** | 接收参数 → 调用 service → 返回结果 | 直接操作数据库（import db/query/pool） |
| **service** | 业务逻辑、数据库操作、调用外部 API | 直接操作 req/res 对象 |
| **route** | 注册路由、挂载中间件 | 写业务逻辑、直接操作数据库 |
| **shared** | 纯工具函数、不依赖 Express | 依赖 req/res、使用 Express 类型 |
| **middleware** | 请求拦截、鉴权、校验 | 写业务逻辑 |
| **config** | 导出配置常量 | 写业务逻辑、依赖 runtime 状态 |

## 四、统一返回格式

### 4.1 返回体结构

```typescript
// 成功
{
  code: "0",
  msg: "成功",
  data: T,           // 可选
  traceId: string,   // uuid v4
  apiCost: 1         // 固定为 1
}

// 失败
{
  code: "400",       // 或其他错误码
  msg: "错误描述",
  traceId: string,
  apiCost: 1
}
```

### 4.2 工具函数位置

- `shared/response.ts` — `ok<T>(data?: T)` 和 `fail(msg: string, code = "400")`
- **字段名必须是 `msg`，不是 `message`**
- 必须包含 `traceId` 和 `apiCost`

### R54 遗留 — 生产环境登录API 500错误修复 [P0]

- **状态**：✅ 已完成
- **完成时间**：2026-07-23
- **核心内容**：
  1. **根因定位**：`auth.service.ts` 的 `getUserPermissions`（R54-15 新增）用 `JSON.parse(role.permissions)` 处理数据库返回值，但 `t_sys_role.permissions` 字段是 `JSON DEFAULT NULL` 类型，**mysql2 默认会把 JSON 类型列自动解析为 JS 对象/数组**，对 JS 数组调用 `JSON.parse` 会先 `数组.toString()` → `"product:read"` → `JSON.parse("product:read")` 抛 `SyntaxError`，导致登录接口 500
  2. **修复方案**：新增 `normalizePermissions(raw: unknown): string[]` 容错函数，健壮处理 permissions 的所有返回形态：
     - 数组 → filter 后直接使用
     - 字符串 → 先 JSON.parse 再校验（空字符串返回 []）
     - null/undefined → 返回 []
     - 非法 JSON → 容错返回 []
  3. **status 查询兼容**：`getUserPermissions` 的 SQL status 条件从 `r.status = 'ACTIVE'` 改为 `(r.status = 'ACTIVE' OR r.status = 1 OR r.status = '1')`，兼容 VARCHAR 和 TINYINT（因为 079_权限矩阵.sql 的 seed 数据 status=1 是数字，但 init_database.sql 定义 status 是 VARCHAR(16)）

- **教训**：vitest 的模块转换会影响运行时 `typeof` 判断

### 坑 4：路由注册 order 导致认证中间件失效
- **关键词**：Express, 中间件, 路由顺序
- **现象**：`/me` 端点未认证访问时崩溃，`req.user!` 非空断言 NPE
- **原因**：`/me` 路由在 `requireAuthWithTenant` 中间件之前注册
- **解决**：将 `/me` 路由移到 `requireAuthWithTenant` 之后
- **教训**：Express 路由注册顺序就是中间件执行顺序

### 坑 9：controller 层 try-catch 绕过全局 errorHandler
- **关键词**：错误处理, try-catch, errorHandler, 飞书告警
- **现象**：47 个 controller 的 168 个 try-catch 直接 res.json 返回错误，全局 errorHandler、飞书告警、错误日志全部失效
- **解决**：移除 controller 中的 try-catch，让 asyncHandler 自动传递错误
- **教训**：先建立全局错误处理机制，再写业务代码

### 坑 18：re-export 文件用 `export { x } from` 在 v8 覆盖率中显示 0%
- **关键词**：vitest, coverage, v8, re-export, shared/
- **现象**：5 个纯 re-export 兼容文件覆盖率恒为 0%
- **原因**：命名导出 re-export 语法，v8 视为不可达代码
- **解决**：全部改为 `export * from`
- **教训**：`export *` 统计正确，`export { x } from` 统计为 0%。re-export 文件覆盖率恒为 0% 时先改语法

### 坑 19：`Number(undefined) ?? 0` 返回 NaN（不是 0）
- **关键词**：JavaScript, NaN, ??, ||, Number, 隐式类型转换
- **现象**：product-sync.ts 中 affectedRows 变成 NaN 透传
- **原因**：`Number(undefined)` 返回 NaN，`??` 只在左侧为 null/undefined 时取右侧，NaN 不是 null/undefined
- **解决**：改用 `|| 0`（NaN 是 falsy，正确兜底）
- **教训**：`?? 0` 只能兜底 null/undefined，不能兜底 NaN/0/""。涉及 `Number()` / `parseInt()` 转换时必须用 `|| 0`

### 坑 20：migration.ts safeExec 长 `||` 链导致分支爆炸
- **关键词**：vitest, coverage, branches, || 短路, 重构
- **现象**：10+ 个 `||` 短路分支，每个都需单独测才能 100% branches
- **解决**：提取到 `SKIP_PATTERNS` 数组，用 `.some()` 遍历替代 `||` 链，分支数从 13 降到 1
- **教训**：**测试覆盖率 100% 不是靠堆测试用例，而是靠重构代码减少分支。** `||` 链超过 5 个就改数组 + `.some()`
