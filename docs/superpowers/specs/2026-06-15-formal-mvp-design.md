# 智享营销系统方案 A：正式可用版设计

## 目标

把当前演示型系统推进到第一阶段正式可用状态。第一阶段不追求完整商业系统的全部能力，而是优先打通日常经营闭环：后台能管理基础资料和订单，门店端能开单收款和查库存，小程序能连接正式 API，下单与订单查询能正常使用，部署前能通过自动验收。

本阶段完成后，用户应能用系统完成以下真实操作：

- 后台维护商品、门店、客户和库存。
- 后台查看订单、销售单、收款、支付、库存流水和基础报表。
- 门店端搜索商品、选择客户、创建销售单、线下收款、挂单/取单、查看库存。
- 小程序连接 `https://api.onepan.cn/api`，浏览商品、提交订单、查看订单。
- 线上部署包和小程序包不再包含 `localhost`、演示模式或错误域名。

## 不包含范围

第一阶段明确不做以下内容，避免影响主闭环交付：

- 真实微信支付 V3 统一下单、回调验签和退款回调。
- 完整退款审核流。
- 复杂 RBAC 权限矩阵。
- 高级经营报表、毛利分析和多维 BI。
- 打印小票。
- 多仓调拨、盘点审批、交接班。
- 大规模 UI 重设计和品牌视觉升级。

这些内容放入第二阶段。

## 当前问题

当前系统能部署、能打开，也有基础接口，但仍偏演示型：

- 后台是一个大工作台页面，没有正式模块路由。
- 商品新增后缺少正式上架/下架闭环。
- 门店端开单需要手输 SKU ID，不适合真实门店操作。
- 门店端缺少线下收款 UI，虽然后端已有 `offline-payment` 接口。
- 销售单和库存没有形成完整扣减流水闭环。
- 小程序默认配置仍是 `localhost` 和 `demoMode: true`。
- 小程序登录、订单查询和客户类型仍偏开发模式。
- 自动验收脚本没有覆盖“小程序正式包”和“正式可用业务闭环”。

## 总体方案

采用“模块补齐 + 业务闭环 + 验收门禁”的方式推进。

后台、门店端、小程序/API、数据权限和验收脚本分线实现，但共享同一套业务口径：

- 商品只有 `ON_SALE` 才能被小程序和门店端销售。
- 销售单收款状态以 `receivable_amount`、`received_amount`、`unreceived_amount` 为准。
- 库存变化必须写入 `inventory_ledger`。
- 门店端默认只操作当前门店数据。
- 线上构建产物不得出现 `localhost:8080`。
- 小程序正式包不得出现 `demoMode: true` 或 `touristappid`。

## 后台正式可用线

### 页面结构

后台从单页工作台拆为以下模块：

- `/login`：登录页。
- `/dashboard`：经营首页。
- `/products`：商品管理。
- `/stores`：门店管理。
- `/members`：客户管理。
- `/orders`：小程序订单。
- `/sale-bills`：销售单。
- `/inventory`：库存管理。
- `/payments`：支付和收款记录。
- `/reports`：基础报表。

第一阶段可以使用简单的前端路由或内部模块切换，但用户必须能明确进入各模块，而不是所有表格堆在一个页面里。

### 商品管理

补齐能力：

- 商品列表支持关键词、状态筛选。
- 新增商品时填写商品名称、SKU 名称、条码、分类、价格、库存预警阈值。
- 商品可编辑基础信息。
- 商品可上架、下架。
- SKU 可改价。
- 改价写入价格日志。

后端接口：

- `GET /api/admin/products`
- `POST /api/admin/products`
- `PUT /api/admin/products/:spuId`
- `PATCH /api/admin/products/:spuId/status`
- `PUT /api/admin/products/:skuId/price`
- `GET /api/admin/products/:skuId/price-logs`

验收标准：

- 新增商品默认为 `DRAFT`。
- 点击上架后状态变为 `ON_SALE`。
- 上架商品能在小程序商品列表和门店商品搜索中出现。
- 下架商品不能被小程序和门店端继续销售。
- 改价后价格日志可查。

### 门店管理

补齐能力：

- 门店列表、详情、新增、编辑。
- 修改营业状态。
- 启用/停用门店。
- 门店编码规则前后端一致：后台可输入编码；未输入时后端自动生成。

后端接口：

- `GET /api/admin/stores`
- `POST /api/admin/stores`
- `GET /api/admin/stores/:storeId`
- `PUT /api/admin/stores/:storeId`
- `PATCH /api/admin/stores/:storeId/status`
- `PATCH /api/admin/stores/:storeId/business-status`

验收标准：

- 新增门店后列表立即可见。
- 编辑门店后详情和列表一致。
- 停用门店不再作为可售门店出现。
- 营业状态能在后台和门店端一致显示。

### 客户管理

补齐能力：

- 客户列表、新增、编辑。
- 客户类型维护：零售、批发。
- 客户归属销售员选择，不再硬编码 `staffId=1`。
- 客户价格参考可选择 SKU。

后端接口：

- `GET /api/admin/members`
- `POST /api/admin/members`
- `PUT /api/admin/members/:memberId`
- `PATCH /api/admin/members/:memberId/status`
- `GET /api/admin/staff`
- `POST /api/admin/members/:memberId/assign`
- `GET /api/admin/members/:memberId/price-history?skuId=`

验收标准：

- 新增客户可被门店端搜索到。
- 批发客户在开单时默认使用批发价。
- 分配销售员时从员工列表选择。
- 价格参考不再固定 SKU 1。

### 订单管理

补齐能力：

- 订单列表筛选：关键词、状态、日期。
- 订单详情展示商品、收货信息、支付状态、履约状态。
- 后台可取消订单、备注订单。
- 状态流转必须有校验。

后端接口：

- `GET /api/admin/orders`
- `GET /api/admin/orders/:orderNo`
- `POST /api/admin/orders/:orderNo/cancel`
- `POST /api/admin/orders/:orderNo/remark`

验收标准：

- 非法状态流转返回明确错误。
- 取消后门店端和小程序订单状态同步。
- 订单详情信息完整。
- 订单导出结果与筛选条件一致。

### 库存管理

补齐能力：

- 库存总览支持门店、SKU、库存类型筛选。
- 后台可调整库存。
- 调整原因必填。
- 库存变化必须写流水。
- 库存预警口径统一使用 SKU 阈值。

后端接口：

- `GET /api/admin/inventory/balances`
- `POST /api/admin/inventory/adjust`
- `GET /api/admin/inventory/logs`
- `GET /api/admin/inventory/alerts`

验收标准：

- 调整库存后余额变化正确。
- 每次调整都产生 `inventory_ledger`。
- 调整后库存不能小于 0。
- 库存预警后台、门店端口径一致。

## 门店端正式收银线

### 页面结构

门店端保留轻量工作台，但必须形成清晰操作区：

- 工作台指标。
- 小程序订单。
- 快速开单。
- 销售单。
- 库存。
- 收款记录。
- 挂单。

### 商品选择

门店端不再要求手输 SKU ID。补齐：

- 商品关键词搜索。
- 条码搜索。
- SKU 选择器。
- 显示零售价、批发价、库存。
- 加入购物车。

后端接口：

- `GET /api/store/products?keyword=&barcode=`

验收标准：

- 店员可以通过商品名或条码选择商品。
- 选择商品后自动带出价格和库存。
- 库存不足时明确提示。

### 客户选择

补齐：

- 手机号搜索客户。
- 客户姓名搜索。
- 新增临时客户。
- 根据客户类型决定默认价格。

后端接口：

- `GET /api/store/members?keyword=`
- `POST /api/store/members`

验收标准：

- 批发客户开单默认批发价。
- 普通客户开单默认门店价或零售价。
- 没有客户也可匿名开单。

### 销售单与线下收款

补齐：

- 多商品购物车。
- 创建销售单。
- 现金/转账/其他线下收款入口。
- 部分收款。
- 收款后刷新销售单状态。

复用已有接口：

- `POST /api/store/sale-bills`
- `POST /api/store/sale-bills/:billNo/offline-payment`

验收标准：

- 创建销售单后列表可见。
- 全额线下收款后销售单变为已收。
- 部分收款后销售单变为部分收款。
- 收款金额不能超过未收金额。

### 库存扣减

第一阶段采用“销售单收款成功后扣减库存”的规则。

补齐：

- 线下收款成功时扣减对应门店 `OFFLINE` 库存。
- 写入库存流水。
- 重复收款或重复请求不能重复扣库存。

验收标准：

- 销售 1 件后门店线下库存减少 1。
- 库存流水显示销售出库。
- 重复提交不会重复扣减。

### 挂单/取单

现有挂单能力保留并补齐：

- 挂单保存购物车、客户和备注。
- 取单回填购物车。
- 取单并成功开单后，挂单自动关闭。

验收标准：

- 同一挂单不能重复转销售单。
- 删除挂单后不能再取单。
- 取单金额和商品明细一致。

## 小程序/API 线

### 正式配置

补齐：

- `miniapp/app.js` 支持正式 API 配置。
- 构建正式体验包时自动替换 `apiBase` 为 `https://api.onepan.cn/api`。
- `demoMode` 必须为 `false`。
- `project.config.json` 不得继续使用 `touristappid`。

验收标准：

- 小程序正式包内不含 `localhost`。
- 小程序正式包内不含 `demoMode: true`。
- 小程序正式包内不含 `touristappid`。

### 商品与订单

补齐：

- 小程序商品列表连接正式 API。
- 提交订单连接正式 API。
- 订单列表按当前用户或临时用户隔离。
- 订单详情可查看状态。

第一阶段仍可暂不接真实微信登录，但必须避免全量订单暴露。可以采用临时会员 token 或设备级匿名 memberId。

验收标准：

- 小程序能看到上架商品。
- 下单后后台和门店端能看到订单。
- 小程序订单列表只显示当前用户相关订单。

## 数据与权限线

### 初始化数据

补齐正式演示种子：

- 超级管理员账号。
- 门店店长账号。
- 门店操作员账号。
- 默认门店。
- 示例商品和库存。
- 零售客户。
- 批发客户。

验收标准：

- 管理员可登录后台。
- 门店账号可登录门店端。
- 示例商品可销售。
- 批发客户价格生效。

### 基础权限

第一阶段只做基础权限，不做复杂矩阵：

- 后台接口要求管理员角色。
- 门店接口要求门店角色或管理员。
- 门店角色只能访问所属门店数据。
- 无权限返回 403。
- 前端支持退出登录。
- token 过期后回到登录页。

验收标准：

- 门店 A 账号不能查看门店 B 数据。
- 未登录访问业务接口返回 401。
- 角色不符返回 403。

### 后台线

负责：

- `admin-web`
- `backend/src/routes/admin.routes.ts`
- 后台相关验收脚本

不能改：

- 小程序 UI。
- 真实支付实现。

### 门店线

负责：

- `store-terminal`
- `backend/src/routes/store.routes.ts`
- 门店验收脚本

不能改：

- 后台页面结构以外的管理模块。
- 真实微信支付。

### 小程序线

负责：

- `miniapp`
- `scripts/build-mobile-beta.mjs`
- `scripts/check-miniapp-release.mjs`
- `backend/src/routes/miniapp.routes.ts`

不能改：

- 后台和门店端主体交互。

### 数据权限线

负责：

- `docs/phase1_schema.sql`
- `docs/phase1_seed.sql`
- `backend/src/shared/auth.ts`
- 权限中间件和种子数据

不能改：

- 前端大规模布局。

### 验收线

负责：

- 新增验收脚本。
- 接入 `package.json` scripts。

- 业务实现逻辑，除非是为了暴露测试入口且经主线确认。

## 交付顺序

1. 数据和权限基础：种子账号、门店角色、基础鉴权。
2. 后台商品/门店/客户/库存可维护。
3. 门店商品选择、客户选择、购物车和线下收款。
4. 小程序正式配置和下单链路。
5. 销售单收款后库存扣减和流水。
6. 自动验收脚本。
7. 服务器部署和线上验收。

## 第一阶段完成定义

以下全部满足才算第一阶段完成：

- 后台能登录并完成商品上架、门店维护、客户维护、库存调整。
- 门店端能登录并完成商品选择、开单、线下收款、库存扣减。
- 小程序正式包连接线上 API，能浏览商品和下单。
- 后台、门店端、小程序看到的数据一致。
- 线上验收脚本全部通过。
- 生产构建产物不含 `localhost`。
- 小程序正式包不含演示模式。

## 风险与处理

### 真实支付暂不接入

第一阶段用线下收款作为正式可用闭环。分享收款和真实微信支付放第二阶段，避免因为支付资质、证书、回调域名等问题拖慢核心经营功能。

### 权限不做复杂矩阵

第一阶段只区分管理员和门店角色，确保数据隔离。更细的角色权限放第二阶段。

### UI 不做大改版

第一阶段重点是业务可用。页面会模块化和清晰化，但不追求完整视觉重设计。

### 存量数据可能有测试记录

验收脚本应使用独立前缀或测试标记创建数据，避免和真实经营数据混淆。
