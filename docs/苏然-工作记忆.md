## 一、胖路由问题（Fat Routes）

### 定义：端点 > 30 或 跨多个业务域

| 排名 | 文件 | 端点数 | 严重度 | 问题 |
|:---:|------|:---:|:---:|------|
| 1 | `admin.routes.ts` | **83** | P0 | 10 个 controller，涵盖员工/门店/商品/订单/客户/报表/日结/采购/会员/财务 10 个业务域 |
| 2 | `marketing.routes.ts` | **59** | P0 | 7 个 controller，涵盖优惠券/团购/秒杀/积分商城/满减/赠品/仪表盘 |
| 3 | `store.routes.ts` | **46** | P1 | 10 个 controller，门店端所有功能全塞一个文件 |
| 4 | `instant-retail-new.routes.ts` | **45** | P1 | 即时零售所有功能 |
| 5 | `report.routes.ts` | **26** | P2 | — |
| 6 | `credit.routes.ts` | **24** | P2 | — |

### 影响
- 单文件过大，修改冲突概率高
- 新人无法快速定位路由
- 无法按模块独立部署/测试
- `admin.routes.ts` 一个文件挂了影响全部 83 个 API

### 建议
- 按业务域拆分：`admin-product.routes.ts`、`admin-order.routes.ts` 等
- 或按 controller 拆分：每个 controller 对应一个路由文件
- 目标：每个路由文件 ≤ 15 个端点

## 二、API 层问题

### 2.1 Controller 层 try-catch 绕过 error-handler

| 指标 | 数值 |
|------|:---:|
| 有 try-catch 的 controller 文件 | **31 个** |
| 这些错误不会被 error-handler 捕获 | ❌ |
| 错误不会被持久化到 error_logs | ❌ |
| 飞书告警收不到 | ❌ |

**典型文件**：`purchase-return.controller.ts`、`purchase-payment.controller.ts`、`inventory-batch.controller.ts` 等

```typescript
// 问题代码模式
export const approve = asyncHandler(async (req, res) => {
  try {
    const result = await service.approve(...);
    res.json(ok(result));
  } catch (e: any) {
    res.status(e.statusCode || 400).json({ code: ..., message: e.message });
    // ❌ 错误在这里被吞掉，不会走到 error-handler
  }
});
```

### 2.2 输入校验缺失

| 指标 | 数值 |
|------|:---:|
| 总 controller 文件 | 124 |
| 有 Zod 校验的 | 55 (44%) |
| **无任何校验的** | **69 (56%)** |

**69 个 controller 没有任何输入校验**，可能导致：
- 空字符串写入数据库
- 非法参数导致 SQL 错误
- XSS/注入风险

### 2.3 响应格式不一致

| 方式 | 使用情况 |
|------|------|
| `ok()` / `fail()` 统一格式 | 大部分 |
| 直接 `res.json({ code: ..., message: ... })` | 1 处（payment.controller.ts） |
| 直接 `res.json(data)` 不包装 | 少量 |

### 2.4 缺少认证中间件的路由

| 文件 | 端点数 | 风险 |
|------|:---:|------|
| `platform.routes.ts` | 3 | 平台接口无认证 |
| `share.routes.ts` | 4 | 分享链接无认证 |
| `wechat.routes.ts` | 6 | 微信回调无认证 |

> 注：部分可能是故意公开的（如微信回调），但需逐一确认。

### 2.5 多租户隔离不一致

`admin.routes.ts` 中员工管理（staff）4 个端点使用 `requireAuth` 而非 `requireAuthWithTenant`，可能跨租户访问员工数据。

## 四、架构问题

### 4.1 server.ts 路由注册
- 84 行 `app.use(...)` 手动注册
- 无自动路由发现机制
- 新增模块需手动改 server.ts，容易遗漏

### 4.2 mock-db.ts 单体
- 1778 行，所有表的 mock 逻辑全在一个文件
- 无法按模块独立维护
- 新增表需要修改这个巨型文件

### 4.3 前端无错误捕获
- 无 Vue 全局错误处理器
- 无 axios 拦截器错误上报
- 前端错误无法上报到后端 error_logs
