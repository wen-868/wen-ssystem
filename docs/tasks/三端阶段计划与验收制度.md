# R101 · 三端阶段计划与验收制度（业主 2026-09-22 指令后建立）

> 业主指令原文：「**先把总平台全部做完并完成验收，下一步开始做工作台改造验收，最后做手机端完善验收，须建立完善的工作流程、进度等相关工作制度，不能想起什么就做什么。**」
> 本文件是该指令的**落地制度**：定义三端顺序、每端"做完"的判据、阶段门、以及进度台账。
> 与既有的《派单规范》§八（批次制与六步闭环）配套：**本文件管"顺序与完成定义"，§八 管"每单怎么走"**。
> 维护人：凌舟（总负责人）

## 一、三端阶段（顺序不可颠倒）

| 阶段 | 端 | 范围 | 状态 |
|---|---|---|---|
| **阶段一** | **总平台** `saas-admin`（+ 其所需后端接口） | 平台运营端：租户/套餐/公告/模板中心/开放平台/对账/监控/AI 配置/商品库/运营/应用版本/管理员权限 | 🟢 **进行中** |
| 阶段二 | **工作台** `admin-web` | 商家工作台（含 S3-72 统一色板落地、S3-67 边框族、工作台改造验收） | ⏸ 待阶段一收口 |
| 阶段三 | **手机端** `app-mobile` | 移动端完善（含 S3-76 `--safe-top` 修复、状态文字层替换、离线同步上线验证） | ⏸ 待阶段二收口 |

**跨阶段的例外**（可并行，不违反顺序）：
- **等待外部输入的阻塞项**（如推送凭据）；
- **已在飞行的批次**（如 16-B S3-80 离线同步后端 —— 属阶段三的服务端前置，已开工）；
- **纯运维/观察类**（如 D-3 观察期）。

## 二、每端"做完"的定义（端级 DoD，缺一条即不算做完）

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | **代码零待办** | 该端 `TODO/FIXME/待接入/未实现` **计数归零**（或每条都有"不做"的书面裁定与理由）——基线用可复跑命令给数字 |
| 2 | **接口闭环** | 该端调用的每个后端接口**存在且有响应**；不存在的一律补后端（或产品裁定不做并从前端移除入口） |
| 3 | **构建与类型** | `npm --workspace <端> run build` EXIT=0；该端 `tsc --noEmit`（若有）EXIT=0 |
| 4 | **单测** | 该端关联的后端服务/前端逻辑有单测，**全绿**；该端自身若无测试框架，必须**先补齐最小测试能力**（不能长期零测试） |
| 5 | **门禁** | CI 门禁全绿：`build-and-test` / `e2e` / `CodeQL`（`migration-check` 为既存非必需项，需在报告里单列） |
| 6 | **e2e/浏览器证据** | 该端在 `e2e` 里有**真实跑通**的用例（saas-admin 目前仅"对比度矩阵"降级覆盖 ⇒ 阶段一必须把浏览器 axe 跑起来或给出书面降级裁定） |
| 7 | **生产验证** | 合并 → Auto Deploy success → 生产端到端冒烟（关键路径人工/脚本各一次） |
| 8 | **文档与记账** | 端级验收报告（引用可复跑证据）+ 队列状态更新 + 总进度记账 + Issue 关闭 |

## 三、阶段门（Stage Gate）

- 只有**当前阶段**的端级 DoD **8/8 全部通过**，才允许开启下一阶段的第一单。
- 阶段切换时，凌舟出一份**端级验收报告**（一页），含：DoD 逐条结论 + 证据索引 + 未完成项（若有必须写明挂起原因与唤醒条件）。
- 若某条 DoD 无法取证（如外部凭据缺失），**必须显式裁定"降级通过"并写清代价**，不得默认跳过。

## 四、进度台账制度（三处同步，禁止单点记录）

| 台账 | 文件 | 作用 |
|---|---|---|
| **队列**（要做什么、到哪一步） | `docs/tasks/当前批次.md` | 唯一队列；状态只有 4 档：待起跑 / 进行中 / 已验收 / 已挂起 |
| **进度源**（整体到哪了） | `docs/tasks/R101-总进度与推进计划.md` | 每单闭环的第⑥步必须记账 |
| **Issue**（对外可见的闭环） | GitHub Issue | 每单一个 Issue；**验收通过即关闭**，关闭评论里必须贴验收结论 |

**计量基线（可复跑，数字必须能对齐）**：
- 总平台：`rg -c 'TODO|FIXME|待接入' saas-admin/src` → **当前 235 处 / 116 个接口**（2026-09-22 基线）
- 每完成一批，**在同一命令下复测并记录新数字**，直到归零（或每条有裁定）。

**每个子批次的固定动作（缺一不算完成）**：
1. **清账**：把该模块的 TODO 逐条分类 —— ①前端补接（后端已有）②后端新建 ③产品裁定不做（书面理由 + 移除前端入口）；
2. **后端**：接口（按既有 `routeConfig` 约定）+ 租户/权限隔离 + 单测；
3. **前端**：接真实接口、删除 TODO、补空态/错误态；
4. **证据**：接口 curl 原始输出 + 页面截图或 e2e 用例 + 单测输出；
5. **闭环**：六步闭环（派单规范 §八）+ 记账。

### 6.1 阶段三 · 推送上线（M-1）—— 已按业主裁定**排期到手机端工作周期内**

**为什么放这里**：推送的瓶颈不在后端（后端已就绪：`config/env.ts:172-187` 声明变量、`POST /register` 在、`sendToUser` 在、S3-78 已接通知链路），而在**客户端原生插件 + 重新打包发版 + 真机验证** ⇒ 天然属手机端。

| 项 | 内容 |
|---|---|
| 起跑条件 | ① 业主在**极光控制台**建应用（包名 `com.zhixiang.app`）并给出 **AppKey + Master Secret**（或裁定走 **Plan B** 应用内提醒）② 移动端有 HBuilderX 打包与插件授权 |
| 交付物 | ① `manifest.json` 配推送原生插件（极光；可选华为）② 重新打包的 App 构建产物 ③ 生产 `.env` 4 行 + `.env.example` 变量名 ④ 真机验证记录（`t_push_token` 有记录 + 收到一条真实通知） |
| 验收判据（硬） | ① 真机登录后 `t_push_token` 出现该设备记录（可复跑 SQL）② 触发一条真实通知 → **手机通知栏收到**（截图/录屏）③ 无凭据时必须是 no-op + 日志（已有单测覆盖）④ 关闭推送不影响通知记录写入 |
| 两案裁定时点 | **阶段三开工时**由业主二选一（Plan A 极光 / Plan B 应用内提醒）。**建议**：若选 A，请在阶段二期间就把极光账号与应用建好——账号/应用创建常有数小时到 1 天审核，提前办可免阶段三卡壳 |
