# 快速开单 —— 四种单据类型改造（派单）

> 派单人：凌舟 ｜ 负责人：app-mobile 前端（墨/阿澈）＋ 后端接口（阿坚，按需）
> 验收：凌舟（高标准，不合格打回重做）
> 截止：按顺序分阶段交付，每阶段验收通过再继续
> 文件：app-mobile/src/pages/sales/create-sale.vue（前端主文件）

## 一、目标

快速开单已按「销售/采购 + 订单/出货(进货)/退货/收款单」做单据类型分段。本次把**每种单据类型做成各自正确的业务表单**，字段、底部动作、提交接口各自独立，不允许统一套一个"转销售单/收款"。

务必先读后端对应路由与 `app-mobile/src/api/modules/*` 现有方法，**按真实接口字段实现，禁止臆造字段、禁止写死假数据**。

## 二、四种单据方案（按此实现）

### 1. 订单（docMain=sale, docSub=订单）—— 先做，已闭环
- 字段：客户(散客)、商品(−数量+)、配送方式、日期、门店/仓库、备注、追溯码/条码
- 底部动作：保存 / **转销售单** / 分享
- 提交：`salesApi.createSale`（/store/sale-bills），不收款、底部不显示应收金额

### 2. 进货（docMain=purchase, docSub=进货）—— 第二阶段
- 字段：**供应商**(非客户)、商品(−数量+)、入库仓库、日期、备注
- 底部动作：保存 / **确认入库** / 分享
- 提交：`purchaseApi.createInStock`（/admin/purchase-in-stocks）——先读该接口真实参数(supplierId/storeId/items)再写

### 3. 收款单（docSub=收款单）—— 第二阶段
- 字段：**关联销售单**(源单选择器)、收款金额、收款方式、日期、备注
- 底部动作：保存 / **确认收款** / 分享
- 提交：`receiptsApi.create`（/admin/receipts）——先读该接口真实参数

### 4. 退货（docSub=退货，销售/采购）—— 第三阶段
- 字段：**关联源销售单/采购单**、退货数量、退货原因、日期
- 底部动作：保存 / **提交退货** / 分享
- 提交：销售退货 `/admin/sale-return`、采购退货 `/admin/purchase-return`——移动端若缺封装需先补（后端同事配合）

### 5. 出货（docMain=sale, docSub=出货）—— 暂缓，单独定方案
- 后端无明确销售发货接口，**本阶段不做**，先占位提示，避免臆造

## 三、防屎山红线（必须遵守）

1. **复用现有 API**：四种单据都调 `api/modules/` 里已有方法；缺的才新增（新增需注明接口来源与字段依据）。
2. **按类型切换表单**：同一页面按 `docSub`/`docMain` 用 `v-if` 切换不同区块，不写互相干扰的全局逻辑；状态量用对应命名（`inStockStore/sourceBillNo` 等），不共用混乱变量。
3. **不伪造数据**：所有提交用真实接口，不写 `mock`/写死返回值；无接口的类型（出货）明确提示"待开放"，不假装成功。
4. **不破坏现有逻辑**：订单(转销售单)现有功能必须保持可用；改动只增量，不顺手重构无关代码。
5. **代码评审自检**：提交前跑 `npm run build:h5` 通过；不 copy 大段重复模板。

## 四、验收标准（凌舟逐项）

1. 四态切换后：客户/供应商、商品选择、底部按钮文案、提交接口**随类型正确变化**，无张冠李戴。
2. 订单→转销售单能建单；进货→确认入库、收款单→确认收款能**真落库**（数据库可见，非假成功）。
3. 表格字段与后端接口参数一致，无 400/缺字段报错。
4. 页面无 JS 报错、无"开发中/模拟数据"残留；build:h5 通过。
5. 任一不达标 → 凌舟附具体差距打回，重做后再验。

## 五、阶段交付

- 阶段 A：订单(已闭环) + 进货 + 收款单 —— 完成后交付验收
- 阶段 B：退货（先补后端/移动端接口）
- 阶段 C：出货（单独定方案后）

每阶段交付时在仓库提交（信息用中文），凌舟验收通过后进入下一阶段。

## 七、凌舟验收反馈（A 阶段 d04f29fb —— 【不通过 / 打回重做】）

验收时间：2026-08-23。结论：**不符合"全部真实商用环境可用"标准，打回重做**。核心问题不是视觉，而是**提交到真实后端的字段与接口契约不匹配，实测提交 500，无法真正落库**。两处提交均用 `as any` 绕过类型检查，把字段错误掩盖到了运行时——这正是"应付任务/屎山"信号，且与你汇报的"字段均来自真实接口契约"不符。

### 收款单（receipt）——实锤缺陷
后端 `POST /api/admin/receipts`（`controllers/admin/receipt.controller.ts` → `services/admin/receipt.service.ts#createReceipt`）期望的字段：
`customerId、customerName、receiptType、amount、paymentMethod、bankAccountId、receivedDate、remark`

而移动端 `submitReceipt`（create-sale.vue）发送的字段：
`customerName、receiptDate、receiptAmount、paymentMethod、remark`

差异：缺 `customerId`、缺 `receiptType`；`amount` 被写成 `receiptAmount`；`receivedDate` 被写成 `receiptDate`。

线上实测（store_manager 登录）：
- 移动端负载 → `{"code":"500","msg":"服务器内部错误"}` ✅ 复现失败
- 正确契约负载 `{"customerId":1,"customerName":"张三","receiptType":"SALE","amount":100,...}` → `{"code":"0","msg":"成功","data":{"receiptNo":"SK...","status":"CONFIRMED"}}` ✅ 成功

结论：收款单提交**必然失败**，字段名错配是唯一根因。

### 进货单（purchase-in）——实锤缺陷
后端 `POST /api/admin/purchase-in-stocks`（`services/admin/purchase-in-stock.service.ts#create`）期望 snake_case 字段：
`supplier_id、supplier_name、store_id、remark、items[{sku_id、sku_name、box_qty、bottle_qty、unit_price、...}]`

移动端 `submitPurchaseIn` 发送 camelCase 字段：
`supplierId、supplierName、warehouseId、warehouseName、inStockDate、items[{productId、productName、quantity、unit、unitPrice、subtotal}]`

差异（两类）：字段名全为 camelCase（`supplierId→supplier_id`、`sku_id` 被写成 `productId`、`box_qty/bottle_qty` 被写成 `quantity`）；且后端**根本没有仓库（warehouse）概念**，只有 `store_id`（入库门店）——你用 `storesApi.list` 门店列表当"仓库"并把 `warehouseId/warehouseName` 塞进去是**维度错误**，与后端契约冲突。

线上实测：`/api/admin/purchase-in-stocks` 的 `GET 列表` 与 `POST 创建` 均返回 500，说明该端点整体尚未部署到位（疑似 `t_purchase_in_stock` 表缺失 / 迁移未应用），叠加字段错配。

### 必须修正后重交
1. **以真实后端契约为准**重写两处提交字段（不要 `as any` 硬闯）：进货单用 snake_case（`supplier_id/store_id/items[].sku_id/box_qty/bottle_qty/unit_price`），并确认后端确实提供该端点后可用；收款单补 `customerId/receiptType/amount/receivedDate`。
2. 处理"进货单后端端点当前 500"的部署/表结构问题（迁移 `t_purchase_in_stock` 相关 SQL 需确认已应用到生产），否则前端字段改对了也无法落库。
3. 删除所有 `as any` 掩盖类型的行为；提交体用明确的 TS 类型。
4. 不要再用门店列表当仓库（除非后端确实用 `store_id` 且语义一致），对照后端 DTO 确认"入库仓库"到底映射哪个字段。
5. 修正后请先本地、再打一个真实的落库验证（提交后能在列表/明细看到该单据），再交验收。

### 1. 不执行 `002_missing_business_tables.sql`（驳回）
workBuddy 的「表没建」探因**是错的**。已实测生产库：
- `t_receipt`：`GET /api/admin/receipts` → 200（存在）
- `t_purchase_in_stock`：`GET /admin/purchase-in-stocks/RK-nope` → **404「入库单不存在」**（表存在，SELECT 正常，仅无数据）

### 2. 进货 list 500 真因（凌舟已定位并修复）
根因：`services/admin/purchase-in-stock.service.ts` 的 `list` 里 `WHERE 1=1 AND tenant_id = ?` **未限定列名**，而查询 `LEFT JOIN t_store`（t_store 也含 tenant_id），导致 MySQL `Column 'tenant_id' in where clause is ambiguous` → 500。`detail` 用 `p.tenant_id` 所以正常（404）。
修复：已把该处改为 `p.tenant_id`，后端构建通过、`purchase-in-stock.service.test.ts` 3/3 通过。**提交 `1ef3d39f`**。

### 3. 进货 create 500（未定位，需后端排查）
用合法 `sku_id=10 / supplier_id=1 / store_id=1` 实测仍 500。`injectTenantCondition` 对已含 tenant_id 的 SELECT 不会重复注入；INSERT 列与参数数量核对一致。**这不是前端、也不是缺表**，需在服务器看 zhixiang-api 日志的 traceId（如 `602c435c-f834-4db6-8be7-8bc976a4ac51`）定位，属后端/部署运维排查。

### 4. A 阶段前端（69b62c34）契约判定：通过，但发现 1 项真实契约错
- 进货 `submitPurchaseIn`：`supplier_id/supplier_name/store_id/items[{sku_id,sku_name,box_qty,bottle_qty,unit_price}]` ✅ 对齐
