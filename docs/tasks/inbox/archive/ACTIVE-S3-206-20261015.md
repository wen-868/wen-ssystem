## 〇、**凌舟已定位根因（2026-10-15）——省掉"复现"步骤，直接按此修**

**根因不在某一条 SQL，而在注入启发式本身**：`backend/src/config/database.ts:215-218`

```js
// 检查是否已经有 tenant_id 条件
if (sql.toLowerCase().includes('tenant_id')) {
  return { modifiedSql: sql, modifiedParams: params };   // ← 直接不注入
}
```

`queryWithTenant` 用 **"整条 SQL 里出现过 `tenant_id` 这个词"** 作为"已有租户条件"的判据 —— **太弱**：
- `JOIN … ON … AND o.tenant_id = a.tenant_id` 是**跨表同租户匹配**，**并未**把结果限制在调用者租户；
- 只要这种写法（甚至只是列名 `SELECT tenant_id`、注释里提到）出现一次，**注入就被静默跳过** ⇒ **租户隔离整体失效**。

**凌舟扫到的同形嫌疑点**（同根因）：
```
services/admin/aftersale.service.ts:100 / :222        LEFT JOIN t_miniapp_order o ON o.order_no=a.order_no AND o.tenant_id=a.tenant_id
services/admin/approval-records.service.ts:382/:418   JOIN t_approval_instance i ON … AND i.tenant_id=t.tenant_id
```
（`community-marketing.service.ts` 的 `AND gb.tenant_id = ?` **不属**此列——那是显式参数。）

### 因此本单的修法口径**不是**"给 sales-ranking 补一行条件"，而是：

1. **收紧注入启发式**：只有当 SQL 里存在**绑定到调用者租户**的条件时（例如 `tenant_id = ?` 这种带参形式，或明确的调用者表达）才跳过注入；**单纯出现标识符不算**。改完必须给"反例集"（构造 `JOIN … AND x.tenant_id = y.tenant_id` 的夹具 ⇒ **改前不注入**、改后**注入生效**）。
2. **全量重扫**：按"SQL 里出现 `tenant_id` 但**没有调用者租户条件**"的口径扫全仓，逐条列出并处置（改 SQL 或确认安全）；**同形点多于 1 处时按清单一次性处置，不要只修一处**。
3. **回归用例**：把"JOIN 带 tenant_id 但不带调用者条件"做成**常驻用例**（属门禁，不是一次性探针），防止复发。
