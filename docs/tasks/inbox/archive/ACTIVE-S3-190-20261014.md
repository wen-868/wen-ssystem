## 一、三项现状（凌舟已亲验，下面都是实测读数，不是推测）

**第 55 项 · 空库下 seed 中断 ⇒ 演示账号与全部种子数据从未创建（最急）**
- 装置：本机私有 MariaDB 11.4.5 空库，跑 `backend/dist/shared/migration.js` 的 `runMigrations()`（S3-186 的 harness 可直接复用，见 §六）。
- 原始读数：日志出现 `[migration] 种子数据初始化失败:` + `"Unknown column 'mobile' in 'INSERT INTO'"`。
- 成因：`backend/src/shared/seed-data.ts:102` 的 `INSERT INTO t_sys_user (tenant_id, username, password_hash, real_name, mobile, store_id, status, created_at, updated_at)` 需要 `t_sys_user.mobile`，而该列由**外部迁移语料**（在 in-code 种子**之后**才执行）补上 ⇒ 空库上种子必然抛 `ER_BAD_FIELD_ERROR`，且**整个 seed 的 try 块**在"插入默认门店"之后即中断。
- 实测后果（跑完整个启动期迁移的空库）：`t_store` **1 行**（默认门店已插）、`t_member` **0**、`t_sale_bill` **0**、`store_manager` + `store_operator` **0 行**；全库只剩 `admin` / `tenant_admin` 两个平台管理员。
- 影响：生产不受影响（列已存在）；**新环境 / 灾备重建会缺演示账号与全部种子数据，且是"静默半成品"**。

**第 56 项 · `backend/src/shared/migration.ts:675` 未加守卫的 `DROP INDEX`**
- 语句：`ALTER TABLE t_sys_config DROP INDEX uk_config_key, ADD UNIQUE KEY uk_config_key_tenant (config_key, tenant_id)`。
- 原始读数（空库）：`[migration] t_sys_config.uk_config_key_tenant 失败: Can't DROP INDEX 'uk_config_key'; check that it exists`（迁移 `005_phase3_sys_config.sql:22` 已直接建出 `uk_config_key_tenant`）。
- 后果：**同一条语句里的 `ADD` 一并未执行**；新库功能无缺（005 已建该键），但**非幂等 + 恒红日志**，会掩蔽真错误。

**第 53 项 · 24 条 `CALL` 的表名缺 `t_` 前缀 ⇒ 恒失效**
- 分布：`092_租户ID.sql` 12 条、`120a_合规凭证字段.sql` 8 条、`137_sys_user_dept_position.sql` 2 条、`138_approval_business_link.sql` 2 条。
- 现象：这些 `CALL add_column_if_not_exists('sys_config', …)` 传的是**不带 `t_` 前缀**的表名，而真实表名是 `t_sys_config` 等 ⇒ 恒 `ER_NO_SUCH_TABLE`（S3-186 改写时**按原样保留语义**，故仍未生效）。
- **首先必须自证这条是否成立**（见 §三.1）——若成立，则空库结构比生产**少这批列/索引**，属真实缺口。
