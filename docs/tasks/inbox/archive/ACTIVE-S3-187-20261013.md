## 一、五条现状（凌舟/前序单已取证，勿再重复求证）

| 项 | 现象 |
|:--|:--|
| **A** | `POST /api/miniapp/marketing/coupons/claim` 的 controller 读 `req.params.templateId`、`/flash-sales/grab` 读 `req.params.id`、`/group-buys/teams/join` 读 `req.params.teamId`，而**三条路由都没有路径参数** ⇒ 三个 ID **恒 NaN**、业务层直接 **404**；**契约文档写的是带参路径**（`docs/API接口文档.md:2839 / :2852 / :2868`） |
| **B** | `backend/src/routes/commerce-fix.routes.ts:28` 的 `{ prefix: "/api/store", auth: "requireAuthWithTenant" }` **前缀级**覆盖**全部** `/api/store/**`（连它不匹配的子路径也先过认证+CSRF）；注册顺序由**文件名排序**决定 ⇒ 改名即静默改变全局防护面，且让"某文件自己有没有挂 CSRF"的审计失真 |
| **C** | `GET /api/miniapp/marketing/points/my` 的身份取 `Number(req.params.userId)`（`marketing-points.controller.ts:40`），该路由**没有 `:userId`** ⇒ 恒 **NaN** |
| **D** | 老 miniapp（微信原生）客户端：`pages/coupons/index.js:74/104` 调 `/coupons/mine`、`/coupons/${templateId}/claim`（后端是 `/coupons/my`、`/coupons/claim`），且 `Authorization` 用**微信令牌**（`requireAuthWithTenant` 不认）⇒ 该客户端对 `/api/miniapp/marketing/*` **目前实际不可用** |
| **E** | `backend/src/routes/wechat.routes.ts` 的 4 个写端点经 `requireWxAuth`，但该中间件**只设 `req.wxUser`、不设 `req.user`**；而 `csrfMiddleware` 在 `!req.user` 时**直接放行** ⇒ 直接挂上去是**假安全** |

## 二、处置口径（已定）

### A（第 28 项）：**以契约为准**修路由

- 按 `docs/API接口文档.md` 的带参路径**改路由注册**（三条），使参数真实存在；
- 🔴 **前提已具备**：S3-178（PR #288）已给这批端点补了**消费者侧身份绑定**（`req.user.id`）⇒ 修完参数后**不会**变成"可冒充任意用户的可用写接口"。**再加一层**：入参里的 `templateId` 等属于"被操作对象"，必须做**归属/存在性校验**（不属于本租户/不存在 ⇒ 400/404），不得只取不校验；
- 同时按**新路径**同步 `miniapp/src/api/*`（新客户端）的调用；老客户端（D）按下面 D 处置。

### B（第 29 项）：消除"前缀级静态覆盖"

- 先给**证据**：`commerce-fix.routes.ts:28` 到底覆盖了哪些**它并不拥有**的路径（举 2~3 个实测例子，含"不存在的子路径也 403"）；
- 口径二选一并说明理由：(a) 把它改成**显式声明**（只覆盖自己真正拥有的路径段）；(b) 或在 `auto-routes` 里对**prefix 完全包含关系**出**阻断/告警**（并给出实测红）。
- 🔴 无论选哪个，**不得**削弱现有防护（`/api/store/**` 的认证+CSRF 必须继续生效）。

### C（第 30 项）：`points/my` 身份改取登录态

- 身份改取 `req.user.id`；若要与 `/api/admin/marketing/points/user/:userId` 共用函数，则加**显式分支**：有 param 用 param（并做归属校验）、无 param 用登录态。

### D（第 31 项）：老 miniapp 客户端 —— **先定性再处置**

- 先判**是否仍在用**（是否仍被构建/发布/打包）：给出证据（构建脚本、发布清单、`rg` 引用）；
- **在用的** ⇒ 修：路径对齐 + 令牌口径对齐（若它用的是微信令牌而后端要 JWT，如实说明"需先解决登录态载体"，**不要在客户端硬塞 JWT**）；
- **确证已弃用** ⇒ 给出弃用证据并**明确标记/删除**该调用（不许留"看起来能用、实际 404"的入口）。

### E（第 32 项）：`wechat.routes.ts` 的 CSRF —— **按已裁定方案 A 落地**

- `requireWxAuth` 校验通过后**同时设置 `req.user`（最小可用的 AuthUser 形状）与 `req.tenantId`**，然后给 4 个写端点挂 `csrfMiddleware`（**顺序：认证在前**）；
- 🔴 **必须反测**：把 `req.user` 的赋值去掉 ⇒ 挂 CSRF **不该**再"放行即通过"（要用请求证明：缺 CSRF 头 ⇒ 403；带正确 CSRF ⇒ 到业务层）。
