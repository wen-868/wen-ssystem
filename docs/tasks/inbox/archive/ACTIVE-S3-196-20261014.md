## 一、现状（凌舟已实测）

1. **Taro 小程序端（`miniapp/src`）`: `rg csrf miniapp/src` ⇒ **0 命中** —— 客户端**根本不会携带** `x-csrf-token`。
2. **原生 miniapp**：只有 `app.js request()` 全局带；而**通知页等直接用裸 `wx.request` 的调用点不带**（例：`miniapp/pages/notifications/index.js:128-133`）。
3. 后果：凡挂了 `csrfMiddleware` 的**消费者端**写端点，在未改造的调用点上恒 **403**（营销 `claim`/`buy`/`join`、wechat 4 个写端点、通知已读）。
4. 载体问题（第 52 项）：`/api/miniapp/marketing/*` 的"我的"与写端点由 `requireAuthWithTenant` 保护，要的是**商家 JWT**；老端手上只有**微信令牌**（`wxUserId/openid`）⇒ 即便路径对了也 401。

## 二、凌舟已定的方向（照此做，不要另选机制）

- **不换 JWT**，而是新增**消费者身份适配**：让消费者侧端点接受**微信令牌**并解析出绑定的消费者身份（最小可用 `req.user`，`roles` 不含商家角色），注入 `req.tenantId`（来源顺序：令牌 → `X-Tenant-Id` → **不伪造**）。**两者都缺时必须显式失败（400/401）且不落库**，并有用例锁死。
- **CSRF 打通**：登录响应下发 `csrfToken`（复用既有 `generateCsrfToken`）；**所有**消费者端调用点必须经**统一 request 封装**携带 `x-csrf-token`（含原生端的裸 `wx.request` 调用点）；目标是**让每个挂 CSRF 的消费者端写端点真能用**。

## 三、交付物与判据

1. **端点清单**：先枚举「消费者端（`/api/miniapp/**`）挂了 `csrfMiddleware` 的写端点」＋「各端调用它们的位置」，逐条列台账。
2. **客户端改造**：Taro 端 `miniapp/src` 统一封装携带令牌；原生端把所有裸 `wx.request` 写调用点改成带上 `x-csrf-token`。给逐文件 diff。
3. **端到端实证**（每端点）：改造前 403 ⇒ 改造后 200/业务码（真实产物 + 本机库，逐条给原始响应）。
4. **收口第 58 项的豁免**：打通后**删除** `backend/scripts/guard-route-auth.mjs` 里 `R2_EXEMPT` 的**两条豁免**，并给 `notification.routes.ts` 的 2 个写端点补 `csrfMiddleware`（认证在前）；`guard-route-auth` 必须仍 **EXIT=0**（此时靠真覆盖、不靠豁免）。
5. **反测**：① 客户端摘掉 `x-csrf-token` ⇒ 对应端点回到 **403**（红）；② 服务端给 notification 端点摘掉 `csrfMiddleware` ⇒ G3 **红**（红侧由"豁免已删 + R2 逐端点判据"给出）；③ `bind` 两源都缺 ⇒ **显式失败且不落库**。
