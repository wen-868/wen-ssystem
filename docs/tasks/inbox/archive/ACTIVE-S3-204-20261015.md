## 一、凌舟已下的两处判断（照此执行，不要另起口径）

1. **先查现成资产，再谈新建**。我在最近一轮迁移证据里见过 **`t_product_price_log`** 这张表（S3-186 的索引清单里有 `idx_product_price_log_tenant`）⇒ **价格历史很可能已经存在**。第一步必须：列出现有与"销售明细 / 价格 / 调价"相关的**全部表与列**（`information_schema` 原文），并判定"是否已满足需求 2.1 的字段（旧值/新值/时间/操作人/来源/价格等级）"。**已存在 ⇒ 只补缺口，不新建重复表**；确需新建 ⇒ 必须说明"为什么现有表不够"，并走幂等迁移。
2. **契约按 MS 规范落地**：路径用 MS 既有风格（`/api/admin/...`，走 `routeConfigs` 声明式鉴权 + 写端点挂 `csrfMiddleware`），**返回体用 `{ code, msg, data }` 既有包装**；AI 侧给的契约是**建议**，命名/结构以本仓为准并在回执里给出**最终契约**（供 AI 侧照此开发）。

## 二、需求 1：按维度销售时间序列（**只读**）

- 入参：`dimension`（product|sku|category|customer）、`targetId`（必填）、`granularity`（day|week|month）、`start`、`end`。
- 出参：按期序列 `[{ period, qty, amount, orderCount }]`（字段名以 MS 现有销售统计口径为准，**沿用既有字段名而不是新造**）。
- **必须带租户隔离**：走 `queryWithTenant` 或等价（`AND tenant_id = ?`）；**不得**出现跨租户数据（本仓已有 `requireAuthWithTenant`）。
- 判据：近 12 期可返回；与 `querySaleBills`（销售单明细）**交叉核对一致**（给 SQL 对照与数字）；空数据返回**空数组不报错**。

## 三、需求 2：价格历史 ＋ 走势查询

- **2.1 落历史**：任何改价成功后写历史，**两条路径都要覆盖**（后台改价 + AI 改价）；字段含 `sku_id / price_level / old_price / new_price / changed_at / operator / source(admin|ai)`。**若 `t_product_price_log` 已存在且字段够用 ⇒ 只把缺的那条路径接上**。
- **2.2 查询接口（只读）**：入参 `skuId` + 可选 `priceLevel` + `start/end`；出参 `[{ date, priceLevel, price }]`；同样**带租户隔离**。
- 判据：改价后历史表**真有记录**（旧值/新值/时间/来源齐全，给原始行）；查询接口按 SKU 返回时间序列；**两条改价路径都落历史**（各给一次实证）。
