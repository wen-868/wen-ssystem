# R101-S3-213 · 第 67 项「平台 RBAC 后继」凌舟裁定（2026-10-15）

> 来源：S3-193（平台侧权限机制落地）留下的两条后继项；业主已授权我按最优方案决策。

## 一、待决两问

1. **绑定结构**：现复用 `t_platform_admin.role`（一管理员一角色）⇒ 是否改建**独立绑定表**（多角色）？
2. **目录外 4 域**（`library` / `open` / `review` / `miniapp`，共 **28 条**写端点）⇒ 是否扩 `PERMISSION_CATALOG`？

## 二、裁定

**① 绑定结构：暂不建独立绑定表（按需启动）。**
理由：当前生产**唯一平台管理员**是 `PLATFORM_SUPER_ADMIN`（全通），一管理员一角色**足以覆盖现状**；独立绑定表必须**连带做角色管理界面**才有意义（否则界面无处可配），属"为未来需求提前付大成本"。⇒ **登记为"按需启动"**：出现"同一管理员需多角色"或"非超管平台账号需细分授权"的真实需求时再开。

**② 目录外 4 域：**不在商家侧 `PERMISSION_CATALOG` 里扩**，改为在平台侧目录里扩。**
理由（这是关键取舍）：扩商家侧目录会**改"18 条 / 8 域"既有契约 ＋ 8 条断言 ＋ 联动 saas-admin 角色矩阵页**——**为一个平台侧需求去动商家侧契约**是错的方向。而平台侧**已有自己的矩阵结构**（`t_platform_role_permission.module_code`，S3-193 已建），4 个域应当**加在平台侧目录**：
- 平台侧权限点命名沿用既有 `<moduleCode>:<action>`（如 `library:manage` / `open:manage` / `review:manage` / `miniapp:manage`）；
- **不动**商家侧 `PERMISSION_CATALOG` 与那 8 条断言；
- **不动** saas-admin 角色矩阵页的既有契约（新增域由平台侧目录驱动渲染）。

**③ 落地范围（下一单）**：平台侧目录扩 4 域 → 给那 28 条端点按域接线（**逐域分批，每批先做生产角色核对**——这条方法在批 1 已拦下 trace 域的 403 回归）→ 台账与基线同步。

## 三、为什么这样最优（一句话）

**把改动关在"平台侧"这个边界内**：既兑现了"平台侧 105 个写端点要有权限机制"的目标，又**不去动商家侧已冻结的契约与断言**——避免为了一个局部需求引发全局回归。

## 四、附带更正：**"以生产 `information_schema` 为唯一权威"这条不能无条件用**（2026-10-15）

**起因**：S3-212（第 65 项）如实报备"生产库不可达 ⇒ 改用运行期真值"。我用只读通道核了生产，发现 `tenant_id` 的类型**本身就是多宽度**：

```
varchar(36) 245 表 ／ varchar(64) 109 表 ／ varchar(32) 55 表 ／ int 4 表
```

那 4 个 `int` 是：`subscription`、`tenant_admin`、`tenant_module_access`、**`t_tenant_module_access`**。

**反转点**：`t_tenant_module_access` 正是 **S3-194 修过的那张"从来建不出来、终于建成"的表** —— 它的 `varchar(36)` 是**目标形状**（对齐 `t_tenant.id`），**生产里的 `int` 才是遗留漂移**。

⇒ **裁定（同时更正我自己的卡面）**：类型收敛的权威**分两种情形**：
1. **列在生产里被正常建立且被应用正常读写** ⇒ 以**生产真值**为权威（我原卡面的口径适用）；
2. **该表/列在生产里从未被正确建出（历史迁移失败遗留）、或生产自身即漂移** ⇒ 以**意图形状**为权威（对齐被引用列/应用写入形态），**不得**把生产的坏形状当标准抄回语料。

判定方法：拿"该列是否有外键指向 `varchar(36)` 的 `id`"「应用是否写 UUID」作为意图证据；**证据不足时不改**，登记待复核。
