## §2 并入方案与风险说明（交付物②）

### 2.1 本轮结论

**没有"含部署/重启但未入组"的 workflow ⇒ 本轮无可并入对象。** C-2 的 `production-deploy` 组**已覆盖全仓唯一的生产部署路径**，范围外风险为零（截至 main `af1dd244`）。

### 2.2 未来扩展的处理规则（建议固化为规范）

按派单红线「不得为省事把不相关 workflow 硬塞进同一组」，处理顺序应为：

| 情形 | 处理 | 理由 |
|---|---|---|
| 新 workflow / 已有 workflow 新增了**会改变生产运行态**的动作（ssh / pm2 / systemctl / nginx reload / 生产库写入 / 容器发布到生产） | **并入 `production-deploy`**：在该 workflow 顶层加 `concurrency: {group: production-deploy, cancel-in-progress: false}` | 与生产部署互斥，避免"两份部署日志各自成功、生产停半状态"（S3-62 立项动机） |
| 该动作与生产部署**无资源竞争**，但自身需要串行 | **另起独立组**：`group: <动作语义>-production` | 既不与部署互相拖延，又防止自身并发 |
| 纯只读 / 纯构建 / 纯制品上传（CodeQL、e2e 取样、GitHub Release 上传） | **不并入、不另起组** | 无共享可变资源，并入只会造成误排队 |

### 2.3 风险说明

- **R1（组名语义）**：`production-deploy` 的 group 名是**排队身份**，改名＝另起一组，已生效的互斥保护**立即失效**。任何"为了美观重命名"的改动都必须视为破坏性变更。
- **R2（`cancel-in-progress` 必须 false）**：true 会在中途取消部署，留下"拉了一半"的半状态（比串行更糟）。前述 S3-62 已锁定为 `false`，任何并入操作都不得改动这一项。
- **R3（误排队的代价，反对硬塞）**：把不相关 workflow 并入同组会导致**双向拖延**——例如把 `codeql.yml` 并入后，一次静态扫描会排在生产部署之后执行；反过来，一个 8 分钟的 e2e 会把紧急热修部署堵住。**这是本单明确拒绝做的事**，即使那样能让"所有 workflow 看起来都受保护"。
- **R4（`ci.yml` 的特殊性，即使未来"求保护"也不建议并入）**：`ci.yml` 同时由 `pull_request` 触发。若并入 `production-deploy`，**每个 PR 的 CI 都会与生产部署互相排队**，PR 密集期会让部署被反复推迟。故 ci.yml 应保持独立。
- **R5（`deploy.yml` 自身在 `paths-ignore` 内）**：改 `deploy.yml` 不会自动触发部署（`.github/**` 在忽略名单），因此**并入后无法靠"改一次"来验证生效**，验证必须走 `workflow_dispatch` 或等下次真实代码提交。此点在评估任何并入方案时都要计入。
