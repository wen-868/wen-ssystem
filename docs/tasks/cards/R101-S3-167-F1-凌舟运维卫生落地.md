## 一、问题（实测，不是推断）

按「服务器会不会爆」这条线去查，查到的**不是代码问题，是运维累积**：

| 位置 | 清理前 | 说明 |
|:--|--:|:--|
| 服务器 `/root/.npm` | **8.7 GB** | 历次 `npm ci` 的下载缓存，占 40GB 系统盘用量的 ~40% |
| 服务器 `…/liquor-inventory-system/.git` | 61 MB / **20 个 pack** | 每次 `git fetch` 新增 pack，无自动回收 |
| 本地 `wen-ssystem/.git` | **1186 MB / 52 个 pack** | 历次 bundle 中转累积的重复全量包 |
| 服务器根盘 | 40GB，**已用 22G / 剩 17G（57%）** | npm 缓存是最大单一占用项 |

`deploy/auto-deploy.sh` 每次部署都跑 `npm ci`（把依赖下载进 `/root/.npm`），但**从不清缓存、也不回收 git 对象** ⇒ 磁盘只增不减。

## 三、本卡改动（根治，防复发）

`deploy/auto-deploy.sh` 新增「运维卫生」段（20 行，纯追加，位于全部构建之后）：

```bash
NPM_CACHE_MB="$(du -sm /root/.npm 2>/dev/null | cut -f1 || echo 0)"
if [ "${NPM_CACHE_MB:-0}" -gt 3000 ]; then npm cache clean --force >/dev/null 2>&1 || true; fi
git gc --auto --quiet >/dev/null 2>&1 || true
```

设计要点：
1. **超阈值才清（3000MB）** —— 既封住磁盘增长，又保留正常部署的下载缓存加速（不是每次都清空）。
2. **放在全部构建之后** —— 本次部署的安装已用上缓存，清理不影响本次部署。
3. **一律 `|| true`** —— 卫生步骤失败**绝不允许**把一次成功部署判成失败。

## 五、🔴 顺带查出的**新隐患**（已登记，建议另立卡）

**本仓没有 `.gitattributes`，`.sh` 文件的行尾不受保护。**

验证时实测：把 Windows 工作副本（`core.autocrlf=true` ⇒ CRLF）直接 `scp` 到 Linux，`bash -n` 立即报
`syntax error near unexpected token $'do\r'` —— **整段脚本不可执行**。同一次用 LF 副本则 `SYNTAX_OK`。

⇒ 任何人「把本地看到的 `deploy/*.sh` 手拷上服务器」都会踩到，症状还是"部署脚本莫名语法错"。
**建议**：加 `.gitattributes` 钉死 `*.sh text eol=lf`（另立卡，本卡不夹带）。

### 8.2 🔴 首次部署没执行新段 —— 根因是**脚本自更新竞态**

部署日志从 `==> 部署完成` **直接跳到** `==> 工作区自检`（相隔 0.1ms），卫生段回显一条都没有；
而服务器上脚本**确实含**该段（`grep -n '运维卫生' deploy/auto-deploy.sh` → 150 行）。

**根因**：`auto-deploy.sh` 开头 `git reset --hard origin/main` **把正在运行的自己换掉了**；bash 启动时已把脚本读入缓冲 ⇒ **本次调用按旧内容执行**，改动要**下一次部署**才生效。

### 8.3 对照验证（手动再跑一次）

手动触发 `workflow_dispatch` → 部署 `37517078893` **success**，日志如实出现：
```
==> 运维卫生：npm 缓存 / git 对象
  /***/.npm = 660 MB ≤ 阈值 3000MB ⇒ 跳过
  .git = 60 MB
==> 工作区自检（部署不应产生脏改动）
工作区干净 ✅
```
⇒ 卫生段**确实执行**，且阈值分支行为正确（660MB 未超 3000MB，跳过而非清空）。

已立踩坑 **[164]**：改"自己会 `git reset --hard`"的脚本后，**必须再跑一次部署**才算验证通过；首次看不到新逻辑是预期现象。

### 8.5 本卡追加落地：`.gitattributes` 钉 `.sh` 为 LF

新增 `.gitattributes`（`*.sh text eol=lf`）。依据：`git ls-files --eol '*.sh'` 实测索引侧均为 `i/lf`，
但工作副本出现 `w/crlf` 与 **`w/mixed`**（`deploy/02-mysql-backup.sh`、`deploy/06-onepan-bootstrap.sh`）——本机状态已不一致；
而 CRLF 版 `.sh` 送到 Linux 会 `bash -n` 直接失败（§五实测）。**只钉 shell，不做全仓 `text=auto` 重归一化**，避免大面积行尾漂移。
