```
【派单 S3-124】把 `admin-web` 路由守卫里"`userRoles` 为空数组 ⇒ 跳过角色校验直接放行"改为**缺省拒绝**（fail-closed），并补断言锁死。

起跑条件（硬）：**S3-123（Issue #165）合并完成后再开工** —— 两者同属 `admin-web/**` 文件域，避免同域双写。
基线：以起跑当日 `origin/main` 为准（开工第一步 `git log --oneline -1` 自证；并在回传里写明该 sha）

背景与证据（凌舟实测，全部只读）：
  1. **前端守卫现状**（`admin-web/src/router/index.ts:309-316`）：
     `if (allowedRoles.length > 0 && userRoles.length > 0 && !userRoles.some(r => allowedRoles.includes(r))) { 拒绝 }`
     ⇒ `userRoles` 为空数组时**整段角色校验被跳过**，直接 `next()`（**缺省放行**）。
  2. **后端口径不同**（`backend/src/middleware/auth.ts:26-41`）：无角色用户 `getUserAccessInfo` 仍会给一个接入模式
     （`accessModes=["CASHIER"]`，`defaultMode="CASHIER"`）⇒ 后端是"给默认模式"，前端是"不校验"，**两者语义不一致**。
  3. **后端无角色回退**：`auth.service.issueLoginResult`（`:174-186`）的角色只来自 `t_sys_user_role ⋈ t_sys_role`
     （`status` 有效），**没有任何按 `t_sys_user.role` 列的兜底** ⇒ 角色为空是可达状态（例如角色被停用/链接被删）。
  4. **生产可达性（凌舟只读取证，2026-09-26）**：`t_sys_user` 账号 **7** 个，其中"**无有效角色**"的 **0** 个
     （SQL：对每个账号统计 `t_sys_user_role ⋈ t_sys_role` 且状态有效的行数，`SUM(CASE WHEN active_roles=0 ...)`）。
     ⇒ 本项**当前不是生产暴露面**，属**防御性加固**（所以定 P2）；但一旦出现空角色账号，前端会**放行所有页面**，
     而**未接权限点的读接口**（占多数路由）后端也不拦 ⇒ 组合起来是"能看到页面 + 能读数据"。

裁定（凌舟，本卡即裁定）：
  R1. 守卫改为**缺省拒绝**：当 `allowedRoles.length > 0` 且 `userRoles.length === 0` 时，**判为拒绝**
      （提示与既有拒绝分支**同一套**文案/跳转，不新增第二种交互）；
  R2. **不得**改后端 `getUserAccessInfo`（它是"接入模式"提示，不是授权判定）——本单只改前端"授权判定"这一处口径；
  R3. **不得**放宽任何既有允许分支：`userRoles` 非空且命中 `allowedRoles` 的行为、无 `meta.roles` 的路由行为**一字不变**。

交付物：

     并说明命令；用例必须覆盖三分支：命中放行 / 有角色但不命中拒绝 / **空角色拒绝**）；
  ③ 回传卡 `docs/tasks/cards/R101-S3-124-墨回传.md`（照抄下方「回传格式」十项）。
```
