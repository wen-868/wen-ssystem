## 背景与依据（凌舟已取证，非估算）
- AI 底座工具集含 **30+ 个写操作工具**（`create-sales-order` / `create-purchase-order` / `create-refund` / `create-payment-reconciliation` / `create-expense` / `update-product-price` / `inventory-transfer` / `convert-purchase-plan` / `create-sales-return` / `create-purchase-return` 等），均经**唯一执行入口** `src/tools/tool-executor.ts` 的 `executeToolCall()`。
- 该入口已有完整治理链（凌舟已逐行核实）：写全审核门 `:78` → tenantId 校验 `:105` → customerScope 隔离 `:118` → 工具级熔断 `:131` → 执行 `:146`。
- **缺口**：链上无「幂等闸门」。LLM 重试 / 客户端重发 / 网络超时重试 ⇒ 同一业务操作可能**重复落单**（重复销售单、重复退款、重复记账）。
- 前置已就绪：R101-AI-10 共享 Redis provider（`src/common/redis.provider.ts`，按策略分池，长连接 4→2）已收口，**不会再出现第 6 份连接池**。
- 选型已定（业主口径）：**唯一索引落 MySQL 表 + Redis 只做 SET NX 前置闸门**。

## 交付物（一份方案文档 + 一份迁移草案，均不执行）
1. **方案文档** `docs/plans/阶段3-幂等键-方案.md`，须包含：
   - **幂等键的来源与范围**：由谁生成（客户端？服务端？）、键的构成（建议含 tenant_id + tool_name + 业务幂等键）、生命周期（TTL 取值依据）
   - **闸门位置**：在 `executeToolCall` 治理链中的精确插入点（凌舟建议：熔断之后、执行之前，`:131` 与 `:146` 之间）—— 论证为何不放在工具内部
   - **Redis SET NX 前置闸门**：命中/未命中各自的行为（未命中＝重复 ⇒ 返回什么给 LLM？是"幂等成功返回既有结果"还是"拒绝"？**给出建议与理由**）
   - **MySQL 唯一索引兜底**：表设计（列、唯一键、TTL/清理策略）、为何需要它（Redis 宕机/重启后 SET NX 失效 ⇒ 唯一索引是最终防线）
   - **存量影响面**：该改动对既有 30+ 写工具的行为影响（哪些不受影响、哪些需适配）
2. **迁移草案**（**只写不跑**）：`migrations/016_ai_idempotency.sql` 的草案文本，须含 `CREATE TABLE IF NOT EXISTS` + 唯一键 + 索引，**不得执行**。
3. **风险与回滚**：迁移的回滚语句；若唯一索引上线后存量脏数据导致建索引失败，如何处理（预检 + 处置方案）。
