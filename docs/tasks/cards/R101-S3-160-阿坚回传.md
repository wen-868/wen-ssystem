## 五、风险与自我报备

1. **与《项目统一标准》§11.3-2 的冲突（已按卡执行，主动报备）**：标准写"JWT mock：使用 vitest mock 模块，**不在测试中生成真实 token**"；本单卡④明确要求"用真实 `jwt.verify` 解，不许只断言 mock 调用参数"。我以卡为准（卡更具体、更新、且是验收标准③），新单测文件因此**真实签发 token 再用 `jwt.verify` 解**。若凌舟裁定标准优先，请回卡，我改为旁路取证（装置里做真实解，单测只做参数断言）——但那样验收标准③就落不到单测上，请一并明确口径。
2. **响应新增字段 `expiresIn` 的契约影响**：这是**新字段**（`{token,user,csrfToken,expiresIn}`），前端 S3-161 未在本单范围；旧客户端忽略未知字段不受影响。字段值与实签 TTL 同源（同一 `rememberMe` 布尔决定），**不含任何密钥信息**。按红线①只能等凌舟登记 API 文档。
3. **`expiresIn` 的"同源"边界（我发现的实现细节，如实报备）**：`expiresIn` 由 `rememberMe` 布尔计算，TTL 由同一布尔挑常量 —— 真实代码里两者恒一致；但反测把**常量**改成 30d 时，`expiresIn` 仍报 14400（因为它不看常量）。即：若将来有人只改常量不改 service，会出现"字段与实签不一致"。本单未引入该问题（默认就是 4h）；如需彻底同源，可把秒数也放 `middleware/auth.ts` 与常量并列（我未擅自扩大改动面）。
4. **长效 token 的既有副作用被放大（需产品知情）**：踩坑日志既有结论——**权限串签进 JWT（原 4h）**，改权限/角色后必须重新登录才生效。勾选「记住我」后该延迟从最长 4h 变为最长 **30d**（本单不加 refresh，符合卡内"不加 refresh 机制"）。若后续要做"权限变更即时生效"，属另一立项。
5. **未改动的相邻点（明确声明，便于凌舟抽验）**：未动 `signPlatformToken`（平台端 8h）、未动 `services/store/auth.service.ts`（其 `login` 不被 `/api/store/auth/login` 使用，避免扩大范围）、未动 `demoLogin`、未动 MFA 路径（仍 4h）、未动前端三端、未改表、未加 refresh、未碰 `docs/migrations/**`、`.github/**`、`deploy/**` 及任何共享文档。
6. **`backend/src/middleware/auth.ts` 文件末尾补了一个换行**（原文件 `\ No newline at end of file`）。属编辑同类文件时的行尾规范化，无语义；如凌舟要求零字节噪声可回退。
