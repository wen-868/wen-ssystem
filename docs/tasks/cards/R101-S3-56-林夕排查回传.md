### 1.3 关键事实（推翻原假设的根因）

1. **生产存在「两套」表**：
   - 无前缀：`tenant`(id `int`)、`subscription`(id `int`)、`subscription_plan`(id `int`)、`retail_order`(id `bigint`)、`product_sku`(id `bigint unsigned`)
   - 带前缀：`t_tenant`(id `varchar(36)`)、`t_subscription`、`t_subscription_plan`、`t_retail_order`、`t_product_sku`
2. **迁移文件的 FK 全部引用「无前缀」表名**（`tenant`/`subscription`/`retail_order`/`subscription_plan`），生产里这些无前缀表确实存在，所以 FK 实际指向无前缀表。
3. **原假设「t_tenant.id=varchar(36) 被 INT 引用」错在**：迁移 016/032/034 的 FK 引用的是 `tenant`(**int**)，并非 `t_tenant`(**varchar(36)**)。因此在「被引用列 = `tenant.id`(int)」口径下，`t_tenant_module_access.tenant_id`(INT) **并不错配**；而 `t_tenant_admin.tenant_id` 在生产已被后续迁移（如 `169_tenant_admin_uuid.sql`）改为 `varchar(36)`，同样**无错配**。
4. **真正在生产成立的类型错配只有两条**：`t_retail_order_item.order_id` 与 `t_delivery_record.order_id` 写成 `int`，但其逻辑父 `retail_order.id`(及 `t_retail_order.id`) 为 `bigint`。这两列**无强制 FK**（仅普通索引），属「逻辑外键 + 类型不一致」，JOIN 时会触发隐式转换、且 `order_id` 取值超过 2,147,483,647 会溢出 int。

## 2. MySQL 8 改列类型代价评估（仅针对真实错配 #6、#7）

目标类型：`t_retail_order_item.order_id` → `BIGINT`；`t_delivery_record.order_id` → `BIGINT`（与 `retail_order.id` 对齐）。

- **能否 `ALGORITHM=INPLACE` / `LOCK=NONE`？**
  `int` → `bigint` 属于「改列数据类型且存储尺寸变大」，**MySQL 8.0 不支持 INPLACE**，必须 `ALGORITHM=COPY`（整表重建 + 长时间锁）。
  - MySQL 8.0 Online DDL 规则：列类型变更（尺寸变化）走 COPY，期间写被阻塞（至少 `LOCK=SHARED`，写阻塞；无法 `LOCK=NONE` 在线）。
  - 判据：仅当新类型可在原行内原地表示（如 `VARCHAR` 长度在同源字节上限内扩、或 nullable 变更等）才可 INPLACE；`INT→BIGINT` 不满足 → **必须 COPY**。
- **锁表时长量级（估算！非实测）**：
  - 当前两表均 **0 行 / 16KB**，COPY 重建 **< 1 秒**，写阻塞窗口亚秒级，几乎无感。
  - 若未来有数据，时长 ≈ 行数 × 行宽 ÷ 重建吞吐；实例 `innodb_buffer_pool_size=128MB` 偏小，大表重建会受 buffer pool 与 IO 制约，量级需以实测为准。
- **实例参数（生产实测）**：
  - `version` = `8.0.46-0ubuntu0.24.04.2`
  - `innodb_buffer_pool_size` = `134217728`（128 MB）
  - `innodb_online_alter_log_max_size` = `134217728`（128 MB，仅 INPLACE 在线 DDL 用；COPY 不走此日志）
  - `innodb_buffer_pool_instances` = `1`
- 🔴 **未在生产执行任何 ALTER**（红线）。以上为基于 MySQL 8.0 online DDL 文档规则的推算，非实测。

在副本（从库 / 备份恢复库）上验证，判定标准可勾选：

- [ ] 校验与父一致：`SHOW COLUMNS FROM t_retail_order LIKE 'id';` 期望 `bigint`，确保 `order_id` 与 `id` 同为 `bigint`
- [ ] 校验无孤儿：`SELECT COUNT(*) FROM t_retail_order_item oi LEFT JOIN t_retail_order o ON oi.order_id=o.id WHERE o.id IS NULL;` 期望 `0`（当前 0 行应得 0）
