---

## 0. 一句话结论

`.github/workflows/deploy.yml` **没有 `concurrency:` 组**。
往 main 连推两笔（或连合两个 PR）→ 跑出**两个并发的生产部署**：两次 `git fetch` / `reset --hard` + 前端重建 + pm2 重启 + nginx reload **在服务器上互相打架**。

---

## 1. 证据

| 项 | 内容 |
|---|---|
| 文件 | `.github/workflows/deploy.yml` |
| 触发器 | `push: branches: [main]`（带 `paths-ignore`）+ `workflow_dispatch` |
| `concurrency:` | **不存在**（已逐行确认，全文 39 行，jobs 下只有 `deploy` 一个 job） |
| 已验证 | 2026-09-19 凌舟连续合并 PR #20（`e9f54b25`）与 PR #16（`de46b46d`），**靠人工串行**（合一个、等 Auto Deploy 绿、再合下一个）才没撞上 |

**为什么这不是理论风险**：deploy job 的脚本是 `cd /opt/zhixiang/liquor-inventory-system && bash deploy/auto-deploy.sh`。
两个实例同时执行时，以下步骤会交错：

1. `git fetch` + `reset --hard`（第二次可能拉到第一次还没拉完的引用 → 半状态）
2. 前端重建（同一 `dist` 目录被两个进程写）
3. `pm2 restart`（重启到一半被另一个重启打断）
4. `nginx reload`（配置可能落在两次之间的中间态）

⇒ 最坏结果是**生产停在一个既不是旧版也不是新版的半状态**，且两份部署日志各自显示"成功"。

---

## 2. 修法（凌舟给定，照此实施）

```yaml
concurrency:
  group: production-deploy
  cancel-in-progress: false
```

🔴 **`cancel-in-progress: false` 是硬要求，不能图省事改成 `true`。**
理由：中途取消会留下「拉了一半」的半状态 —— 那比串行更糟。
`false` 的语义是**排队**：第二次部署等第一次跑完再开始。

放置位置：workflow 顶层（`on:` 之后、`jobs:` 之前），对整个 workflow 生效。

## 3. 验收标准（🔴 必须含反测，未反测＝未验收）

| # | 标准 | 门槛 |
|---|---|---|
| 1 | **反测**：故意连推两笔**非文档**提交 | 第二次部署必须显示 **queued**，且**不是**与第一次并发执行。要在 Actions 页面拿到两个 run 的时间线证据（第一个 running 时第二个是 queued/pending） |
| 2 | 反测走**分支 + PR**，不污染 main | 反测用的提交不能推 main（那会真的部署两次） |
| 3 | 确认 `cancel-in-progress: false` 语义生效 | 第一个跑完后第二个**照常执行**（排队，不是被取消） |
| 4 | 不得为满足门槛而放宽断言、`|| true`、跳过检查 | — |

⚠️ **只看到 `concurrency` 字样不算。** 这是门禁铁律的延伸：验证必须有预先约定的判定标准，且必须证明它会生效。

**反测怎么在不污染 main 的前提下做**：改一个会触发部署的非文档文件（如 `deploy/auto-deploy.sh` 里加一行 echo），在同一 PR 里连推两笔，观察 Actions；验证完把这个 PR 关掉不合并。
