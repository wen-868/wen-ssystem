## 一、问题：不是"沉默"，是"给出一条具体但错误的线索"

2026-09-16 22:30 一次真实部署（run `35108691110`）里，服务器到 GitHub 出现瞬时 TLS 抖动：

```
==> [AI底座] 更新独立仓库 /opt/zhixiang/ai-base
fatal: unable to access 'https://github.com/wen-868/ZXQL-AI.git/':
       GnuTLS recv error (-110): The TLS connection was non-properly terminated.
HEAD is now at 8884b8c security(S3-35): ...        ← 旧 commit
```

**`fetch` 失败了，却没有任何失败标记**，流程照常往下走，最后 `ai_fail` 报出的是：

> `pnpm install --frozen-lockfile 失败（多为 ZXQL-AI 的 pnpm-lock.yaml 与 package.json 不同步）`

→ **把"网络拉取失败"报成了"lock 失同步"。** 排查者第一眼就被推向"去重算 lock"的方向。

**根因就两行**（原文，已取证）：

```bash
git -C "${AI_TARGET_DIR}" fetch origin main 2>&1 | tail -3 || true
git -C "${AI_TARGET_DIR}" reset --hard origin/main 2>&1 | tail -3 || true
```

`|| true` 吞掉 fetch 失败 → 紧接着 `reset --hard origin/main` 落到 **本地已过期的 remote-tracking 引用**
（fetch 失败时 `origin/main` 不会更新）→ **拿旧代码继续跑**。

**定性**：与 [71]「假 CI 门禁」、[74]「失败当成功」同族（"报错/绿灯 ≠ 真实状态"），
但**更隐蔽** —— 前两条是"沉默/假绿"，这条是**主动给出错误线索**，
会把人推向错误的修复方向，比不报错更贵。

## 二、修复（逐条对应凌舟给定的 5 条口径）

| # | 要求 | 落实 |
|---|---|---|
| ① | fetch 失败即**显式失败**，且**不得再 reset** | `if git fetch … >"$FETCH_LOG" 2>&1; then … else ai_fail "拉取 ZXQL-AI 失败（… 已保留现有代码、未做 reset）：$FETCH_ERR"; fi` |
| ② | 用 `FETCH_HEAD`，或仅在 fetch 成功分支内 reset | 两个都做了：reset **只在成功分支内**，且目标是 **`FETCH_HEAD`**（不依赖可能过期的 `origin/main`） |
| ③ | 打印**拉到的 commit** | 成功分支打印 `==> [AI底座] 已重置到 <git log --oneline -1>`；另打印 `远端 origin = <url>` |
| ④ | `ai_fail` 文案**区分**"拉取失败"与"lock 失同步" | 拉取失败＝"拉取 ZXQL-AI 失败（…）"；pnpm 失败＝"lock 与 package.json 的 overrides 不一致（…）"，并补上 S3-43 的排查要点（**pnpm 9 只读 `package.json#pnpm.overrides`**） |
| ⑤ | `AI_REPO_URL` 改 **SSH** | `AI_REPO_URL="${AI_REPO_URL:-git@github.com:wen-868/ZXQL-AI.git}"`（可用环境变量覆盖，便于临时切回 HTTPS 排障） |

**⑤ 的一个必要补充（容易漏）**：老检出是 **HTTPS 克隆**的，**只改 `AI_REPO_URL` 变量不会影响已存在 remote 的 URL**
→ 必须显式 `git remote set-url origin "${AI_REPO_URL}"`，否则"把远端切到 SSH"这一步等于没做。已加。

**⑥ 我加的第 6 条（超出你给的 5 条，请裁定，可驳回）**：

```bash
export GIT_SSH_COMMAND="${GIT_SSH_COMMAND:-ssh -o BatchMode=yes -o ConnectTimeout=15}"
```

理由：**切到 SSH 会引入一个新的失败模式 —— 挂死**。
`ssh` 在需要交互（未知 host key、密钥口令）时会等待输入，而部署是自动化、没人应答 →
会把整条部署**挂住**（比原来的 90s 超时失败更糟）。`BatchMode=yes` 禁止一切交互提问、
`ConnectTimeout=15` 限制连接阶段挂死，与本次"让失败快速且显式"的方向一致。

另外 `clone` 分支（无 `.git` 时）原先也是 `|| true` 吞失败 → 同样改为显式 `ai_fail` 并打印检出到的 commit。
