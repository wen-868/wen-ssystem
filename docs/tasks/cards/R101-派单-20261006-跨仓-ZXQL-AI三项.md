## 一、三项（按阻塞程度排序）

### ① 🔴 迁移注释非法（**最急**：卡住 `deploy/ai-base-deploy.sh` 的迁移步骤）
| 位置 | 现状 | 要求 |
|:--|:--|:--|
| `migrations/007_e5_auto_close.sql:7` | 注释写成 `--（MariaDB 语法）…`（`--` 后**直接跟中文**、无空白） | 改为 `-- （…`（**只加一个空格**，注释内容不变） |
| `migrations/009_audit_lane_categories.sql:9` | 同上（`--（见 src/database/database.module.ts …`） | 同上 |

**为什么急**：MySQL 要求 `--` 后至少一个空白/控制字符才是注释，否则**整行被当 SQL** ⇒ `ERROR 1064`。凌舟 2026-10-05 手工执行时是靠"执行时临时归一化"绕过的；一旦 wen-ssystem 的 `deploy/ai-base-deploy.sh` 迁移步骤（S3-166 / PR #263）合入，**每次 AI 底座部署都会炸在这两个文件上**。
**验收**：`mysql < 007_e5_auto_close.sql` 与 `mysql < 009_audit_lane_categories.sql` 在**已应用过的库**上重跑 ⇒ **不报 1064**（应输出"已存在，跳过"之类）。

### ② 🔴 迁移幂等（`004` / `005` 裸 `ADD COLUMN`）
| 位置 | 现状 | 要求 |
|:--|:--|:--|
| `migrations/004_platform_ai_config_fallback.sql`、`005_session_archive_billing.sql` | 直接 `ALTER TABLE … ADD COLUMN`，**无 `information_schema` 判定** ⇒ 生产已应用过，重放报 **1060 Duplicate column** | 按 `007~011` 已有写法补 `information_schema` 判定 + `PREPARE` 动态 SQL，做到**可安全重复执行** |

**为什么**：S3-166 已加"窄口径容忍 1060/1061/1050/1091"，但那只是**兜底**；根因是这两个文件不幂等，容忍会让"真有列冲突"的新问题也被吞掉的风险变高。
**验收**：对同一库**连跑两遍** `004`、`005` ⇒ 第二遍**零错误码**（不是靠容忍），并打印"已存在，跳过"。

### ③ 该仓**没有任何 CI**（S3-37）
**现状**：`ZXQL-AI` 无 `.github/workflows/`（对账表 §三·C#25 取证）。而它是**生产在跑的 AI 底座**（`/opt/zhixiang/ai-base` 检出该仓），改动直接影响生产却零自动校验。
**要求**：新增最小 CI（PR + main）：`install`（`npm ci` 或 `pnpm i --frozen-lockfile`，按该仓实际包管理器）→ `build` → **单测**（该仓已有大量 `*.spec.ts`，跑 `jest`/`vitest` 按实际配置）。**必须阻断**（不得 `continue-on-error`）。
**验收**：CI 在该仓最近一次 PR 上跑出 **build + 单测**结论（贴 run 链接）；并在 PR 描述里附"故意改坏一个单测 ⇒ 该 job 必须红"的证据（至少一次反测）。
