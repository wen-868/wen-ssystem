## 四、这组数字对阶段一的直接含义（供实现方照做）

1. **app-mobile 当前的可见性 = 前缀级**：只要用户持有某前缀（如 `goods`），该前缀下**所有**页面都可见——包括上面 25 个"生产没有对应菜单行"的页面。
2. **一旦把判定改成"按页面 code 精确匹配"，这 25 页会立刻对所有人不可见**（因为它们在菜单表里不存在，谁来都没这个码）。
3. ⇒ 阶段一**必须**先补这 25 个码，并按"现状等价"分配角色（等价规则见派单卡：**持有该前缀的角色 ⇒ 补码后持有该码**），否则就是**行为变更**，与派单卡 §二"逐格不变"的硬判据冲突。
4. **不得**用"给所有人补全部码"来图省事：那会让 `STORE_OPERATOR` 多出 `finance*` 等页面，**同样**是行为变更。
5. 补码走**迁移文件**（`docs/migrations/**`），由凌舟在生产链路执行；**执行方不得连生产库**。

> 口径提醒：`SUPER_ADMIN` 在生产**0 条菜单行**，说明超管不依赖菜单表 ⇒ 对照表里超管的"可见性"应按**现状实现**（若现值是全可见，则取全可见）单独确认，**不要**按"0 条 ⇒ 全不可见"推。
