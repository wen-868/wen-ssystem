## 二、⚠️ 先报一项「我自己造出来、已回退」的设计缺陷

**原设计**：把组1 无结构化列承载的配置项（API 日额度 / AI 月额度 / 升级 / 降级 / 续费 / 限时活动）塞进 `t_subscription_plan.features` 的 JSON 包。

**为什么必须回退**（两条硬证据）：

1. 该列**生产语义是「功能特性码数组」**——种子数据就是
   `'["basic_sales","basic_inventory","basic_report"]'`（`docs/migrations/016_phase9_tenant_subscription.sql:172`）；
2. 公开端点 `GET /api/platform-miniapp/plans`（`auth: none`，`platform-miniapp.service.ts:139` `features: parseFeatures(row.features)`）
   **原样透出该字段**。塞入内部配额与策略＝**泄露给未鉴权调用方**，同时破坏对外展示。

**修正**：策略类配置改落 **`t_platform_config`**（`platform='SAAS'`、`tenant_id='platform'`、
`config_key='plan_policy:<planId>'`、`category='plan'`）——与 R97-01 `saas_settings` **同表同约定**，
**零 DDL、零索引变更**，符合口径 X 与护栏①。`features` 列恢复为 `z.array(z.string())`。
详见 `docs/配置项契约登记表.md` §2.5 与踩坑日志 [64]。

> 附带修正：我此前在 API 文档里误写公开端点为 `/api/miniapp/plans`，真实路径是 `/api/platform-miniapp/plans`，已订正。

## 三、组1（套餐类）落库闭环

### 3.1 新增端点（2 个，零 DDL）

| 端点 | 说明 |
|---|---|
| `GET /api/platform/subscriptions-management/plans/:planId/policy` | 读策略包；未配置返回 `{version:1,_unconfigured:[全部],_configured:false}` |
| `PUT .../plans/:planId/policy` | 整包保存；`planPolicySchema` zod 校验，越界枚举/负数额度→400 |

（同一 controller 另有 `/api/platform/plans` 前缀存量，新端点两个前缀均已挂载。）

### 3.2 护栏落实

| 护栏 | 落实方式 |
|---|---|
| ① 不建表 | 复用 `t_platform_config` 既有列（`config_key`/`config_value`/`category`/`updated_by` 由 `152_business_columns_fill.sql` 补齐） |
| ② 契约先行 | 独立提交 `6536b4ad`，先登记《配置项契约登记表》再动代码 |
| ③ zod + version | `planPolicySchema`；`version` 缺省/非法值规范为 1；`updated_by = req.user?.username ?? 'system'` |
| ④ 未配置≠已配置 | `_unconfigured` / `_configured` 只读元字段（`_` 前缀）；`null` 与元字段不落库；**清空全部＝写入 `{version:1}`，不固化占位值** |
| ⑤ 无 DDL | 本批 **0 条 DDL**，无需登记《数据库变更清单》 |

### 3.3 顺带修掉的「原会 400」契约不一致

- `planType` 补齐 `QUARTERLY` / `PERMANENT` / `CUSTOM`（原仅 3 个值，前端选季付/自定义会 400）；
- `status` 补齐 `DRAFT` / `INACTIVE`（原只有 ACTIVE，「存为草稿」会 400）；
- `POST /plans` **补返回 `id`**（向后兼容，原只返回 `plan_code`）——否则新建后拿不到主键，策略包无从落库。

- `PackageForm.vue`：保存主记录后**单独 PUT 策略包**；失败**不跳转**，内容区显示错误态（遵守「双 toast 收敛口径」，不重复弹窗）；

## 五、未达成 / 需裁定（不擅自改）

### 5.1 `module_access` 存的是中文功能特性文案，而生产消费方按「模块码」使用 —— 存量缺陷，越出本批边界

- 现象：前端 `PackageForm` 把 23 项功能特性的**中文条目名**写入 `module_access`（**存量行为，本批未改**）；
- 但生产消费方把它当模块码用：
  `subscription.service.ts:264-268` 与 `subscription-renewal.service.ts:124` 均为
  `for (const mod of modules) INSERT INTO t_tenant_module_access (module_code, module_name) VALUES (mod, mod)`
  → `module_code` 会写入中文文案，与 `t_module.module_code`（如 `sales` / `inventory`）不一致；
- 影响面：租户开通/续费时的**模块授权落库**，属跨服务数据语义问题；
- **请求裁定**：是否在本批修正（需同时改前端写入口径 + 存量数据订正迁移），或另立卡。

### 5.2 卡面「28 项」vs 设计稿实际「23 项」

- 功能开关矩阵按设计稿为 **5 组 / 23 项**，`TOTAL_FEATURE_COUNT` 现按 23 动态计算；
- 卡面口径「28 项配置项」若指全部 10 组，**与组1 矩阵项数不是同一口径**，请确认以哪个为准（涉及后续各组计数文案）。
