## 一、先认我自己的错：**卡面 §一 的库值前提写错了**

我的卡面写「`t_tenant.status` 存字符串，`WHERE … status = 'ACTIVE'` 即是反证」，并要求「status 落 `'DISABLED'`」。
**这个反证是错的**：在 TINYINT 列上做字符串比较会**隐式转换**，`= 'ACTIVE'` 恒不成立/恒成立都不说明列类型。执行方用 5 条权威证据推翻了我的前提：

1. 权威建表 `backend/src/shared/migration.ts:539` 与 `docs/migrations/092_租户ID.sql:76` 均为 **TINYINT**；
2. `docs/evidence/MIG-1/outputs/02-plan.json:2043` 注记「与 092 迁移及生产一致」；
3. `docs/tasks/cards/R101-C4-0-阿坚清账.md:437`（A7）判 `t_tenant.status` 为 TINYINT；
4. `docs/migrations/169_tenant_admin_uuid.sql` 的生产注释：写 `'ACTIVE'` 字符串 ⇒ **500**；
5. S3-150 真库实测写字符串 ⇒ **`ER_TRUNCATED_WRONG_VALUE_FOR_FIELD(1366)`**。

**结论：执行方按真实 schema 落地是对的，且这是必须的行为**（要是我坚持字面口径，端点会恒 500）。
**教训（我写进踩坑日志）**：凌舟的卡面**不得凭一句 SQL 片段反推列类型**；凡涉及"库值/枚举"的派单，必须写明"以真实 schema 为准，先查 `information_schema` 再落地，前提不符就停下报备"。这条正好被本次证明有效——执行方**照做了并报备**。

## 三、裁定

**① 越界入参处置：取方案 (b)「400 拒绝」⇒ 认可。** 理由：拒绝比静默改写更不会掩盖调用方错误；「暂停/到期停用」用既有 `suspend_reason` + `suspended_at` 表达，`status` 只落 ACTIVE/DISABLED（与 S3-150 既有口径一致）。

**② 迁移 199 的判据：认可「按字符串比较」而不是照我卡面字面执行。**
理由（执行方给的论证我复核认可）：字面执行 `status IN ('EXPIRED','SUSPENDED')` 在 TINYINT 上会隐式转成 `status = 0` ⇒ **命中所有本来就停用的行**、把 `suspend_reason` 一并改写，且**第二遍仍有变更（不幂等）**。改成字符串比较后：TINYINT 形态下 `CAST(status AS CHAR) ∈ {'1','0'}` ⇒ 越界判据恒不命中 ⇒ **迁移是 no-op（当前生产形态安全）**；VARCHAR 老库形态下才真正订正。

**③ 迁移 199「不做的事」：认可**（不在迁移里批量停用"订阅已到期但仍启用"的租户——那是订阅到期作业的职责；该作业此前因 1366 恒失败，本单已修 ⇒ 部署后由作业自愈）。

**④ 门禁改写：认可，并作为**方法**沉淀。** 我把两条写进踩坑日志：**(a)** 例外条目**不得用行号**定位（会静默失效/错放行）；**(b)** "经服务层写"的 controller 入口是 R3 类机械信号的**已知盲区**，需显式清单补入。

**⑤ 本单不新增收口项**（执行方提出的 controller Zod 第二套取值已在 R4 收编处理）。
