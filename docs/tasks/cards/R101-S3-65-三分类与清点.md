## 三、marketing-points 存量脏数据：只读清点 SQL + 判据（不连生产）

### 三.1 事实与代码依据（为什么会有脏数据）

| 项 | 依据 |
|---|---|
| 扣减语句（命中集 #19） | `backend/src/services/admin/marketing-points.service.ts:292-296`：`UPDATE t_user_points SET points = ?, total_spent = total_spent + ? WHERE user_id = ?`，实参 `[newBalance, points, userId]` |
| 病灶 | 修复前 `injectUpdateTenant` 把 `tenantId` 前置 ⇒ `SET points = <tenantId>`、`WHERE id/user_id = <points> AND tenant_id = <userId>` ⇒ **静默 0 行**（`database.ts:281` 修复前写法） |
| 为什么同函数 INSERT 不受影响 | `:300-303` 的 `INSERT INTO t_points_record (..., tenant_id) VALUES (...)` **自带 `tenant_id`** ⇒ 注入短路 ⇒ 修复前也能正常写流水 |
| 结论 | 修复前每一次"积分兑换"都会：**流水写入成功、余额与累计消耗未变** ⇒ "流水已记、余额未扣"，且 `total_spent` 同样漏加 |

### 三.2 只读清点 SQL（4 段，可直接在生产只读执行；**不给连接命令**）

```sql
-- Q0 前置：确认生产库 t_points_record 的列族是否齐全（只读）
SELECT ORDINAL_POSITION, COLUMN_NAME, DATA_TYPE, IS_NULLABLE
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 't_points_record'
ORDER BY ORDINAL_POSITION;

-- Q1 逐条候选：确认异常（"流水已记、余额未扣"）明细
SELECT r.tenant_id, r.user_id, r.id AS record_id, r.created_at,
       ABS(r.amount) AS lost_points, r.balance AS recorded_balance_after,
       p.points AS actual_points, p.total_spent AS actual_total_spent, p.updated_at AS points_updated_at
FROM t_points_record r
JOIN t_user_points p ON p.tenant_id = r.tenant_id AND p.user_id = r.user_id
WHERE r.user_id IS NOT NULL
  AND r.type = 'SPEND'
  AND r.source_type = 'REDEEM'
  AND r.amount < 0
  AND p.points = r.balance + ABS(r.amount)
ORDER BY r.tenant_id, r.created_at, r.id;

-- Q2 汇总：异常条数 / 涉及会员数 / 未扣减积分总量 / 时间窗
SELECT COUNT(*) AS suspect_records,
       COUNT(DISTINCT CONCAT(r.tenant_id, '|', r.user_id)) AS affected_members,
       COUNT(DISTINCT r.tenant_id) AS affected_tenants,
       SUM(ABS(r.amount)) AS lost_points_total,
       MIN(r.created_at) AS first_seen_at, MAX(r.created_at) AS last_seen_at
FROM t_points_record r
JOIN t_user_points p ON p.tenant_id = r.tenant_id AND p.user_id = r.user_id
WHERE r.user_id IS NOT NULL AND r.type = 'SPEND' AND r.source_type = 'REDEEM'
  AND r.amount < 0 AND p.points = r.balance + ABS(r.amount);

-- Q3 全量对账：以 user_id 家族流水重放，核对当前余额与累计消耗（含非单笔差额的疑似异常）
SELECT p.tenant_id, p.user_id, p.points AS actual_points, p.total_spent AS actual_total_spent,
       COALESCE(SUM(CASE WHEN r.type = 'EARN' THEN ABS(r.amount)
                         WHEN r.type = 'SPEND' THEN -ABS(r.amount) ELSE 0 END), 0) AS ledger_net,
       COALESCE(SUM(CASE WHEN r.type = 'SPEND' THEN ABS(r.amount) ELSE 0 END), 0) AS ledger_spent,
       COUNT(r.id) AS ledger_rows
FROM t_user_points p
LEFT JOIN t_points_record r
       ON r.tenant_id = p.tenant_id AND r.user_id = p.user_id AND r.user_id IS NOT NULL
GROUP BY p.tenant_id, p.user_id, p.points, p.total_spent
HAVING p.points <> ledger_net OR p.total_spent <> ledger_spent
ORDER BY ABS(p.points - ledger_net) DESC;
```

**SQL 行数**：代码块共 **42 行**（含 2 行空行分隔），按语句拆分为 Q0 **5** 行 + Q1 **12** 行 + Q2 **10** 行 + Q3 **13** 行 = **40 行 SQL（4 段）**；均为 `SELECT`，无任何写语句、无 `INTO ... OUTFILE`、无临时表。

### 三.3 判据（期望值怎么算 / 异常怎么定义）

1. **期望值怎么算（单条口径，最可靠）**：`createPointsRedeem` 先用 `newBalance = 交易前余额 − points` 计算，再把**同一个 `newBalance`** 分别写进 ① UPDATE 的 `points`（`marketing-points.service.ts:293`）和 ② 流水的 `balance`（`:301`）。因此**该笔流水的 `balance` 就是"这笔兑换之后应有的余额"**；若 UPDATE 真生效，`t_user_points.points` 必然等于该 `balance`。
2. **异常怎么定义**：
   - **确认异常**＝`现在 points = 该笔 balance + |amount|`（差额恰好等于本次扣减额）⇒ 该笔扣减**完全没生效**，Q1 命中即此类。
   - **疑似异常**＝Q3 `HAVING` 命中但 Q1 未命中（差额≠任一单笔金额）⇒ 可能是"另有收支路径未写流水""人工调账""另一列族（`customer_id`/`points`）混写"等，**只登记不自动修**。
   - **非异常**＝差额为负（`points < balance`，余额比流水更少）⇒ 可能已被人工补扣或另有扣减，**不得计入异常**。
   - **前置缺口**＝Q0 显示 `user_id`/`amount`/`balance` 列缺失或全为 NULL ⇒ 该库为旧列族（`customer_id` 系），本次清点**不适用**，需先跑迁移 151 再清点。
3. **涉及会员数**：Q2 的 `affected_members`（`tenant_id + user_id` 去重），不要用 `COUNT(DISTINCT user_id)`——`user_id` 在不同租户下可重复。
4. **清点后如何修复（两种可选策略，各自风险）**：

   | 策略 | 做法 | 风险（必须逐条认领） |
   |---|---|---|
   | **A 逐用户重放对齐（推荐）** | 以该用户 `user_id` 家族流水的最后一笔 `balance` 为准修正 `t_user_points.points`；`total_spent` 按 `SUM(ABS(amount)) WHERE type='SPEND'` 修正 | ① 前提是 `user_id` 家族流水自用户注册起**完整且按时间单调**——若期间有其它路径改积分却不写该流水（例如 `customer-care.service.ts:151` 改的是 `t_customer_points`），重放会算错；② 清点与修复之间仍有新写入，必须以"清点水位线（max record id）"为界做增量重算，否则修完立刻又不一致；③ 修前必须留备份（先导出 Q3 结果 + 相关行），否则不可回滚 |
   | **B 逐条补扣（最小改写）** | 对 Q1 每条命中记录执行一次 `UPDATE t_user_points SET points = points - ABS(amount), total_spent = total_spent + ABS(amount) WHERE tenant_id = ? AND user_id = ?` | ① 只处理"差额恰好等于单笔金额"的记录，**漏掉 Q3 的疑似异常**（差额由多笔叠加时不会命中 Q1）；② 同一用户多笔命中时逐条相减可能把余额减成负数（无余额下限保护），需先按用户汇总再决定；③ 不修正非兑换类漏账；④ 修复后**必须复跑 Q1 断言为 0 行**，否则等于没修（技术债铁律：不允许"绕过当修复"） |

   > 两策略共同红线：**只允许改 `t_user_points`，不允许改写/删除已存在的 `t_points_record` 流水**（流水是账，`balance` 字段本身是正确的"应有值"）；修复动作必须可复算、可回滚、有前后对比证据。

### 三.4 明确无法在静态层面确定的部分（不得当结论使用）

1. **生产库实际是否有命中数据**：本卡未连库，Q1/Q2 的结果数、涉及会员数、金额总量**全部未知**，只能由执行清点的人回填。
2. **流水 `balance` 字段的历史语义是否恒定**：本卡只证明了"当前代码把 `newBalance` 写进 `balance`"；历史版本是否曾写别的值（例如某些版本写 `balance_after`/`points` 或 0）**无法从静态层确认**，需抽样比对（抽 5～10 条 EARN/SPEND 记录逐笔手算）。
3. **两列族是否混写**：`t_points_record` 同时存在 `user_id`/`amount`/`balance`（小程序会员系，迁移 108）与 `customer_id`/`points`/`balance_after`（admin 旧营销系，`services/admin/points.service.ts:115`）——**生产库里两族的写入分布未知**，Q1/Q2 只统计前者；若后者也参与同一会员余额，清点口径需扩大。
4. **迁移 151 在生产是否已执行**：`t_points_record` 缺失列与索引由迁移 151 幂等补齐（见 `docs/验收总览报告.md` 第 13 项、`backend/src/__tests__/shared/migration-points-columns.test.ts`），**生产是否已跑过 151 未验证** ⇒ 先跑 Q0 判定。
5. **`t_user_points` 唯一约束在生产是否成立**：表定义有 `uk_user_points (tenant_id, user_id)`（`docs/migrations/124_drift_tables_fill.sql:371-382`），但**存量库是否已建该索引未验证**；若同一 `(tenant_id, user_id)` 存在多行，Q1/Q3 会重复计数，修复也会打偏 —— 清点时先加一条 `SELECT tenant_id, user_id, COUNT(*) c FROM t_user_points GROUP BY 1,2 HAVING c > 1;`。
6. **清点→修复窗口内的新写入量**：需要人工确认，静态无法计算。
