## 1. 生产库现在的表是怎么建起来的？（Q1）

## 2. `safeExec` 失败会怎样？（Q2）

**结论：吞掉继续（记日志返回 false），不会抛错中断，服务照常启动。**

代码 `backend/src/shared/migration.ts:131-149`：

```
131  export async function safeExec(conn, sql, label): Promise<boolean> {
132    try {
133      await conn.query(sql);
134      return true;
135    } catch (e: unknown) {
136      const err = (e ?? {}) as { code?: string; message?: string };
137      const code = err.code || "";
138      const msg = (err.message || "").toLowerCase();
139      // 静默跳过所有已知可忽略的错误
140      const shouldSkip = SKIP_ERRORS.has(code)
141        || SKIP_PATTERNS.some((p) => msg.includes(p));
142      if (shouldSkip) {
143        logger.info(`[migration] ${label}: 跳过 (${code || 'OK'})`);
144        return false;
145      }
146      logger.error(`[migration] ${label} 失败: ${err.message || String(e)}`);
147      return false;          // ← 注意：未知错误也返回 false，不抛出
148    }
149  }
```

- 已知可忽略错误码（`SKIP_ERRORS`，`:32-40`）：`ER_DUP_FIELDNAME / ER_DUP_KEYNAME / ER_DUP_ENTRY / ER_NO_SUCH_TABLE / ER_TABLE_EXISTS_ERROR / ER_BAD_TABLE_ERROR / ER_BAD_FIELD_ERROR / ER_CANT_CREATE_TABLE / ER_ERROR_ON_RENAME / ER_GET_ERRNO / ER_IO_WRITE_ERROR / ER_SP_DOES_NOT_EXIST / ER_PARSE_ERROR / ER_TRUNCATED_WRONG_VALUE_FOR_FIELD`。
- 已知可忽略错误模式（`SKIP_PATTERNS`，`:73-78`）：`duplicate column / duplicate key / already exists / doesn't exist / innodb / storage engine / can't create/write / permission denied / incorrect integer / unknown column / sql syntax / if not exists / procedure`。
- 两条分支都 `return false`，**没有任何 `throw`**。因此单条语句执行失败 → 仅记录日志、继续下一条，**不会导致迁移中断、也不会让服务起不来**。
- 叠加 `runMigrations()` 整体外层 `try/catch`（`:956`）与所有裸 `conn.query` 均位于各自 `try` 内（Step1.5 `:300-338`、Step4 `:382-397`、Step5.5.7b `:759-772`、Step6/7 `:812-899`），`runMigrations()` 本身永不抛出。

→ 这**排除了"语句报错→服务崩溃"**的风险，但**不**排除"语句成功执行→真实改数据/改结构"的风险（安全执行的部分才是关注点）。

## 4. 上线风险结论与建议（Q4）

### 4.1 是否可直接随主干推生产？
**不建议直接裸推。** 理由：
1. 受影响块真实数量 **475**（首块 125，远超首块 114），修复后将在生产**首次**执行，其中 **83 条数据变更 + 1 条结构变更**会真实生效；
2. 生产当前种子数据状态**未经核对**——若部分表已通过其它路径（如 `runMigrations` 其它步骤 / 手动）存在数据，纯 INSERT 会被吞并可能留下与预期不一致的种子（如 `079_权限矩阵` 显式 `id`）；
3. 存在 1 条不可逆结构变更（[76] collation `MODIFY`）。

但**也不禁止**——因为：
- `safeExec` 保证任何单条失败都被吞，服务**不会**因此崩溃（已证于 §2）；
- 多数受影响块是**有益补齐**（缺失表/缺失种子），且 `CREATE TABLE(无 IF NOT EXISTS)` 在表从未建时成功建表、在表已建时被吞；
- 无破坏性 `DROP` 会被执行（`:944` 跳过；`grep` 未发现潜伏 `DELETE/TRUNCATE/DROP`）。

### 4.2 推荐灰度 / 预演方案（按优先级）

**方案 A（首选）：生产副本预演 + 结构比对**
1. 用 `deploy/02-mysql-backup.sh`（已核实存在，mysqldump `--single-transaction` + 14 天保留 + 可选异地 rsync）对**生产库做全量备份**；并据此恢复出一个**生产副本**（同版本 MySQL 8）。
2. 在副本上，**仅对生产库副本**执行 `scripts/run-migration.mjs` 全量扫描逻辑做一次演练：即把 `runMigrations()` 第 8 步的 `splitSqlStatements` 新逻辑跑一遍（可临时在副本用 `node scripts/run-migration.mjs` 对每个 `docs/migrations/*.sql` 跑，或用修复后的 `migration.ts` 起一次服务）。
3. 部署前后各导出 `SHOW TABLES` 与关键表 `SHOW CREATE TABLE`，做 diff：确认**仅**预期表结构变化（如 [76] 的 collation）、无意外删列/改类型。
4. 检查副本 `backend.log` 中 `[migration] ... 跳过` 与 `失败` 行，确认无 `ER_DUP_ENTRY` 之外的新错误，且 `t_subscription_plan` / `t_tenant_module_access` / `t_sys_menu` / `t_sys_role` 等补齐成功。

**方案 B（低峰期 + 备份后启服务）**
- 在低峰期、先跑 `deploy/02-mysql-backup.sh` 留可回退快照，再合 main 触发自动部署；保留部署后 `backend.log` 与备份。该方案省去副本，但不如方案 A 有"事前可见性"。

**方案 C（修复与自动部署解耦，作保底）**
- 若希望先合 main 但暂不自动部署：可在合并 PR 描述/CI 中避免触发 `auto-deploy.sh` 自动流程（如以 `workflow_dispatch` 手动触发，或临时在提交信息加 `[skip deploy]` 这类 CI 跳过的约定标记，需确认 CI 是否支持）。注意：本仓自动部署由 `push main` 触发，**解耦需改 CI/部署触发条件**，属仓库配置变更，应与你方确认后再做。

### 4.3 验收指标（部署后如何证明"生产表结构未发生非预期变化"）
1. **结构比对**：部署前导出 `mysqldump --no-data --single-transaction liquor_inventory > pre.sql`；部署并重启服务后导出 `post.sql`；`diff pre.sql post.sql` 应**仅**出现预期差异（预期内：补齐的缺失表、[76] 的 `tenant_id` collation、新增索引/列）。任何"删列 / 改字段类型 / 删表"均视为非预期，立即回退。
2. **表清单比对**：`SHOW TABLES` 前后集合差应仅为"此前因 bug 从未建立的表"（如 `t_subscription_plan` 等），不应有表消失。
3. **关键表行数/内容核对**：重点核对 `t_sys_role` / `t_sys_menu` / `t_sys_data_permission` / `t_sys_field_permission` 行数是否符合 `079_权限矩阵.sql` 预期；`t_subscription_plan` / `t_tenant_module_access` 是否补齐。
4. **启动健康**：`/health` 返回 200，且 `backend.log` 无 `[migration] ... 失败` 非预期错误（仅有 `跳过` 属正常）。
5. **回退预案**：若 diff 出现非预期变更，用 `02-mysql-backup.sh` 的快照 `mysql < backup.sql` 还原，并回退到修复前提交。
