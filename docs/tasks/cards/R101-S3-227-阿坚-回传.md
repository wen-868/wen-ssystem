## 八、风险与自我报备

1. **"两批并行不再冲突"未完全达成**（派单卡 §三.1 的字面要求）：裸数字那行已删，但**和式行 + 逐文件 map 的 spread 行 + 期望 map 的循环行**仍是每个批次都要改的共享行。我**没有**顺手改成"自注册式"（会大改 15 个批次块，且当前 S3-226 正改同一文件）⇒ 列为待裁定项（§十.2）。当前四条判据保证"取一侧"必然变红，不会静默丢数。
2. **两个"已接线数"不是同一个数**（255 vs 226）：本单把口径写进台账说明与用例注释，并留 `10-metric-diff` 逐文件对照 —— 避免后人误把门禁的 255 当成和式右端而写出恒红的断言。
3. **C 的登记机制无法判断业务语义**（静态扫描不可能知道"改不改数据"）⇒ 用"人读台账同一行含『查询型』"做锚点。**残余风险**：只要有人在台账里写一行含该路径 + 「查询型」的判定，即可登记任意 POST；本单已用 C1 反测证明"无台账判定 ⇒ 拒收"，但"伪造台账判定"这一路径**只能靠人工审阅本清单**挡住（已在脚本头写明）。
4. **B 的命中面很窄**（仅 1 个文件 / 6 条）：其余消费者端文件（`miniapp.routes.ts` / `aftersale.routes.ts` / `notification.routes.ts` 等）用的是**命令式挂载**形态，且这些文件里**混有其它 router 的缺口**（如 `aftersale` 的 admin 端点）⇒ 我把归类**锚在 router 变量**上而不是文件上，否则会把它们的真缺口一并洗绿（这正是 §二.4「禁止按文件白名单一把放过」的落点）。B3 反测覆盖了这一点。
5. **`_counts` 与实时扫描的一致性只提示不判红**：本轮新增了实时读数，但把"台账陈旧"升级为 `--strict` 判红属**加严**，超出本卡授权 ⇒ 待裁（§十.3）。
6. **未做生产侧核对**：本单不涉及权限码选择，不需要 `t_sys_role.permissions` 复算；`--holders` 未改动。
7. **证据含端点路径与权限码字面量**（无口令/密钥）：`guard-evidence-secrets` EXIT=0（`56-guard-evidence-secrets.txt`）。
8. **工作树依赖**：本工作树创建时**没有** `node_modules`（`S3-223`/`S3-225` 用的是 Junction），我按同样方式把 `node_modules` / `backend/node_modules` / `admin-web/node_modules` 建成指向主仓库的 **Junction**（`.gitignore` 覆盖，不入提交、不影响主仓）。若验收时发现依赖异常，删除这三个 Junction 即可（非仓库内容）。
