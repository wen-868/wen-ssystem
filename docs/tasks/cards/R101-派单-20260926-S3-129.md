# 【派单 S3-129】（P1 门禁真实性）把 admin-web 的**类型门禁**接进 CI（阻断），并做"故意改坏证明会红"

```
【派单 S3-129】在 CI 的 build-and-test 里把 admin-web 的构建步骤换成 `build:check`（= vue-tsc -b && vite build），让刚变绿的类型门禁真正生效；并做反测证明它会红。
派单人：凌舟（总负责人）｜2026-09-26
执行方：林夕（`.github/**` · WorkBuddy 侧）
优先级 / 时间盒：**P1（门禁真实性）** · 一次跑完（改 + 反测 + 回传）
基线：以开工当日 `origin/main` 为准（开工第一步 `git log --oneline -1` 自证并写进回传）

## 一、背景（凌舟实测，可复跑）

1. **S3-123（PR #167，已合并 `689f2baa73`）已把 admin-web 的 `npx vue-tsc --noEmit` 从 42 处错误清到 0**（凌舟本机复跑 EXIT=0，反测：回退 3 个文件 ⇒ 6 处错误重新变红）。
2. **但这条路 CI 一次都没走过**：`.github/workflows/ci.yml:101` 的 admin-web 步骤是
   `run: npm --workspace admin-web run build`，而 `admin-web/package.json` 里 `build` = **`vite build`（esbuild 只转译、不做类型检查）**。
3. 仓库**已有** `"build:check": "vue-tsc -b && vite build"` 脚本，**但没有任何 workflow 调用它**。
4. ⇒ 结论：**类型门禁在 admin-web 上从未生效**；S3-123 把它修绿了，若不接 CI，下次一样会静默退化（与踩坑 [37]「没有 CI 的仓库，lint/format 类门禁默认视为未生效」、[143] 同族）。

## 二、交付物

① `ci.yml` 的 **build-and-test** job 中，admin-web 的构建步骤由 `npm --workspace admin-web run build` 改为
   **`npm --workspace admin-web run build:check`**（等价于"先 `vue-tsc -b` 类型检查，再 `vite build`"）；
   · 若 `vue-tsc -b` 在本仓的 project references 下不可用（例如缺 `tsconfig` 引用），**允许**改为两步：
     先 `npx --workspace admin-web vue-tsc --noEmit`（独立阻断步骤），再 `npm --workspace admin-web run build`。
     **任选其一，但必须写明选了哪条与原因**；
   · 步骤**不得**加 `continue-on-error`，**不得**加 `|| true`，**不得**放进可选/观察期 job。
② **反测证据（本单核心）**：在**分支**上故意制造 1 处类型错误（例如在任一 `.vue` 的 `<script setup>` 里加
   `const __probe: number = "not a number";`）⇒ **CI 必须变红且失败在该步骤**；给运行链接 + 失败日志片段；
   随后**还原该探针**（给出还原后该 job 变绿的链接或 SHA 证据），**不得**把探针留在合并内容里。
③ 回传卡 `docs/tasks/cards/R101-S3-129-林夕回传.md`（照抄下方「回传格式」十项）。
④ **同批接入 admin-web 的守卫用例**（凌舟 2026-09-26 追加）：S3-124（PR 见关联卡）已新增
   `admin-web/tests/role-guard.spec.mjs` 与脚本 `"test": "node tests/role-guard.spec.mjs"`（断言"空角色缺省拒绝"等三分支），
   但**无任何 workflow 调用它** ⇒ 同样会静默退化。请在 build-and-test job 中**增补一个阻断步骤**
   `run: npm --workspace admin-web test`（无需浏览器、耗时约 2s），并与 ① 的类型门禁步骤一样**不得**加 `continue-on-error` / `|| true`。

## 三、验收标准（硬）

① **门禁确实在跑**：给出 CI 运行里该步骤的名称与耗时（`gh run view <id> --log` 或 Actions 页面证据），证明它是**本 PR 新引入/替换**的步骤，而不是既有步骤换了皮；
② **反测"该红就红"**：给出**故意改坏**那次的运行链接 + **失败步骤名 + 原始报错**（须能看到 `error TS`）；
③ **合并内容不含探针**：`git show <merged-sha>:<探针文件>` 或 `rg -n "__probe"` 证明探针不在最终内容里；
④ **不改业务代码**：本单 `git diff --stat` 只应出现 `.github/workflows/ci.yml`（+ 必要的注释）与回传卡；
⑤ 主分支该 job 在真合并后仍为 **success**（给出链接）。
⑥ **守卫用例确实在跑**：给出该步骤在 CI 里的名称与原始输出（应能看到 `小结：3 passed / 0 failed` 与
   `守卫判定行 → …` 那两行）；若该步骤被跳过或未出现，判**未通过**。

## 四、明确不在本单范围（避免顺手做）

1. **admin-web 的 `lint:check` 目前是红的**（6 problems：2 error + 4 warning，见 **S3-128**）⇒ **本单不得**把 `lint:check` 接进 CI（接了必红、随后会被"临时放宽"）。**lint 门禁的接入另立 S3-131，起跑条件＝S3-128 清零**。
2. 不得动 `e2e.yml` 的既有矩阵/分流结构；不得改 `paths-ignore`；不得改分支保护设置（那是仓库设置，属凌舟职责）。
3. 不得改 `admin-web/**` 业务代码（探针只允许在**反测分支**上出现，且必须还原）。
```
