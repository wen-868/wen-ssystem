## 二、裁定

**① 「6 条外键真实存在」与既有 `169` 冲突 ⇒ 取 (a)：接受「5 条 + 建成证明」。**
依据：`169_tenant_admin_uuid.sql:1` **只** `DROP FOREIGN KEY t_tenant_admin_ibfk_1`（注释写明"原外键指向不存在的 tenant 表"），是既有的、有理由的迁移；本单职责是**让 016/034 的建表被 MySQL 8 接受**（消除 errno 3780），不是推翻 169 的既有决策。执行方用语句级探针证明了该约束**被 MySQL 8 成功建成**，随后由 169 按既有口径移除 —— 这个表述可接受。
**连带登记第 64 项**：`169` 之后 `t_tenant_admin.tenant_id` **没有任何外键保护**（只 DROP 不重建）。须定性：这是"漏配"还是"有意为之"。**不在本单处理**。

**② 017 的 `t_retail_order_item` 形状对齐（12 行 → 16 行）⇒ 认可，且认为它是必要动作而非扩范围。**
依据：修好 017 的 FK 后，017 的建表**由恒失败变为成功** ⇒ `074` 里那份更完整的定义**整条 no-op** ⇒ 全新库会拿到较窄形状（缺 `sku_id`/`tenant_id`/`created_at`），而 `instant-retail/retail-shop.service.ts:332` 按 `WHERE order_id = ? AND tenant_id = ?` 读该表 ⇒ **会新引入 `Unknown column 'tenant_id'` 真故障**。执行方把它对齐到 `074` 的既成口径（= 生产既有形状），是**消除新故障**。备选方案会把"新库与生产形状不一致"永久留在库里，不采。

**③ 范围外发现（`173` 的 `ALGORITHM=INSTANT` 在 MySQL <8.0.29 报错、`tenant_id` 宽度漂移 11 表、`008` 3 条同族、共 92 组同列异型）⇒ 登记第 65 项**（迁移语料类型/形状漂移收口），不在本单扩围。

**④ `t_delivery_record` 在全新库新增外键 `ON DELETE CASCADE` ⇒ 接受（附证据），并登记第 66 项。**
我亲验：`docs/migrations/017_phase10_instant_retail.sql:155/199` 的外键子句含 **`ON DELETE CASCADE`**；全仓 `rg "DELETE FROM t_retail_order|DELETE FROM t_delivery_record"` ⇒ **0 命中**（无物理删除路径）⇒ 该 CASCADE **当前不会触发**，可接受。
**连带登记第 66 项**：一旦将来引入零售订单的物理删除，会**静默删掉配送审计记录**；届时必须改 `RESTRICT` 或改软删。要求把这条写进该表附近的注释（第 65 项一并做）。
