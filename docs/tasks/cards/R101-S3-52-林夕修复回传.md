### 改后（`migration.ts`，具名清单 `TABLE_NAME_PATTERNS: {name, regex, note}[]`，共 12 个）
- 原 10 个全部保留（仅标识符捕获组由 `[a-z_][a-z0-9_]*` 升级为 `[`a-z_][`a-z0-9_]*` 以兼容可选反引号），并补入 2 个新模式：
- **新增 `REFERENCES`**：`/(REFERENCES\s+)([`a-z_][`a-z0-9_]*)/gi` —— S3-52 主修复点。
- **新增 `CREATE_INDEX_ON`**：`/(CREATE\s+(?:UNIQUE\s+|FULLTEXT\s+|SPATIAL\s+)?INDEX\s+[`a-z_][`a-z0-9_]*\s+ON\s+)([`a-z_][`a-z0-9_]*)/gi` —— 仅前缀 `ON` 后的表名，索引名不当表名。

```ts
export const TABLE_NAME_PATTERNS: TableNamePattern[] = [
  { name: "CREATE_TABLE",    regex: /(CREATE\s+TABLE\s+(?:IF\s+NOT\s+EXISTS\s+)?)([`a-z_][`a-z0-9_]*)/gi, ... },
  { name: "ALTER_TABLE",     regex: /(ALTER\s+TABLE\s+)([`a-z_][`a-z0-9_]*)/gi, ... },
  { name: "INSERT_INTO",     regex: /(INSERT\s+(?:IGNORE\s+)?INTO\s+)([`a-z_][`a-z0-9_]*)/gi, ... },
  { name: "UPDATE",          regex: /((?:^|\n)\s*UPDATE\s+)([`a-z_][`a-z0-9_]*)/gim, ... }, // 仅语句开头
  { name: "DELETE_FROM",     regex: /(DELETE\s+FROM\s+)([`a-z_][`a-z0-9_]*)/gi, ... },
  { name: "FROM",            regex: /(\bFROM\s+)([`a-z_][`a-z0-9_]*)/gi, ... },
  { name: "JOIN",            regex: /(\b(?:LEFT|RIGHT|INNER|OUTER|FULL|CROSS\s+)?JOIN\s+)([`a-z_][`a-z0-9_]*)/gi, ... },
  { name: "INTO",            regex: /(\bINTO\s+)([`a-z_][`a-z0-9_]*)/gi, ... },
  { name: "REFERENCES",      regex: /(REFERENCES\s+)([`a-z_][`a-z0-9_]*)/gi, ... },         // 新增
  { name: "CREATE_INDEX_ON", regex: /(CREATE\s+(?:UNIQUE\s+|FULLTEXT\s+|SPATIAL\s+)?INDEX\s+[`a-z_][`a-z0-9_]*\s+ON\s+)([`a-z_][`a-z0-9_]*)/gi, ... }, // 新增
  { name: "RENAME_TABLE",    regex: /(RENAME\s+TABLE\s+)([`a-z_][`a-z0-9_]*)/gi, ... },
  { name: "DROP_TABLE",      regex: /(DROP\s+TABLE\s+(?:IF\s+EXISTS\s+)?)([`a-z_][`a-z0-9_]*)/gi, ... },

```

> 替换回调统一：`bare = tableName.replace(/`/g, "")`，若 `bare` 以 `t_` / `information_schema` / `mysql` 开头则原样返回（保留反引号、避免双前缀 `t_t_`）；反引号标识符在替换时原样保留。

**保留的既有行为（红线内）：**
- `t_` / `information_schema` / `mysql` 开头不加分前缀（`:98` 等价逻辑）。
- `UPDATE` 仍只匹配语句开头（`/(?:^|\n)\s*UPDATE\s+/`），防误伤 `ON UPDATE CURRENT_TIMESTAMP` / `ON DUPLICATE KEY UPDATE col`。
- **未**加入 `ON` 这类高歧义关键字（会把 `ON DELETE CASCADE` 里的东西当表名）；改为用精准的 `CREATE INDEX...ON` 模式覆盖"ON 后的表名"。
- **未**改动 `safeExec`（`migration.ts:131-149`）的错误处理逻辑（红线：不得放宽/抛错）。

## 七、seed 顺序矛盾登记（只登记、不改代码）

> 来源：`backend/src/shared/seed-data.ts` + `backend/src/shared/migration.ts` 执行顺序

### 现象（自相矛盾的两行日志 + 一行失败）
1. `[seed] t_store 已有数据，跳过`（seed-data.ts:59）
2. 紧接着 `[seed] 获取门店ID失败: Table 'liquor_inventory.t_store' doesn't exist`（seed-data.ts:74）
3. `[seed] 种子数据初始化失败: Unknown column 'mobile' in 'field list'`（migration.ts:815 捕获 seedData 抛错）

### 时序证据
- seed 在 `migration.ts` **第 6 步**执行（`await seedData(conn)`，约 :811–816，日志时间戳早于外部迁移）。
- 外部迁移文件（008/016/017/018/031… 等建 `t_store` 及 `t_sys_user.mobile` 列）在 **第 8 步**执行（约 :917 起）。
- 即 **seed 早于外部迁移**；空库首次启动时，业务表与 `mobile` 列尚未由外部迁移创建，seed 先跑必然踩空。

### 判断（二选一 → 实为两者叠加）
- **根因 A — 时序问题（主因）：** seed 在外部迁移之前执行，空库下 `t_store` 表、`t_sys_user.mobile` 列都还不存在，故 seed 的 SELECT/INSERT 必然失败（`Table doesn't exist` / `Unknown column 'mobile'`）。
- **根因 B — 判空逻辑 bug（放大并掩盖）：** `isTableEmpty()`（seed-data.ts:31-40）的 `catch` 分支在"表不存在"时返回 `false`，与"表非空"混为一谈。调用方把 `false` 一律当成"已有数据，跳过"，于是表其实不存在时却打印"t_store 已有数据，跳过"，**静默跳过本应插入的门店**，直到紧随其后的 `SELECT id FROM t_store` 才暴露"表不存在"。这正是两行日志自相矛盾的直接来源。

**结论：** 以**时序问题为主因**（seed 早于外部迁移），**判空逻辑 bug 放大并掩盖**了它（把"缺失表"误判为"已有数据"，既不插入也不报错到 `safeExec` 层级）。空库首次启动 seed 必然失败。建议后续修复方向：① 将 `seedData` 调用移至外部迁移（第 8 步）之后；② `isTableEmpty` 对"表不存在"返回 `true`（应尝试插入）或显式区分缺失表与非空表。**本次仅登记，未改动相关代码。**
