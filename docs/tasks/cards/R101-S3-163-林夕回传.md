### §2 守卫规则（可复跑：`npm run guard:logout` 或 `node scripts/s3-163-logout-uniqueness-guard.cjs`）

守卫扫描 `app-mobile/src/**` 的 `.ts/.js/.vue/.mjs/.cjs`（`.vue` 只取 `<script>` 段），先剥注释再匹配，避免注释里的示例代码误判。

| **R1** | 死导出已删 | `export function logout` 命中 ≠ 0 |
| **R2** | 口径一致：每个「会话清理实现」（函数体内出现 `removeToken()` / `removeStorageSync('merchant_token')` / `removeSecureStorage('merchant_token')` / `removeUser()` / `removeTenant()` / `removeCsrfToken()`）必须二选一 | 既没有同函数内 `clearSavedCredentials()`＋`setRememberMe()`，又不满足 401 例外 |

**401 例外为什么不是静默放行**：例外**绑定语义**而非文件名——必须同时满足「文件是 `api/request.ts`」**且**「该文件确实含 401 语义（`登录已过期` ＋ `unauthorizedHandling`）」。一旦 `request.ts` 被重构得不再是 401 处理，例外**自动失效并判红**。
**为什么 401 必须例外**：401 是**被动**会话失效而非用户退出；S3-161 场景 C 硬要求「token 失效后打开 ⇒ 账号口令自动带出」，故 401 路径**必须保留** `saved_*`；且派单明确「不改 request.ts 的 401 逻辑」。

## 六、风险与自我报备

**R1（守卫的漏检面，必须说清）**：本守卫用"向上找最近函数声明 + 花括号配平"来定位函数体，**不是 AST**。因此存在一类**漏检**：如果有人把违规的清理代码写在一个**本身已含 `clearSavedCredentials()` + `setRememberMe()` 的外层函数内部**（例如把清理塞进 `logout()` 体内、或塞进某个恰好也调用了这两个函数的外层函数），它会被归因到那个"合规"外层而被判 OK。
反向的误报方向是安全的：顶层清理代码会被归到 `(top-level)`，仍然 FAIL。
处置建议（请裁定）：(a) 接受现状（覆盖 99% 的真实写法，误报方向安全）；(b) 另立卡升级为 AST（`ts-morph` 或 ESLint `no-restricted-syntax` 规则），彻底消除归因歧义。我倾向 **(b) 但不急**——因为 S3-162 已把正解收敛成唯一函数，实际风险不高。

**R2（401 例外的设计取舍）**：我把"401 被动清理"做成**语义绑定**的例外（`api/request.ts` ＋ 文件内含 `登录已过期`/`unauthorizedHandling`），而不是无脑按文件名放行。代价：如果未来有人把 401 处理挪到别的文件（或改掉这两个标识符），例外会自动失效 ⇒ 守卫判红 ⇒ 需要显式更新守卫。这是有意的"例外必须显式登记"设计，但**请确认你认可把 `request.ts` 作为唯一例外**；若你要求"零例外"（即 401 也必须退凭证），那会与 S3-161 场景 C 直接冲突，需要先改 S3-161 的口径。

**R3（守卫本身是"零信号门禁"的风险已自测消除）**：我刻意做了三组红侧而不是只做一组。若只做"新增违规出口"这一组，能证明 R2 有效，但**证明不了 R1 与 R3 有分辨力**（它们在绿侧一直通过）。三组红侧分别让 R1、R2、R3 都至少红过一次 ⇒ 三条规则都不是恒真。

**R4（未改动既有口径）**：本单**只删死代码 + 加守卫**，未触碰 S3-161（默认勾选 + 自动带出）与 S3-162（退出即退凭证）的任何口径；`stores/user.ts` 的 `logout()` 与 `login.vue` / `profile.vue` **0 改动**（见 §二 改动面）。回归自证（§6）也证明 S3-162 的四场景行为未受影响。
