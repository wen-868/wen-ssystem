## 〇、结论先行

1. **全仓写端点 754 条**（`backend/src/routes/**` 748 + `backend/src/server.ts` 手挂 6 条），其中**租户域 631 条**（高风险写 122 / 幂等只读型 POST 52 / 普通写 457）；平台域 123 条归 T7。逐条清单见附表。

5. 接线点建议放在 `auto-routes.ts` 的声明式配置里（不动路由文件），并对 `server.ts` 手挂的 6 条单独处理；**`auth:"requirePlatformAuth"` 的路由不可以直接挂 `requirePermission`**——平台 JWT 载荷没有 `roles` 字段，会 `TypeError` → 500（§3.2）。
6. **6 项需凌舟裁定**（含 52 条幂等 POST 中 6 条"含写副作用"的存疑项、建议权限点的命名口径），见 §6。执行方不代凌舟定口径。

### 2.4 ⚠ 三份种子并存 ⇒ 角色集合有漂移风险（裁定项 A）

## 三、为什么"直接接线"会锁死用户（关键前置缺陷）

### 3.1 判定函数不支持通配符（P0 前置缺陷，硬证据）

`backend/src/services/admin/rbac.service.ts:189-196`：

```ts
const perms: string[] = role.permissions ? JSON.parse(role.permissions as string) : [];
if (perms.includes("*") || perms.includes(permCode)) { return true; }
return false;
```

⇒ `perms.includes("inventory:*")` **不能**通过 `"inventory:adjust"`；`perms.includes("*:view")` **不能**通过任何 view。

| 角色 | 建议权限点 `inventory:adjust` | matcher 现状 | 修好通配符后 |
|:--|:--|:--|:--|
| SUPER_ADMIN（`*`） | 通过 | ✅ | ✅ |
| STORE_MANAGER（`inventory:*`） | 应通过 | ❌ 403 | ✅ |
| WAREHOUSE_STAFF（`inventory:*`） | 应通过 | ❌ 403 | ✅ |
| SALES_STAFF / FINANCE_STAFF / CUSTOMER_SERVICE / PURCHASE_STAFF | 应 403 | ❌ 403（结论对、原因错） | ❌ 403 |
| READONLY（`*:view`） | 应 403 | ❌ 403（结论对、原因错） | ❌ 403 |

**结论：`SUPER_ADMIN` 之外的 6 个角色在"任何域的任何权限点"上都会被拒**（唯一例外是 `STORE_OPERATOR`/`SALES_STAFF` 那类精确串，如 `sale:create`）。⇒ 若今天接线，**商家自建的店长/仓管/财务/客服账号会整体瘫痪**。

### 3.2 平台域会 500（不是 403）

`backend/src/middleware/auth.ts:147` 把平台 JWT 载荷直接塞进 `req.user`，载荷是 `{id, username, realName, type}`（`platform-auth.service.ts:57-62`），**没有 `roles`**。
而 `rbac-auth.ts:12` 会执行 `user.roles.includes("SUPER_ADMIN")` ⇒ `TypeError` ⇒ 由于该中间件没有 try/catch，错误落到 `errorHandler` ⇒ **500**。
⇒ 平台域（123 条）**不能**复用 `requirePermission`；要么先给平台 token 补 `roles`，要么只对租户域接线。

### 3.3 角色被烘焙进 JWT ⇒ 授权变更最长 4 小时不生效

`auth.ts:76-83`（`signToken`）把 `roles` 签进 JWT，`expiresIn: "4h"`。接线后**给角色补权限点必须重新登录**才生效——灰度和回退时都要把这一点算进去（回退同理：改回权限表后，旧 token 仍按旧权限放行，最长 4h）。

### 3.4 `ADMIN` 角色 permissions = NULL

`migration.ts:1143-1147`/`1179-1183` 创建 `ADMIN` 角色时**没有写 permissions 列** ⇒ `normalizePermissions(null) → []` ⇒ 该角色在任何权限点下都会 403。接线前必须给它补权限点（§6-C）。

### 3.5 已有门禁与新门禁的叠加关系

`price.routes.ts` 的 12 个写端点同时会被 `requirePriceManagementAccess()`（角色白名单）和新的 `requirePermission("goods:price")` 判定；**两者不一致时以更严者为准**（`STORE_MANAGER` 能过前者、但按 §5 的域覆盖表它能过 `goods:price` 吗？→ **不能**，`STORE_MANAGER` 只持有 `store:/sale:/customer:/inventory:/report:/dashboard:`）。⇒ **接线会让现在能改价的店长反而被拦**（§5.3 第 2 行）。

## 四、接线方案

### 4.1 目标与红线

- 只拦"**写**"，且**只拦已声明的端点**；未声明的端点默认放行 ⇒ 天生可灰度、可回退。
- 公开/幂等 POST（登录、验证码、支付回调、硬件回调、导入导出、试连、预览）**不进权限表**。
- 不修改任何路由文件里的业务逻辑；不加成"顺手重构"。

### 4.2 落地方式（推荐：声明式，唯一挂载点）

**前置修复（必须先做，否则整单不可执行）**：

1. `rbac.service.ts#checkUserPermission`：支持 `dom:*` 与 `*:view`（并在命中 `*:view` 时**只放行 view**）。
2. `rbac-auth.ts#requirePermission`：`user.roles ?? []` 防御 + 用 try/catch 或 `asyncHandler` 包裹，避免平台域 500；顺带把 `req.tenantId` 的类型从 `as any as number` 改为实际类型（`tenant.ts:13` 定义 `req.tenantId?: string`）。
3. 补 `ADMIN` 角色 permissions（§3.4）。

**接线方式（三选一，建议 A）**：

| 方案 | 做法 | 优点 | 缺点 |
|:--|:--|:--|:--|
| **A（推荐）** | 扩展 `RouteConfig`，新增 `permissions?: Record<string,string>`（键 = `"METHOD /path"`，值 = permCode）；由 `setupRoutes()` 在 `app.use(prefix, ...middlewares, config.router)` 之前，把该声明编译进 `config.router.stack` 对应 layer 的 handler 链 | 只改 `auto-routes.ts` + 一张声明表；不动 185 个路由文件；未声明即放行 ⇒ 天然灰度/回退 | 需要按 Express layer 的 path/method 匹配（含 `:param` 与 `(\d+)` 正则）；`config.auth==="none"` 的路由需单独处理 |
| B | 逐行改路由文件：`router.post("/x", requirePermission("dom:action"), handler)` | 直观、粒度最精确 | 改 600+ 行、185 个文件；与"最小改动"红线冲突；回退成本高 |
| C | 新增集中式权限表文件，在 `setupRoutes()` 里按前缀+路径做整表注册 | 与 A 类似 | 与 `routeConfig` 双份真相源，易漂移 |

**方案 A 的兼容处理**：

- `auth: "requirePlatformAuth"` 的 123 条：**不入权限表**（平台域归 T7），或先补平台 token 的 `roles` 再评估。
- `auth: "none"` 的公开路由（17 个文件，如 `/api/pay/wx/callback`、`/api/instant-retail/webhook/*`、`/api/store/hardware/callbacks/*`）：**不入权限表**，其中 `/applications` 已由 `tenant-register.routes.ts:22` 的 `requirePlatformAuth` 保护。
- `server.ts` 手挂 6 条：5 条登录类不入表；`POST /api/admin/orders`（运营推单受理）**必须单独补挂**，否则成为权限体系的旁路。
- 端点级已有中间件（`price-guard`、`requirePlatformAuth`、`apiKeyAuth`）保持不动，只追加权限点判定。

### 4.5 回退方式（每步都要能"一步回退"）

1. **首选（分钟级）**：环境变量开关 `RBAC_ENFORCE_PERMISSIONS=off`（实现时在 `setupRoutes()` 读一次），重启后端即恢复"只判登录态"。
2. **次选（一次提交）**：删除该步在权限表里新增的条目（只动 1 个声明文件 + 1 个映射表），重新部署。
3. **最后手段**：`git revert` 该步提交（不动路由文件 ⇒ revert 无冲突风险）。
4. 注意 §3.3：回退后旧 JWT（≤4h）仍按旧权限放行，**不要用"P0 回退生效"当验收依据**，要看新登录 token。

### 5.2 场景一：今天直接接线（不改 matcher）

- **会被拦**：所有非 SUPER_ADMIN 账号的**全部**权限点判定（§3.1）⇒ 店长/仓管/采购/财务/客服/只读/ADMIN 全部 403。

- **现实影响面（为什么"能上线但仍是错的"）**：`admin-web` 101/161 页面仅超管可见 + 演示账号与新租户管理员都是超管 ⇒ 主链路短期"看不出问题"；**但商家一旦给店员/仓管/财务开账号，该账号所有写操作立即 403**（且错误原因是 matcher 缺陷、不是权限设计）。
- **判定：禁止**。场景一必须走 G0 之后才可接线。

### 5.4 前端 `meta.roles` 与后端权限点口径不一致（系统性风险）

`admin-web/src/router/index.ts` 161 条路由全部带 `meta.roles`，取值分布：

| 角色组合 | 条数 |
|:--|--:|
| `["SUPER_ADMIN"]` | 101 |
| `["SUPER_ADMIN","STORE_MANAGER"]` | 43 |
| `["SUPER_ADMIN","STORE_MANAGER","CASHIER","STORE_OPERATOR"]` | 13 |
| `["SUPER_ADMIN","STORE_MANAGER","STORE_OPERATOR"]` | 2 |
| `["SUPER_ADMIN","STORE_MANAGER","FINANCE_ADMIN","WAREHOUSE_ADMIN"]` | 1 |

问题：`CASHIER`、`FINANCE_ADMIN`、`WAREHOUSE_ADMIN` **在 `t_sys_role` 里根本不存在**（§2.2）；而 `SALES_STAFF`/`PURCHASE_STAFF`/`CUSTOMER_SERVICE`/`READONLY` 在 `meta.roles` 里**一次都没出现**。⇒ 前端可见性判断与后端权限点判定是**两套独立口径**，接线时必须逐页面核对（这也是裁定项 D 的内容）。

### 5.5 影响面结论（可直接执行）

1. **按当前建议映射直接接线（在 G0 之后）会拦到 5 类既有流程**：店长改价（第 3/4 行，页面 `router/index.ts:177` 明确对店长开放）、操作员退货（第 8 行）、小程序订单流转（第 9 行）、即时零售写（第 11 行，页面全是超管 ⇒ 属"预期拦截"，需凌舟确认）、营销写（第 12 行，同上）。**其中第 3/4 与第 8 行是"真实误拦"，必须先补权限点（或改映射）再接线。**
2. **不会被拦的既有流程**（已核对）：收银开单（`sale:create`）、采购入库（`purchase:*`）、财务收款（`finance:*`）、库存调整（`inventory:*`）、销售退货中的店长路径（`sale:*`）、角色权限管理（仅超管）。
3. **可以"零误伤"接线的最小集合**（建议 G1 首批只收这些）：`inventory:adjust`、`sale:create`、`purchase:create`、`finance:create`、`stock-check:create`、`transfer:create`、`trace:create` —— 这 7 个权限点在现网已有非超管角色持有，**且不会被超管以外的正常流程误拦**（`inventory:adjust` 的调用方只有 `app-mobile`，见 §6 裁定项 G）。
