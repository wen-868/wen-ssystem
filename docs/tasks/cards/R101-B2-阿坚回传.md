## 二、一句话结论 + 代码依据

**结论：幂等性成立（数据层确实只落一单），但不是"幂等成功语义"，而是"重复即拒绝"**；成立靠**两道防线叠加**，且核验另发现 2 个与本单直接相关的红点（§五）。

### 2.1 为什么只落一单（代码依据，文件:行 均为仓库当前版本）

| # | 机制 | 位置 | 说明 |
|---|---|---|---|
| 1 | **服务层按 `draftNo` 预检**（租户内查重） | `backend/src/services/sync/delta-sync.service.ts:681-688`（`SELECT bill_no AS billNo FROM t_sale_bill WHERE bill_no = ? AND tenant_id = ?`）→ 命中即 `throw new AppError("单号 X 已存在，禁止重复提交", 409)`，被 `:764-770` 捕获后写入 `results[].success=false` | 幂等键 = `draftNo`，**且 `draftNo` 直接当服务端 `billNo` 落库**（`:715-723`、`:759`） |
| 2 | **DB 唯一键 `uk_sale_bill_no (bill_no)` 兜底** | 定义 `docs/migrations/001_phase1_schema.sql:365`；运行时兜底建表同定义 `backend/src/shared/migration.ts:601`；全仓无 `DROP uk_sale_bill_no` 记录 | "先查后插"间隙的**独立防线**：预检按 `tenant_id` 过滤、对他租户放行，但仍被该键挡住（S5 直接证据） |
| 3 | 事务原子性 | `:691-760`（主表 + 明细同一事务；`transaction()` 实现见 `backend/src/config/database.ts:288-307`） | 明细失败则主表回滚，不留"半张单" |

### 2.2 幂等键的落库位置

- 幂等键**没有独立列**：`draftNo` 被复用为 `t_sale_bill.bill_no`（`:680` 注释 + `:723` 实参 + `:759` 返回值）⇒ 幂等性实际由 `bill_no` 的**唯一性**承载。
- `t_sale_bill` 插入**带 `tenant_id`**（`:734`）；`t_sale_bill_item` 插入**不带 `tenant_id`**（`:741-744`）——见 §五 红点①。

### 2.3 端到端链路（只读核对，未改）

`backend/src/routes/sync.routes.ts:28`（`POST /offline-orders`）→ `:32-36`（`prefix: "/api/sync"`、`auth: "requireAuthWithTenant"`）→ `backend/src/controllers/admin/sync.controller.ts:117-127`（`operatorId` 缺失 401 / `orders` 空 400）→ `delta-sync.service.ts:660-779`。

## 五、缺陷清单（缺陷描述 + 最小修复方案 + 影响面）——**只交方案，等凌舟裁定**

### 红点①：`t_sale_bill_item.tenant_id` 未随租户落库（租户归属错误）

- **现象**：租户 `b2-tenant-a` / `b2-tenant-b` 提交的明细行，落库 `tenant_id` 均为 `'default'`（同一张单的**主表** `tenant_id` 正确）。
- **复现步骤**：跑 §3.1 主探针，看 S6 段落原始输出：`明细 A：[{"bill_no":"B2-ISO-A-001","tenant_id":"default",...}]`。
- **根因**：明细 INSERT 的列清单不含 `tenant_id`（`delta-sync.service.ts:741-744`），且该语句走 `transaction()` 的 `conn.execute`，**不经过** `queryWithTenant` 的租户注入（`config/database.ts:288-307` 只给 `conn.query` 补表前缀、无租户注入）⇒ 落库取列默认值 `'default'`（列定义 `docs/migrations/092_租户ID.sql:141`：`NOT NULL DEFAULT 'default'`；全仓无触发器）。
- **影响面（已验证）**：按租户过滤读明细的路径**读不到这些明细**，例如分享收款单明细 `backend/src/services/share.service.ts:133` 与 `:188`（`FROM t_sale_bill_item WHERE bill_no = ? AND tenant_id = ?`）。
- **最小修复方案（仅方案）**：在 `delta-sync.service.ts:741-744` 的列清单补 `tenant_id`、参数数组补 `tenantId`（与主表 `:734` 对齐）。**同一缺陷在开单主流程有同类写法**（`backend/src/services/store/sale-bill.service.ts:312-321` 同样省略 `tenant_id`；对照 `backend/src/services/admin/demo.service.ts:178-181` 是显式带 `tenant_id` 的写法）⇒ 建议**另立单**统一处理，并评估是否一次性 UPDATE 回填存量明细（回填 SQL 必须走迁移清单，不由本单出具）。
- **存量数据是否已有重复/污染**：**是**（可判定）：凡经上述两条 INSERT 路径产生的明细行，`tenant_id` 均为 `'default'`；**具体条数**需真库执行 `SELECT tenant_id, COUNT(*) FROM t_sale_bill_item GROUP BY tenant_id;`（列入 §六 待办 3）。

### 红点②：`uk_sale_bill_no` 全局唯一 ⇒ 跨租户同名 `draftNo` 相互顶掉

- **现象**：租户 A 先占用单号后，租户 B 提交**同名** `draftNo` 被拒（`Duplicate entry '...' for key 't_sale_bill.bill_no'`），B 无法使用该单号；且 B 的 `results[].errorMsg` 会把该单号原文回显给 B。
- **复现**：主探针 S5 段落原始输出（§3.4）。
- **根因**：唯一键为 `UNIQUE KEY uk_sale_bill_no (bill_no)`（`001_phase1_schema.sql:365` / `migration.ts:601`，**不含 tenant_id**；对照 `092_租户ID.sql:235` 只加了普通索引），而服务层预检是**租户内**查重（`:681-688`）⇒ 两道防线口径不一致。
- **最小修复方案（仅方案，二选一，需 DDL 决策）**：① 唯一键改为 `(tenant_id, bill_no)`（DDL 变更，须走迁移清单 + 凌舟裁定）；② 服务端落库单号加租户前缀（`draftNo` 仍是幂等键，但不再等值当 `bill_no`）——注意会改动"单号即 draftNo"的既有约定，影响对账/排障口径。
- **影响面**：仅多租户下**跨租户撞号**触发；单租户场景不可见。

### 红点③（观察，非本单结论）：重复提交返回"失败"，客户端会永久重试

- **现象**：第二次提交返回 `success=false`（而非幂等成功），客户端 `app-mobile/src/utils/sync-manager.ts:428-438` 会把它标成 `SYNC_FAILED`；而 `app-mobile/src/api/local-db.ts:711` 的 `listPending` **包含** `SYNC_FAILED` ⇒ 该草稿**每轮同步都重试、永远失败、永远进不了 `SYNCED`**（典型触发："第一次已写库成功但响应丢失"）。
- **可选口径**：命中"已存在"时返回 `success:true` + 既有 `billNo`（幂等成功语义），使客户端转入 `SYNCED`。**属产品语义决策 → 待裁定**，本单不改。
- **同类文案漂移**：`app-mobile/src/api/sync.ts:208` 注释称"使用服务端 `makeBizNo("XS")` 生成 billNo"，实际实现是用 `draftNo` 当 `billNo`（`delta-sync.service.ts:723`）⇒ 客户端契约注释与后端实现不一致（红线禁止改 `app-mobile/**`，故仅报备）。
