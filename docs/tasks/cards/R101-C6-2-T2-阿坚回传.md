## [131] 执行方沙箱**能跑真 vitest**：tsc 先编译成 JS + pool=threads + 两处无关调用打桩（2026-09-26，阿坚在 C6-2-T2 实测）

**背景**：[118] 已定「沙箱无子进程 ⇒ 不能起服务/浏览器/连库/跑 vitest 全量」。本次在 issue-139 复核并**部分推翻**：
vitest 起不来有两层原因，第二层可绕。

**第一层（不可绕）**：`npx`/`node_modules/.bin` 需要 spawn 子进程 ⇒ `EPERM`；`vitest.mjs` 直接 `node` 调用可以起。
**第二层（可绕）**：vitest 默认配置 + `.ts` 源码要过 esbuild（`spawn EPERM`）。绕法三件套：
① `tsc` 把源码与单测编译成 JS（`outDir` 到临时目录），vitest 只加载 JS；
② `--configLoader runner`（vite ≥6.1，避免用 esbuild 打包配置）+ 配置里 `pool: "threads"`（worker_threads 不受限）；
③ preload 打两处**与测试无关**的桩：vite 在 Windows 上探测网络盘的 `exec("net use")`、`vite:define` 用的 `esbuild.transform`
（`spawn` **保持原样**，真子进程仍照原样 EPERM，不会掩盖问题）。

**实测**：C6-2-T2 的 3 个测试文件 / 47 条用例全绿；四轮反测（删 retry 校验、初始态改 GENERATING、INSERT 假 SUCCESS+假 fileUrl、日志排序改 DESC）
均能稳定判红，复原后转绿。**口径**：结论为 B 级（跑的是编译产物，且只覆盖被编译进来的文件），
**全量门禁判绿权仍在凌舟本机**；路径/fixture 依赖型用例（如 `auto-routes.test.ts` 的 `resolve(__dirname,"../fixtures/routes")`）在该布局下会误红，不能当回归。

**另一坑（同批实测）**：`tsc` **不清理旧产物** —— 改过 `include` 后不删 `dist/`，陈旧的 `*.test.js` 会被 vitest 一起收集（本次先出现「6 failed」假象）。
