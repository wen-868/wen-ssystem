## 〇、结论先行

1. **本单的对象确实是空的**：全仓（除 `docs/**`）匹配"调取"的文件只有 **2 个**，且都是平台侧展示文案 —— `saas-admin/src/views/library/LibrarySpus.vue`、`saas-admin/src/views/library/LibraryBrands.vue`；**没有任何租户侧复制端点**（命令与原始输出见 §一.1）。
2. **现有"调取口径"是错的，必须先纠正再建表**：平台页面"调取热度 / 累计被调取"渲染的是 `t_library_spu.hit_count`（`LibrarySpus.vue:132/154/576-583`），而该列的唯一写点是**扫码查询**（`services/admin/library-lookup.service.ts:103-106`）⇒ 现在的"调取次数"统计的是 **SCAN 查询**，正是凌舟钉死口径要排除的那一类（§一.2）。
3. **调取流水建议只建 1 张**：`t_library_call_log`（字段/索引/collation 全量给出，§三），**零预置数据**（MIG-4 写闸门默认 block）；是否**另加**一张幂等映射表见第 4 条与 Q7。
4. **租户私有档案一律复用既有三张表写入**（`t_product_spu` / `t_product_sku` / `t_product_price`）；**分歧只在"要不要一张映射表"**：方案 A（纯复用）vs 方案 B（新增 `t_tenant_library_copy`），**推荐 B**，理由 = 幂等与"平台有新版本可同步"必须有唯一键载体，方案 A 只能靠名称/条码猜（§三.4）。
5. **端点建议 4 条租户侧 + 4 条平台侧**（调取结果查询复用既有商品详情）；**不得把动作动词写进 URL**（标准 §2.4）⇒ 执行调取落为 `POST /api/admin/library/copies`（§四）。
6. **权限点建议 2 个新码**：`library:view`（检索/预览）与 `library:copy`（执行调取）；**不默认给所有角色**，且须注意 `READONLY` 角色的 `["*:view"]` 会**自动命中 `library:view`**、不命中 `library:copy`（matcher 实证，§五）。
7. **配额有一处硬事实必须先说清**：本仓**没有"商品配额写入侧拦截"**——`max_products` 全仓只被"只读聚合"读取（§六.1）。若只给 COPY 加拦截，手工建品仍可绕过；本单按红线不改码，只登记为待裁定项 Q5。
8. **一处必须上报的约束冲突**：`t_product_sku.barcode` 是**全库唯一键（不含 tenant_id）**（`init_database.sql:447`、`migration.ts:870`），而规划要求"条码带入"⇒ 复制式调取必然撞唯一键；这是本单最重要的落地风险（§七.3 + Q2）。

## 二、统计边界（凌舟已钉死；本卡落成字段口径）

判据只有一条（规划原文）：**"是否产生租户私有档案"**（`docs/智享全链_总后台建设规划_v1.3.html:1127` 逐字："调取的本质是**租户主动发起的单向数据复制**（公共主数据 → 租户私有档案），落库即隔离"）。

| 动作 | 触发方 | 现状 | 是否＝"调取" | 计数落点建议 |
|---|---|---|---|---|
| **COPY** 复制式调取 | 租户在商家后台检索公共库 → 选定 → 生成私有 SPU/SKU | **不存在**（本单建议新增） | ✅ **是** | 写 `t_library_call_log`（本次新增）＋扣商品配额 |
| **SCAN** 条码/扫码查询 | `POST /api/admin/library/lookup`（含移动端扫码自动填充） | 已有 | ❌ 否（查询） | 复用既有 `t_library_spu.hit_count`（唯一写点 `library-lookup.service.ts:105`） |
| **API** 公共库读取 | `GET /api/open/library/*`（API Key） | 已有（C3 产物） | ❌ 否（查询） | 复用既有 `t_library_api_key.today_count` + `daily_limit`（`middleware/api-key-auth.ts:34/58/65`）；`t_open_api_call_daily` **当前无写入方**（`docs/migrations/175_open_platform_api_call_daily.sql` 文件尾注释逐字） |
| 页面人工检索 | 商户后台搜索框（本次新增页面能力） | 不存在 | ❌ 否 | **建议不落库**（成本>收益；真要计须另立单新建计数表） |

**三条红线（写进实现单）**：
1. 不得把 `/api/open/library/*` 或 `lookup` 的调用写进 `t_library_call_log`（否则"调取"被查询灌水，与裁定 6 冲突）。
2. 不得继续用 `hit_count` 当"调取次数"（§一.2）；平台侧统计一律取 `t_library_call_log`。
3. `t_library_call_log` **只记成功动作**（一次成功调取 = 一行；被拒（配额/权限/状态）不写行、不占配额）。理由：统计口径须等于"配额扣减次数"，写入失败会与扣减分叉；替代方案见 Q6。

### 3.2 为什么这么定（逐条给依据）

1. **不建物理外键**：`t_tenant.id` 是 `VARCHAR(36)`、`t_library_spu.id`/`t_product_spu.id` 是 `BIGINT UNSIGNED`，跨表类型/排序规则不一致；该家族已两次因外键在**全新空库**建表失败（`R101-C6-2-批2-立项卡-T1+T2+T3+T5.md` §三.1），179~185 全部采"逻辑引用 + 不建外键"。
2. **文本列显式 `utf8mb4_0900_ai_ci`**：不默认继承库 collation（179/180/183 同规；`R101-C6-2-批1-立项卡-T6+T7.md` §二）。
3. **存名称/编码快照**：平台主数据可被删除（`DELETE /api/platform/library/spus/:id`，`platform-library.routes.ts:48`），流水只存 id 会在主数据删除后变成不可读的孤儿行；两个 VARCHAR 换"统计表自洽"。
4. **不存版本号**：`t_library_spu` **当前无版本列**（`docs/migrations/117_library_spu_sku.sql:19-46` 无 version），规划 4.15.2 的"版本号"尚未落库；现在写只会写空值（禁止"无载体却假装有"）。若凌舟决定先补版本列，流水加 `library_version INT NULL` 即可（INSTANT 加列）。
5. **零预置数据**：迁移只做结构（MIG-4 默认 block，`migration.ts:1216-1219`）；可执行语句顶格写在注释块之前（规避[63]）。

### 3.4 租户侧私有档案的落地方式：两方案优劣 + 推荐

**共同点（不争议）**：调取产物一律写进**既有租户商品体系** `t_product_spu` + `t_product_sku` + `t_product_price`（规划 4.15.1 逐字："按现有系统商品中心结构生成租户侧档案…调取落库后即可在商家后台正常编辑、上下架、配置价格"，`规划:1129`）。这样改价/上下架/库存/开单/报表**零额外开发**，配额计数（`COUNT(t_product_spu)`）也自动成立。

| 维度 | 方案 A：纯复用（不建映射表） | 方案 B：复用 + 新建 `t_tenant_library_copy` 映射表 |
|---|---|---|
| 新增表 | 0（除流水表） | 1（+ 流水表 = 共 2 张） |
| 幂等判据 | 只能猜（按 `tenant_id`+名称+规格，或按条码）⇒ **会把商户自己手工建的同类商品误判为"已调取"** | 精确：`UNIQUE KEY (tenant_id, library_spu_id)` ⇒ 二次调取必命中 |
| "平台有新版本可同步"（`规划:1176`） | **无载体**（除非给 `t_product_spu` 加列） | 有载体（可扩 `library_version`） |
| 平台侧统计 | 只能读流水 | 流水 + 映射（可做"某商品被哪些租户持有"） |
| 核心表改动面 | 若需溯源就得 ALTER `t_product_spu`（该表被商品列表/核价/开单/报表/导入导出共用；历史上靠 `migration.ts` Step 5.5.4 幂等补列维护，`migration.ts:967-986`） | 零改核心表 |
| 删除后重新调取 | 无法判定历史是否调取过 | 可判定（映射行保留，见 Q4） |
| 主要风险 | 幂等不可靠 ⇒ 重复档案、重复占配额 | 多一张表、多一次写入（须与档案写入同事务） |

## 五、权限点与角色矩阵

### 5.1 matcher 语义（实证，不靠猜）

`backend/src/services/admin/rbac.service.ts:288-315`（`matchPermission`，纯函数）按顺序判定：

1. `"*"` ⇒ 全通过；
2. `"<dom>:*"` ⇒ `permCode` 以 `<dom>:` 开头即通过；
3. `"*:<action>"` ⇒ `permCode` 以 `:<action>` 结尾即通过；
4. 精确相等 ⇒ 通过；其余不通过。

路由级拦截：`middleware/rbac-auth.ts:6-24`（`requirePermission(permCode)`）—— 无 `req.user` ⇒ 401；`user.roles` 含 `SUPER_ADMIN` ⇒ 直接放行；否则查 `t_sys_user_role` × `t_sys_role.permissions`，不通过 ⇒ 403。

### 5.2 新权限码建议（2 个，域 `library`）

| 权限码 | 语义 | 挂载端点 |
|---|---|---|
| `library:view` | 检索/预览公共库 + 查看本租户调取流水（**只读**） | T1 / T2 / T4 |
| `library:copy` | 执行调取（**写**：生成档案 + 写流水 + 扣配额） | T3 |

**为什么不合成一个码**：`READONLY` 内置角色权限为 `["*:view"]`（`docs/migrations/079_权限矩阵.sql:93`），按 matcher 规则 3 会**自动命中 `library:view`**，而**不会**命中 `library:copy` ⇒ 读写分离后只读角色自然"能看不能调取"（无需改它的权限数组）。若只用一个写码，要么只读角色看不到检索页，要么给它开了写权限。

## 七、幂等与去重

### 7.1 建议语义（推荐：**跳过**；不覆盖、不新建）

| 场景 | 建议行为 | 理由 |
|---|---|---|
| 同租户、同 `library_spu_id` 第二次调取 | `SKIPPED`，返回既有 `spuId`；**不新增档案、不写流水、不扣配额** | 幂等；避免重复占用商品配额 |
| 覆盖（用平台最新数据重写租户档案） | **不建议** | 与规划 4.15.4 逐字冲突："公共主数据后续更新时不自动改动租户已调取档案"（`规划:1176`）；会静默改写商户已改的价格/图片 |
| 新建版本（同租户再建一份） | **不建议** | 同租户出现重复档案 + 重复占配额，且与幂等判据冲突 |
| 平台主数据被删除/下架后再调取 | 404（不可检索、不可调取） | 规划 4.15.3 逐字"商品下架后不再可被检索与调取，但已被租户调取的私有档案不受影响"（`规划:1167`） |
| 租户删掉自己的档案后再调取同一 SPU | **待裁定（Q4）** | 见 Q4：若允许"删了再调"，则"删-调"循环可绕过配额 |

### 7.2 判据（必须可执行，不能靠猜）

- 唯一判据 = `t_tenant_library_copy` 的 `UNIQUE KEY (tenant_id, library_spu_id)`（方案 B）。
- 方案 A 下无精确判据（只能按名称/规格或条码猜），会把商户手工建的同类商品误判为"已调取" ⇒ 这是**推荐 B** 的直接原因（§3.4）。

### 7.3 条码/编码的**唯一键冲突**（本单最重要的落地风险）

| 事实 | 依据 |
|---|---|
| `t_product_sku.barcode` 是**全库唯一键**（不含 `tenant_id`） | `docs/init_database.sql:447`（`UNIQUE KEY uk_product_sku_barcode (barcode)`）、`backend/src/shared/migration.ts:870`（同） |
| `t_product_sku.sku_code`、`t_product_spu.spu_code` 亦为全库唯一 | `init_database.sql:446/417`、`migration.ts:869/842` |
| 现有建品用 `makeBizNo("SPU"/"SKU")` 生成编码，**不复制外部编码** | `backend/src/services/admin/product.service.ts:404`（`makeBizNo("SPU")`）、`:421`（`makeBizNo("SKU")`） |
| 规划与设计稿都要求调取时"条码带入" | `saas-admin/src/views/library/LibrarySpus.vue:379` 逐字"类目 / 品牌 / 条码带入"；`规划:1138`（"GS1 标准条码…双键查重"） |

⇒ 冲突必然发生：A 租户调取后，B 租户调同一 SPU 会写相同 `barcode` ⇒ **`ER_DUP_ENTRY`**（1062）。候选处置（**本单不选，交凌舟裁定 Q2**）：

1. **不带条码**（写 `NULL`；MySQL 唯一键允许多个 `NULL`）—— 安全，但违背"条码带入"，且租户失去扫码销售能力；
2. **带条码，冲突降级**（插入失败则写 `NULL` + 响应 `warnings` 提示）—— 结果不确定、体验差，且同一操作在不同租户得到不同数据形态；
3. **改索引语义**（`uk_product_sku_barcode` → `(tenant_id, barcode)`）—— 影响既有扫码/查重/销售全链路，属**结构性变更**，须先出只读影响面评估（本卡不评估，也不建议本单夹带）。
