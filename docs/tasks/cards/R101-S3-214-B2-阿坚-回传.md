## 七、风险与自我报备

1. **`purchase:create` / `purchase:approve` / `purchase:supplier` 在生产只被 SUPER_ADMIN 持有**（按派单卡 §三 的角色集）：本批把这些码挂在「采购岗专属」端点上（采购单审核/作废/改/删、合同 4 条、供应商主数据 8 条），**当前实际可调用者≈超管**。若生产另有 `PURCHASE_STAFF`（仓库种子里有该角色，持 `purchase:*`、`supplier:*`），它会一并通过；**这不影响零回归，但意味着「采购员能否用这些端点」取决于生产是否真有该角色** ⇒ 请凌舟在生产确认一次。
2. **供应商对账选 `report:finance` 而非 `supplier:statement`**：因为店长（页面 `meta.roles` 的成员）不持 `supplier:statement`，用它必 403（批 1 `trace:*` 同款形态）。副作用是**采购员（`report:purchase`）不通过**对账端点 —— 对账页只给超管/店长，故不构成回归，但若业务上采购员也要对账，需补授权（另立单）。
3. **店长对付款审核端点的"宽授"**：生产店长持精确码 `finance:payment`，故店长在 API 面亦通过 `POST /purchase-payments/:paymentNo/approve`。付款页 `meta.roles` 只有 SUPER_ADMIN，页面不可达 ⇒ 非页面回归；若要收窄为「财务专属」，需新立码（不在本单）。
4. **排除项的判据是"当下前端形态"**：M 类 4 条一旦移动端补了权限门（或在页签上加码），即可按同一张表直接接线；本单已把"接线后必 403 的组合"写进注释与台账，避免下批重新调研。
5. **跨批计数断言已被本单更新**（`rbac-g0-wiring.test.ts` 的「全量接线总数」82 → 107，以及一条已接线端点移出「未纳入 G0」名单）。这是**该断言的既定维护方式**（S3-198/S3-209 同样处理），G0 名单行与其逐行 403/200 断言**一字未动**；已在文件内留注释，便于凌舟对照。
