## 三、第 3 项：`wechat.routes.ts` 取证与方案（**本单未动手**，等裁定）

### 1) `csrfMiddleware` 的真实实现

`backend/src/middleware/csrf.ts:33-53`

| 判据 | 实现 | 行号 |
|:--|:--|:--|
| 放行的方法 | `SAFE_METHODS = ["GET","OPTIONS","HEAD"]` → `next()` | L7 / L35-37 |
| **未认证时** | **`if (!req.user) return next();`（放行）** | **L39-42** |
| 读哪个字段 | 请求头 `x-csrf-token` | L44 |
| 比对基准 | `generateCsrfToken(req.user.id)` = `HMAC-SHA256(CSRF_SECRET \|\| JWT_SECRET, String(userId)).hex` | L14-21 / L45 |
| 不符时 | `403 { code:"403", msg:"CSRF token 无效或缺失" }` | L47-50 |

⇒ **对 `requireWxAuth` 保护的端点，直接挂 `csrfMiddleware` = 永远不生效**（`req.user` 恒 undefined，走 L40-42 放行）——这正是"假安全"。

### 2) `requireWxAuth` 设了什么 / `req.wxUser` 结构

`backend/src/middleware/wechat-auth.ts:9-23`：取 `Authorization: Bearer <token>` → `jwt.verify(token, env.JWT_SECRET)`（**只校验密钥，不校验 issuer/audience**）→ `req.wxUser = { id: decoded.wxUserId, openid: decoded.openid }`。

- **不设 `req.user`**（因此也永远进不了 csrfMiddleware 的比对分支）；
- **不设 `req.tenantId`**（tenantMiddleware 不在这条线上）；
- 令牌由 `signWxToken(wxUserId, openid)` 签发 = `jwt.sign({ wxUserId, openid }, JWT_SECRET, { expiresIn: "7d" })`（L50-52）；**与商家 JWT 不同源**（商家令牌带 `issuer=zhixiang-system`/`audience=zhixiang-client`，见 middleware/auth.ts:95-102/138-142，微信令牌两处都没有）。
- 登录响应只回 `{ token, userInfo }`（services/wechat.service.ts:65-75），**不下发任何 CSRF 令牌**。

### 3) 微信侧写端点的实际调用方（谁调、能不能带自定义头）

| 端点 | 鉴权 | 调用方（全仓 rg 命中） |
|:--|:--|:--|
| `POST /api/miniapp/wechat/auth/decrypt-phone` | requireWxAuth | `miniapp/pages/profile/index.js:173` |
| `PUT /api/miniapp/wechat/auth/profile` | requireWxAuth | （客户端调用点未命中，仅 GET profile：`pages/profile/index.js:111`、`app.js:65`） |
| `POST /api/miniapp/wechat/auth/bind` | requireWxAuth | `miniapp/pages/profile/index.js:227` |
| `POST /api/miniapp/wechat/auth/unbind` | requireWxAuth | `miniapp/pages/profile/index.js:256` |
| `POST /api/miniapp/wechat/auth/login` | 公开 | `miniapp/pages/profile/index.js:136`、`app.js:34` |

- 唯一调用方是仓内 `miniapp/`（微信原生小程序），走 `wx.request`/`app.request()`：**技术上可以带任意自定义头**（微信小程序无 CORS 限制，域名白名单只限制域名）；当前客户端只带 `Content-Type` + `Authorization`（同款写法见 `pages/coupons/index.js:59-62`），**且登录响应没有可带的 CSRF 令牌**。
- ⇒ 直接给这 4 个写端点挂 `csrfMiddleware`：因为 L40-42 恒放行，**它拦不住任何人**（假安全）；若先补齐 `req.user` 再挂，则**必须同步改客户端**（否则 4 个端点全部 403）。
- 另记录一处既有缺陷（不在本单范围）：`bind` 用 `req.tenantId`（controllers/admin/wechat.controller.ts:89），该线上恒 `undefined`。

### 4) 2~3 个可选方案 + 推荐

| 方案 | 做法 | 改动面 | 风险 | 对既有客户端影响 |
|:--|:--|:--|:--|:--|
| **A（推荐）把微信登录态并入统一身份载体** | `requireWxAuth` 校验通过后**同时**设置 `req.user = { id: wxUserId, roles: [...], tenantId }`（并设 `req.tenantId`）→ 之后 4 个写端点按全站一致写法挂 `requireWxAuth, csrfMiddleware`；令牌体系不变 | `middleware/wechat-auth.ts`（1 处赋值 + 语义注释）、`wechat.routes.ts` 4 行、登录响应补 `csrfToken`、miniapp 端 4 处带 `x-csrf-token` | 中：`req.user` 的 `roles/storeId` 取值口径需凌舟定（这条线上目前**没有**任何代码读 `req.user`，故不回头影响既有链路）；顺带可纠正 `bind` 的 `tenantId` 缺失 | 需改客户端（否则 403）；**当前客户端本就不带令牌，属"必须同批改"** |
| B（过渡）CSRF 令牌与登录态解耦 | `csrfMiddleware` 增加分支："无 `req.user` 但有 `req.wxUser` ⇒ 按 `req.wxUser.id` 校验 `x-csrf-token`" | `middleware/csrf.ts`（+1 分支）、`wechat.routes.ts` 4 行、登录响应补 `csrfToken`、客户端带头 | 中低：改动最小，但把"CSRF 认谁"分裂成两套维度，今后每加一种自有鉴权都要再开分支（技术债） | 同上，需改客户端 |
| C 自造等价机制（不推荐） | 不动 csrfMiddleware，改为令牌绑定 + 限流/二次确认 | 新机制 + 客户端改造 | 高：等于新造第三套机制，与"不得新造第三套鉴权/身份来源"冲突 | 需改客户端 |
