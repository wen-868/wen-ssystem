## 一、这一批要解决什么

批 2.1 上线后我自己报备了一条局限：**图形验证码填错也计次**——连续 5 次看错验证码即触发
「IP + 账号双维度锁 15 分钟」。裁定③的判定是：**拿它触发账号锁会直接变成投诉**，
验证码看错一位属正常交互噪声，自动化尝试按 IP 抑制就够。因此改成**按失败类型分流**：

| 失败类型 | 维度 | 阈值 | 超限行为 |
|:---|:---|:---|:---|
| **凭据错误（401）** | IP + 账号**双维度** | 5 次 / 5 分钟 | 最长锁 15 分钟（**维持批 2.1 原强度，一字未改**） |
| **验证码错误（400）** | **仅 IP 维度** | 20 次 / 5 分钟 | **只拒绝并要求重新获取验证码**，绝不锁账号 |

### 分流实现（最小改动，与裁定③的建议一致）

裁定③原话：「让 limiter 只对 401 计数（按响应状态码决定是否计），`requireCaptcha` 的 400
单独走一条 IP 维度弱阈值计数器、不进账号维度」。落地方式：

```ts
// 判定「成功」的回调默认是 res.statusCode < 400；把它重写成
// 「响应码 ≠ 本通道关心的状态码」→ 只有 401 计入凭据桶、只有 400 计入验证码桶
skipSuccessfulRequests: true,
requestWasSuccessful: (_req, res) => res.statusCode !== opts.countStatus,
```

- 凭据通道：`createLoginFailLimiters()` → 双维度 × 双窗口（5min + 15min 锁定），**只计 401**。
- 验证码通道：`createCaptchaFailLimiters()` → **仅 `ipKey`**，单窗口 5min、`max=20`，**只计 400**。
- **账号键根本不出现在验证码通道**——`requireCaptcha` 的 400 物理上进不了账号桶。

### 动态中文文案（裁定③附带要求：说清第几次、还要等多久）

`message` 支持函数式，从 `req.rateLimit` 取计数与 `resetTime`：

- 凭据：「登录失败次数过多（已连续失败 **N** 次），该账号与来源 IP 已临时锁定，**请约 X 分钟后重试**」
- 验证码：「图形验证码错误次数过多（已达 **N** 次），请重新获取验证码，**请在 X 秒后重试**」

`remainText()` 把 `resetTime` 转中文：≥60 秒说「约 X 分钟」、否则说「X 秒」。

### 真实链路取证（`USE_MOCK_DB=true`，端口 18080，非单测）

**取证方法说明**：两条通道各自持有**独立的 MemoryStore**，且限流器串联在前——
一旦某个桶被填满，同一 IP 的后续请求会被该桶拦住，从而无法再推进另一个桶。
所以两条通道**必须用各自独立的服务进程**取证（同一进程内无法穷尽）。
脚本：`D:/workBuddy/2026-09-12-02-26-01/b22-evidence.cjs`（仓外一次性工具，不进仓库）。
正确验证码由 **SVG `<text>` 明文**解出（`<text ...>X</text>` 逐个取字符），不猜、不绕过。

**取证 A｜验证码通道 → 证明「不锁账号」（`rate-limit-captcha.json`）**

```
错误验证码 #1  ~ #19   -> HTTP 400  msg="图形验证码错误"
                          ↑ 19 次验证码错误，全在阈值内

★★ 19 次验证码错误后，用【正确验证码 + 正确密码】登录
                          -> HTTP 200  msg="成功"  token=true
                          ↑ 关键证据：验证码错 19 次也**不锁账号**、不消耗凭据额度

错误验证码 #20         -> HTTP 400（达到阈值仍放行）
错误验证码 #21         -> HTTP 429
                          msg="图形验证码错误次数过多（已达 20 次），请重新获取验证码，请约 5 分钟后重试"
                          Retry-After: 299
                          ↑ 超限文案是验证码口径、含真实失败次数与剩余时间，且**无「锁定」字样**

超限后再用【正确验证码】-> HTTP 429
                          ↑ 顺带证明超限后是「短时拒绝」（IP 维度），而非账号锁定
```

**取证 B｜凭据通道 → 回归确认「维持原强度」（`rate-limit-credential.json`）**

```
错误密码 #1 ~ #5（验证码均正确） -> HTTP 401  msg="用户名或密码错误"
                                    RateLimit-Remaining: 4 → 3 → 2 → 1 → 0
第 6 次用【正确密码】            -> HTTP 429
                                    msg="登录失败次数过多（已连续失败 5 次），该账号与来源 IP 已临时锁定，请约 5 分钟后重试"
                                    Retry-After: 296
```

**一句话结论**：验证码错 19 次仍能正常登录（账号不被锁）；密码错 5 次即锁——
分流目标达成，且批 2.1 的凭据防护强度未削弱。

## 四、如实报备

1. **本批自纠一处文案 off-by-one（已修）**。首轮取证时验证码超限文案报的是「已达 **21** 次」——
   express-rate-limit 在拦截时给出的 `used` 是**含本次被拦请求**的计数，而本次请求根本没进业务层、
   不算一次失败。改为 `used − 1` 后与契约文档写的 20 次一致；并**补了钉死数字的断言**
   （`toContain("已达 2 次")` / `toContain("已连续失败 2 次")`）防回归。
   同理凭据通道现在报「已连续失败 5 次」（修前会报 6 次）。

2. **`RateLimit-*` 响应头反映的是「最后一个执行的 limiter」，不是两个通道各自的余额**。
   实测：验证码通道的 400 响应带 `RateLimit-Remaining: 4`——那是**凭据限流器**写的头
   （挂载顺序在验证码限流器之后，后写覆盖先写）。
   **这不影响拦截行为**（行为由各自 store 决定，已由上表 401/400/429 精确证明），
   但**运维/前端不要用这个头去判断验证码通道剩余次数**。要精确观测需给两条 limiter 分别命名头，
   属可选加固，本批未做（避免扩大改动面）。

3. **超限「约 5 分钟」是固定窗口语义，不宣称精确**。沿用批 2.1 的如实标注：
   底层是固定窗口，实际封锁到窗口结束（≤ 5 分钟），不是「命中时刻起算精确 5 分钟」。

4. **MemoryStore 仍是进程内计数、不建表**；多实例部署不共享（已登记 S3-17）。

5. **`requireCaptcha` 自身零改动**——分流完全靠限流器侧的状态码过滤实现，
   中间件与 `platformLogin` controller 都没动，既有 15 个 controller 级用例零修改即通过。
