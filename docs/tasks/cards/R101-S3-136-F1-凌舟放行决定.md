## 一、为什么放行（不是"破例开工"，是**分类**）

业主的三段门（2026-09-22）是**防"东做一点西做一点"**，并已写明三类合法例外：等外部输入的阻塞项、**已飞的阶段三服务端前置（S3-80）**、纯观察类。本单归入**同类第二项**，理由三条：

1. **它不改任何用户可见行为**：本单硬判据是"**8 角色 × 44 页可见性逐格不变**"，即"把现状可见性显式化 + 把判定粒度从前缀改成 code"，前端渲染结果**前后一致**。既不是新功能，也不是行为变更。
2. **它是 P0 安全线的唯一解锁前置**：G2 的 11 行后端写接口（`bank-account` 关闭 / `receipt` / `reconciliation` / `store-value-card` / `payment-new` / `sale-return` 等）当前**零权限校验**，任何登录角色都能调。要挂权限（阶段三）**必须先**让前端"看不见不应看见的入口"，否则会造出"点得到但 403"的故障——而"看得见谁"这件事，只有本单能把口径钉成可判定。
3. **零资源冲突**：全部落在 `app-mobile/**` + 新增迁移文件，与阶段一 C6（`saas-admin/**` + 后端）**文件域不重叠**、工作树独立，不挤占 C6 的推进节奏。

## 二、放行边界（写死，违反即判红）

1. **不得改后端权限**：`backend/**` 一律不动；**尤其不得**给 G2 的 11 行挂 `requirePermission`——那是阶段三，且必须在本单之后。
2. **不得连生产库、不得执行任何写 SQL**：迁移文件只写不跑。
3. **可见性逐格不变**：对照表 **8 角色 × 44 页**，差异格必须为 0；任何一格变化 ⇒ 判红（属阶段二）。
4. **迁移必须幂等 + 带回滚**（本项为凌舟 2026-10-01 追加要求，见 §三）。
5. 其余红线照派单卡执行（不得改 `admin-web/**`、`saas-admin/**`、`e2e/**`、`.github/**`、`deploy/**`、共享文档）。

## 三、追加要求（针对"生产数据写入"这一层，原卡未覆盖够）

本项目的部署链路**会在后端启动时自动执行 `docs/migrations/**` 的待执行迁移**（C6-3-1 的 184/185 即如此上线），因此本单的迁移文件**合并即等于对生产菜单表写入 25 个码 + 角色映射行**。据此追加三条硬要求：

1. **幂等**：重复执行不得报错、不得重复插入（用 `INSERT ... SELECT ... WHERE NOT EXISTS` 或 `INSERT IGNORE` + 唯一键；并在回传卡给出**"连续执行两次"**的原始输出）。
2. **回滚脚本**：在回传卡内**逐字给出**把本次新增的 25 个 `menu_code` 及其 `t_sys_role_menu` 映射行删掉的 SQL（限定 `menu_code IN (…)`，不得用宽条件）。
3. **执行前三件套**（由凌舟执行，执行方只提供）：① 备份命令（沿用 `deploy/02-mysql-backup.sh` 口径）；② 迁移前 `SELECT COUNT(*)` 快照；③ 合并后**只在生产做只读核对**（`t_sys_menu` 新增 25 行、`t_sys_role_menu` 新增行数 = 预期值、app-mobile 8 角色可见性对照表复核）。
