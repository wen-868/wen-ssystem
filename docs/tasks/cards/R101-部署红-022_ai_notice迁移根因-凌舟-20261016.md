## 四、修法（三选一，由执行方按业务语义定，**需给依据**）

1. **前缀索引**：`KEY idx_ai_notice_receiver (tenant_id, receiver(191))`（键长 `144 + 4×191 = 908 ≤ 3072`）—— 前提：查询是以 `tenant_id + receiver` **等值/前缀**过滤；若业务查询是 `LIKE '%…%'`，该索引本就用不上，应选 3；
2. **收窄列**：`receiver VARCHAR(191)`（键长 908）—— 仅在能证明"principal 串最长 ≤191 字符"时可用（该列语义是"首尾逗号归一化的接收人串"，**多接收人时会变长 ⇒ 需给上界证据**）；
3. **删掉该索引**：若 `receiver` 只参与 `LIKE '%…%'` 或应用侧过滤 ⇒ 索引无收益。
   ⚠️ **先核"哪些环境已成功应用过 022"**：**从未成功应用** ⇒ 可直接改 `022` 本体；**若某环境已应用** ⇒ 走**新迁移**（如 `023_…`）修正，**不得回改历史语料**（AI 侧同款纪律）。
4. **回滚路径**：`DROP INDEX idx_ai_notice_receiver ON t_ai_notice`（或对应新迁移的回滚块）——须在迁移里写明。
