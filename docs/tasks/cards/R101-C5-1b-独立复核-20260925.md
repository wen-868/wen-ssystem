## 四、修复正确性与风险

### 4.1 该写法是否**必然**消除 1267？反向假设是否成立？

**结论：必然消除该比较的 1267；反向假设下同样不报 1267，但"保住索引"的结论会反转。**

- 规则依据（MySQL 8.0 排序规则强制/coercibility 规则）：① 两侧同为 IMPLICIT 且 collation 不同 ⇒ 报 `ER_CANT_AGGREGATE_2COLLATIONS`(1267)；② **显式 `COLLATE` 子句的 coercibility = 0，优先于任何列（2）**，比较一律采用显式指定的 collation ⇒ 有显式 COLLATE 就不会出现"无胜出者"。本例显式 COLLATE 加在 `a.tenant_id` 上，比较 collation 被钉死为 `utf8mb4_0900_ai_ci`。
  （离线引用官方规则，沙箱无网络无法抓取原文链接 —— 属"离线引用"，已在 §八 报备。）
- **关键反证（假设真库两侧正好相反：`t_tenant.id`=unicode_ci、`t_ai_audit_log.tenant_id`=0900）**：`ON t.id = a.tenant_id COLLATE utf8mb4_0900_ai_ci` **仍不报 1267**（显式 COLLATE 胜出），但比较 collation（0900）会与 `t.id` 索引自身的 collation（unicode_ci）不一致 ⇒ **丢 `PRIMARY` 探测**，"COLLATE 加在非索引侧就保住索引"的论证前提崩塌。
- 语义差别提醒（同一前提反转时才会咬人）：`utf8mb4_unicode_ci` 是 **PAD SPACE**，`utf8mb4_0900_ai_ci` 是 **NO PAD**（尾随空格在等值判定上不同），且 `'ß'='ss'` 在 unicode_ci 为真、在 0900_ai_ci 为假。本库 tenant id 形态为 `default`/UUID（`[0-9a-z-]`，`092:78` 种下 `'default'`），两种 collation 的等值结果一致 ⇒ **当前数据下无差异**；但若将来出现尾随空格或非 ASCII 值，等值结果可能不同（这是"选哪个 collation"的语义选择，不只是性能选择）。

### 4.2 索引影响

**判定：阿坚"COLLATE 加在非索引侧 ⇒ 保住 PRIMARY 探测"—— 推理成立，但沙箱无 MySQL `EXPLAIN`，属待真库证实的推理，不是实测结论。**

推理链：LEFT JOIN 的语义强制 `a` 先被读取、`t` 为被驱动表；MySQL 只有在"**比较所用 collation = 索引列 collation**"时才允许用该索引做 `ref/eq_ref` 探测。本例比较 collation 取自显式 COLLATE = `t.id` 自身的 0900_ai_ci，二者一致 ⇒ 应仍可用 `PRIMARY`；反之若把 COLLATE 加到 `t.id` 侧或选 unicode_ci，比较 collation 即偏离索引 collation ⇒ 该索引不可用于本次探测。证据物：阿坚 §四.④ 的 `EXPLAIN`（判据可接受：LEFT JOIN 保证 a 在前；空库也可能给 `1 row` 的形态差异，真正要看的是 `t` 行 `key=PRIMARY` 而非 `type=ALL/key=NULL`）。

### 4.3 结果语义与排序

- **匹配结果**：对 `[0-9a-z-]` 形态的租户 ID，两 collation 等值判定一致；实测修复后 SQL 的 `params`/`WHERE` 与修前逐字一致（只有 JOIN 谓词多一个 COLLATE），**不改变筛选含义**。
- **排序**：`ORDER BY a.created_at DESC, a.id DESC` 未被加 COLLATE；`created_at` 为 DATETIME、`a.id` 为 BIGINT ⇒ 排序不受 collation 影响。
- **SELECT 列表**：`a.tenant_id AS tenantId` 的返回值不受 ON 子句里的 COLLATE 影响。
- 真库侧仍需实证"LEFT JOIN 真能命中租户行"（建议断言 `tenantName` 非空，见 §六.3）。
