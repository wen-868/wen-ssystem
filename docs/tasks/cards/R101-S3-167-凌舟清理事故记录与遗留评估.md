### 1.1 现象（有原始输出）

清理过程中一次 `git status --short` 出现 **640 个 ` D`（工作树删除）**，且根 `node_modules` 从约 1GB 掉到 **5 项 / 8MB**：

### 1.2 根因（探针复现，非推断）

Windows 的目录联接（Junction）对"目录搬运 / 递归删除"是**透明**的：

> 探针实测：对一个「含 Junction 的目录」执行 `Move-Item`
> ⇒ `linkExistsAfterMove=False`
> ⇒ **`targetKeepExistsAfterMove=False`**（联接目标的真实内容被搬走，原目标被删除）

**触发条件（已收窄，重要）**：**同盘** `Move-Item` 是重命名（只改目录项，不碰联接目标），**跨盘** `Move-Item` 是"复制 + 删除源"，**复制阶段跟随联接**。本次事故正是 `C:\...\Temp\*` → `D:\...\_hygiene-quarantine-*\` 的**跨盘**移动；同盘的 `ZXQL-MS\` 根清理（D: → D:）则未造成破坏。

**级联链条**：

1. npm workspaces 在 `node_modules/` 下按包名建**目录联接**指向真实子包（如 `node_modules/zhixiang-app-mobile -> app-mobile`）；
2. 临时验证沙箱把 `node_modules` 建成指向主仓的联接（实测 `%TEMP%\s3150f2-verify-496687869\node_modules -> wen-ssystem\node_modules`）；
3. 清理时对这些含联接的目录执行 `Move-Item`
   ⇒ 跟随第 1 层联接进入主仓 `node_modules`
   ⇒ 再跟随第 2 层联接进入 `admin-web/`、`miniapp/`、`saas-admin/`…
   ⇒ **级联搬空**。

### 1.3 失败方向对比（三种原语，均为实测结论）

| 原语 | 是否跟随联接 | 判定 |
|:--|:--|:--|
| `Move-Item <含联接目录>` | **跟随**（搬走目标内容并删除原目标） | ❌ 禁用 |
| `Remove-Item -Recurse` | **跟随** | ❌ 禁用 |
| `[IO.Directory]::Delete($p, $true)` | **不跟随**，遇联接抛 `Access is denied` | ⚠️ 可用，但需先摘联接 |
| `[IO.Directory]::Delete($link, $false)` 作用于联接本身 | 抛 `Could not find a part of the path` | ❌ 摘不掉联接 |
| `fsutil reparsepoint delete <path>` | 只摘重解析点标记，**目标毫发无损** | ✅ 摘联接的正确原语 |

**同型排查（已完成，结论=非本次事故）**：隔离区 `zxqlms-root-junk` 内经扫描发现 **17,446 个 symbolic link**（来自 2026-09-16 被 trash 的 ai-base 子工程 `.ai-base-trash-20260916\node_modules\*`，pnpm 布局）。逐个解析目标：**`resolving=0`（全部悬空）**；对应活跃位置 `backend/ai-base` 现为**空目录且 0 个跟踪文件**，说明该子工程在 2026-09-16 被移走时链接即已失效，**与本次事故无关**。隔离区其余分区复查：**活联接 0 个**。

**安全配方**（已固化为工具，见 §三）：
① 手工遍历收集 reparse point（遇到即记录、不深入）→ ② 逐个 `fsutil reparsepoint delete`
→ ③ `[IO.Directory]::Delete(root, $true)`。
第 ③ 步对**残留**联接会**直接抛异常**，因此漏项时**报错停下**而不是静默销毁目标——**失败方向安全**。
