## 一、一句话结论

点一次「记住我」（**默认已勾选**）→ 登录请求带 `rememberMe:true`（等 S3-160 换 30 天 token）→ 账号与口令写入 AES-256-GCM 加密存储 → 之后打开客户端：token 有效就直接进首页（**一次登录请求都不发**），token 真失效就停在登录页且**账号口令已自动带出**，用户零手输；取消勾选登录则存储内**不留残留**。

## 六、风险与自我报备

**R1（安全权衡·本单最需要你点头的一条）**：「记住我」把**口令本身**长期保存在客户端（虽经 AES-256-GCM 加密，且密钥由设备指纹派生、与 token 同一套机制）。这与业界通行的「只记账号、用 refresh token 代替记口令」不同。
风险敞口：设备被 root/提取时，密文与派生密钥可被一并取得 ⇒ 等价于泄露口令明文。
我的处置：**按派单明确要求实现**（凌舟已拍板），但建议后续评估：(a) 增加「记住我」默认关闭 + 首次登录后弹一次引导；(b) 后续改为 refresh token 方案，本单的口令存储作为过渡；(c) 至少在「我的/设置」里给用户一个**清除已记住凭据**的显式入口（**本单未做**，`clearSavedCredentials()` 已具备能力，接一个入口即可）。请裁定优先级。

**R2（判据与真实性的边界）**：四场景**全部**由本进程 mock 应答。已验证的是「**给定后端这样回，前端这样应对**」，**没有**验证「后端真的会这样回」。这是密闭红线⑥下的必然取舍（且 S3-160 未落地，想验真也验不了）。

**R3（派单反测措辞与因果不一致，已按实测处理）**：派单写「去掉自动带出 ⇒ **B/C** 必红」，但 B 的判据（重开后不发登录请求）与「自动带出」无因果关系。我把反测拆成两组分别对应 C 与 B，并在 §2 如实标注（见「判据分辨力说明」）。请确认这个处理方式你认可。

**R4（演示登录未纳入「记住我」）**：`handleDemoLogin()`（S3-159 的一键演示入口）**保持原样**——它不读「记住我」、也不把演示凭据写入「记住的账号口令」。理由：演示凭据本就是公开信息，写进"记住的账号"会污染用户自己的账号记录。
副作用：**点过演示登录后，「记住我」勾选态与存储内容不变**。若你希望演示登录也走同一套记住逻辑，请回卡，我另改。

**R5（退出登录口径·派单要求"口径须写明并给证据"）**：
`userStore.logout()` ＝ **始终清 token / 用户态 / 租户 / CSRF**；**账号口令按「记住我」勾选状态决定**——
- 勾选 ⇒ **保留**（下次回来仍是零输入，符合"记住我"的字面承诺）；
- 未勾选 ⇒ **清除**（不留残留，与验收④同一口径）。
证据：`app-mobile/src/stores/user.ts:105-112`（`if (!getRememberMe()) clearSavedCredentials()`），改动面见「二」③。
理由：退出是**主动动作**而非安全事件；真正的凭据销毁手段是「取消记住我并登录一次」（验收④已证）。

**R6（本轮踩到的两个取证装置坑，已写进装置注释，供参考）**：
1. 🔴 Playwright 路由通配 `**/api/**` 会**连 dev 模式的源码模块一起拦下**（本项目有 `app-mobile/src/api/**` 目录 ⇒ 请求路径含 `/api/`）⇒ 模块脚本被替换成 JSON，页面直接空白、`waitForSelector` 超时。正确做法：**用路径前缀谓词** `url.pathname.startsWith('/api/')`。
2. ⚠️ mock 版本检查接口若回 `data:{}`，会被 `utils/update.ts:131` 判成「有新版本」⇒ 弹 `uni-modal` **遮住登录按钮**，`page.click` 一直超时。正确做法：回 `data:null`。
两条都是"装置自己制造假故障"，不是产品缺陷——记录在此避免后人重复踩。

## 附二：一句话摘要
