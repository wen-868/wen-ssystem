## 六、风险与自我报备

1. **D1 的租户范围是本单自定的口径**：两条 UPDATE **不带 `tenant_id` 过滤**，对全部租户的 `STORE_MANAGER` 行生效
   （理由：各租户店长是同一角色定义的克隆行，只改 `default` 会让 demo 等租户店长权限不一致）。
   若你要收敛到 `default`，改 `WHERE` 加 `tenant_id = 'default'` 即可（迁移与 ops 各两处，回滚同）。
   ⇒ 已列入 §九-④，**请确认**。
2. **14 个新码当前不给任何角色**：`system:*` 菜单只授予 `OPERATION_ADMIN`（0 账号）/`READONLY`（观察员）/`STORE_ADMIN`（0 账号）。
   若 `OPERATION_ADMIN` 将来被启用（0 账号 → 有账号），它靠 `["*"]` 自动命中，无需补码；
   但**接线后**若发现某个在用角色其实能看到这些页面，就会 403 ⇒ 接线批必须按 I1' 重判（本单已在文档写明）。
3. **本单未能验证的边界（明写在先）**：
   ① 生产库的真实数据形态（店长行数、是否已有其中一个码）未读——生产只读须走 R-PROD-READ 通道；
   ② 迁移在 MySQL 8.0.28 上验证，未在 8.4/9.x 上验证；
   ③ `t_sys_menu` 的 `visible/status` 取值沿用 203 的 `1/1`，未复核各租户历史行的既有取值分布。
4. **反测 C 曾临时改动真实迁移文件**（删 1 行），已按 SHA256 逐字节复原并复跑全绿（`raw/62-*`）；

   —— 若你要按端点 1:1 拆，请在下批卡面写明粒度，否则前后批会同域两套粒度。
7. **卡外观察两项**（回执 §六）：① 空库启动后角色权限串为空（079/128 被守卫跳过）⇒ 灾备/新库重建拿不到生产权限串；
