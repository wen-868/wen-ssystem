## 二、根因假设 + 证伪/证实（验收标准②）

### H1：主要耗时 = 顺序 import 全部 185 个 `.routes.ts`，与文件数线性相关 ✅ 证实
沙箱探针（`out/sandbox-probe.txt`）：
- **A) 185 文件顺序 import**：总耗时 **40254ms**，均值 **217.6ms/文件**，最大 **4381ms**（`admin-auth.routes.ts`），导入失败 0。
- **C) 子集线性度**：N=25→1195ms、N=50→1987ms、N=100→4047ms；由 N=25 线性外推 N=100 预测 4780ms，实测 4047ms，**偏差 −15.3% → 强线性**。
- **B) setupRoutes 冷 426ms vs 二次（同进程已缓存）346ms，ratio 0.81** → 证明耗时几乎全部是模块加载，setupRoutes 自身逻辑微秒级。

### H2：冷启动 transform 占比高、是抖动源 ❌ 证伪（降级为"固定冷启动税"）
3 次真实跑 transform = 19.56/20.44/38.04s，相对恒定；case1 抖动（42–98s）在 tests 阶段、与 transform 无关。结论：transform 抬高 wall 但不导致 120s 判红抖动；真正抖动是 tests 阶段 185 文件顺序 import 的并发放大。

### H3：存在"连库/起服务"被顺带加载的慢模块 ❌ 证伪
H2 的 B 项二次调用仅省 80ms，无重初始化；且只有扫描真实整目录的 case1 慢（≤489ms 的其余用例均用 fixtures 小目录或纯函数）。setupRoutes 仅 `readdirSync + import + app.use`，无 DB/服务连接 → 排除"某模块连库"假设。

## 三、处置建议（治标 + 治本，标注代价与覆盖面）（验收标准③）

### 治标（过渡，立即可做）
- **把 case1 的 `120000` 抬到 `180000`（3 分钟）**。
- **倍数余量理由**：≈10× 凌舟空闲基线 18.18s；≈1.85× 本机单跑最差 97.69s；比原 120s 阈值高 60s，给并发放大留缓冲。
- **为什么不直接抬到 10 分钟（600s）**：routes 文件数会随业务增长，600s 会掩盖"真慢"，使门禁退化为"永远绿"，违背 S3-125/G2 已踩的"红=真缺陷"可信度原则（派单一已点明）。
- **强制加「耗时基线告警」（凌舟硬性要求）**：当 case1 实际耗时 > 历史中位数 3× 时输出 warn。本机中位数 ≈ (42.26+46.73)/2 ≈ 44.5s ⇒ 告警线 ≈ 135s，逼近 180s timeout 即提前预警，下次漂移在判红前就被发现。

### 治本（推荐，治本优先）
**方案 A — 判据重构（推荐首选）**：把 case1 从"扫描整个真实 `routes/` + `resolves.not.toThrow()`"改为：
1. **固定已知前缀清单 `toContain` 断言**：从当前 199 个注册前缀抽代表集（或全量快照），断言 `prefixes` 必含这些关键前缀；
2. **新增文件护栏**：扫描目录得文件集合，与基线 diff，**新增的 `.routes.ts` 必须贡献 ≥1 个新前缀，否则红**。

- **覆盖面影响**：原"扫整目录"是"全量但零断言"（反测 A 已证它什么都不校验）。改为固定清单后，覆盖面从"假全量"变为"真校验关键前缀 + 护栏抓新增"——**覆盖面不收窄，反而获得真实正确性信号**。代价：routes 大量新增/重命名时需同步更新清单（可脚本化生成快照，CI 跑一次即可）。
- **同时治"慢"与"假绿"**：case1 仍扫描目录（保持对新增文件的发现），但断言从"不抛"变"关键前缀必在"，使真实注册失败（如某文件导入失败导致前缀缺失）也能红（反测 B 已证 `toContain` 机制能红）。配合"只 import 清单内文件 + 护栏增量"可把 import 量从 185 降到确定性集合，消除线性增长抖动。

**方案 B — 并行化 import（性能向，可选增强）**：把 `setupRoutes` 顺序 `for...await import` 改为 `Promise.all`（或分批并行）。
- 沙箱探针 D：顺序 N=60=2392ms vs 并行=1032ms，**加速比 2.32×**。
- **代价/风险**：ESM 模块图并行加载可能触发模块级副作用竞态（效期扫描器、`OrderTimeoutScanner`、门店管控定时器等 top-level 启动逻辑），需先在隔离环境验证无竞态；且**不修复反测 A 暴露的断言失明**，仅让超时更晚发生。故只作 A 的可选性能增强，不能替代 A。

**方案 C — transform 缓存/预热**：transform 冷启动 19–38s 是固定税。Vitest 4 默认已共享 transform 缓存（本机 RUN2/RUN3 已降到 ~20s）；若 CI 冷启动仍偏高，可加 `--no-isolate` 或预热。**代价**：仅削冷启动，对 tests 阶段 185 文件 import 抖动无益；覆盖面不变。

**推荐落地顺序**：先 A（兼得"不慢 + 不假绿"）→ B 作为 A 的可选性能增强（并行 import 清单内文件）→ C 视 CI 冷启动是否仍偏高再定。
