## 一、根因（三环相扣）

| # | 环节 | 事实 |
|---|---|---|
| ① | 部署脚本**故意钉死 pnpm 9** | `deploy/ai-base-deploy.sh:55-67`：检测到 pnpm 主版本 ≥10 即**降级为 pnpm@9**，注释写明"pnpm 10/11 需 Node 22，服务器 Node 20 会报 `ERR_UNKNOWN_BUILTIN_MODULE`" |
| ② | **`overrides` 的声明位置随主版本迁移** | **pnpm 9 只读 `package.json#pnpm.overrides`**，**不读** `pnpm-workspace.yaml#overrides`（后者是 pnpm 10+ 的位置） |
| ③ | 4 条 overrides **只写在 yaml** | `ac0550c`（2026-09-05 依赖通告整改）把 `fast-uri` / `@napi-rs/canvas` / `qs` / `@xmldom/xmldom` 只加进 `pnpm-workspace.yaml`，`package.json` 里没有 |

→ pnpm 9 读到**空集**，与 `pnpm-lock.yaml` 里**已记录**的 4 条不一致 → `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH`。

**关键澄清：`pnpm-lock.yaml` 本身没有错。** 其头部 7–11 行写着这 4 条 overrides，`importers['.']` 的解析也与之一致。所以本卡**不需要重算 lock**——原卡"同步 overrides 与 pnpm-lock"的表述，经查证实际指向的是"让 pnpm 9 读得到 overrides"。

**这条也把"升级 pnpm 到 10+"这条常规解法证伪了**：受 ① 的 Node 20 约束，升级会连带升级运行时，属另一量级变更 → **问题被逼成"只能改仓库侧"**。

## 五、连带发现（超出本卡字面范围，已一并修复 —— 请凌舟裁定）

**修好 install 后，`pnpm build` 仍然 EXIT 1。** 根因是 `src/brain/proactive/weekly-plan.service.ts`
的 3 处类型错误：`TS6196`（接口 `WeeklySignalRow` **已声明却从未被使用**）+ 2×`TS7006`（参数 `r` 隐式 `any`，
因 `rows` 来自 `dataSource.query()` 的 `any`）。

**它被掩蔽了两层**：
1. 部署序列是 `install → build`，`install` 一失败就 `ai_fail "<原因>"` 收尾 → **`build` 从未被执行**；
   历史部署更是在**第一步 `npm ci`** 就中止，连 AI 底座都没走到 → **前置失败永久掩蔽后置缺陷**。
2. `tsconfig.json` 开 **`isolatedModules: true`** → **ts-jest 跳过类型检查** →
   `pnpm test` 全绿（"102 套件 978 用例全过"）**但类型是错的**，只有 `nest build`（tsc）才报。

**修法（取原作者意图，非掩盖）**：接口字段（`title`/`content`/`created_at`）与查询完全对应，
故将其用作 `this.dataSource.query<WeeklySignalRow[]>()` 的类型参数 —— **一行同时解掉 3 个错**，
且**消除**了 `any` 的来源。**无运行期行为变化**。

> 凌舟裁定：**不采用 `(r: any)`** —— 那是"掩盖错误"（把报错点挪走、类型仍然丢），
> 与"消除错误"不是"保守 vs 激进"的关系，而是**对 vs 错**。已按此执行。

**凌舟据此给 S3-37（ZXQL-AI 自有 CI）加硬要求：CI 必须包含类型检查（`build` 或 `tsc --noEmit`），
只跑 `jest` 不算门禁。**（与"假 CI 门禁"同族：绿灯被别的东西替代了。）
