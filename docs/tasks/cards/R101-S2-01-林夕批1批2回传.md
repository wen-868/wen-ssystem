**「禁止英文原文上屏」的落地方式**：`pickBackendMessage()` 只接受含中文的文案，纯 ASCII（如后端某分支漏出的 `fail`）一律丢弃并回退到状态码文案。这样既保留后端给出的具体中文原因，又杜绝英文直出。

### 顺带修复（上一轮遗留）

`83e26ba5` 为消除「踢登录时重复弹英文」给 401 分支补了 `return`，副作用是后端给出的真实中文原因（登录页「用户名或密码错误」、普通页「未登录」）也被一并吞掉，与裁定 6「失败场景必须可见」冲突。现改为：先给中文提示，再 `logout` + 跳转；并发请求 1.5s 内只提示一次。

### 实测得出的防误报改动（如实声明：预防性，非修复现行 bug）

扫描 `backend/src` 生产代码，发现 **3 处不守 `code: "0"` 约定的成功响应**，若不识别会被误判为失败并弹出假报错：

| 位置 | 成功时响应 |
|---|---|
| `services/admin/instant-retail.service.ts:259` | `{ code: "200", message: "success" }` |
| `services/instant-retail/platform-integration.service.ts:55` | 同上 |
| `services/admin/payment.service.ts:183` | `{ success: true, code: "SUCCESS", message: "成功" }` |

故 `isBizFailure` 增设 `success: true` 短路 + 成功码白名单（含来源行号注释）。**已实测这 3 处均不在旧客户端 40 个接口的调用链上**（前端 `paySubscription` 走 subscription service，用标准 `ok()`），所以这是防御性的，不是修复现行问题。

### 一条实测边界，须如实报备

探测 7 条后端错误路径，**HTTP 状态码全部正确**（404/400/401），**未发现「HTTP 200 + 业务码非 0」的真实案例**。因此旧客户端「成功拦截器判业务码」的增强在现有后端下不会被触发，实际生效的是 error 分支中文文案。此项属防御性改动，不宣称「修复了静默失败」。

## 二、批2 `e892c1f4`｜图形验证码（裁定 4.1）

### 背景

后端原先**完全没有**验证码实现，前端 `captchaText` 写死「待接入」且只做非空校验——等于没有验证码。而平台登录接口**不限流**（`server.ts:172` 注释「应用户要求不限流」），故验证码是当前唯一的爆破防护。

### 交付内容

| 层 | 文件 | 要点 |
|---|---|---|
| 服务 | `backend/src/services/platform/captcha.service.ts`（新增） | 4 位字符（剔除 `0/O/1/I/L` 易混淆字符）；**零依赖**手写 SVG（未引入 `svg-captcha`/`canvas`）；Redis `SETEX` TTL 300s |
| 中间件 | `backend/src/middleware/captcha-guard.ts`（新增） | 校验失败按「缺参数 / 已失效 / 不匹配」给不同中文文案 |
| 路由 | `backend/src/routes/platform-auth.routes.ts` | 新增 `GET /captcha`；`POST /login` 挂 `requireCaptcha` |
| 控制器 | `backend/src/controllers/platform/platform-auth.controller.ts` | 新增 `getCaptcha`；`platformLogin` **零改动** |
| Redis | `backend/src/config/redis.ts` | 导出 `getRedis` 供非缓存语义复用（复用连接，不多开池） |
| 前端 | `saas-admin/src/api/auth.ts`、`stores/auth.ts`、`views/login/PlatformLogin.vue` | 进页面自动拉图、点击刷新、登录失败自动换图、「待接入」占位移除 |
| 契约 | `docs/API接口文档.md` | 新增 P1b + 详细章节；顺带修正原 login 条目与实现不符的描述（`user`→`admin`、补 `csrfToken`） |

### 三个实现取舍（附理由）

1. **校验放中间件而非 controller**：`platformLogin` 签名与调用方式零改动，既有 controller 单测（14 用例）无需修改；只有经过路由链的集成测试需 mock 该模块。
2. **用 Lua 脚本而非 `GETDEL`**：本机 Redis 实测为 **3.0.504**，`GETDEL` 需 6.2+，Lua 的 `GET`+`DEL` 原子性兼容更低版本。
3. **取出即删（一次性）**：无论校验成功与否都作废本次验证码，防止同一张图被反复试码；前端据此在登录失败后自动换图（不换则重试必然再失败）。

### 测试

- 新增 `services/platform/captcha.service.test.ts`（11 用例）：生成结构 / 图片可解码 / 字符数 / 无易混淆字符 / 唯一性 / 写入键名；校验成功 / 大小写不敏感 / 一次性消耗 / 错误码也消耗 / 缺参数 / 未知 id / Redis 降级路径。
- `routes/platform-auth.test.ts`（+4 用例）：`GET /captcha` 下发结构；验证码错误 400 且**不进入账号密码校验**；已失效与未填写的区分文案。
- **全量：542 files / 5793 tests 全部通过**（基线 5778 + 本轮新增 15）。
- `backend tsc --noEmit` exit 0；前端 `vue-tsc` 20 处（＝基线）。

### 顺带修复：测试夹具与生产契约不一致

`__tests__/fixtures/create-test-app.ts` 的错误响应字段原为 `message`，而生产 `errorHandler` 返回的是 **`msg`**（`shared/response.ts` 的 `fail()`、`error-handler.ts:50`）。

这种「后端发 `msg`、测试断言 `message`」的错配会让契约错误长期测不出来——**前端 F1 的 `message`/`msg` 取错字段正是同类问题**。已把夹具改为 `msg`（并补 `traceId` 与生产对齐），同步修正唯一依赖该字段的 `sale-return.test.ts` 两处断言。

### 真实 HTTP 证据（本机 Redis 3.0.504 + `USE_MOCK_DB`）
