## 七、改键的可执行方案

### 7.1 方案甲（推荐）：直接换成 `(tenant_id, barcode)`

**适用范围**：3 处 DDL 出处 + 既有生产库 1 条迁移（含同型历史副本按表名套用）。

**A-1 前置查重（必须先跑，期望 0 行；有行则先处置数据，再执行改键）**

```sql
-- 跨租户同条码（现键不可能出现，但历史副本/导入工具可能绕过）
SELECT barcode, COUNT(DISTINCT tenant_id) AS tenant_cnt,
       GROUP_CONCAT(CONCAT(tenant_id, ':#', id) ORDER BY tenant_id) AS detail
FROM t_product_sku
WHERE barcode IS NOT NULL AND barcode <> ''
GROUP BY barcode
HAVING COUNT(DISTINCT tenant_id) > 1;
-- 同租户同条码（新键会拒，必须先清）
SELECT tenant_id, barcode, COUNT(*) AS cnt, GROUP_CONCAT(id) AS ids
FROM t_product_sku
WHERE barcode IS NOT NULL AND barcode <> ''
GROUP BY tenant_id, barcode HAVING COUNT(*) > 1;
```

**A-2 切键（幂等：仅当旧键在且新键不在时才执行）**

```sql
-- 幂等写法依据：MySQL 不支持 DROP INDEX IF EXISTS / ADD INDEX IF NOT EXISTS，
-- 先例见 docs/migrations/092_租户ID.sql:34-58（information_schema + PREPARE）
SET @tbl := 't_product_sku';
SET @has_old := (SELECT COUNT(*) FROM information_schema.STATISTICS
                 WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = @tbl
                   AND INDEX_NAME = 'uk_product_sku_barcode');
SET @has_new := (SELECT COUNT(*) FROM information_schema.STATISTICS
                 WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = @tbl
                   AND INDEX_NAME = 'uk_product_sku_tenant_barcode');
SET @sql := IF(@has_old > 0 AND @has_new = 0,
  CONCAT('ALTER TABLE `', @tbl, '` DROP INDEX `uk_product_sku_barcode`, ',
         'ADD UNIQUE KEY `uk_product_sku_tenant_barcode` (`tenant_id`,`barcode`)'),
  'SELECT ''skip: t_product_sku barcode key already migrated'' AS result');
PREPARE stmt FROM @sql; EXECUTE stmt; DEALLOCATE PREPARE stmt;
```

> 单条 `ALTER` 同时 DROP + ADD ⇒ 原子：若前置查重没跑干净（存在重复），整条 ALTER 失败回滚，**旧键保持**，不留"无唯一约束"的中间态。

**A-3 验证 SQL（迁移末尾必须带）**

```sql
SELECT INDEX_NAME, NON_UNIQUE, GROUP_CONCAT(COLUMN_NAME ORDER BY SEQ_IN_INDEX) AS cols
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 't_product_sku'
GROUP BY INDEX_NAME, NON_UNIQUE ORDER BY INDEX_NAME;
-- 期望：uk_product_sku_tenant_barcode | 0 | tenant_id,barcode
--       idx_product_sku_barcode      | 1 | barcode
```

**A-4 回滚（幂等：仅当新键在且旧键不在时才执行）**

```sql
SET @tbl := 't_product_sku';
SET @has_old := (... INDEX_NAME = 'uk_product_sku_barcode');
SET @has_new := (... INDEX_NAME = 'uk_product_sku_tenant_barcode');
SET @sql := IF(@has_new > 0 AND @has_old = 0,
  CONCAT('ALTER TABLE `', @tbl, '` DROP INDEX `uk_product_sku_tenant_barcode`, ',
         'ADD UNIQUE KEY `uk_product_sku_barcode` (`barcode`)'),
  'SELECT ''skip: already rolled back'' AS result');
PREPARE stmt FROM @sql; EXECUTE stmt; DEALLOCATE PREPARE stmt;
```

> ⚠ **回滚前提**：表内不存在"跨租户同条码"。若改键后已写入跨租户同条码，回滚必然失败（`Duplicate entry`）——必须先按 A-1 的口径清理，才能回滚。这就是 §一"可逆窗口有限"的可执行含义。

**A-5 幂等验证方式（反测式，可复跑）**

1. 首次执行 A-2 → 输出 `(无输出，语句返回空)`，A-3 显示新键； 2. **第二次**执行 A-2 → 输出 `skip: t_product_sku barcode key already migrated`，A-3 索引集合不变； 3. 故意把 A-2 的 `@has_new` 判据去掉（反测）→ 第二次执行应报 `Duplicate key name` ⇒ 证明幂等判据确实在起作用（不是"没报错"）。

**A-6 三处 DDL 出处 + 内联路径的改法**

| 出处 | 改法 |
| --- | --- |
| `backend/src/shared/migration.ts:870` | `UNIQUE KEY uk_product_sku_barcode (barcode),` → `UNIQUE KEY uk_product_sku_tenant_barcode (tenant_id, barcode),` |
| `docs/init_database.sql:447` | 同上（`migration.ts:594-598` 启动时解析执行此文件） |

| 生产同型副本 `product_sku` / `t_t_product_sku` | 仓库无建表脚本；迁移脚本建议以变量数组按表名循环套用 A-2/A-3（`t_product_sku` 必做，两张副本由凌舟在服务器侧确认存在性后套用） |

### 7.2 方案乙（保守）：保留旧键，先补数据/口径再改

**做法**：不动键，先做三件事：① 建"条码占用"登记（如 `t_tenant_barcode_claim`）让跨租户占用可查；② 在 `updateSkuBarcode`/建品/导入三处加"跨租户占用"显式提示（400 + 明确文案，不再是 500）；③ `library-copy` 降级改为可配置（撞键时是降级还是跳过）。

**为什么本项目不需要乙**：

1. 生产 `t_product_sku` 仅 **12 行 / 跨租户同条码 0 条** ⇒ 方案甲的前置条件天然满足，不需要"先补数据"这个乙方案的核心动机；
2. 乙方案**不解决根因**（全局唯一键仍在），只把 500 变 400 ⇒ 租户乙依然**永远无法**使用一个已被租户甲使用的条码，多租户业务的硬伤仍在；
3. 乙方案要新建表 + 改 3 处业务逻辑 ⇒ 改动面**大于**方案甲（甲是 DDL-only + 1 条内联 ALTER），违反"最小改动"；
4. 甲方案的风险已被 §八 覆盖（单条 ALTER 原子、12 行、可逆窗口明确）⇒ 没有"必须先降风险才能改键"的必要。
   **结论：乙方案在**本数据实况下**不采纳**；仅当"生产存在跨租户同条码且业务上确实要禁止"时才需要乙（此时应先由产品口径裁定"同条码跨租户到底允许不允许"）。

## 八、风险与窗口

| 维度 | 评估 |
| --- | --- |
| 表规模 | 生产 `t_product_sku` **12 行**（凌舟实测）；即便退化到 `ALGORITHM=COPY` 也是毫秒级 |
| 是否锁表 | 单条 `ALTER ... DROP INDEX, ADD UNIQUE KEY` 在 MySQL 8 对 InnoDB 通常 `ALGORITHM=INPLACE, LOCK=NONE`；建议显式写上并在低峰执行，且先跑 A-1 查重 |
| 索引长度 | `tenant_id VARCHAR(36)` + `barcode VARCHAR(128)`，utf8mb4 下 144+512 = **656 字节**（< InnoDB 3072 上限）⇒ 复合唯一键可建 |
| 并发写入窗口 | DROP+ADD 在**同一条 ALTER** 内，MySQL 8 原子 DDL ⇒ 应用侧不会看到"两个键都不在"的中间态；DDL 执行期间 DML 短暂排队（12 行，可忽略） |
| 失败回滚手段 | ① ALTER 失败 = 自动回滚（旧键保留）；② 成功后需要回退 → 执行 A-4；③ 回退前必须先跑 A-1（跨租户重复会阻断回滚） |
| 数据不可逆点 | 改键后**首个跨租户同条码落库** ⇒ 之后的回滚需先清理数据。建议观察期 24h、期内不做批量导入/调取压测 |
| 生产副本 | `product_sku` / `t_t_product_sku` 同型键未处理时，改 `t_product_sku` 不影响它们（但副本若仍在用则是另一处隐患，需凌舟确认副本是否废弃） |
| 业务口径风险 | 若产品口径是"同一条码全平台只允许一个商品"（如防串货），改键会放开互斥 ⇒ **需凌舟/产品确认口径**；本评估认为多租户 SaaS 下应允许（同型先例：`t_sys_config` 已从 `uk_config_key` 改为 `(config_key, tenant_id)`，`migration.ts:653-661`） |
| 静默跳过风险（内联路径） | `safeExec` 的 `SKIP_ERRORS` 含 `ER_DUP_ENTRY`（`migration.ts:31-41`）⇒ 内联 ALTER 因重复数据失败时**只记 INFO 跳过**。必须配 §7.1 A-6 的 information_schema 自检，否则会重演"门禁/迁移只报不红"的老问题 |
