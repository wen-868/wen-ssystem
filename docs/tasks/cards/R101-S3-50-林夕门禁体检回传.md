## 2. 重点核查项结论

### 2.1 覆盖率门禁：有阈值 → 能红（已红测证明）
`backend/vitest.config.ts` **确实配置了 `coverage.thresholds`**（非 Jest 的 `coverageThreshold`）：
- 全局 `statements:63 / branches:51 / functions:62 / lines:64`
- `src/services/admin/**`：`statements:54 / branches:50 / functions:53 / lines:55`

→ **不是装饰性门禁，能红**。活体红测：PR#8（run 35131597830）把阈值改 100 后 "Backend coverage gate" = **failure**，证明阈值生效。
⚠️ 注意：初次审计我误用 `coverageThreshold`(Jest 写法) 检索得到"无阈值"，实为错误键名；以 `thresholds` 为准。

### 2.2 Dependency audit / Duplication check：非阻断（装饰性）
两者均 `continue-on-error: true` → **结构性不能红**（红绿都不影响 PR/合并结论）。步骤显示名已带 `(non-blocking, baseline recorded)` 注释，但 **建议把 "(non-blocking)" 写进 GitHub 步骤显示名本身**（目前只在注释里），避免被误读为门禁。仅建议，未改动。

### 2.3 Flow / QA / Security smoke：均真实退出非零（源码证据）
- `scripts/self-test.mjs`：任意请求 `!res.ok || body.code!=="0"` 即 `throw`（`request()` 内 `throw new Error(...)`），脚本顶层 throw → 非零退出。→ Flow self test 能红。
- `scripts/qa-regression-test.mjs`：同样模式，多处 `throw new Error(...)`（如 `if(!miniOrder.orderNo) throw...`）。→ QA regression 能红。
- `scripts/security-smoke.mjs`：`:118` `process.exit(passed === results.length ? 0 : 1)`；`:121-124` `run().catch(err => { ...; process.exit(1) })`。任一检查失败即 exit 1。→ Security smoke 能红（RT4 已证）。

### 2.4 Start mock backend / Wait for backend：依赖链有效
`Start mock backend` 是 `&` 后台（exit 恒 0，非门禁）；`Wait for backend` 用 `wait-on ... || (cat /tmp/zhixiang-backend.log; exit 1)` 兜住 → 后端没起来则本步红。**有效，依赖链成立**。

### 2.5 分支保护 / 必需检查：无 → 元层面假门禁（最重要）
`gh api repos/wen-868/wen-ssystem/branches/main/protection` 返回 **`Branch not protected`（HTTP 404）**。
→ **main 没有任何 required status checks**。推论：ci.yml / e2e.yml / deploy.yml 哪怕全红，PR 照合、push 照部。**所有门禁在"拦合并"这一最终目标上全部失效**。

### 2.6 codeql.yml：永远绿
20/20 全 success。CodeQL 默认不使 workflow 失败（仅上传 Security 面板）。历史上从未因发现漏洞变红 → **结构性假门禁**。

### 2.7 build-exe.yml：能红能绿
触发 `admin-web/**` push + `workflow_dispatch`。历史 2 绿 / 18 红，近 2 次转绿 → 有效门禁。

### 2.8 deploy.yml Deploy via SSH：有效但**不受 CI 结果约束**
- 历史有 S3-43/45 转红证据（能红，有效）。
- **但 deploy.yml 是独立 workflow，仅在 `push main`（+paths-ignore）与 `workflow_dispatch` 触发，不依赖 ci.yml 成功**。即 **CI 全红也照样部署** → 部署动作不被门禁保护。建议加 `needs: ci`（或 `if: success()`）使其受 CI 约束（需评估是否影响紧急 hotfix 部署）。

## 5. 哪些门禁其实拦不住合并（元结论）

**结论：在"拦合并"这一最终目标上，目前没有任何门禁生效。**

- **根因**：main 无 branch protection、无 required checks（§2.5）。GitHub 不会因为任何 workflow 红而阻止 PR 合并或 push main。
- **叠加**：deploy.yml 还不依赖 CI 结果（§2.8），所以即便 CI 红，生产部署仍照常执行。
- **对"已修假门禁"的影响**：S3-47/48/49 的修复让对应门禁"能红"，但因为没有分支保护，**它们红了也无人被拦**——修复只恢复了"信号能力"，没恢复"阻断能力"。
- **建议优先级**：先上分支保护 + 必需检查（§4 严重项），再逐个补反测与修 flaky / CodeQL / deploy 依赖。
