### 拍板项 1：反测装置路线口径（**建议你裁定，后续同类单照此执行**）

- **议题**：验证 workflow 类改动时，「既要真实触发、又不能污染生产」该怎么取？本单我用了自创方案，与苏然的建议不一致，两人做法不同会导致同类单证据口径不可比。
- **方案 A（本单实际采用）**：临时把 `push.branches` 放宽到测试分支 + 给真实部署步骤加 `if: github.ref == 'refs/heads/main'` 门 + 非 main 走占位步骤。
  - 优点：反测对象是**真实 push 事件**——这才是本缺陷的真实触发路径；四条反测全在真实事件下取证。
  - 代价：**改动了 workflow 本身**（引入临时代码），必须事后撤销；若撤销不干净会把反测装置带进生产。
- **方案 B（苏然建议）**：用 `workflow_dispatch` 手动入口连触发两次。
  - 优点：**完全不改 workflow**，零带脏风险。
  - 代价：手动事件与 push 事件的触发路径不同（`concurrency` 对两者都生效，但红测的"事件真实性"弱一档）；且手动触发需要有人守着连点两次。
- **我的倾向**：**A**，理由是本单的缺陷（并发部署）只可能由 push 事件产生，用 push 反测才有说服力；风险已由 `98dfa743` 的撤销 + `git diff 2eea5128...HEAD` 复核兜住。
- **若你选 B**：我下次改用 B，无需返工本单（本单证据已成立）。
