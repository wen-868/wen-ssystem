# S3-58 裁定（业主已定）：**总台必须可从公网登录** ⇒ 放弃 IP 白名单/独立入口，改走"公网可用 + 强化认证面"

> 裁定人：凌舟（总负责人）｜日期：2026-10-06｜依据：业主当轮明确"**S3-58 需要从公网登总台**"

## 一、因此**排除**的两条路（我上一轮列过）
| 方案 | 为什么不能用 |
|:--|:--|
| 给 `/api/platform/auth/login` 加 nginx **IP 白名单** | 直接锁死公网登录 ⇒ 与业主需求冲突 |
| 管理入口收敛到**独立域名/端口 + 仅内网/VPN** | 同上 |

## 二、现状复核（我实测的防护链，比预期强）
`POST /api/platform/auth/login` 的中间件链 = `captchaFailLimiters.all` → `loginFailLimiters.all` → `requireCaptcha` → controller：
- **图形验证码**（防脚本化撞库）✅
- **双维度限流**：账号维度 `acct:<username>`（`login-fail-limiter.ts:85-87`）+ IP 维度 `ipKey(req)`（IPv6 按 /56 归并，`:74-77`）；窗口 5 分钟、锁 15 分钟、`skipSuccessfulRequests: true` ✅
- 两个超管口令**已轮换**、**免密 `demo-login` 已在生产 403**（10-05/10-06 两次取证）✅

## 三、剩下的两个**真问题**（公网可用前提下的正解）
1. **攻击者锁死合法账号（DoS）**：现按 `acct:<用户名>` 计数 ⇒ 外部持续失败即可把 `admin` 锁 15 分钟，**你本人也进不去**（10-05 实测：锁定倒计时被反复续期 15→10→8 分钟）。
2. **平台端缺 MFA**：`admin-auth.routes.ts` 有 MFA 端点（`mfa/status|setup|confirm|disable`）但**只绑 `t_sys_user`**；**`t_platform_admin` 表已有 `mfa_secret` + `mfa_enabled` 列**（生产实读），即**表结构早就备好，只是服务/路由没接**。

## 四、裁定（口径）
| # | 裁定 |
|:--|:--|
| **R1** | **不做 IP 白名单、不做入口收敛**（业主需公网登总台）；改为"公网可用 + 强化认证面" |
| **R2** | **限流维度改造**：账号维度键由 `acct:<用户名>` 改为 **(账号 + 归一化 IP)** 为主（快速小阈值锁定）＋**保留"账号维度高阈值兜底"**（防分布式多 IP 打同一账号）。目标：**攻击者无法用单一来源锁死合法账号**，同时分布式爆破仍被兜底拦住 |
| **R3** | **平台端接 MFA**（`t_platform_admin` 列已有）：`/api/platform/auth/mfa/{status,setup,confirm,disable}` + 登录二段（密码通过且 `mfa_enabled=1` ⇒ 只发 `mfaToken`，二段验码后才发正式令牌）；**默认不强制**（避免单管理员未绑定即自锁），但 `/me` 回一个"未开启 MFA"提示位，总台侧引导开启 |
| **R4** | 升 **required 的门禁**不因本项变动；S3-58 结案条件＝ R2 落地 + R3 落地 + 两条口子（免密/默认口令）均已取证（✅ 已完成） |

## 五、派单
见 `R101-派单-20261006-S3-58-F1.md`（后端，阿坚）：R2 + R3，逐项反测，其中 R2 必须给"**合法用户换一个 IP 仍能登录**"与"**分布式多 IP 打同一账号会被兜底拦**"两侧证据。
