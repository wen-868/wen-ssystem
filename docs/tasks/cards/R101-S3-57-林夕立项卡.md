# R101 · S3-57 立项卡：迁移 runner 感知 DELIMITER / BEGIN…END（林夕）

> 类型：结构性缺陷根治（修静默缺陷）
> 验收裁定人：凌舟
> 基线与分支：`origin/main` `3e549ab0` → 本分支 `docs/s3-57-delimiter`
> 关联：S3-50（门禁反测体检，本卡反测须并入其反测表 §3）/ S3-55（B+C 已修「通用 INTO 模式误伤」层，本卡治「过程体被拆散执行」根因）/ S3-56（不可逆类，单独立项）

---

## 0. 一句话结论

迁移管线**两条路径**都**不感知 MySQL 的 `DELIMITER` 指令与 `BEGIN…END` 复合语句**：

- `backend/src/shared/migration.ts` 的 `runMigrations()`（启动自动迁移）把 `DELIMITER` 行删掉后**按 `;` 裸切**，存储过程体被拆散成碎片语句下发；
- `scripts/run-migration.mjs`（手动单次迁移）则把整文件（含字面 `DELIMITER $$`）用 `multipleStatements` 一次性发给服务端，`DELIMITER` 不是服务端语法 → **直接语法错硬失败**。

两条路径对同一份含过程体的迁移（当前仅 `092_租户ID.sql`）表现不一致：一条**静默把过程体拆碎执行**（被 `safeExec` 吞错），一条**整文件硬失败**。根因都是 runner 缺一个 `DELIMITER`/`BEGIN…END` 感知的语句切分器。现网仅 1 个文件命中，但该缺陷是**结构性**的——任何未来含存储过程/函数/触发器的迁移都会踩。

> S3-55（PR #17，`fix/s3-55-bc`）只修掉了 `addTablePrefix` 里「**通用 `INTO` 模式误伤**」这一层（把 `INTO col_count` 当成表名加 `t_` 前缀）；但「**过程体被拆散执行**」这个根因**没有修**——变量即使不加前缀，在无过程上下文里仍是未声明变量，092 在全新库仍可能以别的报错失败。本卡治根因。

## 1. 问题陈述（含 file:line 证据，均来自本分支当前源码）

### 1.1 路径一：`backend/src/shared/migration.ts` · `runMigrations()`（第8步外部迁移）

源码事实（**本分支当前没有名为 `splitSqlStatements()` 的函数**，按 `;` 切块是 Step 8 等多处内联实现，待办 `#94` 曾计划抽该函数，本分支未落地）：

- **`addTablePrefix()`** `migration.ts:81-105`：给表名加 `t_` 前缀。其中 `(INTO\s+)([a-z_][a-z0-9_]*)` 通用模式在 `migration.ts:92` —— 会把 `SELECT ... INTO col_count` 的 `col_count` 当表名前缀成 `t_col_count`（即 S3-55 修的那层误伤）。
- **`safeExec()`** `migration.ts:107-125`：**吞错不抛**。命中 `SKIP_ERRORS`（含 `ER_SP_DOES_NOT_EXIST`，`migration.ts:38`）或 `SKIP_PATTERNS`（含 `"procedure"`，`migration.ts:77`）时仅 `logger.info` 跳过并返回 `false`，不崩、不抛；其它错误 `logger.error` 后也返回 `false`。即**迁移"看起来成功"但可能真改了/没改数据**。
- **第8步外部迁移主流程** `migration.ts:885-932`：
  - 预处理**移除 `USE ` 与 `DELIMITER ` 行**（`migration.ts:900-906`）——注意只删行，`DELIMITER $$` 之后的 `END$$` 结束符**原样保留**。
  - **按 `;` 裸切**：`.split(";").map(trim).filter(非空 && 非 `--` 开头)`（`migration.ts:909-912`）。
  - **跳过含 `CREATE PROCEDURE`/`DROP PROCEDURE` 的块**（`migration.ts:916-919`）——但 `;` 已在过程体内部先切，导致**只有首片（含 `CREATE PROCEDURE … BEGIN …` 到第一个 `;`）被跳过**，过程体内部的后续语句（如 `SELECT … INTO …`、`IF`、`SET`、`PREPARE`/`EXECUTE`）被切成分片、**不含 `CREATE PROCEDURE` 字样 → 不被跳过 → 被 `addTablePrefix` + `safeExec` 当作普通语句下发**。
  - `DROP TABLE` 保护跳过（`migration.ts:923-926`）。
  - 逐片 `addTablePrefix(stmt)` 后 `safeExec`（`migration.ts:928-929`）。
- **第5.5.8 步对 `121_ai_base_tables.sql` 同理**：删 `USE/DELIMITER`（`migration.ts:762-768`）、按 `;` 切（`migration.ts:770-773`）、跳过 `CREATE/DROP PROCEDURE`（`migration.ts:775-777`）。实测 `121` 不含 `DELIMITER`/过程体，此分支为防御性未触发。

**后果（以 `092_租户ID.sql` 为例）**：`DELIMITER` 行被删、`END$$` 残留，按 `;` 切后——
- 首片 `CREATE PROCEDURE add_column_if_not_exists(...) BEGIN DECLARE col_count INT DEFAULT 0`（到 `migration.ts:21` 行 `SELECT COUNT(*) INTO col_count` 前的第一个 `;`）含 `CREATE PROCEDURE` → 被跳过；
- 第二片 `SELECT COUNT(*) INTO col_count FROM information_schema.COLUMNS …`（到 `migration.ts:25` 行 `AND COLUMN_NAME = col_name;` 的 `;`）**不含 `CREATE PROCEDURE` → 不跳过** → `addTablePrefix` 命中 `migration.ts:92` 的 `INTO` 模式 → `col_count` 被前缀成 `t_col_count` → 作为**脱离过程的孤立语句**下发 → MySQL 报 `Undeclared variable`（S3-55 修掉前缀后，该孤立语句仍因"无过程上下文的局部变量"以别的报错失败）。
- 同理 `idx_count`（`092` 第47行 `SELECT COUNT(*) INTO idx_count`）。

更隐蔽的是：**过程体整体从未被真正创建**（`CREATE PROCEDURE` 片被跳过、`END$$` 残留使 `END IF`/`END` 等被并入相邻片或丢弃），于是 `092` 里大量 `CALL add_column_if_not_exists(...)`（`092` 第87–269行）因过程不存在 → `ER_SP_DOES_NOT_EXIST`（`migration.ts:38`）→ 被 `safeExec` **静默吞掉**。即路径一下，092 的「租户ID 补齐」意图**静默 no-op**（靠 `runMigrations` 内置 `TENANT_TABLES` 逻辑 `migration.ts:320-329` 兜底，但 092 自身设计意图落空）。

### 1.2 路径二：`scripts/run-migration.mjs`（手动单次迁移）

- 整文件读入后 `conn.query(sqlContent)`（`run-migration.mjs:65`），连接开启 `multipleStatements: true`（`run-migration.mjs:58`）。
- **不做任何 `DELIMITER`/`;` 预处理**：`mysql2` 的 `multipleStatements` 仅按 `;` 裸切并逐条发服务端，**不认识 `DELIMITER`**（那是 `mysql` CLI 客户端指令，非服务端语法）。
- 于是 `DELIMITER $$`（`092` 第13行）被当作一条 SQL 发给 MySQL → `ERROR 1064 (42000): You have an error in your SQL syntax near 'DELIMITER $$'` → 被 `run-migration.mjs:77-84` 捕获 → 打印「迁移失败」→ `exit(1)`。**整文件硬失败**，092 根本跑不起来。

### 1.3 两条路径行为不一致（铁证）

| 同一份 `092_租户ID.sql` | 路径一 `runMigrations()` | 路径二 `run-migration.mjs` |
|---|---|---|
| `DELIMITER` 行 | 删除（`migration.ts:900-906`） | 原样发服务端 → 语法错 |
| 过程体 | 被 `;` 拆碎、部分孤立下发、过程整体未建、`CALL` 被吞 | 整文件在 `DELIMITER` 处硬失败 |
| 表面结果 | "成功"（日志无致命，吞错），但 092 意图静默 no-op | "失败"，`exit(1)` |
| 真实失败形态 | 静默（数据层可能漏执行） | 显性（流程中断） |

## 3. 根治方案

### 3.1 核心思路

切块前先识别 **`DELIMITER` 块**与 **`BEGIN…END` 复合语句**，把整块（尤其是 `CREATE PROCEDURE/FUNCTION/TRIGGER … BEGIN … END`）作为**单条语句**下发，而不是按 `;` 拆散。

具体算法（设计一个 `splitSqlStatements(sql)` 状态机，取代三处 `.split(";")`）：
1. 逐行扫描，**跟踪当前 delimiter**：遇到 `DELIMITER xxx` 则把切分符切换为 `xxx`（如 `$$`），遇到 `DELIMITER ;` 复位为 `;`。`DELIMITER` 指令行本身不下发。
2. 在遇到 `CREATE PROCEDURE/FUNCTION/TRIGGER` 后，**开启复合块收集**：用 `BEGIN`/`END` 嵌套计数（忽略字符串/注释内的 BEGIN/END），直到匹配到与该 `CREATE` 对应的 `END` + 当前 delimiter 才结束一条语句。
3. 普通语句仍按当前 delimiter 切分。
4. 对切出的每条语句：`USE` 行丢弃；`DROP TABLE` 仍按既有保护跳过；`addTablePrefix` 只对**真正的表名**生效（`INTO` 后的局部变量绝不加前缀）。

> 注意：`mysql2` 不识别 `DELIMITER`，所以必须在 Node 侧预处理。处理方式有两种等价路线：(a) 复用上述状态机，把 `DELIMITER $$ … END$$` 还原为 `… END;`（把 `$$` 结束符替换成 `;`）后再按 delimiter 切；或 (b) 状态机直接按当前 delimiter 收块。推荐 (b)，更不易出错。

### 3.2 对两条路径分别怎么改

**路径一 `migration.ts`：**
- 抽出一个 `splitSqlStatements(sql)`（放在 `migration.ts` 内或 `shared/` 新模块），替换 Step 8（`migration.ts:909-912`）、Step 5.5.8（`migration.ts:770-773`）、Step 1.5（`migration.ts:287-290`）三处裸 `.split(";")`。
- 删除 `migration.ts:916-919` 的「跳过 `CREATE/DROP PROCEDURE`」硬编码——改由切分器把整个过程作为单条语句正确下发，**过程体真正被创建并执行**（不再静默 no-op）。
- 保留 `DROP TABLE` 保护（`migration.ts:923-926`）与 `addTablePrefix`（修正 `INTO` 模式，配合 S3-55 的具名清单化）。

**路径二 `run-migration.mjs`：**
- 同样改用 `splitSqlStatements`（与路径一共用同一份实现），在 `run-migration.mjs:65` 之前先切分，再逐条 `conn.query(block)`（仍以 `multipleStatements` 兜底或逐条执行）。
- 消除「`DELIMITER` 行被当 SQL 发给服务端报语法错」的硬失败，使手动迁移与启动自动迁移行为一致。

### 3.3 两条路径行为不一致本身是否一并收敛（给出判断）

**判断：建议收敛，但作为 Follow-up 技术债登记，不在 S3-57 最小闭环内强行合并。**

- 理由：两条路径共享**同一份** `splitSqlStatements` 才是最稳妥的修复——既能消除"路径一静默、路径二硬失败"的分歧，也避免日后两处逻辑再次漂移。
- 但收敛需改动**始终在线的 `runMigrations()`**（每次启动全量重跑），风险高于只修手动脚本；且与"风险与放量约束"中"修静默缺陷不得裸推生产"的红线冲突。
- 落地方式：S3-57 **最小闭环** = 让两条路径都不再因 `DELIMITER` 破损（路径一不再拆碎、路径二不再硬失败），切分器实现**集中一处**（便于将来共用）；**是否把 `run-migration.mjs` 也切到同一模块、并统一两者的 `DROP TABLE`/幂等语义**，作为**技术债登记**到本卡 §5，待副本演练通过后再排期收敛，不阻塞 S3-57 验收。

## 4. 反测要求（门禁铁律）

> 凌舟裁定：S3-57 立项须带「构造过程体迁移」的反测，并入 S3-50 的反测表。
> 原则：**绕过 ≠ 修复**。本卡不写"临时绕开 092"之类敷衍方案；任何临时绕过必须在本卡 §5 标"未根治"并登记技术债。

### 4.1 反测用例怎么构造（红 → 绿）

构造一个**含过程体**的迁移作为反测 fixture，证明「修复前失败 → 修复后成功」：

- **Fixture**：建一个测试用迁移（如 `test/fixtures/migrations/000_proc_regression.sql`），含 `DELIMITER $$` + `CREATE PROCEDURE`，过程体内部用 `BEGIN … END` 且含多条以 `;` 结尾的语句，其中至少一条 `SELECT … INTO local_var`（复刻 092 第21/47行模式）。过程体后接 `CALL proc()` 实际改数。
- **修复前（红）**：runner 按 `;` 裸切（或路径二 `DELIMITER` 硬失败）→ 过程未被创建 / 过程体被拆碎 → `CALL proc()` 触发 `ER_SP_DOES_NOT_EXIST`（被吞）或孤立 `INTO` 报错 → 断言"过程已建且 CALL 改数成功"**失败**。
- **修复后（绿）**：切分器把 `CREATE PROCEDURE … END` 整块下发 → 过程真正建出 → `CALL` 成功改数 → 断言通过。

### 4.2 必须并入的两层反测（写入 CI 门禁）

1. **Parser 单测（确定性，进 `build-and-test`）**：对新的 `splitSqlStatements` 写单测，断言：含过程体的迁移被**作为一整条**返回；`INTO local_var` **不被**加 `t_` 前缀。该单测在修复前**必红**（旧逻辑裸切/误前缀），修复后转绿——这是 S3-57 的"门禁反测铁证"。
2. **migration-check 真库集成（进 `ci.yml` 的 `migration-check` job，含真实 MySQL 8）**：在真库上跑该 fixture 迁移，断言存储过程存在（`information_schema.ROUTINES`）+ `CALL` 实际改数。作为"修复前失败→修复后成功"的端到端证据。

### 4.3 已并入 S3-50 反测表

已在本分支 `docs/tasks/cards/R101-S3-50-林夕门禁体检回传.md` 的 §3「活体红测证据」表登记一条待实施反测（见该卡 §3 末尾 `S3-57` 行），状态标注为「**要求（门禁铁律），待 S3-57 实施时执行**」，诚实区分"已红测证明"与"已登记待执行"。

## 5. 风险与放量约束（凌舟三条铁律，必写）

**背景**：改 runner 属于「**修静默缺陷**」，且本仓 `runMigrations()` 每次启动**全量重跑且无账本**、`safeExec` **吞错不抛**。

1. **铁律一（首次执行风险）**：修复后，一大批**从未真正执行过**的语句（此前被 `safeExec` 吞掉、被 `CREATE PROCEDURE` 跳过逻辑静默 no-op 的）将**首次真正执行**。必须预期"修复后反而暴露新报错"，不能因为"以前没报错"就以为安全。
2. **铁律二（无账本 + 全量重跑）**：`runMigrations()` 无迁移账本，靠文件幂等（`IF NOT EXISTS` / `DROP … IF EXISTS` / `safeExec` 跳过）保证可重入。修复 DELIMITER 后，092 的存储过程将首次被创建并执行，须确认：过程体内 `CALL` 的幂等性、与 `runMigrations` 内置 `TENANT_TABLES` 逻辑（`migration.ts:320-329`）**不重复/不冲突**。
3. **铁律三（吞错不抛）**：`safeExec` 即便出错也不崩、不抛，日志里"成功"可能掩盖真改数据。修复后 092 路径首次真正走通，**必须独立核对数据层结果**，不能只看日志"无致命"。

**放量结论（红线）**：本项**不得裸推生产**。必须：
- 走 PR 拿 CI 证据（`migration-check` 真库 + parser 单测红→绿）；
- **副本演练**：在副本/演练环境跑全量迁移，核对表/列/数据（尤其 tenant_id 补齐是否到位、有无重复执行副作用）；
- **放量另行裁定**（凌舟），不在本卡内决定。
