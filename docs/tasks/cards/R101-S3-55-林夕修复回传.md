## B 类：`addTablePrefix` 的 `INTO` 模式过宽（2 条）

### 根因（已核实，无需重新定位）
`migration.ts` 中 `TABLE_NAME_PATTERNS` 有一条通用 `INTO` 模式
`/(\bINTO\s+)([`a-z_][`a-z0-9_]*)/gi`，会匹配**任何** `INTO` 之后的标识符。
`092_租户ID.sql` 用 `DELIMITER $$` + `CREATE PROCEDURE`，runner 移除 `DELIMITER` 行后按 `;`
切块，过程体被拆散；其中 `SELECT COUNT(*) INTO col_count`（092 第 21 行）、
`SELECT COUNT(*) INTO idx_count`（092 第 47 行）的 `INTO col_count` 被当成表名加前缀成
`t_col_count` / `t_idx_count`，而 `DECLARE` 声明的是 `col_count`/`idx_count`
（092 第 20/46 行）→ MySQL 报 `Undeclared variable: t_col_count` / `t_idx_count`。

### 全量 INTO 出现位置统计表（证明收窄不漏真实表名）
对 `docs/migrations/*.sql`（170 个文件）全量扫描：

| 类别 | 数量 | 涉及文件数 | 说明 |
|------|------|-----------|------|
| INSERT INTO（含 INSERT IGNORE INTO） | 118 | 31 | 全部由既有 `INSERT_INTO` 模式覆盖，收窄不受影响 |
| REPLACE INTO | 0 | 0 | 仓库内无真实 REPLACE，新增 `REPLACE_INTO` 仅防御（spec 要求） |
| SELECT … INTO（变量赋值） | 2 | 1（仅 `092_租户ID.sql:21/47`） | 正是 `col_count`/`idx_count` 误伤案例 |
| 其它（LOAD DATA … INTO / INTO OUTFILE 等） | 0 | 0 | 无 |

**结论**：删除通用 `INTO` 后，唯一不再被匹配的就是 `092` 的 2 处 `SELECT … INTO` 赋值——
正是要修的误伤；**没有任何真实表名会被漏掉**。

### patterns 改前 / 改后对照（含误伤清单）

**改前**（`migration.ts`）：
- `TABLE_NAME_PATTERNS` 含通用 `{ name: "INTO", regex: /(\bINTO\s+)([`a-z_][`a-z0-9_]*)/gi, ... }`（覆盖 INSERT/REPLACE 之外的 INTO 上下文）→ 把 `SELECT COUNT(*) INTO col_count` 当表名。

**改后**（`migration.ts`，均标注 `S3-55B` + 一句"为什么"）：
1. 删除通用 `INTO` 模式（原 `:113`）。
2. 新增 `{ name: "REPLACE_INTO", regex: /(REPLACE\s+INTO\s+)([`a-z_][`a-z0-9_]*)/gi, ... }`，与既有 `INSERT_INTO` 互补覆盖所有"真实表名 INTO"场景（不重复造 `INSERT INTO`）。
3. 新增具名**误伤清单 `MISFIRE_GUARDS`**（5 项），并在 `addTablePrefix` 每次替换前逐条拦截（`if (MISFIRE_GUARDS.some((g) => g.test(prefix, bare))) return match;`），
   替换了原硬编码的 `bare.startsWith("t_")/information_schema/mysql` 判断，使"什么不加前缀"显式可审计：

| 误伤项 | 判定依据 | 来源/场景 |
|--------|----------|-----------|
| `ALREADY_T_PREFIXED` | `bare.startsWith("t_")` | 已带 t_ 前缀（防 `t_t_x`） |
| `SYSTEM_SCHEMA` | `bare.startsWith("information_schema")\|\|startsWith("mysql")` | 系统库前缀名 |
| `SELECT_INTO_ASSIGNMENT` | `prefix.trim().toUpperCase() === "INTO"` | `SELECT COUNT(*) INTO col_count`（092 实际案例） |
| `ON_UPDATE` | `/(^|\s)ON\s+UPDATE\b/i.test(prefix)` | `ON UPDATE CURRENT_TIMESTAMP` |
| `ON_DUPLICATE_KEY_UPDATE` | `/ON\s+DUPLICATE\s+KEY\s+UPDATE\b/i.test(prefix)` | `ON DUPLICATE KEY UPDATE col` |

> 双向防住（凌舟裁定）：`TABLE_NAME_PATTERNS` 管"加什么"（漏模式方向，S3-52），
> `MISFIRE_GUARDS` 管"什么不加"（过宽模式方向，S3-55B）。`SELECT_INTO_ASSIGNMENT`
> 与"INTO 仅来自 INSERT/REPLACE"结构性约束互为兜底。

## C 类：`151_points_columns_fill.sql` 迁移文件自身 bug（1 条）

### 根因
```sql
ALTER TABLE t_points_rule ADD COLUMN redeem_ratio DECIMAL(6,4) DEFAULT 100 ...
```
`DECIMAL(6,4)` = 总 6 位、小数 4 位 → 整数部分仅 2 位，**最大值 99.99**；
`DEFAULT 100` 超界 → `Invalid default value for 'redeem_ratio'`（全新库执行 151 时失败）。

### 业务语义判断与改法依据（不凭空改数字）
经核 `backend/src/services/admin/marketing-points.service.ts`：
- 第 98 行 `body.redeemRatio ?? 100`：`redeem_ratio` 的硬编码默认值为 **100**；
- 第 288 行 `Math.floor(points / Number(rule?.redeemRatio ?? 100))`：`redeem_ratio` 作为**除数**使用
  （100 积分可抵 1 单位金额，即 1 积分 = 0.01 金额）。

**结论**：`DEFAULT 100` 是业务本意（"100 积分抵 1 单位金额"），**并非笔误** → 选择**放宽列精度**而非改默认值。

**改法**：`DECIMAL(6,4) DEFAULT 100` → `DECIMAL(8,4) DEFAULT 100`（保留 `DEFAULT 100` 与 4 位小数）。
- 理由：
  1. 对存量库影响最小——该列仅由本迁移 151 创建；全新库得到合法列；既有库若已存在该列则 `ALTER ADD COLUMN`
     被 `safeExec` 跳过（`ER_DUP_FIELDNAME`），不参与变更，不触发数据/结构回写。
  2. 4 位小数与兄弟列 `earn_ratio`/`max_redeem_ratio`（均为 `DECIMAL(6,4)`）保持一致，不引入精度语义漂移。
  3. 保留 `DEFAULT 100` 与 service 层 `?? 100` 一致，避免"列默认"与"业务默认"脱节。
- 同步更新了 `migration-points-columns.test.ts` 对该列的断言（`DECIMAL(6,4)`→`DECIMAL(8,4)`）。

### 残留风险
- 无（A 类不触碰，见 S3-56）。
