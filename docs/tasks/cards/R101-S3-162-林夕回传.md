## 六、风险与自我报备

**R1（我发现的一处口径漏洞，建议另立卡）**：`app-mobile/src/api/storage.ts` 里还有**第二个** `logout()` 导出（约 L455-460），它**只清 token/用户态/租户/CSRF，不清 `saved_*`、不复位勾选态**——与本单"退出登录＝退出凭证的唯一出口"直接冲突。
现状：它**是死代码**（全仓无调用方，`grep` 证实），所以不影响本单交付；但它是给后人留的陷阱：谁哪天调用了 `storage.logout()`，就会静默绕过新口径。
按「派单 rewrite：交付物只能落在指定文件域」的纪律，我**没有动它**（它也不在本单「做」的范围里）。**建议另立一张小卡删掉这个死导出**（或让它转调 `stores/user.ts` 的口径），请裁定。

**R2（口径变更带来的用户可感知变化，需你确认是否可接受）**：「退出登录 = 连本机记住的账号口令一起清掉」意味着——**勾了「记住我」的用户，每次退出后下次都要重新输一次**。这是业主当轮口径的必然结果，我已按口径实现并把代价写进二次确认文案。风险是用户可能觉得"我明明勾了记住我"，因此**二次确认文案必须醒目**（已做）。若你希望更柔和（例如先软提示"是否同时清除"），请回卡。

**R3（mock 密闭性 + 与 S3-161 同一批装置坑）**：四场景全部本进程 mock，验证的是「给定后端这样回，前端这样应对」。装置本身复用 S3-161 的两个已修坑：① 路由**前缀谓词**（通配 glob 会拦掉 dev 源码模块 `/src/api/`）；② 版本检查接口必须回 `data:null`（否则弹更新框遮住按钮）。**本轮新增一个自伤坑**：注释里写 `**/api/**` 会提前闭合块注释导致 `ReferenceError: api is not defined`——已修并留在装置里做提醒。

**R4（判据分辨力，已显式标注）**：`§2` 显示红侧里 `token已清` / `回登录页` / `记住我复位` 三项**仍为 true** ⇒ 判「退出是否真的清了凭据」的**唯一有效判据**是「`saved_*` 是否消失」与「两框是否为空」。若后人把断言简化成「退出后回到登录页就算过」，本装置测不出这个缺陷。
