## 二、剩余 10 条失败的三类根因（均已定位到源码/文件行号）

### 类型 A：迁移文件内**列类型错配**（7 条）— 高风险，需裁定

| 文件 | 引用列 | 被引用列 | 冲突 |
|---|---|---|---|
| `016_phase9_tenant_subscription.sql` | `t_tenant_module_access.tenant_id INT` | `t_tenant.id VARCHAR(36)` | INT ≠ VARCHAR |
| `016_phase9_tenant_subscription.sql` | `t_tenant_admin.tenant_id INT` | `t_tenant.id VARCHAR(36)` | INT ≠ VARCHAR |
| `032_add_tenant_module_access.sql` | `tenant_id INT` | `t_tenant.id VARCHAR(36)` | INT ≠ VARCHAR |
| `034_add_tenant_admin.sql` | `tenant_id INT` | `t_tenant.id VARCHAR(36)` | INT ≠ VARCHAR |
| `017_phase10_instant_retail.sql` | `t_retail_order_item.order_id INT` | `t_retail_order.id BIGINT AUTO_INCREMENT` | INT ≠ BIGINT |
| `017_phase10_instant_retail.sql` | `t_delivery_record.order_id INT` | `t_retail_order.id BIGINT AUTO_INCREMENT` | INT ≠ BIGINT |

（016/017 各报 2 条，合计 6 条；另有 1 条同类。）

证据：`t_tenant` 定义于 `016_phase9_tenant_subscription.sql`，`id VARCHAR(36) PRIMARY KEY`；
`t_retail_order` 定义于 `017_phase10_instant_retail.sql`，`id BIGINT AUTO_INCREMENT PRIMARY KEY`。

- **性质**：迁移文件本身写错了引用列类型（MySQL 要求外键两侧类型完全一致，含符号/字符集）。
- **风险**：修法是改**迁移文件里的列类型**。在**存量库**上这意味着 `ALTER TABLE ... MODIFY COLUMN`
  改列类型 —— **不可逆且可能锁表/丢精度**，绝不能随 S3-51 一起静默上生产。
- **建议**：单独立项；先只在「全新库/灾备」路径上保证正确（改迁移文件即可），
  存量库是否同步改类型需单独评估并走维护窗口。

### 类型 B：`migration.ts:113` 的 `INTO` 通配模式**误伤过程变量**（2 条）— 低风险，可立即修

报错：`092_租户ID.sql :: Undeclared variable: t_col_count` / `t_idx_count`

注意变量名多了 `t_` 前缀 —— 源码里 `DECLARE` 的是 `col_count` / `idx_count`（092 第 20/46 行），
证实是 `addTablePrefix` 加的。定位：

```ts
// backend/src/shared/migration.ts:113
{ name: "INTO", regex: /(\bINTO\s+)([`a-z_][`a-z0-9_]*)/gi,
  note: "INTO <tbl>（覆盖 INSERT/REPLACE 之外的 INTO 上下文）" },
```

`SELECT COUNT(*) INTO col_count` 里的 `INTO col_count` 被当成「表名」→ `t_col_count`。

- **性质**：runner 缺陷（与 S3-52 同族，都是「多加/漏加一个模式」的清单设计问题）。
  与 S3-52 相反：S3-52 是**漏**模式，本条是**多加了一个过宽**的模式。
- **诱因**：092 用了 `DELIMITER $$` + `CREATE PROCEDURE`；runner 移除 `DELIMITER` 行并按 `;` 切块，
  **过程体被拆散**，体内片段被当独立语句执行（`END$$` 也处理不了）。
- **建议**：① 收窄 `INTO` 模式（改为显式 `REPLACE INTO`，移除 catch-all）；
  ② 或增加「`SELECT ... INTO <变量>` 不加前缀」的排除规则；
  ③ 更根本的是让 runner **感知 `DELIMITER`/`BEGIN...END` 块**（整块提交，不按 `;` 拆）。
  ①②③ 需凌舟裁定，其中 ③ 改动面最大但才是对的修法。

### 类型 C：迁移文件自身 bug（1 条）— 低风险，可立即修

`151_points_columns_fill.sql:12`

```sql
ALTER TABLE t_points_rule ADD COLUMN redeem_ratio DECIMAL(6,4) DEFAULT 100
```

`DECIMAL(6,4)` 表示总共 6 位、小数 4 位 → 整数部分仅 2 位，**最大值 99.99**；
`DEFAULT 100` 超出取值范围 → `Invalid default value`。

- **建议**：改为 `DECIMAL(10,4)`（或把默认值改为 99.99）。需确认业务语义后再定。

## 三、与 S3-51 生产放量的关系（重要）

这 10 条失败发生在 **CI 的全新 MySQL 容器**上。生产库已有 483 张表、列已存在，
因此：

- 类型 A（7 条）：生产的 `CREATE TABLE` 会被跳过（表已存在）→ **大概率不会触发**；
  但若某张表恰好不存在，就会带着错类型建出来 —— 需在副本演练中确认。
- 类型 B（2 条）：`092` 的语句在生产会真实执行 → `Undeclared variable` 被 `safeExec` 吞掉，
  **不中断启动，但该过程本该做的事没做**（条件加列/加索引被静默跳过）。
- 类型 C（1 条）：生产 `t_points_rule` 若已存在，`ADD COLUMN` 会报 duplicate 被吞；
  若不存在则会建表并在此失败。

**结论**：这批不阻塞 S3-51 的「备份 + 副本演练 + 逐条批准」路径，但**副本演练的逐条清单里
必须把这 10 条标出来并给出预期结果**（成功/跳过/报错），否则演练结论不成立。
