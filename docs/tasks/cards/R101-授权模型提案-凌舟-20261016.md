# R101 · 授权模型提案（A/W 类 + 需立码域的解锁路径）

> 出案人：**凌舟（总负责人）**｜日期：**2026-10-16**｜依据：生产只读底稿（角色 × 权限码、角色 × 菜单、**角色 × 账号使用**）
> 触发：B2 批次累计 66 条 B 类 + 29 条 A/W 类 + 5 个域（94 条）因"**页面可见角色 ⊉ 码持有者**"或"**无现成码**"被卡住；逐个域临时裁定会反复摇摆 ⇒ 一次性定模型。
> 证据：`docs/evidence/_shared/prod-roles-20261016.txt`（角色×权限码）、`prod-menu-matrix-20261016.txt`（角色×菜单）、`prod-role-usage-20261016.sql`（角色×账号）

---

## 〇、模型与不变量（先说清，后面所有裁定都由它推导）

1. **码** = 能力单元，命名 `模块:动作`（少数为 `模块:子域:动作`）；模块名取自 `079_权限矩阵.sql` 既有模块码。
2. **页面可见性**由前端 `meta.roles` / 菜单授予决定；**写能力**由码决定。两者**必须同源**：
   > **不变量 I1**：凡能"看到"某页面的**在用**角色，必须持有该页**写端点**所用的码；否则接线即 403 回归。
3. **在用** = 生产 `t_sys_user_role` 里被至少一个账号绑定的角色。

## 一、生产事实（本轮实测，决定下述裁定）

| 角色 | 持码要点 | 绑定账号数（active） | 结论 |
|:--|:--|--:|:--|
| `SUPER_ADMIN` | `["*"]` | **2**（`admin`、`store_manager`） | 在用 |
| `STORE_MANAGER` | `store:* sale:* customer:* inventory:* report:* dashboard:* finance:payment goods:price finance:daily-settle` | **1**（`tenant_admin`） | 在用（单店管理员角色） |
| `STORE_OPERATOR` | `sale:create sale:view sale:return inventory:view dashboard:view finance:daily-settle` | **1**（`store_operator`） | 在用 |
| `READONLY` | `["*:view"]` | **1**（`smoke_bot`，冒烟测试） | 在用（**观察员**：写 403 是期望） |
| `OPERATION_ADMIN` | `["*"]` | **0** | 未用（保留） |
| `PURCHASE_STAFF` | `purchase:* supplier:* inventory:inbound report:purchase` | **0** | 未用（**码归属正确**，仅无账号） |
| `FINANCE_STAFF` / `WAREHOUSE_STAFF` / `SALES_STAFF` / `CUSTOMER_SERVICE` | 各自域码 | **0** | 未用（保留） |
| **`SALESMAN` / `STORE_ADMIN`** | **旧词表**（`product:read`/`order:*`/`inventory:read|write`） | **0** | **旧词表遗留角色、无人使用** |

**营销菜单授予角色** = `OPERATION_ADMIN`（0 账号）/ `READONLY`（观察员）/ `STORE_ADMIN`（0 账号）**——没有任何"在用写角色"被授予营销菜单**。

## 二、裁定

| # | 类别 | 裁定 | 依据 / 落地 |
|:--:|:--|:--|:--|
| **D1** | **A 类·商品 15 条**（页面（含店长）可见，店长不持 `goods:*` 写码） | **给 `STORE_MANAGER` 增补 `goods:create` + `goods:edit`（不含 `goods:delete`）**，随后接线 | 店长是在用角色、已持 `goods:price`（同族）、页面本就对店长开放；删除属高风险留给超管/运营。落地：**独立单**（码目录 `user-permissions.ts` + **幂等迁移**改角色权限 + 生产执行 + 只读复核 + 双侧反测） |
| **D2** | **W 类·营销 14 条**（页面可见角色含 `STORE_ADMIN`/`READONLY`） | **接线（挂 `marketing:create`）** 且**同时登记菜单错配待治理**：`STORE_ADMIN`（0 账号、旧词表）本不应看到营销菜单 | 不变量 I1 只约束**在用**角色；`STORE_ADMIN` 0 账号、`READONLY` 是观察员（写 403 期望）⇒ **接线无在用账号回归**。菜单收回属"菜单治理"，另立小单（不阻塞接线） |
| **D3** | **旧词表角色**（`SALESMAN` / `STORE_ADMIN`） | **不迁移、不补码**；登记为"**未使用遗留角色**"；若将来要启用，须先按新码体系重画权限串 | 0 账号 ⇒ 迁移成本无收益；但**必须留痕**（防后人误判"它持 `order:write` 所以能写单"——在新码体系里它等于无写权限） |
| **D4** | **B 类 66 条**（移动端页面/入口无权限门） | **必须由前端补权限门**（按码显隐入口）**再收编**；本阶段维持不接 | B 类的使用者是**在用**角色（店长/店员），挂码而不补门 ⇒ 点击即 403 ⇒ 违反 I1。⇒ 立**前端权限门单**（含 B 类清单 + 各端点所需码） |
| **D5** | **查询型 POST / 消费者端形态** | 已由 **S3-227** 落地判据（`READ_ONLY_POSTS` 具名登记 + `consumerEnd` 现场解析成对认证）；后续**逐条裁定登记**（我出裁定行，执行方照登记） | 判据不动，只补登记 |
| **D6** | **需立码的 5 域（94 条）** | **允许新增商家侧码**，但必须走**同一套落地面**（见 §三） | 这些页面/端点在用角色确实需要写能力；无码可用 ⇒ 只能立码（属机械扩展，非模型变更） |
| **D7** | **`sale:cancel` 菜单未授予任何角色** | 登记：取消类端点（S3-209）当前仅超管可用；若业务要店长可取消，须**单独**在角色矩阵里授予（不顺手给） | 高危操作默认最小授权 |

## 三、新立码的落地面（D6 的强制清单，缺一即不合格）

新增一个码**必须同批**改全 5 处，并在回执逐处给行号：

1. `backend/src/shared/user-permissions.ts` 的 **`PERMISSION_CATALOG`**（商家侧目录，含模块名/码名/类型）；
2. `docs/migrations/` 下 **幂等迁移**：把码写进 `t_sys_role_permission` 矩阵（**并同步 `079_权限矩阵.sql` 的模块/按钮码清单**，保持语料与生产一致）；
3. 前端**菜单/按钮码**（admin-web / app-mobile 里与该码绑定的入口）；
4. **角色种子**（哪些角色默认持有；若涉及"给在用角色补码"，必须走 D1 同款的独立角色变更单）；
5. **门禁与断言**：`guard-rbac-wiring --strict` EXIT=0；目录相关既有断言（域数/条数）同步更新。

命名规范：`模块:动作`（动作取 `create/edit/delete/approve/export/config/settle/...`）；同一语义跨域必须**同名动作**；禁止 `xxx:manage` 这类"万能码"（平台侧 `library:manage` 等属历史例外，商家侧不再新增）。

## 四、落地顺序（依赖关系）

1. **D6 立码单**（含 D1 的 `goods` 写码授权）⇒ 解锁 A 类 15 + 5 域 94 条；
2. **D4 前端权限门单** ⇒ 解锁 B 类 66 条（其中营销/商品/客户等域的 B 类可随门单成批收编）；
3. **D2 接线**（营销 W 类 14 条）⇒ 可直接进下一批；
4. **菜单治理小单**（D2 的 `STORE_ADMIN` 菜单错配 + D7 的 `sale:cancel` 授予口径）⇒ 不阻塞接线；
5. 各域续批（批 9 起）按"**先查在用角色 → 再按 I1 判是否可接**"执行（本轮起写进批次卡）。
