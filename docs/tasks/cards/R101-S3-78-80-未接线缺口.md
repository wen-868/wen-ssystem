## S3-78 · 通知：**4 份实现并存，且"推送"从未接线**（P0）

### 取证

| 实现 | 谁在用 |
|---|---|
| `backend/src/shared/notification-sender.ts` | `services/admin/monitor.service.ts`、`routes/notification.routes.ts`（re-export） |
| `backend/src/services/notification.service.ts` | `services/store/sale-bill.service.ts` |
| `backend/src/services/admin/notification.service.ts` | `controllers/admin/notification.controller.ts` |
| `backend/src/services/admin/notification-sender.service.ts`（**带推送**，注释标注「关联任务 R51-07」） | **全仓 0 引用** |

三份"只落库"的实现都往**同一张 `t_notification`** 写一样的数据；带推送的那份从未被调用。
`push.service.ts` 已实现 `sendToUser`（JPush + HMS），但**唯一调用点在 `controllers/admin/push.controller.ts`（管理员手动推送）**。

### 实际使用体验影响（这才是重点）

**用户在 App 里收不到任何"事件推送"**：审批、订单、告警、订阅到期提醒都只写进 `t_notification`，**必须打开 App 才能看到**。
对"订单异常/订阅到期"这类**有时效性**的通知，等于错过；等于把"通知"退化成"留言板"。

### 修法（建议）

1. 收敛为**一个**入口：保留 `sendNotificationWithPush(params, { enablePush })`（已具备"推送失败不阻塞记录"的错误隔离），把另外 3 处调用点切过去；
2. 按类型决定是否推送（避免打扰）：如 `ALERT/ORDER/PAYMENT` 推送，`SYSTEM` 可只落库；
3. 无凭据时必须 **no-op + 日志**，绝不阻断业务（现有实现已满足）。

### 🔴 阻塞项（只有业主能给）

生产 `.env` **完全没有推送凭据**：`JPUSH_APP_KEY` / `JPUSH_MASTER_SECRET` / `HMS_APP_ID` / `HMS_APP_SECRET` **四项均缺失**（服务器实测）。
⇒ 即使现在接线，推送也是 no-op。**需要业主提供极光 / 华为推送的应用凭据**，并确认哪些通知类型要推送。

### 验收标准

① 4 份实现收敛为 1 份（`rg` 证明旧入口不再被调用）；② 无凭据环境下发送通知 → 记录写入成功、推送走降级分支、**无异常抛出**（单测覆盖）；③ 配好凭据后真机收到推送；④ 反测：把推送 mock 成失败 → 通知记录仍写入成功。

## S3-79 · 即时零售：**从不扣库存、也不自动拒单**（P0）

### 取证

- `services/instant-retail/inventory-deduction.service.ts` 的 `deductStock` / `batchDeductStock` / `restoreStock`：**全仓 0 调用**；
- `services/instant-retail/shortage-handler.service.ts` 的 `checkStock` / `handleShortage`（注释写明"处理缺货 - 自动拒单"）：**全仓 0 调用**；
- 该目录桶文件 `instant-retail/index.ts` 只导出 types / base-adapter / registry，**未导出 shortage-handler**；
- 订单来源是**平台单**（`order-receiving.service.ts` 的 `listOrders/getOrderDetail/confirmOrder/cancelOrder` 操作 `t_platform_order`）。

### 实际使用体验影响

**接到平台的订单时，系统既不校验库存、也不扣减库存、更不会自动拒单** ⇒ 商品实际无货时门店**照样接单**，随后只能人工取消（对平台评分与用户体验伤害最大的一类事故）；同时 `t_retail_product.stock` **永不减少**（超卖）。

### 修法（建议）

在"接单/确认"路径前置 `checkStock(...)`：不足 → 走平台拒单（adapters 已具备"更新库存/拒单"能力）+ 落日志 + 可选通知（联 S3-78）；充足 → 正常接单并 `batchDeductStock`。

### 🔴 阻塞项（只有业主能给）

① **业务规则**：无货时是"**自动拒单**"还是"**仅告警给人处理**"？（自动拒单会改变对外行为，必须业主确认）
② 生产是否已配置可用的平台适配器（美团/饿了么等）与凭据。

### 验收标准

① 模拟无货订单 → 按确认后的规则动作正确且留日志；② 有货订单 → 接单成功且库存正确扣减（可复跑 SQL 对照）；③ 反测：把库存置 0 → 必须触发拒单/告警分支。

### 🔴 附带修掉一个真实资金等价风险（业主提醒触发）

> 业主提醒：「**要扣减库存，库存就变成负数，这是业务逻辑，要谨慎**」——查证**属实**，已修 `inventory-deduction.service.ts`：

| 原隐患 | 修法 |
|---|---|
| `deductStock` 的 `SELECT ... FOR UPDATE` 与 `UPDATE` **不在同一事务** ⇒ 并发下可同时通过检查、**扣成负数**（TOCTOU） | 改为**单条原子语句** `... WHERE id=? AND tenant_id=? AND stock >= ?`，`affectedRows!==1` 即失败且**不写数据** |
| `batchDeductStock` **无事务** ⇒ 中途失败留部分扣减 | 改为**同一事务**，任一项不足即抛错 ⇒ **整体回滚** |
| `restoreStock` 会把 `sales_count` 减成负 | `GREATEST(sales_count - ?, 0)` 兜底 |
| 非法数量（0/负/小数）照样发 SQL | 入口校验，非法直接拒绝且**不发 SQL** |

并在文件头写明业务约束：**禁止在本文件之外手写 `stock = stock - ?`**。新增测试 4 类专盯红线（SQL 必须含 `stock >= ?`；非法数量不发 SQL；批量失败即中止不回退；回退含 `GREATEST`）。
