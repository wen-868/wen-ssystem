## 二、裁定：**取 A**（我的反测判据写错了，代码不改）

判红 v2 §三.4「反向②：去掉 `DEMO_TENANT` 限定 ⇒ B 或 C 必须变红」——**实测不成立**，且**是我这条判据写错了**：

`demoLogin()` 的绑定写是 **"缺失才插"的追加式**（`INSERT … WHERE NOT EXISTS (user_id, role_id)`），**不会覆盖**迁移已修好的绑定，所以去掉租户限定后 B/C 仍 PASS。

它的真实危害是另外三条（执行方原样交出、我采纳）：
1. 超管查询会命中 `default` 的角色行 ⇒ 该账号**多出一条跨租户绑定**（绑定租户 `demo` / 角色行租户 `default`）；
2. 登录返回的 roles 出现**重复 SUPER_ADMIN**；
3. 随后**重跑 197 直接 `ER_DUP_ENTRY` 1062 报错停下**（撞 `uk_sys_user_role (user_id, role_id)`）。

对照组（保留 `tenant_id = ?`）实测：命中 demo 自己的角色行（`role_id=8155`）、**跨租户绑定 0 条**、登录后**重跑 197 无错**、装置自断言 10/10。

**裁定 A：保留现有代码形态（③ 的 `tenant_id = ?` 不变）；把"反向②"的判据改写为它真正能分辨的三条——**
「登录一次后：① 跨租户绑定 = 0 ② roles 无重复 ③ 重跑 197 不报 1062」。
否掉 B（把登录绑定写改成"按 role_code 重指向"）：那会引入新的 1062 风险，而现状已无危害。
