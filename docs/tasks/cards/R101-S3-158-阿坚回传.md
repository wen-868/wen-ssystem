```sql
SELECT COUNT(*) FROM t_product_category;     -- → 0
SELECT COUNT(*) FROM t_product_spu;          -- → 0
SELECT COUNT(*) FROM t_member;               -- → 0
```

结论：#8 不是"只报一行日志"——`seed-data.ts` 在插入演示账号处 `throw`，被 `migration.ts` 第 6 步的 `catch` 捕获后**整段种子数据中止** ⇒ 全新库没有商品分类 / SPU / 会员 / 演示账号（**真实功能缺口**，非噪声）。

## 七、风险分级 + 建议实施顺序

### 7.1 两档划分

**① 可随主干上**（只改"全新库/灾备库"路径上的 `CREATE TABLE IF NOT EXISTS` 声明；对存量库整条 no-op，不产生任何 `ALTER`，触及不到生产既有数据）

- **A-1 / A-2 / A-3 / A-4**（4 个文件 6 处列类型对齐）
- **C（甲 或 乙）**（第 0 步补 `mobile` 或 seed 兼容）

**② 必须先备份 + 演练**（对**已上线库**真的会执行 DDL，或改变门禁口径）

- **B**（`t_sys_config` 索引幂等化）：执行前必须 ① `deploy/02-mysql-backup.sh` 备份 ② **库副本演练**（两种形状各一次：`uk_config_key_tenant` 形状、旧 `uk_config_key` 形状）③ 核对生产 `t_sys_config` 索引现状（名称是否存在）并把演练结果附在实现单回传。
- **D**（`SKIP_ERRORS` 收窄）：改变门禁口径，必须先全量实测影响面 + 反测；**必须单独立单**。

> 说明：A 类**不**需要"改生产存量列类型"。若裁定要求生产表与代码声明**逐列一致**，那才需要另立"对生产 `ALTER TABLE … MODIFY`"单——那是**不可逆 + 可能锁表 + 需停机窗口**，必须独立评估（见 §九-3）。

### 7.2 建议实施顺序（哪条先、哪些必须单独立单）

1. **单①（P0，可随主干上）：A 类 6 处列类型对齐**（016/017/032/034）。
   *为什么先做*：A-1/A-2 之外，`t_tenant_module_access` **没有任何补偿迁移**（074/046/192 都补不到它）⇒ 全新库该表永远建不出来，是**唯一"靠补偿也解决不了"的功能缺口**；且修完它 migration-check 才可能对 A 类转绿。
2. **单②（P1，可随主干上）：C 类 —— 第 0 步 `t_sys_user` 补 `mobile`**（推荐甲）。
   *为什么第二*：修完全新库 seed 才不再中断（分类/SPU/会员/演示账号才能落库）。
3. **单③（P1，须先备份+演练）：B 类 —— `t_sys_config` 索引幂等化**。
   *为什么第三*：它是**存量库**唯一会被真实执行的 DDL，风险最高，须先核对生产索引现状 + 副本演练。
4. **单④（P1，必须单独立项，防复发）：D 类 —— `SKIP_ERRORS` 收窄**。
   *为什么最后*：它会改变"红/绿"判定口径；若先做，会把尚未修的 A/B/C 一起变红，制造"混红"难以归因；必须在 ①②③ 之后做，并配反测。

6. **门禁观察期**：合并后 `migration-check` **保持非 required**，按分支保护条款④连续 10 次无漂移后再议；观察期内不得用 job 级 `continue-on-error` 把红洗成绿。

1. **是否豁免《项目统一标准》§12.2-1「禁止修改已执行的迁移文件」？**
   现况：016/017/032/034 四条语句若不改文件就**无法消红**（补偿迁移只能补"表不存在"，不能让这 4 条语句本身不报错）。仓内已有改同文件类型的先例：`d39fe66cdf` / `72dac1771d`（R95-06，016/017 类型 DDL 对齐）、`02b8c5da5d`（S3-109，151 默认值）。**不豁免则 A 类只能长期挂红**，与"长期红会掩蔽真问题"的目标冲突。

3. **A 类是否需要同步到生产存量表？** 本单结论：**不需要**（存量库该表已存在 ⇒ 语句整条 no-op）。若裁定"代码声明必须与生产逐列一致"，须另立 `ALTER TABLE … MODIFY` 单（不可逆/可能锁表/需停机窗口）。
