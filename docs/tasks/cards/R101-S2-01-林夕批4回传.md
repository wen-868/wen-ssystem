### 2.1 六个维度的数据源（全为现有表）

| 设计稿项 | 用量 | 上限 |
|:---|:---|:---|
| 账号数 | `COUNT(*) t_sys_user WHERE tenant_id` | 套餐 `max_users` |
| 商品上限 | `COUNT(*) t_product_spu` | 套餐 `max_products` |
| 仓库数 | `COUNT(*) t_store WHERE store_type='WAREHOUSE'` | 套餐 `max_stores` |
| 存储容量 | `SUM(file_size) t_upload_file WHERE status=1` → GB | `t_tenant_config.storage_limit`（MB/GB），取不到回退套餐 `max_storage_mb` |
| API 日额度 | **无数据源 → `null`** | 无 |
| AI 额度 | `SUM(chat_count) t_ai_usage_daily`（本月） | `t_tenant_ai_billing.monthly_chat_limit`（0=不限 → `limit:null` + `unlimited:true`） |

限额取「最近一次 ACTIVE 订阅」的套餐：
`t_subscription s JOIN t_subscription_plan p ON p.id = s.plan_id ORDER BY (s.status='ACTIVE') DESC, s.created_at DESC, s.id DESC LIMIT 1`。

### 2.2 换算口径（裁定③：换算在后端，前端零除法）

- 存储用量：`ROUND(bytes / 1024^3, 2)`，响应 `unit` 恒为 `"GB"`
- 存储上限：`storage_limit_unit='MB'` → `/1024`；`'GB'` → 原值；`'TB'` → `×1024`；**单位不在白名单或租户级配额缺失 → 回退套餐 `max_storage_mb`（列名含 `_mb`，按 MB→GB 折算）**
- AI 上限 `0` = 不限量 → `limit:null` + `unlimited:true`
- 前端**只把 `used/limit` 算成百分比用于画条**，展示文本直接用后端给的 `used`/`limit`，不做任何数值换算

## 四、如实报备

1. **修正了凌舟裁定 4.3 里的一处事实判断**。裁定原文把「存储占用 / API 调用次数 / AI 额度」并列为
   「无数据源 → 返回 null」。实测：
   - **存储占用有数据源**：`t_upload_file`（`SUM(file_size) WHERE status=1`）+ `t_tenant_config.storage_limit`
     （`storage-guard.ts` 已在用这套），故本批**返回真实值，不返回 null**；
   - **AI 额度有数据源**：`t_ai_usage_daily.chat_count` + `t_tenant_ai_billing.monthly_chat_limit`；
   - **真正无源的只有「API 调用次数」**：全仓无任何调用计数表，`config/api-billing.ts` 是静态常量且 `ENABLED:false`。
     → 按裁定返回 `null` + 前端「—」，**登记 S3-21**。
   即：原判断偏保守（少做了两个能做的维度），本批按实测扩大到了能做的范围；无源的那一个严格按裁定处理。

2. **面板是新增界面元素，请确认范围**。「资源配额使用情况」面板在 `TenantDetail.vue` 此前**完全不存在**
   （页面只有待接入的「租户概况」）。要让配额「接通」就必须把它建出来。我按设计稿 v1.6 第 586–593 行
   逐项还原（6 行 `.qrow` + `.bar`，复用 `components.css` 已有样式，未新增设计令牌），
   底部保留设计稿第 593 行原文说明。**若判定超出「接口对接」范围，可单独 revert 前端那一处，后端接口不受影响。**

3. **进度条告警阈值取 `>= 80%`**（契约写的规则）。依据：设计稿 `sec-tenant` 列表里 43%/38%/31% 为普通条，
   80%/83%/86% 为 `.bar o`。但设计稿第 592 行 AI 额度 74% 也标了 `o`——这是设计稿演示数据自身的口径不一致。
   我取多数证据 `80%`。**若要按「AI 额度更敏感、74% 即告警」处理，改一个常量即可。**

   面板另有一句「扩容走审批流（有效期>30天）；配额达 100% 由计量引擎硬拦截。」是设计稿原文（静态说明文案，非业务数据）。

5. **本机证据效力边界（沿用既有口径）**：本机无真实数据库，`USE_MOCK_DB` 未播种 `t_tenant`，
   所以真机取证只能走到「空态分支」（used=0 / limit=null）。**带真实数值的分支由路由级 + service 级
   mock 单测覆盖**（14 用例）。另注：取证响应里 `stores.used=1` 是 mock 对 `t_store` 的固定返回，
   属**环境产物**、非代码编造。

6. **`t_store` 口径 → 已修正为仅计 `store_type='WAREHOUSE'`**（见 §七）。设计稿第 589 行标签是「仓库数」，
   且 `warehouse.service.ts:3` 明示「仓库与门店同表（`t_store`），通过 `store_type='WAREHOUSE'` 区分」，
   其仓库查询即 `WHERE tenant_id=? AND store_type='WAREHOUSE'`。原「计所有行」与「仓库数」标签语义不符，
   故采纳独立复核建议改为只计 `WAREHOUSE`。

7. **`t_tenant_config` 定位 → 已修正为 `AND config_key='storage_limit'`**（见 §七）。该表为 key/value 结构，
   权威消费者 `storage-guard.ts:22` 即用 `WHERE tenant_id=? AND config_key='storage_limit'`；
   原查询只加 `storage_limit IS NOT NULL`，同租户其它 `config_key` 行若该列非空会被误取。
