# 派单（跨仓）· ZXQL-AI 迁移链：001 建表未落地 ＋ 跨库未限定 schema ⇒ **每次部署都 fail**

- 派单人：凌舟（wen-ssystem 总负责人）｜2026-10-08
- 执行方：**AI 底座线**（`wen-868/ZXQL-AI`）
- 性质：**P0 常驻红灯**（S3-166 把 AI 底座迁移接入部署流水线后，暴露出来）
- 证据来源：wen-ssystem 生产部署 run `37665016905`（2026-10-07T18:12Z）

---

## 一、现象（部署日志原文）

```
==> [AI底座][迁移] 012_push_log_tenant.sql → 跳过（EXIT=0，幂等：已存在，跳过）
ERROR 1146 (42S02) at line 33: Table 'liquor_inventory.ai_sample' doesn't exist
==> [AI底座][迁移] 013_backfill_sample_task_type.sql → 失败（EXIT=1）
==> [AI底座][迁移] 结果汇总：尝试 12 个 / 成功 3 / 跳过 8 / 容忍（已应用） 0 / 失败 1
❌ [AI底座] 部署失败：数据库迁移失败，已阻断本次 AI 底座部署（未重启进程，旧版本继续服务）
```

**同一次部署的其余部分都是好的**：主后端/前端部署成功、冒烟 **30/30 通过**；唯一失败项就是 `013`。
但部署脚本按"存在失败项 ⇒ 退出码 1"的规矩结束 ⇒ **从这一刻起，每次部署都会报 fail**，红灯失去分辨力。

## 二、根因（两条，缺一不可）

| # | 根因 | 证据 |
|:--:|:--|:--|
| **1** | **`001` 建表从未落地** —— `ai_sample` / `ai_experience` / `ai_correction` / `ai_evolution_version` 的 `CREATE TABLE` 不在仓库 | `ZXQL-AI/migrations/README.md:32` 自己写着：`\| 001 \| ai_experience / ai_correction / ai_sample / ai_evolution_version \| ai_db（P1-1 独立库） \| **待落地** \|` |
| **2** | **`013` 跨库未限定 schema** —— 写 `UPDATE ai_sample`（无库名前缀），而该表属 `ai_db` ⇒ 打到部署默认库 `liquor_inventory` ⇒ 1146 | `013_backfill_sample_task_type.sql:33/35/37…` 全是不带库名的 `UPDATE ai_sample` |

**同族历史（同一病，方向相反）**：`007_*.sql` 里**硬编码** `ai_db.ai_evolution_version` ⇒ 库名一旦不叫 `ai_db` 就变成"假绿灯"（判定已存在、实际没建）。⇒ 本仓迁移链在**跨库引用**上既没有统一约定、也没有基线建表，这才是"反复出问题"的根。

## 三、交付物

| # | 要求 |
|:--:|:--|
| ① | **把 `001` 建表落地**：`ai_db` 下 `ai_experience` / `ai_correction` / `ai_sample` / `ai_evolution_version` 四张表的 `CREATE TABLE IF NOT EXISTS`（显式 `utf8mb4` + 显式 collation + 不建物理外键），并让 README 的 001 行状态与实际一致（不许再写"待落地"却当成已完成） |
| ② | **统一跨库引用口径（二选一并全链贯彻）**：<br>· **A**：所有脚本显式 `USE ai_db;` 开头；或<br>· **B**：所有对象引用一律写 `ai_db.<table>`。<br>**禁止混用**（现状就是混用）。 |
| ③ | **`013` 改为幂等且不因缺表中断**：表不存在 ⇒ 输出"跳过（表不存在）"并 `EXIT=0`；表存在才执行回填。 |
| ④ | **全链体检**：逐脚本核对"引用的对象是否都有对应建表脚本 / 是否都带统一库限定"，把结果列成表（脚本号 → 依赖对象 → 建表出处 → 限定方式），**把不一致的一次性改齐**（不要只修 013）。 |
| ⑤ | **反测两侧**：<br>· 造"缺表"环境 ⇒ 迁移链**不得中断**（EXIT=0，且如实打印跳过）；<br>· 正常环境 ⇒ 回填真实生效（`SELECT COUNT(*) FROM ai_sample WHERE task_type IN ('createSalesOrder',…)` = 0 且归一后的值命中）。 |

## 四、验收标准（硬）

| # | 标准 | 判据 |
|:--:|:--|:--|
| ① | 迁移链**从零可建** | 在本地 MySQL 8.0（**不是 MariaDB**，其容忍度更高会掩盖问题）上，对空库按序跑**全量**迁移 ⇒ 零错误码 |
| ② | 幂等 | 同一库**连跑两遍** ⇒ 第二遍零错误码、零重复副作用 |
| ③ | 跨库口径一致 | `rg -n 'UPDATE [a-z_]+ SET|SELECT .* FROM [a-z_]+' migrations/*.sql` 逐条能回答"这个对象在哪个库、由哪个脚本建"——**不得再有裸引用 `ai_db` 的表** |
| ④ | 部署不再红 | 下一次生产部署 run 的 AI 底座段落**无失败项**（整 run 结论 = success） |
| ⑤ | 不留假绿 | 缺表/缺列一律"跳过并打印"，**不得**用 `|| true` 静默吞掉真实错误（区分"可容忍的已应用"与"真失败"） |

## 五、红线

1. **不得**直接在生产库执行任何写操作（迁移由部署流水线或运维按流程执行）。
2. 不得用 `|| true` / `2>/dev/null` 掩盖真实错误。
3. 不得只修 `013` 就交差（§三.④ 的全链体检是主要交付）。
