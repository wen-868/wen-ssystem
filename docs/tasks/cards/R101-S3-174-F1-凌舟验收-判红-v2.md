## 三、判红项 —— 第 4 处硬伤（本单**引入**的功能回归）

### 3.1 装置输出（原文）

```
PASS  A. JWT roles 含 SUPER_ADMIN（issueLoginResult 形状）  <- ["SUPER_ADMIN","STORE_OPERATOR"]
FAIL  B. permissions 非空（getUserPermissions 形状）        <- rows=0
FAIL  C. getUserMenus 能识别超管（否则菜单接口返回空）      <- []
```

### 3.2 证据链（逐条可核，行号取自本仓）

1. **生产角色是"租户内实体"**：`t_sys_role` 唯一键 = `uk_role_code_tenant (role_code, tenant_id)`；`backend/src/services/admin/rbac.service.ts:76-95 createRole(..., tenantId)` 按调用方租户建角色、按 `(role_code, tenant_id)` 查重。
   生产只读核对：**12 个角色行全部 `tenant_id='default'`**（`SUPER_ADMIN`/`OPERATION_ADMIN`/`STORE_MANAGER`/`STORE_OPERATOR`/… ）。
2. 迁移把演示账号与绑定搬进 `demo`，但**没有为 demo 建角色行**；绑定行 `role_id` 仍指向 `default` 的角色。
   （197 第 4 条"兜底补 SUPER_ADMIN"带 `ur.id IS NULL` 条件，生产**有**绑定 ⇒ 该句 0 行生效，补不到。）
3. **三条读路径都要求角色落在请求租户**：
   - `backend/src/services/admin/auth.service.ts:119-126` `getUserPermissions`：
     `JOIN t_sys_role r ON r.id = ur.role_id AND r.tenant_id = ur.tenant_id` + `WHERE ur.tenant_id = ?` ⇒ demo 命中 **0 行** ⇒ `permissions = []`。
   - `backend/src/services/admin/menu-permission.service.ts:89-96` `getUserMenus`：
     `... WHERE ur.user_id = ? AND (r.status…) AND r.tenant_id = ?` ⇒ **0 行** ⇒ `roleIds=[]` ⇒ 第 100-102 行**直接 `return []`**。
     ⚠️ **根本到不了**第 105/109-118 行的"超管返回本租户全量菜单"分支 —— 因此回传卡 §二.5 与本迁移注释中"超管直接返回本租户全量菜单，不查角色-菜单绑定"的推断**不成立**。
   - （`auth.service.ts:207-214` `issueLoginResult` 只按 `ur.tenant_id` 过滤、不带 `r.tenant_id` ⇒ JWT 的 `roles` 仍正常含 `SUPER_ADMIN`。**正因为它正常，问题被掩盖**：中间件层不报错，只有菜单/权限两条静默变空。）
4. **`req.tenantId` 来自 JWT**：`backend/src/middleware/tenant.ts:25 req.tenantId = req.user.tenantId`，而 JWT 的 `tenantId` 取自 `account.tenant_id`（`issueLoginResult:206`）⇒ 迁移后 = `demo`。
5. **前端后果**：`app-mobile/src/stores/menu.ts` 的 `load()` 在"接口**成功**但返回空集"时 → `buildMenuVisibility(空集)` → `status='ok'`（**不是 `firstfail`，不会提示"请重试"**）→ `isPageVisible` 对每一页返回 `false`。
   使用方：`app-mobile/src/pages/functions/functions.vue:92-100`、`app-mobile/src/pages-sub/admin/more/more-functions.vue:80-96`。
   ⇒ **演示账号进手机端后，功能中心与"更多功能"整屏空白，用户看不到任何原因。**
6. **反证（证明是本单引入、不是既存问题）**：迁移前 demo 在 `default`、角色也在 `default`，三条路径**全部命中**，功能中心正常。是隔离动作本身造成了回归。

## 六、装置保真：**我自己的两处纠错**（如实登记）

本装置首跑（2026-10-10）暴露了两处**装置自身的保真缺口**，均已修复并复跑。记在此处，因为二者正是"反测该红不红"的典型：

1. **`t_sys_user` 用了"只含被测字段"的最小表，缺 `updated_at`**；而 197 第 2 条 `UPDATE ... SET tenant_id, updated_at` ⇒ 装置当场 `1054 Unknown column` 崩。
   **生产 `t_sys_user` 确有 `updated_at`**（DDL 原文见 ddl.txt）⇒ 这是**装置保真缺口，不是迁移缺陷**。改为：197 写到的表**一律直接用生产 DDL**。
2. **夹具把 `default` 租户的 `tenant_code` 写成 `'T-DEFAULT'`，而生产是空串 `''`**；`t_tenant` 上 `tenant_code` 与 `uk_tenant_code` **两个唯一键**。
   旧版 `INSERT IGNORE` 漏写 `tenant_code` ⇒ 取隐式 `''` ⇒ 与 default 行**撞唯一键** ⇒ **整行被跳过**（这正是判红 ① 的真实成因）。
   初版夹具恰好"避开"了这次撞键 ⇒ 旧版在装置里**竟然建成了** demo 租户 ⇒ **反测一度失去分辨力**。按生产真值回填后，旧版才正确复现判红 ①（`demo_tenant=0`）。
