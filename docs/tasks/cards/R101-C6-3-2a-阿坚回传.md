## 七、风险与自我报备

**①【最高优先级 · 真库风险】归因落点①「开租户」的租户 ID 在真实库上取不到 ⇒ 该落点很可能整体不可用；等价装置恰好掩盖了这一点。**

事实链（全部可复跑）：

1. `t_tenant.id` 是 `VARCHAR(36) PRIMARY KEY`，**无 `AUTO_INCREMENT`、无默认值** —— 四处 DDL 一致：`docs/migrations/016_phase9_tenant_subscription.sql:11`、`029_add_tenant.sql:3`、`092_租户ID.sql:65`、`backend/src/shared/migration.ts:532`。
2. `backend/src/services/platform-tenant.service.ts:116` 用 `const tenantId = (result as unknown as { insertId: number }).insertId;` 取租户 ID（该行是**改动前既有代码**，本单未新增），且该 INSERT **不写 `id`**（同文件 `:110-114`）。
3. 按 MySQL 语义：**无自增列的 INSERT，`insertId` 恒为 0**。
4. C 用"忠实于真实 DDL"的桩复跑真实源码（`docs/migrations` 未改动，仅替换 db 桩）：

```
--- nonstrict（非严格模式） ---
RESULT: createTenant 抛错 -> 404 租户不存在，无法写入归因：0
SQL 轨迹: select id, status from t_promo_code… | insert into t_tenant … | insert into t_sys_user … | select id from t_tenant_attribution where tenant_id = ? | select source from t_tenant where id = ?
--- strict（严格模式） ---
RESULT: createTenant 抛错 -> ER_NO_DEFAULT_FOR_FIELD Field 'id' doesn't have a default value
```

即：非严格模式下**租户与管理员已写库、接口却返回 404**（半成品脏写）；严格模式下**建租户这一步本身**就 1364 失败。两者都让落点①的"归因行 +1 且 source 合规"无法成立。
