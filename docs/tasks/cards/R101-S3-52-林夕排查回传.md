## 三、根因（已读码证实）

`backend/src/shared/migration.ts:81-105` 的 `addTablePrefix()` 只覆盖 10 种模式：

```
CREATE TABLE / ALTER TABLE / INSERT INTO / UPDATE / DELETE FROM /
FROM / JOIN / INTO / RENAME TABLE / DROP TABLE
```

**没有 `REFERENCES`** → `FOREIGN KEY (tenant_id) REFERENCES tenant(id)` 里的 `tenant` 保持无前缀，而实际表名是 `t_tenant` → MySQL 报 `Failed to open the referenced table 'tenant'`。

## 四、为何此前从未暴露（掩盖链）

这些语句此前被 S3-51 的"注释块丢弃"缺陷整块丢掉、**从未执行过**。S3-51 与 S3-52 是**掩盖关系** —— 与踩坑[82] 同族：**修好一层，才看得见下一层**。
推论：**每修好一条长期失效的管线，都要预期会暴露下一批"从未被执行过"的欠账**，不要假设"修完就干净了"。

## 五、建议修法（未实施）

在 `addTablePrefix()` 的 `patterns` 里补一条（已有的 `t_` 前缀判断可直接复用）：
```ts
/(REFERENCES\s+)([a-z_][a-z0-9_]*)/gi,
```
并加守门反测：构造 `CREATE TABLE t_x (... FOREIGN KEY (tenant_id) REFERENCES tenant(id))`，断言输出变成 `REFERENCES t_tenant(`。

## 六、顺带暴露：seed 在空库上的两处异常（建议并入或另立）

1. `[seed] t_store 已有数据，跳过` **紧接着** `[seed] 获取门店ID失败: Table 'liquor_inventory.t_store' doesn't exist`
   —— **自相矛盾**，判空逻辑可疑（先说有数据，后说表不存在）。
2. `[migration] 种子数据初始化失败: Unknown column 'mobile' in 'field list'`。
3. 时序问题：seed 在外部迁移**之前**执行（日志时间戳 `:745` vs `:785`），**空库下必然踩空**。

## 七、红线

⚠️ **禁止为让 `migration-check` 变绿而**放宽 `grep "失败"`、加 `continue-on-error`、或禁用该 job。
这条红是 S3-48 修好门禁之后才有的**真信号**；按红线②，不得为变绿而降低检查。
