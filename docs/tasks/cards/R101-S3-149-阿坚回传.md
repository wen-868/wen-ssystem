## 一、一句话结论

### ② 为什么不落迁移、也不改 `init_database.sql`（卡里"二选一"的答案）

1. `docs/init_database.sql:117-138` 的 `t_store` **已经是生产形状**——`:119 tenant_id VARCHAR(36) NOT NULL`、`:129 status VARCHAR(20) NOT NULL DEFAULT 'OPEN'`（与卡 §三 给的生产读数逐字一致）；

3. 修复前空库之所以是"缺列/类型不同"，是因为**这 62 条建表根本没执行**，`t_store` 改由 `docs/migrations/001_phase1_schema.sql:109`（`CREATE TABLE t_store`，无 `tenant_id`、`status TINYINT NOT NULL DEFAULT 1`）建成；`t_sys_config` 则从来没被建出来——`005_phase3_sys_config.sql:12-24` 的 `CREATE TABLE` 把 `UNIQUE KEY uk_config_key_tenant (config_key, tenant_id)` 建在**本表未定义**的 `tenant_id` 上，MySQL 报 `Key column 'tenant_id' doesn't exist in table`，而该文案命中 `SKIP_PATTERNS` 的 `"doesn't exist"` ⇒ **静默跳过**。原始输出：反测空库 `neg-run-fresh-old.txt:260` `005_phase3_sys_config.sql: 跳过 (ER_KEY_COLUMN_DOES_NOT_EXITS)`；修复后同一文件变成 `run-fresh-fixed.txt:219` `跳过 (ER_TABLE_EXISTS_ERROR)`（因为 `init_database.sql` 已经把它建好了）。⇒ **`docs/migrations/**` 里没有任何一处能建出 `t_sys_config`**；
