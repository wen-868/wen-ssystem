## 二、裁定

**① 未绑定管理员取 **403（收紧）**⇒ 认可。**
理由：生产唯一管理员 `admin` 是 `PLATFORM_SUPER_ADMIN`（全通）⇒ 影响面为 **0**；而"未绑定即放行"会让试点域门禁对存量账号形同虚设，与"不许用登记/放行换绿"的同一条纪律相悖。

**② 绑定结构复用 `t_platform_admin.role`（一管理员一角色）⇒ 认可现状；独立绑定表转后继项（第 67 项）。**
理由：本单目标是"把机制建起来 + 一个试点域"，不是把权限模型一次做到终局；独立绑定表需连同**角色管理界面**一起做，否则界面无处可配。**不阻塞本单**。

**③ 目录外 4 域（library/open/review/miniapp，共 28 条）暂不扩目录 ⇒ 并入第 67 项。**
理由：扩目录会改既有契约（"18 条 / 8 域"）+ 8 条断言 + 联动 saas-admin 角色矩阵页，属**独立变更**；本单已把它们**逐条登记在台账的"需扩目录"列**，不会丢。

**④ 权限码命名取既有规范 `<moduleCode>:<action>`（`sysconfig:manage`），不采纳我卡面的 `platform:<域>:<manage>` ⇒ 认可。**
理由：避免同一个域出现两种写法。**这是我卡面第二处不准确**（与 S3-192 的库值前提同类），教训合并写进踩坑日志：**凌舟的卡面给"命名/取值"示例时，必须写明"以仓内既有规范为准，发现冲突就按既有规范并报备"**。

**⑤ `guard-rbac-wiring` 判据扩展（新增识别 `requirePlatformPermission(`）⇒ 认可。**
理由：不扩展则平台域接线后仍被判"无权限检查"、台账失真；执行方给了反测，并实测**全仓 762 个写端点中受影响仅 4 条**（已接线 53→57、缺口 709→705）。

**⑥ 两处存量红：根 `npm run build`（第 62 项，已有）+ `guard-rbac-wiring --strict` 的 3 条未登记缺口（`marketing-miniapp.routes.ts:55/72/80`）⇒ 后者登记为第 68 项。**
