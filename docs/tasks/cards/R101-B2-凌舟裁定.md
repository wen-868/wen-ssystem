## 二、核验同时挖出 3 项，逐项裁定

### 裁定 1（红点①）：`t_sale_bill_item.tenant_id` 未随租户落库 ⇒ **P0 修复 + 全量清扫 + 回填**

**凌舟独立复核（不看自述、只看代码与生产）**：

1. **列定义**：`docs/migrations/092_租户ID.sql:141` —— `t_sale_bill_item.tenant_id VARCHAR(36) NOT NULL DEFAULT 'default'` ⇒ **省略该列即静默写 `'default'`**，不报错。
2. **两条 INSERT 都省略该列**：
   - 主开单流程 `backend/src/services/store/sale-bill.service.ts:313-321`（**这是主干道**）；
   - 离线同步 `backend/src/services/sync/delta-sync.service.ts:741-744`。
   对照：`backend/src/services/admin/demo.service.ts:178-181` **显式带了** `tenant_id` ⇒ 说明"该带"，前述两处是漏。
3. **生产实测（只读查询，服务器 MySQL）**：

   | 查询 | 结果 |
   |---|---|
   | `SELECT id, tenant_code, name FROM t_tenant` | **2 个租户**：`default`（默认租户）+ `f0cbfe78-…`（真实租户 T2026090895839） |
   | `t_sale_bill` 按 `tenant_id` 分组 | `default` 524 张 / 真实租户 **1 张** |
   | `t_sale_bill_item` 总行数 / `tenant_id='default'` 行数 | **521 / 521** |
   | `明细 tenant_id='default' 但 header tenant_id<>'default'` 的单数 | **1**（即真实租户那张单） |

   ⇒ **缺陷已在生产实际发生**：真实租户的那张单，明细行归属错误。按租户过滤读明细的路径（如 `backend/src/services/share.service.ts:133` / `:188`）**读不到自己的明细**。

**裁定**：

- **优先级 P0**（租户隔离级；一旦开放注册，每张单都会中）；
- **一次性做三件事**：① **全量同族扫描**（找出所有"列有 `DEFAULT 'default'` 且 INSERT 列清单不含 `tenant_id`"的明细/子表写路径，给清单与数字，不得只修碰到的那两处 —— 见 `AGENTS.md`《技术债铁律》第 2 条）；② **修代码**（各 INSERT 补 `tenant_id`，与父表/单据 tenant 对齐）；③ **出回填迁移**（仅回填"明细 `tenant_id='default'` 且其 header `tenant_id<>'default'`"的行；回填值取 header 的 tenant_id）。
- **回填属不可逆生产数据写入** ⇒ 必须：**先备份**（`deploy/02-mysql-backup.sh`）→ 经**迁移链**执行 → 跑后核对（回填行数 = 预期 1 张单的明细行数；`明细tenant<>header tenant` 的计数必须归零）。
- **反测**：修复后新写入的明细必须带正确租户；回填 SQL 必须**只**动应动的行（构造"header 也是 default"的行作为不该动的反例）。

### 裁定 2（红点②）：`uk_sale_bill_no` 全局唯一 ⇒ 跨租户同名单号互顶 —— **本轮不改，登记 S3-84**

- 依据：`docs/migrations/001_phase1_schema.sql:365` / `backend/src/services/...migration.ts:601` 的唯一键**不含 `tenant_id`**，而服务层预检是**租户内**查重 ⇒ 两道防线口径不一致。
- **不改的理由**：改唯一键属 **DDL + 存量影响面未知**（需先确认真库是否存在已跨租户重复的单号、以及外部对账/排障是否依赖"单号全局唯一"这一既有约定）；不可逆动作不得顺手做。
- **登记 S3-84**，要求先出：① 真库"跨租户同名单号"实际发生次数；② 两个方案（改 `(tenant_id, bill_no)` 唯一键 / 落库单号加租户前缀）的风险对比与演练方案；③ 对既有对账/排障口径的影响。

### 裁定 3（红点③）：重复提交返回"失败" ⇒ 客户端永久重试 —— **裁定改为幂等成功**

- 依据链：第二次提交返回 `success=false` → `app-mobile/src/utils/sync-manager.ts:428-438` 标 `SYNC_FAILED` → `app-mobile/src/api/local-db.ts:711` 的 `listPending` **包含** `SYNC_FAILED` ⇒ 该草稿**永远重试、永远失败**（典型触发："第一次已写库成功但响应丢失"）。
- **裁定**：命中"已存在"时**返回 `success:true` + 既有 `billNo`**（幂等成功语义），使客户端转入 `SYNCED`。**这是产品语义修正，凌舟裁定，随裁定 1 的修复单一起做**。
- 同时要求执行方修掉**契约注释漂移**：`app-mobile/src/api/sync.ts:208` 注释称用服务端 `makeBizNo("XS")` 生成 `billNo`，实现却是用 `draftNo` 当 `billNo`（`delta-sync.service.ts:723`）⇒ 二者必须一致；因红线禁改 `app-mobile/**`，**改后端实现或改注释由执行方在回传里给方案**，不得擅动客户端。
