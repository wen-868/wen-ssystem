## 六、风险与自我报备

1. **"同一事务"未达成（卡内自相冲突，主动报备，等裁定）**：派单卡交付物③要求"于**同一事务**追加一条流水"，但验收标准⑥/红线③同时**冻结** `platform-s3-110.test.ts` 的 9 条断言；其中 2 条把"状态流转的 UPDATE 必须走 `shared/db.query` 且参数为 `[status, reviewedBy, id]`"写死（`hoisted.query.mock.calls.find(c => String(c[0]).includes("UPDATE t_library_spu"))`）。要把 UPDATE 与 INSERT 放进**同一个** `transaction(conn)`，UPDATE 必须改走 `connExecute` ⇒ 这 2 条断言必红，与"9 条全绿"直接互斥。本单按"冻结断言优先"落地（不改任何既有断言），因此：
   - 现状 = 先 UPDATE 成功后 INSERT；**INSERT 失败会让整个请求 500，而状态已改、流水缺失**（不吞错，符合红线④；但没有回滚）。
   - 若要真原子，请裁：**方案 A（推荐，零改动面）** 接受现状并在卡内把"同一事务"改为"同一成功分支、同一连接池顺序写"；**方案 B** 授权把上述 2 条断言的 UPDATE 观测点从 `query` 改为 `connExecute`（等价白盒口径），我再补真事务。
2. **`reason` / `operator_name` 超长截断**：列宽由迁移 183 钉死（VARCHAR(255) / VARCHAR(64)），服务层 `normalizeReviewLogText` 去首尾空白后为空 ⇒ `NULL`，超长 ⇒ 截断到列宽。**截断是静默的**（避免 >列宽时 MySQL 严格模式报 500 把状态流转整体打挂）。若凌舟要求"超长即 400"，请给口径（属新增校验分支，会改变既有端点的入参容忍度）。

4. **`operator_name` 来源**：取当前平台令牌 claims（`realName` 优先、回落 `username`，两者都无则 `NULL`），**不额外查 `t_platform_admin`**（避免为留痕引入新的表依赖与一次 SELECT）。`operator_id` 取令牌 `id`。
