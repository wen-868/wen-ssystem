## 六、风险与自我报备

1. **我写错过一次，已修并留档**：生成器首版把 `--   底稿 sha256：…` 前缀写漏成裸文本行，导致 205 的**第一块**（表头注释 + 首条 `INSERT`）被启动链的 `splitSqlStatements` 当成一条语句、
   且因"剥掉注释后的首词不是写关键字"而**绕过写闸门被真的执行** ⇒ `ER_PARSE_ERROR`（红线基线里实测到）。
   修复后重跑，205 的 `ER_*` 行 **0**；装置 `tools/probe-205-chunks.mjs` 留证（打印 25 个切块首关键字）。
   **建议记入 `docs/踩坑日志.md`**（外部迁移文件里任何一行都不能漏 `--` 前缀，否则整块被判成非写语句、在 `gate=block` 下反而真下发）——本单未擅自改踩坑日志，等凌舟定。
2. **本单最大风险不在 205 本身，而在写闸门**：默认 `MIGRATION_WRITE_GATE=block` 会把 205 的 24 条写语句**全部跳过**
   （实测：同一份空库、同一个 205，`block` ⇒ 0/12，`allow` ⇒ 12/12）。即"205 落库 ≠ 灾备库有权限"。
   这意味着**第 72 项只在"闸门放行 + 迁移被执行"两个条件同时成立时才算修好**，见 §九.1/§九.2。
3. **自检 SQL 的口径我做过一次自我纠正**：初版把"在用角色"定义为"有绑定 **且 `status='ACTIVE'`**"，
   实测同一台空库里角色 status 口径并不统一（绑定到演示账号的 5 个角色是 `status='1'`）⇒ 该过滤会把真在用的角色整体排除，形成**假绿**，故改为只认"有绑定"这一条客观事实（文件头留了口径与理由）。
4. **红线库里还有 247 条别的 `ER_*` 跳过**（来自其它既有迁移），属存量语料问题，本单只保证 205 自身零错误；未扩大范围去动它们。
