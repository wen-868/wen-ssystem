## 〇、共性根因（两处同源，先说清）

`backend/src/config/database.ts` 的注入层按语句类型分派（`:193-206`）：`injectTenantCondition` → SELECT/INSERT/UPDATE 三个分支。
**三处分支对"注入点之后的参数序列"处理方式不一致**：

| 分支 | 位置 | 参数处理 | 现状 |
|---|---|---|---|
| SELECT · 无 WHERE（含 ORDER BY/GROUP BY/LIMIT/HAVING） | `database.ts:229-247` | 按 `placeholderCount` 在**同一位置**插入 tenantId | ✅ R95-03 已修（正确） |
| SELECT · 含 WHERE | `database.ts:221-226` | `[tenantId, ...params]` **前置** | ❌ **S3-68（本卡）** |
| INSERT | `database.ts:251-266` | 正则重建整句 SQL，`VALUES (?, ${values})` **丢弃 match 之后的原文** | ❌ **S3-69（本卡）** |
| UPDATE · 含 WHERE | main `database.ts:271-286`（病灶行 `:281`）／分支 `:271-299`（修复块 `:288-294`） | 按 `placeholdersBeforeWhere` 插入 | ✅ **分支 `1c46dd9c` 已修；main 尚未合并**（这正是"修复在分支、主干仍带病"的客观状态） |

## 一、S3-68：读路径 `injectSelectTenant` 参数前置挤位（1 处）

### 1.1 现象

| 项 | 内容 |
|---|---|
| 调用点 | `backend/src/services/admin/report/sales-report.service.ts:154`（`getSalesTrend` 内的 `queryWithTenant<SalesTrendRow>(...)`） |
| 表现 | 销售趋势报表**静默返回空/异常数据**（`period` 为 NULL 或整段空），接口**不报错**（HTTP 200 + 空数组），前端显示空趋势图 |
| 触发范围 | 该函数只有 1 个 SQL 受影响；`formatMap`（`sales-report.service.ts:145-149`）决定 `period` 的入参，三种周期（month/week/day）全部走同一 SQL |

### 1.2 根因（为什么错位）

原始 SQL（`sales-report.service.ts:154-165`）：

```sql
SELECT DATE_FORMAT(sb.created_at, ?) AS period, ... FROM t_sale_bill sb
 WHERE sb.business_status NOT IN ('DRAFT','VOIDED') AND sb.created_at >= DATE_SUB(CURDATE(), INTERVAL 12 MONTH)
 GROUP BY period ORDER BY period ASC
```

实参 `[dateFormat]`（如 `'%Y-%m'`）。

1. 该 SQL **不含 `tenant_id`** ⇒ 不短路；
2. 含 `where` ⇒ 走 `database.ts:221-226` 分支，在 `WHERE` 后插入 ` tenant_id = ? AND `；
3. 该分支仍用 `modifiedParams: [tenantId, ...params]`（**`database.ts:225`**）⇒ 实际参数序列变为 `[tenantId, dateFormat]`；
4. MySQL 按"`?` 在 SQL 文本中的先后"取值 ⇒ **`DATE_FORMAT(sb.created_at, ?)` 拿到 `tenantId`（如 `'default'`），`tenant_id = ?` 拿到 `'%Y-%m'`**；
5. 结果：`tenant_id = '%Y-%m'` 匹配不到任何行 + `period` 被按非法格式串格式化 ⇒ 返回空（不是报错）。

> **判定依据**：本卡复算的是注入函数的**真实源码**（`database.ts:221-226`），不是推理；影响面报告用同一套纯函数复算口径已确认"SELECT 中满足'首个 where 前有占位符'的调用点**全量 1298 处里仅此 1 处**，其余 16 处该值 > 0 的 SELECT 都自带 `tenant_id` ⇒ 短路不命中。

### 1.3 为什么本次修复没覆盖它

1. **修复面**：`1c46dd9c` 的 diff 只含 `injectUpdateTenant`（分支 `database.ts:288-294`）+ 改密服务层 + 测试；**未触碰 `injectSelectTenant`**（同一 `database.ts` 里 `:225` 的原写法一字未改，分支与 main 完全一致）。修复提交的注释还写着"与 R95-03 在 `injectSelectTenant` 中的修法保持一致"，但 R95-03 只改了**无 WHERE 分支**（`:229-244`），含 WHERE 分支从未被改过 —— 注释与事实不符，属须纠正的表述。
2. **扫描口径**：本次影响面扫描的命中集定义是 `UPDATE/DELETE`（写路径 356 处），**读路径不在口径内**；即使扫到 SELECT，本条也只在"首个 where 前存在占位符"这个子判据下命中。
3. **无测试保护**：`backend/src/__tests__/config/database-tenant-injection.test.ts`（该文件仅存在于分支 `fix/s3-65-change-password-fail`，main 上不存在）覆盖的是 UPDATE 分支；SELECT 含 WHERE 分支没有等价断言。

### 1.4 修法

**方案 A（推荐，与 UPDATE 同算法）**：把 `database.ts:225` 改为按占位符位置插入：

```
const placeholdersBeforeWhere = (sql.substring(0, insertIndex).match(/\?/g) || []).length;
modifiedParams = [...params.slice(0, placeholdersBeforeWhere), tenantId, ...params.slice(placeholdersBeforeWhere)];
```

**方案 B（同批可选，须凌舟授权范围）**：抽出私有函数 `insertTenantParamAt(params, index, tenantId)`，由 SELECT 含 WHERE（main/branch 同为 `:225`）与 UPDATE 含 WHERE（分支修复块 `:288-294`）共用，消除"同一算法两处手抄"的分叉。

**红线**：① 不得改动 `injectSelectTenant` 的**注入位置**与 SQL 文本形状（`WHERE tenant_id = ? AND ...` 保持不变），只改参数序列；② 不得放宽/删除既有断言；③ 不得只修这一处而放过方案 B 中的第二处（若选 B 则两处必须同批）；④ 若发现新增用例暴露其它读路径错位，**停下报备**，不得自行扩大修复面。

## 二、S3-69：`injectInsertTenant` 正则重建 SQL 丢尾（1 处）

### 2.1 现象

| 项 | 内容 |
|---|---|
| 调用点 | `backend/src/services/admin/push.service.ts:371`（`registerToken` 的"设备不存在"分支，SQL 文本在 `:372-374`） |
| 表现 | **新设备首次注册推送 token 必然失败**；注入后 SQL 语法错误 ⇒ MySQL 报错 ⇒ 接口 500（**响亮的失败，不是静默**）；老设备走 `:361` 的 UPDATE 分支不受影响 |
| 业务后果 | 新设备拿不到推送 token，推送通道对新设备完全不可用；若前端不重试，用户侧表现为"收不到通知" |

### 2.2 根因（丢的是什么）

`database.ts:258`：

```js
const insertMatch = sql.match(/INSERT\s+INTO\s+(\w+)\s*\(\s*([^)]+)\s*\)\s*VALUES\s*\(\s*([^)]+)\s*\)/i);
```

`:261` 用 `INSERT INTO ${tableName} (tenant_id, ${fields}) VALUES (?, ${values})` **整句重建**。

对 `push.service.ts:372-374` 的语句：

```sql
INSERT INTO t_push_token
 (user_id, device_id, push_token, provider, app_platform, app_version, status, last_active_at)
 VALUES (?, ?, ?, ?, ?, ?, 1, NOW())
```

- `([^)]+)` **不能包含 `)`** ⇒ 捕获 `VALUES` 列表时在 **`NOW()` 的第一个 `)` 处截断**，`values` 实得 `?, ?, ?, ?, ?, ?, 1, NOW(`；
- 正则末尾的 `\s*\)` 把这个 `)` 当成"VALUES 列表的收尾括号"消费掉；
- 重建时**只用捕获组拼串**，`match.index + match[0].length` 之后的原文被**整段丢弃**；
- 最终 SQL 少一个 `)`（括号不平衡 1 个）：`... VALUES (?, ?, ?, ?, ?, ?, ?, 1, NOW(`。

**丢掉的到底是什么（逐项）**：

1. `NOW()` 的右括号 —— 直接导致语法错误（本例）；
2. **匹配点之后的全部原文** —— 这是一个更危险的类别：任何"`VALUES (...)` 之后还有尾子句"的 INSERT（`ON DUPLICATE KEY UPDATE ...`、别名、`RETURNING` 等）都会被**静默截掉尾子句**（不报语法错，行为却变了）；
3. 若字段列表或 VALUES 列表里再出现嵌套括号（函数调用、子查询），截断点会进一步前移，可能连**合法字段都丢**。

> **影响面**：影响面报告用真实函数复算，13 处"未自带 `tenant_id` 且可静态注入"的 INSERT 中**仅这一处括号不平衡**（其余 12 处 VALUES 无嵌套括号）；自带 `tenant_id` 的 INSERT（如 `jobs/report-aggregation.job.ts:43-46`、`services/admin/tenant.service.ts:358`）在 `database.ts:252-254` 短路，**不受影响**。但第 2 类（尾子句被静默吞掉）目前**没有统计数字**——见 §2.5 未证明项。

### 2.3 后果判断

| 维度 | 判断 | 依据 |
|---|---|---|
| 是否静默 | 本例**不静默**（MySQL 语法错误 ⇒ 500），属"响亮失败" | 括号不平衡是语法级错误，无法被优化器容忍 |
| 是否影响生产 | 影响"新设备注册推送 token"这一条路径；老设备更新分支正常 ⇒ 故障表现是"部分设备收不到推送"，不易被归因 | `push.service.ts:354-368`（existing 分支）与 `:371-376`（insert 分支）互斥 |
| 是否有数据残留 | 无（语法错误的语句不会写入任何行） | INSERT 未执行 ⇒ 无部分写入 |
| 优先级建议 | **P1**（不改不会造成数据错乱，但推送通道新设备不可用，且属"同一注入层第三个分叉"） | 影响面报告 §7 表第 5 项 |

### 2.4 修法（两选一，由凌舟拍板）

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **① 最小修（推荐先做）** | 不再整句重建：定位字段列表的 `)` 与 `VALUES (`，仅在两处插入（字段列表尾插 `, tenant_id`；`VALUES (` 之后插 `?,`），**SQL 其余字节原样保留** | 改动最小、不可能丢尾；对已短路的语句行为不变 | 依赖定位正确（需括号/引号感知的定位，不能再用 `[^)]+`）；若 VALUES 中出现字符串字面量内的 `)`（如 `')'`）仍可能定位错 ⇒ 必须同时处理引号 |
| **② 根治（建议随后并入同批）** | 保留尾部原文：`const tail = sql.slice(match.index + match[0].length)` 并在重建后拼接；同时把 `[^)]+` 换成"括号深度扫描"（`(` 深度 +1、`)` 深度 −1，深度归零才算列表结束），并跳过单引号/双引号/反引号内的字符 | 一次封掉"丢尾子句"整类缺陷；对嵌套函数调用安全 | 改动相对大，需要更全的用例矩阵（嵌套括号、字符串内括号、尾子句） |

**红线**：① 短路行为（SQL 已含 `tenant_id` ⇒ 原样返回）不得改变；② 参数序列仍必须是 `[tenantId, ...params]`（`tenant_id` 插在字段列表首位，参数也必须在首位——这两者**同时**改或同时不改，不许只改一处）；③ 不得用"给 `push.service.ts` 的 SQL 加 `tenant_id` 字面量"的方式绕过（那是文件级绕过，违反技术债铁律①，会把 102 处同类风险继续藏着）。
