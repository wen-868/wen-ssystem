## 一、根因（精确定位）

- 文件：`backend/src/shared/migration.ts`
- 旧缺陷行：约 **第 908–912 行**（第 8 步外部迁移）及 **第 770–773 行**（5.5.8 AI 底座建表）——两处同一写法：
  ```ts
  .split(";")
  .map((s) => s.trim())
  .filter((s) => s.length > 0 && !s.startsWith("--"))
  ```
- 机制：按 `;` 切块后，凡"首块 = 文件前导注释块 + 紧跟的第一条真实语句"会落进同一个 chunk；`.trim()` 后以 `--` 开头 → 被 `!s.startsWith("--")` 整块丢弃，**连同其后的首条建表语句一起丢**。
- 触发样例：`031_add_subscription.sql`、`016_phase9_tenant_subscription.sql`、`120d_fix_server_3bugs.sql` 首行即注释，紧跟 `CREATE TABLE t_subscription` / `t_subscription_plan` / `t_error_logs`；`121_ai_base_tables.sql` 首行即注释，首张表 `t_platform_ai_config` 亦被静默跳过。
- 后果：全新 MySQL 8 容器（CI `35126291300`）跑完 170 个迁移显示"done"、服务 `listening on 8095`，随后 `subscription-expiry.service.js:14` 报 `Table 'liquor_inventory.t_subscription' doesn't exist`（ER_NO_SUCH_TABLE）→ 进程 exit 1。**新建库 / 灾备库起不来**，存量库因走另一条路径（见第六节）幸免。

## 二、修复 diff 摘要

改动只在 `backend/src/shared/migration.ts`，**未重构其它逻辑**，`USE`/`DELIMITER`/`CREATE PROCEDURE`/`DROP TABLE` 的跳过行为完全不变。

1. 在 `addTablePrefix` 之后新增**具名导出**函数（约 105–128 行）：
   ```ts
   /**
    * S3-51 + 踩坑[63]：把整段 SQL 拆成可逐条执行的语句数组（按 `;` 切块）。
    * 先剥离 chunk 开头的整行注释（只剥开头，语句中间/末尾的 `--` 一律不动，
    * 保守起见不做行内 `--` 解析），再按 length>0 判断；剥离后为空的纯注释块仍然丢弃。
    * 调用方需先移除 USE / DELIMITER 行（见各调用点的 cleaned 步骤）。
    */
   export function splitSqlStatements(sql: string): string[] {
     return sql
       .split(";")
       .map((s) => s.trim())
       // 先剥离 chunk 开头的整行注释，再判断是否为空，避免把首条建表语句一起丢
       // （尾随的注释行可能无换行结尾，故用 (\n|$) 同时吃掉收尾注释行）
       .map((s) => s.replace(/^(\s*--[^\n]*(\n|$))+/, "").trim())
       .filter((s) => s.length > 0);
   }
   ```
2. 第 8 步外部迁移调用点替换为：
   ```ts
   // S3-51 + 踩坑[63]：改用 splitSqlStatements，剥离 chunk 开头的整行注释后再判断，
   // 避免"以注释开头的整块语句"把首条建表语句一起丢弃（见 splitSqlStatements 注释）。
   const statements = splitSqlStatements(cleaned);
   ```
3. 5.5.8 AI 底座建表调用点替换为：
   ```ts
   // S3-51 + 踩坑[63]：改用 splitSqlStatements 统一修复"注释开头整块被丢"的缺陷
   const aiStatements = splitSqlStatements(aiCleaned);
   ```

核心差异：旧逻辑"`startsWith('--')` 即整块丢弃" → 新逻辑"只剥离 chunk **开头**的整行注释，再判空"，语句中间/末尾的行内 `--` 一律保留（如 `COMMENT 'a--b'`、`SELECT 1 -- 行内注释`）。

## 六、scripts/run-migration.mjs 结论（只读分析，未改动）

- 路径：`scripts/run-migration.mjs` 读取 `.sql` 后，**整文件** `conn.query(sqlContent)`，连接选项 `multipleStatements: true`（`scripts/run-migration.mjs:58,65`）。
- 该路径**没有** `;` 切块、也**没有** `startsWith("--")` 过滤，注释由 MySQL 服务端原生解析（前导 `--` 被服务端跳过），故"注释开头 + 首条建表"**不会被丢弃**。
- 因此：**同一条 `031_add_subscription.sql`，经 `run-migration.mjs` 跑过的存量库有 `t_subscription`，经 `migration.ts` 启动自迁的全新库没有**——两条迁移路径行为不一致。

**凌舟建议（落实方向，非本次改动）**：
1. **统一路径**：让 `migration.ts` 的逐块逻辑与 `run-migration.mjs` 对齐——即不要按 `startsWith("--")` 预丢弃整块，改为交给 MySQL 多语句执行（或复用同一个 `splitSqlStatements` 安全切分器）。本次已把 `migration.ts` 的切块逻辑收敛到 `splitSqlStatements`，但执行仍逐条 `query`，与 `run-migration.mjs` 的整文件 `multipleStatements` 仍有差异（语义等价，仅执行粒度不同，行为已一致正确）。
2. **若暂不统一**：在 `docs/` 显式标注"哪条路径为权威初始化路径"，并在 CI 中统一只用一条路径初始化全新库，避免"本地/存量走 A、CI 走 B"产生的结构性漂移。

> 约束：本卡**不修改** `scripts/run-migration.mjs`，仅作说明与建议。

## 八、可直接粘贴的踩坑[63] 补充文案

> **[63] 迁移管线按 `;` 切块后误丢"注释开头整块语句"（含其首条建表）**
> 位置：`backend/src/shared/migration.ts`（旧第 908–912 行 / 第 770–773 行，两处同一写法）。
> 现象：全新 MySQL 8 容器起服务报 `ER_NO_SUCH_TABLE`，如 `t_subscription doesn't exist`（`subscription-expiry.service.js:14`）；170 个迁移显示"done"却缺表。
> 根因：`.split(";").map(trim).filter(s => s.length>0 && !s.startsWith("--"))` —— 当 `.sql` 首行是注释、紧跟 `CREATE TABLE`（到第一个 `;` 间无分号），整块被当作注释丢弃，**首条建表语句一起没了**。受影响文件首块以 `--` 开头的有 127 个，其中含真实语句 111 个（90 个含 `CREATE TABLE`）。
> 修复：抽取 `export function splitSqlStatements(sql)`，先 `s.replace(/^(\s*--[^\n]*(\n|$))+/, "").trim()` 剥**开头**整行注释，再按 `length>0` 过滤；语句中间/末尾行内 `--` 不动；纯注释块仍丢弃。两处调用点统一改用之，`USE`/`DELIMITER`/`CREATE PROCEDURE`/`DROP TABLE` 跳过逻辑不变。
> 反测：`backend/src/__tests__/shared/migration-split.test.ts` 先红（2 failed）后绿（6 passed），`tsc --noEmit` 通过，迁移全量 85 测试通过。
> 注意：同仓 `scripts/run-migration.mjs` 用整文件 `multipleStatements` 执行、无此过滤，故存量库（走该路径）有表、全新库（走 `migration.ts` 自迁）缺表——两条路径行为不一致，建议统一或显式标注权威初始化路径。
