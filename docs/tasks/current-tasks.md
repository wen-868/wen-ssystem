## 根因分析

### 为什么"越修问题越多"

R1~R6 修了 39 个补丁，但评分从 95 暴跌到 58。根因不是某个 bug，而是：

**1. 补丁式修改引入连锁破坏**

R4-1 墨一次性改了 96 个文件（补字段+清 as any），R6 又改了 97 个文件。大量改动没有经过 `tsc` 类型检查就提交，导致方法名拼写错误、导入路径错误、属性不存在等 247 个 TS 错误。**改得越多，错得越多**。

**2. 缺少构建门禁**

没有 CI/CD 管道，每次提交不强制跑 `tsc --noEmit` + `npm run build`。错误只在苏然做全局测试时才发现。

**3. 全局标准不统一**（已在 R7 审计中记录）

缺少 config/middleware 目录、价格守卫未全局应用、两套编号生成器、追溯码未嵌入流程等。

### 解决思路

**先止血，再治本。**

| 阶段 | 目标 | 顺序 |
|:---:|------|:---:|
| 止血 | 修复 247 个 TS 错误，恢复构建通过 | 第一步 |
| 门禁 | 建立本地构建检查流程 | 第二步 |
| 治本 | R7 全局标准化整改（config/middleware/价格守卫/追溯码等） | 第三步 |

### 阿坚 · 紧急修复（2 天）

#### R8-1 后端 TS 类型错误修复（247 个）— 构建恢复

- 优先级：P0
- 负责人：阿坚
- 预计：2天
- 状态：待开始
- 文件：`backend/src/` 全部 .ts 文件
- 问题：后端 247 个 TS 错误导致构建失败，无法部署。错误类型：TS2339 属性不存在（~150）、TS7006 隐式 any（~80）、TS2551 拼写错误（~10）、TS2305 导入错误（~7）
- 修复：
  1. 运行 `npx tsc -p tsconfig.json 2>&1 | grep "error TS" > ts-errors.txt` 获取完整错误列表
  2. 按文件分组，优先修复 TS2305（导入错误）和 TS2551（拼写错误）— 这两类是运行时必崩的
  3. 然后修复 TS2339（属性不存在）— 多为 R4-1/R6 清除 as any 时引入的类型断言不当
  4. 最后修复 TS7006（隐式 any）— 添加参数类型注解
  5. 每修复一批后跑 `npx tsc --noEmit` 确认错误数递减
  6. 最终目标：`npx tsc --noEmit` 输出 0 错误 + `npm run build` 成功
- 约束：**本次修复只做类型修正，不做功能改动。不改业务逻辑、不改文件结构。**

#### R8-2 建立本地构建检查流程

- 优先级：P0
- 负责人：阿坚
- 预计：0.5天
- 状态：待开始
- 文件：`backend/package.json`
- 问题：没有构建门禁，每次提交不检查 TS 错误和构建
- 修复：
  1. 在 backend/package.json 中添加 `"typecheck": "tsc -p tsconfig.json --noEmit"` 脚本
  2. 在 backend/package.json 中添加 pre-commit 钩子或 `"check": "npm run typecheck && npm run build"`
  3. 写入踩坑日志：每次提交前必须跑 `npm run check`，TS 错误不为 0 则禁止提交
  4. 推荐团队：每个子项目（backend/admin-web/saas-admin/merchant-mobile）都加类似的 check 脚本
