## 二、"怎么拿到带 token 的 URL"（回答 2026-09-21 提问）

已核实的协议事实：host 是 **CodeBuddy Code Remote Control**（`/` 返回其 Web UI）；API 需 `Authorization: Bearer <token>`（实测 `/health`、`/api`、`/openapi.json`、`/docs` 全 401）；**token 来源 = URL 参数 `?token=`**（前端 bundle `URLSearchParams(...).get("token")`）。

token **不在**这些地方（均已实测）：`sessions/*.json`（只有 pid/url/kind/meta，meta 是命名管道 `\\.\pipe\codebuddy-prewarm-*`）、`workbuddy.db`（表：sessions/workspaces/automations/automation_runs/automation_runtime_state/automation_delivery_outbox/buddy_snapshots，无 token 列）、`~/.workbuddy` 顶层小文件、`%TEMP%` 近 6h 小文件。

**token 穷尽搜查结果（2026-09-21 实测，五处落盘点 + 两种二维码全查）**：

| 位置 | 结果 |
|---|---|
| `~/.workbuddy/sessions/*.json` | ❌ 只有 `pid/url/kind/meta`（meta 是命名管道 `\\.\pipe\codebuddy-prewarm-*`） |
| `~/.workbuddy/workbuddy.db`（SQLite） | ❌ 表：sessions/workspaces/automations/automation_runs/automation_runtime_state/automation_delivery_outbox/buddy_snapshots，**无 token 列** |
| `~/.workbuddy/local_storage/entry_*.info`（gzip+base64，已解压解析） | ❌ 内容是模型清单/提示词模板等配置，**无 JWT、无用户 token** |
| `~/.workbuddy` 顶层小文件 + `%TEMP%` 近 6h 小文件 | ❌ 无 |
| 「连接移动端」二维码（小程序码 + App 码，已截图并用 OpenCV 解码） | ❌ App 码解出 `https://www.workbuddy.cn/app-download/`（下载页）；小程序码为微信专用码型，不含遥控 token |

⇒ **结论：遥控 token 由云端按配对会话下发、只存在于进程内存，本机不以明文落盘**。因此 L3 要么等你在 App 里打开 Remote Control 页面复制一次地址，要么走 `auth/login`（需口令，凌舟不索取）。

三条获取路径（按省事排序）：

1. **A（最快，5 秒）**：在 WorkBuddy 里打开那个 Remote Control 页面，**复制地址**（含 `?token=`）给凌舟；若地址被 iframe 藏住，用它自带的分享/扫码入口（侧栏有「扫码 WorkBuddy 小程序」「分享任务」）。
2. **B（不需人工，需一次逆向）**：解析应用自有的 KV 存储 `~/.workbuddy/local_storage/entry_*.info`（bundle 里 token 键为 `Jo`，`jS()` 仅在登出时删除）或用 Chromium/Electron 的 LevelDB 读取器（若 profile 目录存在）。**风险**：版本升级后键名/格式可能变。
3. **C（不推荐）**：`POST /api/v1/auth/login`（需登录口令，凌舟不知道，也不应索取）。

## 四之二、**回执判据（本工作流的关键，无需 token）**

WorkBuddy 每次真正把提示词交给 agent 时，会在 `%TEMP%\workbuddy-prompts\<uuid>.prompt.txt` 落盘一份完整提示词。因此：

- **派单是否真的送达 = 在该目录里 grep 到派单正文**（这是第一方落盘证据，不需要任何 token）；
- 2026-09-21 实测：凌舟经 UI 合成输入的两条派单**在该目录中查无正文** ⇒ 判定"未送达"（与 UI 侧「用户已取消」一致）；
- 反之，D-1/D-2 经 **L1（仓库卡 + 项目记忆）** 投递后由业主确认**已开始执行** ⇒ **L1 有效**，且可用"回传卡 + prompts 落盘"双向核对。

**使用规程（从此派单可多一条通道）**

1. 派单时**新建 GitHub Issue**：标题＝`【派单 <编号>】<一句话目标>`；正文＝该派单的七/十项（或直接指向仓库卡路径）；

**为什么它比 L3 更值得先落地**：官方集成、零逆向、零 token、双向（GitHub→WorkBuddy 事件 + PR/Issue 状态天然回执）。

## 十、`dispatch.ps1` 升级为「一条命令」（2026-09-21）

原 `[5/6]` 直接用本地 `origin/main` 当 bundle 的 base ⇒ 陈旧引用会造成推送竞态或静默失败。现改为：

1. **`[5/6]` 先同步远端真值**：`gh api repos/…/commits/main --jq .sha` 取真值 → 本地缺该提交就从服务器 `bundle origin/main` 取回 → 回写 `refs/remotes/origin/main` → 断言「本地 HEAD 含远端真值」（否则中止并提示先 rebase）。
2. **bundle 的 rev 参数写全名**（`refs/heads/main`）：写 `HEAD` 会让 bundle 记录**字面量 `HEAD`**，服务器 `git fetch` 必败（踩坑 [90]）。
3. 服务器 fetch 的源 ref 与 `git bundle list-heads` **逐字一致**；**去掉 `| tail`**（写操作被 tail 包住会掩盖真实退出码）。
4. **`[7/7]` 自动回执核对**：直接调用 `receipt.ps1 -Marker '派单 <Id>'`，把「送达判据」（`%TEMP%\workbuddy-prompts` 落盘 / 回传卡出现）并入同一条命令。

**升级后首次实跑（H-1）**：`[5/6] 远端 main 真值 = 25cb094b（本地 ref 已对齐）` → bundle → 中转 → `[7/7]` 自动执行。**该次暴露并修掉了上面的 ref 名 bug**，随后补推成功（`b2fe4198`）。

**诚实缺口**：`[7/7]` 的"送达"是**异步**的（WorkBuddy 侧每小时轮询、本地侧每 15 分钟）⇒ 首次跑必然报「未送达」，**这不是失败**，需按 T+1 复核。

## 十二、🔴 轮询器两个致命缺陷已修（2026-09-21，附红→绿证据）

§九 记的是"轮询器第一次真的跑起来了"。但**跑起来 ≠ 跑得动**——首次真实接单（H-1）当场炸出两个缺陷，子代理白跑约 20 分钟假死。两条都已修并复验。

### 12.1 缺陷一：沙箱下 `pwsh` 解析到 WindowsApps 应用执行别名 → 子代理并发起进程必失败

| 项 | 内容 |
|---|---|
| 症状 | 子代理**任何命令都跑不了**：`CreateProcessAsUserW failed: 5 (拒绝访问。)`；它据此判断"有卡住的长驻进程"，反复自救 → 假死 |
| 线索 | 报错带 `cwd=` / `cmd=`，`cmd=` 指向 `%LOCALAPPDATA%\Microsoft\WindowsApps\pwsh.exe`（**0 字节的 Store 别名**） |
| 红 | PATH 无 Codex 运行时目录 → 3 条并发 **1 成功 / 2 失败** |
| 绿 | PATH 前置 Codex 自带 pwsh（真实 Win32 exe）→ 3 条并发 **3/3**；加压 6 路并发 **6/6 全 exit 0** |
| 修法 | `poll-dispatches.ps1` 在拉起 `codex exec` 前把真实 `pwsh.exe` 目录前置到 PATH |
| 取证判据 | 该错误**不写入** `~/.codex/.sandbox/*.log`（进程在 shell 起来前就被拒）⇒ 只能看 exec 返回的 `cwd=`/`cmd=`（踩坑 [93]） |

### 12.2 缺陷二：PS 5.1 管道编码把中文全变成 `?`

| 项 | 内容 |
|---|---|
| 症状 | 任务书文件中文完整，但子代理收到 `# ????? GitHub Issue #37????? H-1?...` |
