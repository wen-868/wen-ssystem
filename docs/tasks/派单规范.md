# 派单与汇报规范（固定格式 + 必须建卡 + 双方署名）

> 生效：2026-09-19 ｜ 提出：项目业主 ｜ 执行：凌舟（总负责人）
> **硬规则：任何需要中转给同事的工作安排，必须①按下方固定格式发出 ②同内容写入任务卡 ③规则栏不得省略或简写 ④派单人署名。**
> **同事的汇报同样有固定格式与署名（见第五章）：汇报对象 / 汇报人 / 日期三项缺一即无效回传。署名不是形式主义——是文档格式规范与责任留痕。**
> 违反任一条 = 无效派单（无据可查、验收时口径对不上）。只发聊天不建卡、或卡里写"详见聊天"，一律视为未派单。

## 一、派单固定格式（十项，逐项不得省略）

```
【派单 <编号>】<一句话目标>
派单人：<姓名（角色）>｜<YYYY-MM-DD>
执行方：<角色>（<仓库/目录>）
优先级 / 时间盒：<P0|P1|P2> · <时间盒>
背景与依据：<文件:行号 / 卡路径 / run id —— 只写已取证的事实，不写推测>
交付物：<逐条可核对，含产出文件路径>
验收标准（硬）：<逐条；必须含"反测"：如何证明它会红>
红线（不得触碰）：<逐条>
回传要求：<照抄本派单卡内的「回传格式」块（= 本规范 §三 汇报十项），逐项填满，不得自拟格式>
关联卡：<docs/tasks/cards/...>
```

## 二、派单硬规则（R1–R7）

- **R1 一单一卡**：每个派单编号对应一张卡，卡内含与聊天**完全相同**的七栏；不得只写"详见聊天"或摘要代替。
- **R2 规则栏不可省**：红线与验收标准必须逐条写出。写"同上"、"按惯例"、"注意安全"一类泛指，一律视为无效派单。
- **R3 变化即改卡**：执行中口径变化时，先改卡并在卡内留变更记录（时间 + 变化点 + 依据）；聊天里的旧版自动失效，不得两版并存。
- **R4 回传即证据**：回传只接受可复跑证据（命令 + 原始输出 + 行号 / run id）。"已通过 / 没问题 / 已修复"的自述不算回传。
- **R5 派单人署名**：每条派单必须带 `派单人：<姓名（角色）>｜<日期>`。无署名的派单视为未发出——执行方有权不认，验收时无责任主体。
- **R6 派单内嵌汇报格式**：每张派单卡必须在开头提供**可照抄的「回传格式」块**（= 本规范 §三 汇报十项），每条派单的 `回传要求` 指向它。**派单自带回传口径**——执行方不需要另问"该怎么汇报"。
- **R7 发出前自检内部一致性**：同一参数（默认值 / 阈值 / 路径 / 编号 / 命令）在 `交付物`、`验收标准`、`红线` 三栏中**只能有一个取值**。三栏对同一参数给出不同取值＝**无效派单**，执行方有权退回要求澄清（实例：A-1 曾同时写"默认保持生产域名""仅显式配置才启用""不得把 127.0.0.1:8080 之外当默认"，三口径冲突，由业主发现）。
- **R8 取样必须可核对**：以**运行期读数**（axe / 日志 / 截图 / 接口返回）为依据下派单前，必须先证明该读数能在**源码或计算样式**里找到对应（颜色值 / 选择器 / 接口路径，至少一项对得上）。对不上的读数只能记为"**待核对取样**"，**不得作为派单依据**（实例：A-8 依 axe 报的 `#406cd4` 下发，事后证明该色值在 admin-web 及全仓历史中**从未出现**，属不可核对取样；同类已发生三次——S3-47 的 color-contrast 归因、56 节点、`#406cd4`）。
- **R8.1 层叠问题只用 computed 值定论**：凡涉及 **CSS 层叠 / 变量覆盖 / 规则优先级**（即"到底哪个变量生效"）的问题，**必须用浏览器 computed 值定论**，**禁止**用源码顺序或打包产物规则先后顺序推理。同题已两次翻车：`--input-border` 被判"死代码"、S3-63"覆盖范围"判反——两次都是顺序推理，两次都被 computed 值推翻。
- **R8.2 验证类派单必须写明"验证目标 ref"**（2026-09-21 立）：验证/反测类派单必须在卡内写明**分支名 + 提交哈希**；实现方一旦把产物放到分支或远端，**必须在回传里显式给出 ref**。验证方在动手前必须先 `git ls-remote origin <ref>`（或 `gh api .../branches/<ref>`）**确认目标存在**——否则会对着不存在的分支下结论。
  - 实例（本轮）：C-4 派单只说"跟分支跑"、未给分支名（当时分支还不存在），实现方把修复放到 `fix/s3-65-change-password-fail` 后**未同步 ref** ⇒ 验证方查了 `fix/s3-65-changepassword`（**不存在的名字**）得"0 提交"，据此判"修复未落库"。真实情况：修复在分支上、已推远端，但**未合并进 main**。
  - 判据：**未给出目标 ref 的验证结论，一律视为"对象不确定"**，不得据此判红或判绿；"未合并进 main"与"仓库里没有这个修复"是两句完全不同的话，不得混用。

## 三、汇报固定格式（同事回传用，十项逐项不得省略）

```
【汇报 <编号>】<对应派单编号> <一句话结论>
汇报对象：<凌舟（总负责人）>
汇报人：<姓名（角色）>｜<YYYY-MM-DD>
交付物：<逐条，含产出文件路径 + 提交哈希>
证据（可复跑）：<命令 + 原始输出摘要 + 行号 / run id / 文件路径>
验收自评：<逐条对照派单的验收标准，逐项写 通过/未通过 + 依据>
未完成与阻塞：<逐条；没有也要写"无">

```

## 四、汇报硬规则（S1–S5）

- **S1 署名不可缺**：`汇报对象`、`汇报人`、`日期` 三项缺一，一律视为**无效回传**，验收不予受理。
- **S2 一报一单**：回传必须写明对应的派单编号；一个派单一次汇报，不得一份汇报混多个派单。
- **S3 证据可复跑**：只写命令 + 原始输出。"已通过 / 没问题 / 已修复 / 应该没事"一律不算证据（本项目已有 4 次因此返工的记录）。
- **S4 两栏必须存在**：`未完成与阻塞`、`风险与自我报备` **必须成栏出现**，没有内容就写"无"——**禁止整栏省略**。这条直接对应本项目历史上"把猜测写成结论""前提有误却未主动报备"的教训。
- **S5 推翻即重报**：结论被推翻或口径变化时，**重发汇报**并在卡内留变更记录（时间 + 旧结论 + 新结论 + 依据），禁止静默覆盖旧卡。

## 五、子代理通道（另一条路，规则相同）

派给本地子代理时，把该卡内容**整段**写入 `docs/tasks/inbox/ACTIVE.md`（子代理开工第一步就是读它）；回执写 `docs/tasks/inbox/ACTIVE-回执.md`（同样要署名），旧卡归档。inbox 同时只允许一张活动卡。

## 八、批次制与六步闭环（2026-09-22 业主指令后新增）

> 业主 2026-09-22 指令原文：「**以后全部要严格按项目规则来执行，任务不能东做一点、西做一点，必须有严格规划、流程，你作为总负责人，有最高决策权限。**」
> 本章是为落实该指令立的**流程硬约束**，与 R1–R8.2 / S1–S5 同级，**违反即视为流程违规**。

### 8.1 唯一队列（单一真相源）

- 全项目只有**一份**队列：`docs/tasks/当前批次.md`。**未列入该文件的工作，一律不得开工。**
- 队列里每一项必须写全：**编号 / 一句话目标 / 执行方 / 优先级 / 起跑条件 / 验收判据 / 状态**。
- 新增需求（含业主口头交办、通道里来的临时请求）**先登记进队列 §四 待排期**，由凌舟定优先级后再进入批次；**禁止插队直接开工**。

### 8.2 一次只推进一个批次

- 队列中**同时只能有一个批次处于"进行中"**；其余只能是"待起跑 / 已完成"。
- 批内各单**按顺序闭环**；前一单**未验收通过**不得开下一单。**唯一例外**：卡内明确标注"阻塞项 / 独立可并行"的单（如等待外部凭据、等待真机验证）。
- 批次切换的唯一依据：上一批次全部项已"已验收"或"已明确挂起（写明原因与唤醒条件）"。

### 8.3 每单必须走完六步闭环（缺一步即未完成）

| 步 | 动作 | 产出（缺一即不算走完） | 负责人 |
|---|---|---|---|
| ① 立卡 | 建 `docs/tasks/cards/R101-<编号>-*.md`，含十项派单栏 + **回传格式块** | 卡路径 | 凌舟 |
| ② 派单 | 按 §一 十项发出（聊天 / Issue / 直投 UI 任一通道），**同内容在卡内** | 派单记录 + 通道回执 | 凌舟 |
| ③ 执行 | 按卡执行；口径变化**先改卡**（R3） | 提交 / 产物 | 执行方 |
| ④ 回传 | 按 §三 十项汇报（署名三项 + 两栏不可省） | 回传卡 + 可复跑证据 | 执行方 |
| ⑤ 验收 | 凌舟独立复核（**不接受自述**）：证据可复跑、与卡逐条对照；不一致必须有反例 | 验收结论（通过 / 判红 + 反例） | 凌舟 |
| ⑥ 记账 | 更新 `R101-总进度与推进计划.md` + 相关 Issue 状态（闭环即关闭）+ 更新本队列状态 | 进度源可见的变更 | 凌舟 |

**判定口径**：只有走完 ⑥ 才算"完成"。任何"改了但没记账""回传了但没验收"的状态，一律记为**未完成**。

### 8.4 决策权与责任

- **凌舟（总负责人）有最高决策权**：口径裁定、优先级排序、批次放行、验收判红判绿、是否合并上线。
- 执行方对**技术事实**负责（证据）；凌舟对**决策与验收**负责。两者都不允许"把猜测写成结论"（S4）。
- 需要业主决策的事项（不可逆、涉钱、涉对外行为、需外部凭据），凌舟**必须显式列出并等待**，不得自行假设。

### 8.5 违规的判定与纠正

| 违规形态 | 纠正动作 |
|---|---|
| 未入队列就开工 | 立即停止；补登记或明确废弃；已改的代码按 R3 补卡 |
| 同时推进多个批次 | 记录违规；非当前批次的工作**降级挂起**，直到当前批次收口 |
| 跳过验收直接合入 | 视为**流程违规**；若已上线，必须补做验收并留痕 |
| 回传缺署名 / 缺两栏 | 按 S1 / S4 判**无效回传**，退回补报 |

### 8.6 成对拆单规则（2026-09-23 立，源自 C1-1/C1-2 事故）

**背景（真实代价）**：C1 批次把「前端消费」与「后端提供」拆成 C1-1 / C1-2 并行单，但**只合并了 C1-1**。结果 main `f2f9e39c` 上 `TenantList.vue` / `TenantDetail.vue` 已在调用 5 个**只存在于 PR #51** 的端点，且该提交已 `Auto Deploy` 上生产 ⇒ 生产 saas-admin 处于「前端调用不存在接口」的中间态。

**规则（硬）**：

1. **成对拆单（前端消费 + 后端提供）必须同批全部合并后才可记为「完成」**；单边合并一律记为**未完成**。
2. 派单卡必须写明 **① 兄弟单编号 ② 合并顺序约束**（默认：后端先合、前端后合）。
3. 未满足顺序约束时，**前端 PR 不得先合并**；若因故必须先合，必须在卡内写明"接受的中间态 + 消除时限"。
4. 验收第 ⑤ 步必须核对**成对两单是否都已进 main**（`git show --stat <merge-sha>` 里能否同时看到两侧文件）。

### 8.7 外部扫描告警的处置口径（2026-09-23 立，源自 CodeQL `js/missing-rate-limiting`）

CodeQL（含 GitHub 默认 code scanning 的 `CodeQL` 检查）在 PR 上只报**新增**告警。遇新增告警时，凌舟按下列口径判定，**不得**无脑逐条打补丁、也**不得**为转绿放宽：

1. **先查同族存量**：`gh api "repos/<owner>/<repo>/code-scanning/alerts?state=open&per_page=100&rule=<rule-id>" --jq 'length'`。
2. 若同族 open 告警数量级为**几十条以上**（实测 `js/missing-rate-limiting` 已 ≥100 条，遍布 `miniapp/subscription/billing/ai-billing` 等既有路由）⇒ 判为**系统性存量**，**不作为单个 PR 的阻塞项**；改为**登记一次根因收敛项**（示例根因：`server.ts` 的全局 `express-rate-limit` 经 `createRateLimiter()` 包装后，CodeQL 识别不到，需在 `app.use` 调用点内联或提供 CodeQL 可识别的限流证据）。
3. 若为**本 PR 独有的新缺陷**（同族存量为 0 或极少量）⇒ 按门禁铁律处理：**同一 PR 内修掉 + 反测**，不得结转。
4. 两种情形都必须在 PR 里留评论说明判定与依据；判定为存量的，必须在 `当前批次.md` §四 登记收敛项，否则记为未处置。
