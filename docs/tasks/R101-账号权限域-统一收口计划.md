## 一、为什么一直反复修（根因，不是现象）

把近两周在该域修过的东西排一下，会发现它们**其实是同一个病**：

| 反复出现的问题 | 本质 |
|:--|:--|
| 演示口令三套并存（`Demo@2026` / `admin123` / `Admin@2026`） | 同一个概念**多处复制**，没有唯一出处 |
| 租户状态口径分裂（`platform-tenant` 写数值 / `admin/tenant` 写字符串） | 同一张表被**两条链路**各写一套 |
| 鉴权挂法分裂（`routeConfig.auth` 声明式 vs `auth:"none"`+端点内联） | 同一个横切关注点有**两种挂法**，其中一种绕过 CSRF |
| 权限接线稀疏（169/189 个路由文件零 `requirePermission(`） | 授权没有**统一入口**，靠人一处一处补 |
| 代码与 schema 不同步（`mfa_enabled` 不存在却先写代码） | 没有"列必须先存在"的机械约束 |
| 迁移编号撞号（197 × 2；历史 194/195 也撞过） | 靠**人工分配**，没有机械占用 |
| 死代码/影子端点（`changeTenantStatus` 无调用方；`api.ts` 死导出） | 没有"谁在用"的机械检查 |
| 演示账号落在真实租户（公网可进 524 张销售单） | **环境隔离**缺失，靠"记得别这么配" |

**共同根因一句话**：**同一概念存在多个副本/多个入口，而没有任何机械门禁去发现"又分叉了"。**
⇒ 所以每次都是"发现一处 → 修一处 → 下次在另一处再发现"。**只修现象，必然反复。**

## 二、方案：5 条"单一真相源 + 机械门禁"（这才是止反复的东西）

规则：**每条都必须同时交付【唯一出处】与【CI 门禁】；只改代码不交门禁的修复，不算完成。**

| # | 域 | 唯一出处（Single Source of Truth） | 机械门禁（进 CI，红了挡住合并） |
|:--:|:--|:--|:--|
| **G1** | **凭据口径** | 后端 `shared/constants.ts` 导出一个 `DEMO_CREDENTIALS`；前端仍走 `VITE_DEMO_*`，默认值与后端同值 | `guard:credentials` —— 全仓扫描：`Demo@2026` 只允许出现在"唯一出处 + 前端回退值"白名单位点；`admin123` / `Admin@2026` 在**代码与脚本**中命中即红 |
| **G2** | **租户状态口径** | `platform-tenant.service.ts` 的 `TenantStatus = "ACTIVE" \| "DISABLED"` + `toTenantStatus/toTenantStatusValue` 为唯一映射 | `guard:tenant-status` —— ①代码里不得再出现第三种状态字面量（`SUSPENDED/EXPIRED/CLOSED/PENDING` 仅允许出现在"显式拒绝"的位置）；②列表筛选收到未知值必须 400（有单测覆盖） |
| **G3** | **鉴权挂载** | `routeConfig.auth` 声明式（`auto-routes.getAuthMiddlewares`）为唯一挂法 | `guard:route-auth` —— 禁止 `auth:"none"` 且端点内联 `requireAuth*/csrfMiddleware` 的组合（显式白名单：`tenant-register` 的公开三端点）；同时断言"凡有写方法的路由文件，其 auth ≠ none 或已白名单" |
| **G4** | **权限接线** | `PERMISSION_CATALOG` + 每路由文件的 `requirePermission` 声明 | `guard:rbac-wiring` —— ①接线总数快照（防减少，已有）；②**新增写端点必须带权限码**（白名单除外）；③前端菜单必须来自 `GET /api/admin/menus/user`（禁止硬编码侧栏） |
| **G5** | **迁移与 schema** | `docs/migrations/*.sql` 编号唯一 + `EXPECTED_MAX_MIGRATION` 快照 + 生产 `SHOW COLUMNS` 核对 | `guard:migration` —— ①编号唯一（已有）②**凡代码新出现 `t_*.列` 的读写，必须能在 migrations 里找到该列**（用轻量 SQL 解析 + 白名单） |

**另外两条"环境级"硬约束（不再靠记性）**：
- **E1 演示环境隔离**：演示账号**必须**在独立租户；门禁断言"演示账号的 `tenant_id` ≠ 任何真实租户"（用只读探针在部署后跑）。
- **E2 默认安全**：`CORS_ORIGINS` 未配置 ⇒ 生产启动 **fail-fast**（不是 `origin:true` 兜底）；错误上报必须打到**同端**端点。

## 四、执行纪律（针对"反复"的三个硬规定）

| # | 规定 | 为什么 |
|:--:|:--|:--|
| **R1** | **一域一批，同域同批**：同一域的问题一次收进同一批，不再"发现一个派一个" | 避免同族修复互相踩（如 S3-172/174/175 都想动 `auth.service.ts`） |
| **R2** | **修而不加门禁 = 未完成**：门禁必须进 CI | 这是止反复的唯一机制 |
| **R3** | **回传卡缺失 = 该交付无效**（本次实测：4 单执行方**零回传卡**）⇒ 一律由我**独立取证**后决定收/弃，且**同一执行方下次派单降为"单笔窄单 + 强制回传"** | 回传卡是验收的输入；没有它，交付不可采信 |

## 六、验收口径（我执行，不接受自述）

1. 每项：**反测两侧**（改坏⇒该红就红；复原⇒绿）原始输出；
2. 每域：**门禁脚本自己先红一次再绿**（防"假门禁"）；
3. 跨域：`npx vitest run` 全量 + `tsc --noEmit` + 相关端 build；
4. 涉及生产：合并后**部署 + 只读探针**核验（如 E1 的演示租户隔离、G5 的列存在）。
