# app-mobile 全站页面 BUG 排查报告（2026-09-11）

排查范围：`src/pages` + `src/pages-sub` 共 **113 个 .vue 页面**（含全部子模块），并逐条比对 `src/api/modules/*` 与 `backend/src/{schemas,controllers,services,routes}` 的真实返回契约。

排查方法（三层交叉验证，避免误判）：

1. **静态模式扫描**：全量 113 页扫描模板 `.toFixed/toLocaleString/charAt/slice`、数组下标运算、静默 catch、H5 专有 API、响应解包 —— 命中 toFixed 104 处/40 文件、静默 catch 160 处、H5 API 28 处、模板字符串函数 14 处、数组下标运算 1 处。
2. **契约比对**：对每个调用 API 的页面向上追溯 `api/modules` 映射层，再向下列比后端 SQL 的 `AS` 别名/Zod schema，确认字段名、字段类型（**重点：金额 DECIMAL 经 mysql2 返回字符串**）与分页键名（`list` vs `records`）。
3. **证据固化**：关键结论均附「前端行号 + api 映射行号 + 后端 SQL/schema 行号」三段证据；服务器实测取过 `t_miniapp_order_item.unit_price = "2899.00"`（字符串铁证）。

> 严重度定义：**P0** = 渲染崩溃/整页白屏，或数据恒为空导致功能不可用；**P1** = 功能失效或业务语义错误；**P2** = 边界/体验缺陷、潜在风险。

## 二、P0 清单（崩溃 / 数据恒空）

### P0-1 订单详情 · 商品明细渲染崩溃（金额未做 Number 转换）

| 项 | 内容 |
| --- | --- |
| 文件 | `app-mobile/src/pages/orders/order-detail.vue` |
| 位置 | 第 72 行、第 73 行 |
| 现象 | 进入订单详情，渲染到「商品明细」即抛异常；App 端整页白屏，H5 端可能表现为金额错乱或偶发空白 |
| 原因 | `¥{{ item.unitPrice.toFixed(2) }}`、`¥{{ (item.totalPrice \|\| item.subtotalAmount \|\| 0).toFixed(2) }}`。`items` 由 `api/modules/orders.ts:161` 原样透传（`items: Array.isArray(r.items) ? r.items : []`，**无逐字段数值映射**），而后端 `services/admin/order.service.ts:220-224` 返回的 `unit_price AS unitPrice` / `subtotal_amount AS subtotalAmount` 是 DECIMAL 列，**mysql2 返回字符串** → 字符串无 `toFixed` 方法 → TypeError |
| 证据 | 服务器实测 `SELECT unit_price, subtotal_amount FROM t_miniapp_order_item` → `"2899.00"`（字符串）；同页第 27/31/35/77 行的 `order.totalAmount` 因 `mapOrder` 内已 `Number()` 而安全 —— 恰好说明问题只在未映射的 `items` |
| 修复建议 | 在 `mapOrder` 内补 items 映射：`items: (Array.isArray(r.items) ? r.items : []).map((it: any, i: number) => ({ skuId: it.skuId, skuName: it.skuName ?? ## 三、P1 清单（功能失效 / 语义错误）

### P1-1 商品详情 · App 端扫码功能不可用（ReferenceError）

| 项 | 内容 |
| --- | --- |
| 文件 | `app-mobile/src/pages/products/product-detail.vue` |
| 位置 | 第 1132-1152 行 `openScanner()`；第 1154-1159 行 `startScan()` 定义在 `// #ifdef H5` 内 |
| 现象 | App 端点击"扫码"无任何反应（异步 ReferenceError，被全局吞掉） |
| 原因 | `openScanner` 只有 `MP-WEIXIN` 分支（第 1134-1140，内含 `return`）与 `H5` 分支（第 1141-1147，仅做环境校验）；**无 `APP-PLUS` 分支**，App 端会继续执行到第 1151 行 `setTimeout(startScan, 320)`。而 `startScan` 定义在 `// #ifdef H5` 包裹的块内（第 1154 行起），App 端编译后被整体剥离 → `startScan` 未定义 |
| 证据 | App 产物 `dist/build/app/app-service.js` 中可 grep 到 `setTimeout(startScan,320)`，但同文件中 `startScan` 无任何定义 |
| 修复建议 | 为 App 端补分支：`// #ifdef APP-PLUS` + `uni.scanCode({ success: (res) => applyScanned(type, index, res.result \|\| ''), fail: () => {} })` + `return`，置于 H5 分支之前（App 端 `uni.scanCode` 由原生模块支持，需确认 `src/manifest.json` 已声明 Barcode 模块） |

### P1-2 订单详情 · 金额语义错误（已付恒 ¥0.00、应收恒等于订单金额）

| 项 | 内容 |
| --- | --- |
| 文件 | `app-mobile/src/pages/orders/order-detail.vue` 第 31、35 行；`app-mobile/src/api/modules/orders.ts` 的 `mapOrder` |
| 现象 | 「已付金额」永远显示 ¥0.00，「应收金额」永远等于订单金额 —— 已收款订单仍显示未收，对账误导 |
| 原因 | `mapOrder` 取 `r.paidAmount ?? r.paid_amount ?? r.receivedAmount ?? 0`、`receivableAmount ?? r.totalAmount ?? 0`；但后端 `services/admin/order.service.ts:205-219` 的 `getOrderDetail` SELECT 只返回 `payable_amount AS payableAmount`、`pay_status`，**不返回任何已付/已收字段** → 全部落到兜底 `0` / `totalAmount` |
| 修复建议 | 后端在 `getOrderDetail` 补 `received_amount AS receivedAmount`、`unreceived_amount AS unreceivedAmount`（`t_miniapp_order` 如有对应列）；若表结构不含金额明细，则前端应改为按 `payStatus`（UNPAID/PARTIAL/PAID）渲染状态文案，不展示无数据来源的金额 |

### P1-4 租户 id 被数字化为 0（跨租户风险同源）

| 项 | 内容 |
| --- | --- |
| 文件 | `app-mobile/src/stores/user.ts` 第 52 行；`app-mobile/src/api/storage.ts` 第 310 行 |
| 现象 | 登录后 `tenant.id` 恒为 `0`，并落盘 `merchant_tenant_id = "0"` |
| 原因 | `tenant.value = { id: Number(result.user.tenantId) \|\| 0, … }`。`tenantId` 是 UUID（如 `f0cbfe78-9f74-4966-9d1e-95aff8402d1c`），`Number(uuid)` = `NaN`，`NaN \|\| 0` → `0`；随后 `setTenant()` 写 `String(tenant.id)` = `"0"`。与 R96-07 已修的 `CacheKeys.…(Number(tenantId))` **同源问题** |

## 四、P2 清单（边界 / 系统性）

### P2-1 静默 catch 共 160 处 —— 假成功温床（系统性）

- 模式：`catch { }` / `catch (e) { console.error(e) }`，无 toast、无 throw → 接口 400/500 被完全吞掉，用户以为操作成功。
- 典型证据：价格管理创建等级曾因前端发送 `{name, code}` 而后端 Zod 要求 `levelCode/levelName` 导致必填校验失败 400，因 catch 静默而表现为「创建成功但列表不显示」（R96-07 已修该处，但同模式仍大面积存在）。
- 分布：`src/pages-sub/finance/*`、`src/pages-sub/product/*`、`src/pages/ai-chat/*` 最密集。
- 修复建议：新增 `src/utils/api-error.ts` 导出 `notifyApiError(e, fallback)`，统一在 catch 内调用；对确需静默的兜底请求显式标注注释说明原因（项目内已有 `silent` 选项可复用）。

### P2-2 创建销售单 `quantity` 语义潜在风险

| 项 | 内容 |
| --- | --- |
| 文件 | `app-mobile/src/api/modules/sales.ts` 第 112 行；契约方 `backend/src/schemas/store-sale-bill.ts` 第 18、26、27 行 |
| 现状 | 前端发送 `quantity: (bottleQty ?? 0) + (boxQty ?? 0)`；后端 `transform` 里 `const totalBottleQty = item.totalBottleQty ?? item.quantity`，并以其计算金额与后续扣库存 |
| 结论 | **当前不构成线上故障**：`pages/sales/create-sale.vue` 未提供整箱录入（第 1676、1797 行显式 `boxQty: 0`，全页仅"规格/单位"占位文案含"箱"），故 `quantity` 恒等于瓶数 |
| 风险 | 一旦放开整箱录入，`2箱(24瓶/箱)+5瓶` 会被算成 7 瓶 → 金额与库存少算 |
| 修复建议 | 改为 `quantity: (boxQty ?? 0) * boxRatio + (bottleQty ?? 0)`，其中 `boxRatio` 取 SKU 的箱规（商品详情已返回）；或由后端按 skuId 自行换算，前端只传箱/瓶拆分数量 |

### P2-3 前后端字段契约长期脱节（系统性）

- 本轮逐条核对 `api/modules/*` 的 interface 与后端真实返回，仍存在声明了后端不返回的字段：`orders.ts` 的 `OrderItem.id / boxQty / bottleQty / totalBottleQty / totalPrice`（P0-2 即由此引发）、`customers.ts` 部分聚合字段等。
- 修复建议：以 Zod schema / controller + SQL `AS` 别名为唯一事实源，对 `api/modules` 做一次全量 interface 校准；对确实需要展示而后端未返回的字段，先补后端，而不是在前端"假设存在"。

### P2-4 列表页「空数据」与「加载失败」不区分

- 多处列表页空态只用 `list.length === 0` 判断，加载失败与真无数据呈现同一套文案（`price-manage.vue` 已在 R96-07 补 toast，其余同类页面未统一）。
- 修复建议：引入 `loadState: 'loading' | 'ok' | 'error' | 'empty'` 四态，失败态提供「重试」按钮。

## 六、修复优先级建议

| 顺序 | 内容 | 理由 |
| --- | --- | --- |
| 1 | P0-1、P0-4（金额 Number 映射） | 崩溃级，用户必然触发；改动小、风险低（只在 api 映射层加 `Number()`） |
| 2 | P0-3（优惠券 records 键名） | 一次改动恢复两个页面的可用性 |
| 3 | P0-2（`:key`） | 与 P0-1 同文件，一起改 |
| 4 | P1-1（App 扫码）、P1-2（订单金额语义） | 功能可用性与业务正确性 |
| 5 | P1-3（5 处 charAt 兜底）、P1-4（租户 id） | 边界防白屏；P1-4 建议连带全站排查 `Number(tenantId)` |
| 6 | P2-1 统一错误提示 | 消除"假成功"，为后续所有接口异常兜底 |
| 7 | P2-2 / P2-3 / P2-4 | 结构性治理，可排入后续迭代 |

> 建议统一约定：**凡金额/数量字段，一律在后端 `toNum()` 或前端 api 映射层 `Number()` 转换完成后才进入视图层**；`api/modules` 中不再有裸 `res?.result ?? res` 返回用于模板渲染的场景。
